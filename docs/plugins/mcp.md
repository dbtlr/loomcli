# MCP plugin

This page documents the MCP plugin, which serves an application's opted-in Commands as tools of a Model Context Protocol server over stdio or streamable HTTP and registers that server with coding agents, and the private protocol package behind it. An author installs it so an agent client can call those Commands as tools.

```ts
// @loomcli/plugins/mcp
import type { Plugin } from '@loomcli/core';

// One HTTP request as the authorize hook reads it, before its body is read.
export interface McpHttpRequest {
  readonly headers: Headers; // a copy of the request's headers, the platform's Headers
}
// Settings that shape the HTTP server alone; none changes a stdio server.
export interface McpSettings {
  // Judges each HTTP request: true serves it, false answers 401. Never called over stdio.
  readonly authorize?: ((request: McpHttpRequest) => boolean | Promise<boolean>) | undefined;
  // The largest POST body the server reads, in bytes, 4_194_304 (4 MiB) by default.
  readonly maxBodyBytes?: number | undefined;
  // How long an initialize-era session may sit idle before it ends, in milliseconds, 1_800_000 by default.
  readonly sessionIdleMs?: number | undefined;
}
export declare function mcp(settings?: McpSettings): Plugin;
```

```ts
// @loomcli/plugins/mcp/extension, declarations alone
import type { Extension, StandardSchemaV1 } from '@loomcli/core';

// The hints a tool carries about its effects.
export interface McpAnnotations {
  readonly destructive?: boolean | undefined; // projected as destructiveHint
  readonly idempotent?: boolean | undefined; // projected as idempotentHint
  readonly openWorld?: boolean | undefined; // projected as openWorldHint
  readonly readOnly?: boolean | undefined; // projected as readOnlyHint
}
// The value an author gives mcpCommand.
export interface McpCommandFacts {
  readonly annotations?: McpAnnotations | undefined;
  readonly description?: string | undefined; // the tool's description, in place of the Command's
}
export declare const mcpCommand: Extension<'command', StandardSchemaV1<McpCommandFacts, McpCommandFacts>>;
// The value an author gives mcpInput: the option's description for an agent, or its exclusion from every tool.
export type McpInputFacts =
  | { readonly description: string; readonly exclude?: undefined }
  | { readonly description?: undefined; readonly exclude: true };
export declare const mcpInput: Extension<'option', StandardSchemaV1<McpInputFacts, McpInputFacts>>;
export interface McpArgumentFacts {
  readonly description: string;
}
export declare const mcpArgument: Extension<'argument', StandardSchemaV1<McpArgumentFacts, McpArgumentFacts>>;
```

```ts
import { Application, Command } from '@loomcli/core';
import { mcp } from '@loomcli/plugins/mcp';
import { mcpArgument, mcpCommand } from '@loomcli/plugins/mcp/extension';

import { getValue } from './actions/get-value.js';

export const get = new Command('get', {
  description: 'Read one value at a path.',
  extensions: [mcpCommand({ annotations: { openWorld: false, readOnly: true } })],
})
  .argument('path', {
    description: 'Dot path to read.',
    extensions: [mcpArgument({ description: 'A dot-separated path from the document root, such as user.name.' })],
    required: true,
  })
  .option('file', {
    description: 'The document to read.',
    required: true,
    short: 'f',
    stdin: true,
    type: 'content',
  })
  .action(getValue);

export const jsonkit = new Application('jsonkit', {
  description: 'Read and reshape one JSON document.',
  plugins: [mcp()],
  version: '0.9.0',
}).command(get);
```

An MCP client launches `jsonkit mcp` and speaks one JSON-RPC message per line over its stdin and stdout. The client finds that command line in its own configuration: `jsonkit mcp install` registers it with Claude Code and Codex, and `jsonkit mcp config` prints the configuration object for any other client, as [Registering with an agent](#registering-with-an-agent) shows. Against the application above, whose `get` declares a local native content `--file` and whose Application declares its version and description, the first line below is the client's request and the second is the server's answer:

```text
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}},"name":"get","arguments":{"path":"user.name","file":"doc.json"}}}
{"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","content":[{"type":"text","text":"\"Ada\"\n"}],"isError":false,"_meta":{"io.modelcontextprotocol/serverInfo":{"name":"jsonkit","version":"0.9.0","description":"Read and reshape one JSON document."}}}}
```

`mcp()` is the MCP plugin. It serves every Command that opts in as one tool of a [Model Context Protocol](https://modelcontextprotocol.io/specification/2026-07-28) server, over stdio or, when the operator names an address, over the protocol's streamable HTTP transport, which [Serving over HTTP](#serving-over-http) states, and it runs each tool call through [`invoke`](../core/invocation.md#invocation-by-name), so a call is the Command's own run with the same validation, failures, and exit codes. MCP is a projection: a tool listing is the graph's facts for the Commands that opted in, and nothing in core knows the protocol. The protocol itself lives in a private package the plugin pack compiles into its own files. [ADR-0063](../decisions/0063-the-mcp-plugin-serves-opted-in-commands-as-tools.md) records the decision.

- **The plugin.** Its identity is `@loomcli/plugins/mcp`. `mcp()` takes three optional settings for its HTTP server, which [Settings](#settings) states, and declares no global option, no middleware, and no view, and it claims no slot. It contributes one [plugin Command](../core/plugin-contract.md#plugin-commands), the three extensions above, and an [`onGraphBuilt`](../core/lifecycle-hooks.md#judging-the-built-graph) hook. The Command is `mcp`, visible, with the description `Serve this application's tools to an MCP client, over stdin and stdout or, with --http, over HTTP.`, no arguments, the one option `--http`, which [Starting the server](#starting-the-server) states, and no result, and its action serves when routing selects none of its three children, which [Registering with an agent](#registering-with-an-agent) states. A root that declares arguments holds the plugin's Commands like any children, so such an application can install the plugin, as [completion](completion.md) does under [ADR-0160](../decisions/0160-a-command-with-an-action-may-declare-arguments-and-hold-children-and-an-exact-child-name-routes-first.md).
- **Opt-in.** A Command is a tool when it carries an `mcpCommand` value, and only then. The root opts in through the Application's `extensions`. An explicit opt-in wins over `hidden`, so a hidden Command that carries the value is a tool, and the listing in help, the manifest, and completion still omits it. A deprecated Command that opts in is a tool whose description opens with its migration message. An alias, a [visible alias](../core/commands.md#visible-aliases) included, is never a tool, never a second name, and never changes a tool's name, so a Command keeps one tool identity. A Command with no action cannot serve a call, so `mcpCommand` on a group is a build fault.
- **Tool names.** A tool's name is the Command's path joined by `_`, with each `-` written as `_`, so `scratch create` is `scratch_create` and `cache clear-all` is `cache_clear_all`. The root's tool is the application name written the same way, so `git-lfs` serves `git_lfs`. A [portable name](../glossary.md#names-and-routing) holds nothing else the protocol's tool-name characters exclude, and `.` stays. There is no name override. Two opted-in Commands that give one name, such as the root and a child named like the application, are a build fault that names both.
- **The description.** A tool's description is the `mcpCommand` value's `description`, or else the Command's core `description`, the Application's at the root. With neither, the tool carries no description. A deprecated Command's description opens with `Deprecated: ` and its migration message, then a line break and the rest. The `mcpCommand` value's `description` is prose under the pack's [prose rule](help.md#help-extensions): every line holds a character other than whitespace, and line breaks are kept. A core description and a migration message are one line each, so each line break the author wrote in one, CRLF or a single terminator, reads as one space; an input's core description and the server identity's description read the same way.
- **Annotations.** `annotations` projects onto the protocol's tool annotations, `readOnly` as `readOnlyHint`, `destructive` as `destructiveHint`, `idempotent` as `idempotentHint`, and `openWorld` as `openWorldHint`. An unset hint is omitted, so the protocol's own defaults apply, and a tool with none set carries no `annotations`. They are hints the author owns and Loom never verifies: Loom infers none from the graph, and nothing but this plugin reads them, neither core nor help nor the manifest. A false claim is a defect in the author's application, and the protocol tells a client to treat annotations from a server it does not trust as untrusted.
- **The input schema.** A tool's `inputSchema` is `{ type: 'object', properties, required, additionalProperties: false }`, with `required` left out when it is empty. `properties` holds every argument of the routed Command in declaration order, then its local options in authoring order, then every global option in graph order, keyed by declared name, so an option's [visible alias](../core/options.md#visible-option-aliases) adds no property, minus a [hidden](../core/commands.md#hidden-and-deprecated-members) option, a [control option](../core/commands.md#control-options), and an excluded option, which **Excluded options** below states. Passthrough is never exposed, on a Command that declares the [passthrough mode](../core/options.md#passthrough) or not, so a tool call's `passthrough` is always `[]`.
  - Each property is the input's [input schema](../core/validation.md#input-schema) without its top-level `$schema` key, because the property lives inside a schema whose dialect is the protocol's default on `2026-07-28` and `2025-11-25`, JSON Schema 2020-12, the target the converter answers. `2025-06-18` names no default dialect, and its listing is the same. Where the graph holds `null`, the property is derived from the node: `{ type: 'string' }` for a string option or an argument, `{ type: 'boolean' }` for a Boolean option, and `{ type: 'integer', minimum: 0 }` for a counted option. A multiple option or a variadic argument wraps its value's schema as `{ type: 'array', items: <schema> }`, with `minItems: 1` when `required` lists it, because core reads an empty list as missing. A scalar option with an [arity](../core/options.md#option-value-arity) is an array of exactly its count of words, `{ type: 'array', items: <schema of one word>, minItems: 2, maxItems: 2 }`, and a multiple one is an array of such arrays, with the same `minItems: 1` when `required` lists it. A call supplies each tuple as an array of strings or numbers, and `invoke` lowers each tuple to one occurrence.
  - The plugin sets `description` from the input's `mcpInput` or `mcpArgument` value, or else its core description, and a deprecated option's opens with `Deprecated: ` and its message, as a tool's does. It sets `default` from a declared default that is plain JSON data and leaves it out otherwise. Either key replaces one the converter wrote.
  - `required` lists each required argument and each required local option, in property order, an argument and a local option that declare `required: 'non-interactive'` included, because a tool call is never [interactive](../core/interaction.md). A global option is never required.
  - `allOf` holds one constraint per [option group](../core/options.md#declared-option-groups) the schema can state soundly, under the rules that page gives, and is left out when there is none. A [one-way requirement](../core/options.md#a-one-way-requirement) is JSON Schema's `dependentRequired`, `{ dependentRequired: { password: ['user'] } }`, when its option is a scalar string option or a scalar content option and each option it needs is a scalar string option, a scalar content option, or a Boolean of `both` polarity; otherwise it is `{ anyOf: [{ not: <claim of the option> }, { allOf: [<presence of each needed option>] }] }`, with the named-value predicates the other groups use, so a multiple option, whose named empty list lowers to absence, reads `minItems: 1` on either side. A requirement is stated only when the tool lists every member and no member binds a variable or carries an extension but this plugin's own or the [completion plugin's value hint](completion.md#value-hints), so a hidden or control member leaves it a rule the run checks. A requirement whose option is excluded constrains nothing, and one that excludes an option it needs and not its option is a build fault under **Required option excluded** below.
  - A Command whose tool would list an argument and an option under one name, a global option included, is a build fault, because a tool's arguments are one object. An author's argument and option may share a name everywhere else.
- **A call.** `tools/call` names a tool and passes `arguments`, an object or nothing. The plugin checks each key against the tool's `properties`: a key outside them, a hidden, control, or excluded option's name included, is a tool execution error whose text is `Tool "get" takes no argument "x". Use a property its input schema lists.`, as the one text item with `isError: true` and no `structuredContent`, and no run starts. Otherwise the plugin splits the object, a key that names an argument going under `args` and every other key under `options`, and calls `invoke(path, { args, options }, { exclude, failure, onProgress, signal, timeZone, view })`. `timeZone` comes from request metadata under **The caller's time zone** below and is omitted when the key is absent. `exclude` names every option the tool leaves out under **Excluded options**, and it is omitted when there is none. `view` is the first view, in record order, whose [media type](../core/results.md#media-types) is `application/json`, and it is omitted when the Command declares no result or no such view. `signal` is the call's own, which `notifications/cancelled` aborts. Values are not checked against the schema: [lowering](../core/invocation.md#invocation-by-name), the validators, and the run's own faults judge them and report by name.
- **The caller's time zone.** On every transport and served revision, `params._meta["io.github.dbtlr.loomcli/timeZone"]` may name the call's IANA time zone. The plugin passes a valid string as `invoke`'s `timeZone`, so the call's `host.timeZone` and nested invocations use it under [Invocation by name](../core/invocation.md#invocation-by-name). Without the key, the call uses the server's zone. The plugin calls `resolveTimeZone` from `@loomcli/core`, sharing invoke's one validity check. It returns the formatter's `resolvedOptions().timeZone`, or `undefined` if construction fails or that resolved name starts with `+` or `-`. `UTC` and runtime-known aliases are accepted and stored with the resolved spelling. Numeric offsets are refused, including inputs with a Unicode minus, and input is not trimmed. If the effective zone differs from the zone the server's declared values were validated under, invoke validates every declared default and implied value anew against the call's host. An omitted zone-less `dateTime()` default and a supplied zone-less token therefore both resolve in the caller's zone unless the validator pins its own. A call in the same zone, or with no key, reuses validated declared values as today. A present non-string value, including `null`, or an invalid name returns a tool execution error: one text content item, `isError: true`, and no `structuredContent`, with `Metadata key "io.github.dbtlr.loomcli/timeZone" requires an IANA time zone name this runtime knows. Use a name such as "Asia/Tokyo".` No invocation starts. Existing envelope, tool-name, arguments-object, and unlisted-argument checks keep precedence. The key is request metadata, never a tool argument, HTTP header, initialize setting, or session default, and it selects no protocol revision. No other caller host fact is settable per call. [ADR-0193](../decisions/0193-invoke-takes-a-per-call-time-zone-and-mcp-reads-it-from-request-metadata.md) records the decision.
- **Excluded options.** An option whose `mcpInput` value is `{ exclude: true }` is excluded: it is off every tool it would join, the routed Command's tool for a local option and every tool for a global option, a plugin's included, and it is part of no tool call. A call that names it is the takes-no-argument error above, and every call passes it under `invoke`'s [`exclude`](../core/invocation.md#invocation-by-name), so neither a variable nor a configuration key bound to it reaches a tool call, and the action reads its declared default. Nothing else changes: help, the manifest, completion, and a command line show and read it, and the option otherwise behaves as any other. A value holds `description` or `exclude`, never both, because an excluded option has no property to describe: the types reject both, and a value that holds both is the [`@loomcli/core/invalid-extension-value`](../core/diagnostics.md#loomclicoreinvalid-extension-value) fault. A hidden option that is not excluded is off the tool and the listings, and the server's environment and configuration still fill it in a call; a hidden option that carries `{ exclude: true }` is excluded as well. A required local option cannot be excluded, because no call could supply it, a build fault below: one that declares `required: true` or `required: 'non-interactive'`, and a content option whose `min` is positive. A global option declares no `required`, so every global option may be excluded. An excluded member is never supplied in a call, so an [option group](../core/options.md) that holds one constrains the tool's schema through its other members alone: an `exclusive` group keeps its rule over them, and a `oneRequired` group requires one of them. A requirement whose option is excluded constrains nothing, because no call supplies its option. A `oneRequired` group whose every member is excluded, a `requiredTogether` group that excludes some of its members and not all, and a requirement that excludes an option it needs but not its option, are build faults below, because a call could never satisfy the first, could never supply the rest of the second, and fails every time it supplies the third's option. A requirement's option that is hidden and not excluded counts as not excluded, because the server's environment and configuration still fill it in a call. A group that also holds a hidden or control member stays a rule the run checks alone, because a call may still fill that member from the server's sources.
- **A completed call.** `isError` is `false`, and `content` holds `output` as one text item and then `messages` as another, each only when it is not empty, or one empty text item when both are. When the view the plugin selected declares `application/json`, `structuredContent` is `output` parsed as JSON, any JSON value, though a connection on an initialize-era revision carries it only when it is an object, as [the protocol package](#the-protocol-package) states; when `output` does not parse, because a view's media type is a promise core never checks, the result carries the text alone. A `jsonl` view's output stays text. No content item carries annotations.
- **A failed call.** `isError` is `true`, and `content` holds `messages`, then any partial `output`, each only when it is not empty. The text is the failure's own report, by build, with no command-line hint, so a model reads what went wrong and what to do instead, and a defect in a distributed build reads the generic defect message. `structuredContent` is what the plugin's failure handler returns, `{ exitCode, failure }`: the outcome's exit code and the handler context's [failure form](../core/failures.md#the-failure-form), `{ code, exitCode, message, hints }`. The form follows the build, so a defect in a distributed build reads `internal` and `Something went wrong.`, and its hints are the by-name hints, with no command-line hint. The handler exposes no cause and no stack. With both `messages` and `output` empty, as under an override view that renders nothing, `content` holds one empty text item, as a completed call's does.
- **Progress.** When a `tools/call` request carries `params._meta.progressToken`, a string or a number, the plugin passes `onProgress` to that call's `invoke`, and each [progress event](../core/output.md#progress-events) of the call becomes one `notifications/progress` on the token. `progress` is always a per-call counter, the number of events the call has delivered, this one included, so every event is sent and `progress` always increases. The notification carries no `total`. `message` carries the event's label, its counts, and its state, joined by single spaces: the label when it is not empty, then the counts when the event carries `completed`, `completed/total` with a total and `completed` alone without one, and no counts for an event that carries `total` without `completed`, each number written as JavaScript's `String` writes it, then the state in parentheses, such as `Fetching packages 3/8 (updated)`, `Fetching packages 8/8 (ended)`, `Building the index (started)`, or `(started)` for an event with no label and no counts. A skipped or warned progress line's end reads its own state, such as `Fetched nothing: the cache is fresh (skipped)` or `Fetched 118 of 120 records 118/120 (warned)`, and a cleared line's end reads `ended` with its last label, such as `Reading the cache (ended)`. Progress lines that run at once in one call share its token and its counter. A call without a token passes no observer and receives no notification. The [protocol package](#the-protocol-package) sends none after the call's response or its cancellation, so a cancelled call's `cancelled` event sends nothing. The progress line's start and end lines still land in `messages`, which the result carries as text.
- **A cancelled call.** The server sends no response for it, as the protocol asks.
- **Protocol errors.** The plugin answers these as JSON-RPC errors rather than tool results, because no run started:

  | Request                                                | Error                                                                                       |
  | ------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
  | `tools/call` naming no tool the server lists           | `-32602`, `Unknown tool "gte". Call tools/list for the tool names.`                         |
  | `tools/call` whose `arguments` is not an object        | `-32602`, `Tool "get" arguments must be an object. Supply a JSON object of named inputs.` |
  | `tools/list` with a `cursor`                           | `-32602`, `The cursor is not one this server issued. Call tools/list without a cursor.`     |
  | Every protocol rule of the private package             | The codes [The protocol package](#the-protocol-package) states                              |

- **Discovery.** `server/discover` answers `supportedVersions: ['2026-07-28', '2025-11-25', '2025-06-18']`, `capabilities: { tools: {} }`, with no `listChanged` because the tool list never changes while the process runs, and no `logging`, `prompts`, `resources`, or `completions` capability. The application's identity is the server's: on `2026-07-28` every result's `_meta` carries `io.modelcontextprotocol/serverInfo` as `{ name, version, description }`, and on an initialize-era revision the `initialize` result carries it as `serverInfo`, the graph's `name` and `version` and the Application's description, which is left out when it declares none and, on `2025-06-18`, always. The result carries no `instructions`, because Loom holds no fact that guides a model beyond the descriptions.
- **The listing.** `tools/list` answers every tool in one page, in graph order: the root first, then each Command depth first in authoring order. It carries no `nextCursor`. On `2026-07-28`, `server/discover` and `tools/list` each carry `ttlMs: 0` and `cacheScope: 'private'`, so a client caches neither: a client may outlive the server process, and the next process may serve a newer application whose tools differ.
- **Concurrency.** Calls may overlap. Each runs through its own `invoke`, and the server writes each response when its call settles. Loom adds no queue, limit, or timer, so an application whose actions cannot overlap serializes its own work.
- **The server's life.** Over stdio, the `mcp` action reads `host.stdin` and writes `host.stdout`, and stdout carries protocol messages alone, each written whole. The server writes no log of its own, and stderr carries core's [log lines](../core/logging.md#at--v) at `-v`, including every tool call's events under the outermost run's verbosity, dotenv warnings when that plugin is installed, a fault the `mcp` run itself reports and what an installed [`onLog`](../core/lifecycle-hooks.md#observing-log-events) hook writes to its destination's stderr, such as the [logging plugin](logging.md)'s console records. When stdin ends, the server aborts every call in flight and answers none of them, waits for each to settle, ends each open subscription with its closing response, and returns, so the run exits 0. When the run's signal aborts, through a caller or a process signal, every call's signal aborts with it and no further tool replies are sent. Open subscriptions receive `notifications/cancelled` and their completion result under the [subscription teardown rule](#the-protocol-package). The run resolves its cancellation code, and an ending process signal then ends the process after the [shutdown](../core/signals.md#the-shutdown), within its budget. A plugin that writes to stdout on a run it does not own breaks the stream, as it breaks [completion](completion.md)'s answer. Over HTTP, [Serving over HTTP](#serving-over-http) states the server's life.
- **Names.** `mcp` is exported from `@loomcli/plugins/mcp`, and `mcpCommand`, `mcpInput`, and `mcpArgument` from `@loomcli/plugins/mcp/extension`, which also exports their facts types `McpCommandFacts`, `McpAnnotations`, `McpInputFacts`, and `McpArgumentFacts`. Their identities are `@loomcli/plugins/mcp/command`, `@loomcli/plugins/mcp/input`, and `@loomcli/plugins/mcp/argument`. `mcpCommand` is an ordinary extension, so a later value replaces an earlier one. The pack's public declarations name no protocol type.

## MCP build faults

The plugin's `onGraphBuilt` hook judges the opted-in Commands on every graph build, a run that never serves a tool included, and throws a `DeclarationError` under a rule of its own, which reports as itself under [Judging the built graph](../core/lifecycle-hooks.md#judging-the-built-graph).

- **Tool name taken.** Two opted-in Commands never give one tool name, such as the Command `scratch create` and a Command named `scratch_create`: [`@loomcli/plugins/mcp/tool-name-taken`](../core/diagnostics.md#loomclipluginsmcptool-name-taken).
- **Tool without action.** `mcpCommand` is never on a Command with no action, such as a group: [`@loomcli/plugins/mcp/tool-without-action`](../core/diagnostics.md#loomclipluginsmcptool-without-action).
- **Tool that needs a terminal.** `mcpCommand` is never on a Command that [needs a terminal](../core/commands.md#a-command-that-needs-a-terminal), because a tool call runs by name with no terminal and would fail every time, as in `Command "top" carries mcpCommand and needs a terminal, which no tool call has.`, corrected by `Remove mcpCommand, or remove needsTerminal from the Command.`, so such a Command never reaches `tools/list`: [`@loomcli/plugins/mcp/tool-needs-terminal`](../core/diagnostics.md#loomclipluginsmcptool-needs-terminal).
- **Property name taken.** A tool never lists an argument and an option under one name, a global option included: [`@loomcli/plugins/mcp/property-name-taken`](../core/diagnostics.md#loomclipluginsmcpproperty-name-taken).
- **Required option excluded.** A tool never excludes what every call needs: a `oneRequired` group's every member, some members of a `requiredTogether` group and not all, an option a [requirement](../core/options.md#a-one-way-requirement) needs while the tool does not exclude the requirement's option, as in `Command "login" makes option "password" require option "user" and excludes "user" from its MCP tool, so a call that supplies "password" always fails.`, corrected by `Exclude "password" from the tool as well, or remove exclude from the mcpInput value of "user".`, where a requirement of several options names each and the first one excluded, `makes option "password" require options "user" and "host" and excludes "host"`, or a required local option, one that declares `required: true` or `required: 'non-interactive'` or a content option whose `min` is positive, such as a `--file` that declares `required: true` and carries `mcpInput({ exclude: true })`: [`@loomcli/plugins/mcp/required-input-excluded`](../core/diagnostics.md#loomclipluginsmcprequired-input-excluded).

## When author code fails

An action that throws or rejects during a tool call takes the [ordinary failure path](../core/failures.md#the-ordinary-failure-path), and an action's catch is final under [ADR-0097](../decisions/0097-one-ordinary-failure-path-where-an-authors-catch-is-final.md). The call answers as the failed call above does: `isError` is `true`, the text is the failure's own report, and `structuredContent` is `{ exitCode, failure }` with its failure form under `failure`, so a defect in a distributed build reads `internal` and `Something went wrong.` A throw while the protocol package handles a request is answered with `-32603`, and the server keeps serving.

## Serving over HTTP

The MCP Command declares `--http`. An application that already declares a global option named `http` must rename it and update its readers before installing this version. Core rejects the colliding declarations when it builds the graph.

Some clients reach a server by URL instead of launching it, such as a client on another machine or in a container, or one that connects to a server that outlives each agent session. `mcp --http <address>` serves those clients the same tools over the protocol's streamable HTTP transport. The tools, the listing, the identity, every call, and every rule above stay the same. Only the transport changes. [ADR-0184](../decisions/0184-the-mcp-plugin-also-serves-its-tools-over-streamable-http-at-an-address-the-operator-names.md) records the decision. The transport rules follow [Streamable HTTP for 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), and [Transports: Streamable HTTP for 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#streamable-http) and [for 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports#streamable-http). Where a revision leaves a choice, Loom takes the smallest one that a mainstream client accepts, and the rule below says so.

In this section, a connection is the protocol package's state for one client, as [The protocol package](#the-protocol-package) defines it. An HTTP connection is the transport's socket, which carries requests and may outlive one of them.

```text
$ jsonkit mcp --http 8080
http://127.0.0.1:8080/mcp
```

### Settings

`mcp()` takes three optional settings that shape the HTTP server. None of them changes a stdio server.

| Setting | Default | Meaning |
| --- | --- | --- |
| `authorize` | none | Judges each HTTP request from its headers, as [Authorization](#authorization) states. |
| `maxBodyBytes` | `4_194_304` (4 MiB) | The largest POST body the server reads, as [The POST body](#the-post-body) states. |
| `sessionIdleMs` | `1_800_000` (30 minutes) | How long an initialize-era session may sit idle before it ends, as [Sessions](#sessions) states. |

`mcp()` fills each omitted setting with its default and judges none of them, under [ADR-0093](../decisions/0093-a-value-that-bypasses-the-types-gets-no-rule.md), as the [logging plugin](logging.md) does: the settings type bounds each key.

### Starting the server

- **The option.** `mcp` declares the string option `--http`, with the description `Serve over HTTP at this address instead of stdin and stdout: a port, or host:port. A port alone listens on 127.0.0.1, and port 0 takes any free port.` It is marked `control: true`, because it says how the run serves and not what a tool does. Like any control option, it is never on a tool, and `mcp` is never a tool anyway. Without the option, `mcp` serves over stdio as [MCP plugin](#mcp-plugin) states, so every registration and every client command line stays as it was. The children of `mcp` do not declare it.
- **The address.** The value is a port, such as `8080`, or `host:port`, where the host is an IPv4 address, a name such as `localhost`, or an IPv6 address in brackets, such as `[::1]:8080`. The port is a decimal from 0 through 65535. Core's usage error for the input, with exit 2, refuses these values: `:8080`, because other tools read an empty host as every interface and Loom will not guess which the operator meant; an IPv6 address without brackets; a port out of range; and a value with a scheme or a path. Its sentence names the forms the option accepts.
- **The bind.** A port alone binds 127.0.0.1, as the protocol advises for a server that runs locally. A host binds as the operator wrote it, and a name binds the first address the runtime resolves it to. The server binds a non-loopback address only when the operator names it, and an unspecified address, IPv4 or IPv6, however it is spelled, such as `0.0.0.0` or `[::]`, counts as named. Loom refuses no address the operator names. The bound address is loopback when it is in `127.0.0.0/8`, is `::1`, or is an IPv4-mapped loopback address.
- **What loopback reaches.** A loopback address is reachable by every user and every process on the machine, not by the operator alone. The `Origin` rule keeps browser pages out, and nothing else does: another account's process can call the tools. An `authorize` hook is how an author restricts that, and without one a loopback server serves every local caller. A loopback bind writes no warning.
- **The URL line.** Once the server listens, the run writes one line to stdout, `http://<host>:<port>/mcp`. The host is the one the operator wrote, `127.0.0.1` for a port alone, with an IPv6 host in brackets. An unspecified address is no address to connect to, so for an unspecified IPv4 address the line writes `127.0.0.1` and for an unspecified IPv6 address `[::1]`, the address that reaches the server from this machine, and the network warning names the address as the operator wrote it. The port is the one the server bound, so with port 0 the line names the port the server took. The run writes it through `out.render` with a view that escapes the text's markup delimiters, as `config` writes its object. Stdout carries nothing else for the life of the run, so a supervisor that starts `jsonkit mcp --http 0` reads the endpoint from the first line.
- **Network warning.** When the bound address is not loopback, the run always writes one warning through `out.warn` before the URL line. It names the address and says one of two things:
  - Without an `authorize` hook: any host that reaches the address can call the tools without credentials. The step is to serve on 127.0.0.1, or to put the server behind something that authenticates.
  - With an `authorize` hook: requests and their credentials cross the network unencrypted, because the server speaks plain HTTP. The step is to put TLS in front of the server, such as a reverse proxy that terminates it. A bearer token sent in the clear can be read and replayed by anyone on the path, which is why [RFC 6750, section 5.2](https://www.rfc-editor.org/rfc/rfc6750#section-5.2) requires TLS for it and the protocol's authorization requires HTTPS. Installing `authorize` supplies no encryption.

  The run then serves.
- **Bind failures.** When the server cannot listen, the run fails before it serves, with a `FatalError` and exit 1. The sentence names the address as the operator wrote it and the cause, taken from the system error's code, with a step:
  - `EADDRINUSE`: another program is using the port. The step names another port, or 0.
  - `EACCES`: the system does not permit the port, such as one below 1024. The step names a port at or above 1024.
  - `EADDRNOTAVAIL`: the address is not one this machine has. The step names an address it has, or a port alone.
  - `ENOTFOUND` or `EAI_AGAIN`: the host name does not resolve. The step names an address or a name that resolves.
  - Any other code: a general sentence that names the address and the code.

### The endpoint

- **One path.** The server answers `/mcp`. The path is compared without its query string. A request for any other path is answered 404 with no body.
- **Order of checks.** The server checks each request in this order: `Origin`, authorization, path, method, then a POST's content type and body. The first check that fails gives the answer.
- **Answered before the body.** Every response the server sends before it has consumed the request's body carries `Connection: close`: 401, 403, 404, 405, and 415, the 500 of an `authorize` hook that throws, and the 413 of a body past the limit. After writing it, the server half-closes the HTTP connection, ending its own side, and reads and discards the body's unread bytes for up to 2 seconds, or until the client closes its side, and then closes the HTTP connection. Closing at once while the client is still sending makes its system answer the unread bytes with a reset, which can destroy the response before the client reads it; [RFC 9112, section 9.6](https://www.rfc-editor.org/rfc/rfc9112#section-9.6) describes this lingering close. The bound keeps a refused client from making the server read an upload it will never use, and the next request opens a fresh HTTP connection that the checks judge from the start.
- **Receipt deadlines.** The runtime's header and request receipt timeouts stay on for every request: 60 seconds for the headers and 300 seconds for the whole request, body included, Node's defaults. The server enforces both with its own timer for each request, under Node and Bun alike, so neither deadline rests on how a runtime's `node:http` implements its timeouts. A request that has not arrived whole by its deadline is answered 408 and its HTTP connection closed. Only an open event stream's idle timeout is turned off, as [Responses](#responses) states.
- **Origin.** A request that carries an `Origin` header, whatever its value, is answered 403. The body is a JSON-RPC error with no `id`, code `-32600`, whose sentence says the server answers no request a browser sends and tells the caller to use an MCP client that is not a web page. Each revision requires the server to validate `Origin` against DNS rebinding and to answer an invalid one with 403. Loom serves no page and answers no CORS preflight, so no page is same-origin with the endpoint, and any request with an `Origin` is cross-origin. Loom keeps no allow-list and makes no exception for a loopback origin: a page at `http://localhost:3000` is still a page Loom did not serve. A client that is not a browser sends no `Origin`.
- **Methods.** POST carries messages, and DELETE ends an initialize-era session. GET and every other method are answered 405, with `Allow: POST, DELETE` and no body. A DELETE's body, which a client rarely sends, is read and discarded under the same limit as a POST's before the DELETE is answered. On `2026-07-28` the GET stream is gone. The initialize-era revisions let a server that offers no GET stream answer 405. This server sends no request and no unprompted notification, so a GET stream would carry nothing.

### The POST body

- **Content type.** A POST whose `Content-Type` is not `application/json` is answered 415, with a JSON-RPC error with no `id` and code `-32600`. Parameters such as `charset` are allowed. Every mainstream client sends that type. A browser cannot send it without a preflight, so the check also backs up the `Origin` rule. The server does not check `Accept`, because the protocol requires a client to accept both answer types.
- **Size.** The server reads at most `maxBodyBytes` bytes of a body, 4 MiB by default. It counts the bytes as they arrive, whatever `Content-Length` says and with chunked transfer coding included, and a `Content-Length` larger than the limit is refused before any byte is read. A body past the limit is answered 413, Content Too Large, under [RFC 9110, section 15.5.14](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.14), with a JSON-RPC error with no `id`, code `-32600`, and a sentence that names the limit. The server stops reading that body into memory, and the response closes its HTTP connection as [Answered before the body](#the-endpoint) states. The limit bounds the memory any one request can take, whoever sends it, because passing the `Origin` and authorization checks says who may call, not what a request may cost. A tool's input arrives as JSON arguments, so 4 MiB holds every plausible call, and an author whose tools take larger content raises the setting. The limit is per body: there is no budget across bodies that arrive at once, so concurrent uploads may together hold up to their count times `maxBodyBytes`, each for no longer than the 300-second receipt deadline.
- **Reading it.** The body is read whole as UTF-8, and then:
  - A body that is not JSON is answered 400, with `-32700` and no `id`.
  - JSON that is not one request, notification, or response, a batch included, is answered 400, with `-32600` and no `id`. None of the three revisions batches.
  - A notification or a response is answered 202 with no body. A response is ignored, as over stdio. [Notifications](#notifications) states what a notification does.
  - [Revisions](#revisions) states how a request is served.

### Authorization

```ts
import { createHash, timingSafeEqual } from 'node:crypto';

import { Application } from '@loomcli/core';
import { mcp } from '@loomcli/plugins/mcp';

const digest = (value: string): Buffer => createHash('sha256').update(value).digest();

export const jsonkit = new Application('jsonkit', {
  plugins: [
    mcp({
      authorize: ({ headers }) => {
        const token = process.env.JSONKIT_MCP_TOKEN;
        if (token === undefined || token === '') {
          return false;
        }
        // RFC 6750: the scheme name compares without regard to case.
        const sent = /^bearer +(\S+)$/i.exec(headers.get('authorization') ?? '')?.[1];
        return sent !== undefined && timingSafeEqual(digest(sent), digest(token));
      },
    }),
  ],
  version: '0.9.0',
});
```

- **The hook.** `authorize` receives `{ headers }`, a fresh `Headers` copy of the request's headers for each request, after the `Origin` check and before the body is read. `true`, or a promise of `true`, lets the request go on. `false` answers 401 with `WWW-Authenticate: Bearer` and no body. The server judges every request this way: a POST, a DELETE, a request for another path, and a request with a method it refuses.
- **What the hook can trust.** The hook runs before any header is checked against the body. The server verifies `Mcp-Method` and `Mcp-Name` against the body only on a request whose `MCP-Protocol-Version` is `2026-07-28`, as that revision's Server Validation section requires; the initialize-era revisions define neither header. A hook that decides by `Mcp-Method` or `Mcp-Name` must therefore refuse a request whose `MCP-Protocol-Version` is anything else, absent included, or it trusts a header no check will hold to the body.
- **Comparing a secret.** The comparison is the author's, and it must take the same time whether or not the values match, and must refuse when the expected secret is empty or unset. The example compares SHA-256 digests with `timingSafeEqual`, which needs inputs of equal length, so the digests hide the token's length too, and it reads the `Bearer` scheme name without regard to case, as RFC 6750 allows a client to write it.
- **No hook.** Without `authorize`, the server serves every request that passes the `Origin` check, every local caller on a loopback address included, and [Starting the server](#starting-the-server) warns when the address is not loopback.
- **A throw.** A hook that throws or rejects refuses that request, which is answered 500 with a JSON-RPC error with no `id` and code `-32603`. The server keeps serving, and the hook stays installed. Core offers a plugin no way to report a defect while the run goes on, so the plugin follows how core reports a throwing [`onLog`](../core/lifecycle-hooks.md#when-author-code-fails) hook:
  - Each throw is an `error` log event that names the hook and carries the thrown value as an Error-shaped field, so `-v` shows its name and message and a logging destination, such as the logging plugin's file, keeps the full copy.
  - When the server stops, the action fails the run with the first throw of the run, once, as an `InternalError` whose cause is that throw. It reports through the [ordinary failure path](../core/failures.md#the-ordinary-failure-path), so everything that path applies holds: in a distributed build the [generic message](../core/release-facts.md#development-builds), written at most once per run, which `override(InternalError, view)` replaces, with any `onFailure` hints under it and any failure encoder in its place; in a development build the Developer Diagnostic [`@loomcli/plugins/mcp/broken-authorize-hook`](../core/diagnostics.md#loomclipluginsmcpbroken-authorize-hook), which names the `authorize` hook, `The authorize hook given to mcp() threw while it judged a request, so the server answered that request with 500.`, corrected by `Return true or false from authorize for every request, and throw from it for none.` A later throw adds no report.
  - The run returns 1, as for any defect, except a cancelled run, which keeps its signal's code and still writes the report, as a throwing `onLog` hook's run does. A server stops when its run's signal aborts, so a server stopped by `SIGINT` or `SIGTERM` exits 130 or 143 and writes the report during the [shutdown](../core/signals.md#the-shutdown).
- **Loom stores nothing.** No setting, option, or file holds a credential, and Loom chooses no header and no scheme. The hook reads what it needs from the author's own sources, such as a variable the operator sets, and the application chooses how to compare the values. Mainstream clients can send a configured header, so the common case is one bearer token.
- **The protocol's authorization.** Authorization is optional in MCP. An HTTP server that supports it implements OAuth 2.1 as a resource server, publishes Protected Resource Metadata, and is reached over HTTPS. Loom implements none of it: it serves no metadata document, validates no token, and speaks plain HTTP. The 401 carries `WWW-Authenticate: Bearer`, because a 401 must carry a challenge, and Bearer is the scheme both the protocol's authorization and clients' configured tokens use. The challenge names no `resource_metadata`. A client that tries OAuth discovery finds none and reports that the server is unauthorized. An author who needs OAuth, or an operator who needs TLS, puts a gateway that provides it in front of the server. The hook is never called over stdio, because the protocol has a stdio server take its credentials from its environment.

### Revisions

- **Per request, on `2026-07-28`.** A request whose `params._meta` names `io.modelcontextprotocol/protocolVersion` is served statelessly. It belongs to no session, an `MCP-Session-Id` header on it is ignored, and the server issues no session id. `Last-Event-ID` is ignored too, as the revision's backward-compatibility rules ask. Before the package's checks, the transport checks the request metadata headers, as the revision's Request Metadata and Server Validation sections require:
  - `MCP-Protocol-Version` is present and equals the protocol version in `_meta`.
  - `Mcp-Method` is present and equals `method`.
  - On `tools/call`, `Mcp-Name` is present and equals `params.name`, once a value in the `=?base64?…?=` form is decoded.
  - Header names compare without regard to case, and values compare exactly.
  - A `_meta` whose protocol version is not a string has no value for a header to equal, so these checks leave it to the package's envelope check, which answers it `-32602` with 400.

  A request that fails any of these checks is answered 400, with a JSON-RPC error that carries the request's `id`, code `-32020`, `HeaderMismatch`, and a sentence that names the header and what it must equal. No tool's input schema carries `x-mcp-header`, so the server recognizes no `Mcp-Param-*` header and ignores each one. The package's checks and methods then run as they do over stdio, as Refused before the handler under [Responses](#responses) states.
- **Initialize era.** A request without per-request `_meta` is served on an initialize-era revision, in a session, as [Sessions](#sessions) states. On those revisions a client cancels with `notifications/cancelled` naming a request id, and only a session tells one client's ids from another's. The protocol scopes an initialize-era revision to the session over HTTP.

### Sessions

- **Opening one.** An `initialize` request that carries no `MCP-Session-Id` opens a session when the package answers it with an `InitializeResult`, as it does over stdio. That response alone carries `MCP-Session-Id`, a fresh UUID from `crypto.randomUUID()`, which is cryptographically secure and visible ASCII, as the initialize-era revisions' Session Management asks. An `initialize` the package answers with an error, such as `-32602` for a missing version, opens no session and issues no id.
- **What it holds.** A session is one [connection](#the-protocol-package): its negotiated revision, the requests it has in flight by id, and the request-id rule. It is the HTTP form of one stdio run.
- **Using it.** Every later request on those revisions carries the session id, and every rule of an initialized stdio connection holds within it:
  - An `initialize` with a known session id is that session's second `initialize`, answered 200 with `-32600`, as [ADR-0122](../decisions/0122-the-mcp-server-serves-the-initialize-handshake-beside-the-per-request-revision.md) answers it over stdio. It never replaces the session.
  - A request with an unknown session id, from a session that ended or a server that restarted, is answered 404 with no body, `initialize` and `ping` included, so the client opens a new session, as those revisions require.
  - A request without a session id, other than `initialize` and `ping`, is answered 400. The body is a JSON-RPC error that carries the request's `id`, code `-32602`, with a sentence that names both ways in, as stdio's request before `initialize` does.
  - `ping` without a session id is answered 200 with an empty result, as stdio answers it at any time.
  - A request without a session id whose `MCP-Protocol-Version` header names `2026-07-28` but whose body carries no per-request `_meta`, `ping` included, is answered 400 with code `-32602`, because that revision requires the `_meta` keys. With a session id, the session's own version check answers it instead, as below.
  - `MCP-Protocol-Version`, when present, names the session's revision. A request whose header names any other version is answered 400, with a JSON-RPC error that carries its `id`, code `-32600`, and a sentence that names the session's revision. Without the header, the session's revision serves. The revisions' fallback to `2025-03-26` applies only when the server has no other way to know the version, and the session is that way.
  - Every other JSON-RPC error inside a session is answered 200, `-32601` included, because on those revisions a 404 tells the client that its session ended.
- **Ending one.** A session ends in three ways, and a later request with its id is answered 404, as both initialize-era revisions' Session Management allow:
  - DELETE with the session id aborts the session's calls in flight, answers none of them, ends the session, and is answered 204 with no body. A DELETE without a session id is answered 400, and one with an unknown id 404, each with no body.
  - A session with no request or notification and no call in flight for `sessionIdleMs`, 30 minutes by default, ends. The clock restarts at each request or notification that carries the session's id and when its last call settles, so a long call never ends its session. A client that stops without DELETE leaves no session behind for longer than the interval.
  - The server stops.
- **No resumption.** No event carries an `id`, no answer carries `retry`, and no stream resumes. The `2025-11-25` priming event exists so a client can reconnect with `Last-Event-ID`, which this server does not offer, so it sends no priming event.

### Notifications

The session protocol-version header check applies to requests alone; a notification with a mismatched `MCP-Protocol-Version` is still answered 202. A notification that carries a known session id is answered 202 and handled by that session as it is over stdio: `notifications/cancelled` aborts the call it names, and every other notification is ignored. A notification without per-request `_meta` that carries an unknown session id is answered 404, as an initialize-era request is; on `2026-07-28` a session id is ignored, as [Revisions](#revisions) states. A notification with no session id is answered 202 and ignored, `notifications/cancelled` included. A per-request notification is answered 202 without the metadata-header checks, which [Revisions](#revisions) applies to a request, because the server ignores it. On `2026-07-28` that notification belongs to stdio, and without a session its id does not say whose request it names.

### Responses

- **Refused before the handler.** The package's checks that run before a request reaches its handler run before the transport chooses a status and a content type: the per-request `_meta` envelope, an unsupported version included, whether the method is served, whether the request id is in use within a session, and whether a `tools/call` names its tool with a string. A request one of them refuses is answered as one `application/json` JSON-RPC error with its mapped status, before any stream opens:
  - `-32602` for a `2026-07-28` request whose `_meta` lacks a required key, such as `io.modelcontextprotocol/clientCapabilities`, or holds one of the wrong type, such as a protocol version that is not a string, is 400, as that revision's base protocol requires of `_meta` on HTTP: "the response status MUST be 400 Bad Request".
  - `-32022`, an unsupported version, is 400, as the `2026-07-28` Protocol Version Header section requires.
  - `-32601` is 404 on `2026-07-28` and 200 in a session.
  - Every other refusal is 200.
- **A stream for calls, JSON for the rest.** Only a request that reaches its handler opens an event stream. `tools/call` and `subscriptions/listen` are then answered 200 as `text/event-stream`, with `Cache-Control: no-cache` and `X-Accel-Buffering: no`, and the headers are sent at once. Each message is one event, a `data:` line of the message's JSON followed by a blank line, with no `event` or `id` field. A call's stream carries its progress notifications, then its result or the error its handler raised, such as an unknown tool, and then ends. Every other request is answered with one `application/json` response. A JSON answer sends nothing until its call settles, so a call longer than the client's response timeout would fail; Node's fetch, for one, waits five minutes. Progress also needs a stream.
- **Keep-alive.** While an event stream stays open, the server writes an SSE comment line every 15 seconds, so neither an idle timeout nor an intermediary closes a long call or an idle subscription. Every SSE reader ignores comment lines.
- **No runtime idle timeout.** The runtime's own idle timeout must not end an event stream. The server turns off the idle timeout of each event stream's socket while the stream is open, so the 15-second comment line keeps it open under Node and under Bun, whose `node:http` closes a socket idle for 10 seconds unless told otherwise, and restores the timeout when the stream ends, so an HTTP connection kept alive after it idles out as any other does. Node's server applies no such timeout to a response by default, and the server sets it anyway, so the rule does not rest on a default. The receipt deadlines under [The endpoint](#the-endpoint) stay on throughout.
- **A subscription.** `subscriptions/listen` is acknowledged on its stream as it is over stdio. The stream stays open until the client closes it, which cancels the subscription, or the server stops, which ends it as [Shutdown](#shutdown) states.

### Cancellation and concurrency

- **On `2026-07-28`.** The revision requires the server to treat a closed response stream as a cancellation. When the client closes a call's stream, or the request's HTTP connection before a JSON answer, the server aborts the call's signal and sends nothing more for it, as stdio's `notifications/cancelled` does.
- **On the initialize-era revisions.** `notifications/cancelled` POSTed with the session id aborts the call it names, and the call's stream ends without a response. Those revisions say a disconnection should not be read as a cancellation. A closed stream there does not abort the call: the call runs to its end, and its answer is dropped. DELETE of the session, and its expiry, abort every call in it. Expiry never finds a call in flight, because a call keeps its session from going idle.
- **Concurrency.** Calls overlap across POSTs, sessions, and clients, each through its own `invoke`. Loom adds no queue, limit, or timer, as over stdio and under [ADR-0059](../decisions/0059-a-command-runs-by-name-through-invoke.md). Every client's calls share one process, its environment, its working directory, and any state the application keeps. An application whose actions cannot overlap, or that needs a rate limit for several clients, applies it in its own actions or in front of the server.

### What a call runs on

A tool call over HTTP runs on the server's host, as it does over stdio. Its time zone defaults to the server's, and the per-call `params._meta["io.github.dbtlr.loomcli/timeZone"]` key above may replace that zone alone. Its clock, environment, working directory, and every other [host fact](../core/host.md#host-facts) remain the server's. The headers reach the `authorize` hook alone. An author whose Command needs the caller's locale or another fact of the caller declares it as an ordinary input, and a call supplies it as an argument.

### Output and stderr

- **Stdout** carries the URL line alone. The server does not use stdout as a transport. A plugin that writes to stdout on this run can push the URL line out of first place, where a supervisor reads it.
- **Stderr** carries what it carries over stdio: core's log lines at `-v`, every tool call's events included, under the outermost run's verbosity, dotenv warnings, a fault the `mcp` run itself reports, and what an installed `onLog` hook writes to its destination's stderr. It also carries the network warning, the report of the `authorize` hook's first throw when the server stops, and the log lines [At -v and in the log](#at--v-and-in-the-log) lists for refused requests, the hook's throws, and an HTTP connection the server could not accept.
- **Progress.** A call whose request carries a progress token gets the same `notifications/progress` as over stdio, on the call's stream before its result. None is sent after the call is answered or cancelled.

### Shutdown

When the run's signal aborts, through a caller or a process signal, the server stops listening and aborts every call, on every revision and in every session, and answers no call. On each `2026-07-28` subscription stream whose HTTP connection is still open, it then sends `notifications/cancelled` naming the `subscriptions/listen` request's id, which the revision's Cancellation section requires of a server that tears down a subscription, and then the completion result its Subscriptions section recommends under Graceful Closure, whose `_meta` carries `io.modelcontextprotocol/subscriptionId` beside the server's identity. A stream whose client already left gets no write. The server then ends every open stream and closes every HTTP connection, idle keep-alive ones included, and resolves once each call has settled. The run resolves its cancellation code, and an ending process signal then ends the process after the [shutdown](../core/signals.md#the-shutdown), within its budget. Nothing drains: a call the server stops answers nothing, as over stdio. The subscription teardown is the one the stdio run's signal sends too, under [The protocol package](#the-protocol-package), because the revision requires it of a server that tears down a subscription on any transport. Stdin plays no part. The server does not read it, and its end does not stop the server.

### Runtime and loading

The server is `node:http`. Node, Bun, and a compiled Bun binary all provide it, so one implementation runs under all three. `Bun.serve` runs under Bun alone, and a fetch-style handler would need an adapter on Node. The request and response of `node:http` are the Node stream shapes `@loom/mcp` already takes. The `mcp` action imports `serve.js` as before, and `serve.js` imports the HTTP server module only when `--http` is given. So neither another Command nor a stdio server loads `node:http`.

### Operator sentences

These sentences live in the plugin's `messages.ts`, and the protocol error text lives in `@loom/mcp`'s `messages.ts`, under [ADR-0164](../decisions/0164-looms-operator-messages-live-in-message-modules-and-a-voice-test-per-package-reads-them.md). Each is listed by its meaning, and its wording comes with the code. Each value a sentence repeats is escaped.

- An `--http` value the option does not accept, with the forms it accepts.
- Each bind failure under [Starting the server](#starting-the-server), and the general one.
- The two network warnings, with and without an `authorize` hook.
- The protocol error text over HTTP: a body that is not JSON, a message that is not one request or notification, a content type that is not JSON, a body past the limit, a refused `Origin`, each metadata header that is missing or unmatched, a request with no session id, and a protocol-version header that is not the session's.
- The log-line templates [At -v and in the log](#at--v-and-in-the-log) lists for HTTP.

The URL line is data, not a sentence, and the `mcp` Command's new description and the `--http` description are help text.

## Registering with an agent

An agent finds an MCP server only when its own configuration names the command that starts it. The `mcp` Command's children write that registration through each agent's own command-line interface, remove it, or print it for an agent that has no such interface. [ADR-0111](../decisions/0111-the-mcp-plugin-registers-its-server-with-claude-code-and-codex-through-each-agents-cli.md) records the decision.

```text
$ jsonkit mcp install
Registered jsonkit with claude to run /home/me/.local/bin/jsonkit mcp.
Skipped codex, because codex could not start.
$ jsonkit mcp uninstall
Removed jsonkit from claude.
$ jsonkit mcp config
{
  "mcpServers": {
    "jsonkit": {
      "command": "/home/me/.local/bin/jsonkit",
      "args": [
        "mcp"
      ]
    }
  }
}
```

- **The Commands.** `mcp` keeps its action, which serves as [MCP plugin](#mcp-plugin) states whenever routing selects no child, so the command line every client launches is unchanged. It is a Command with an action and children under [Nested Commands and groups](../core/commands.md#nested-commands-and-groups), and its three children are each visible with no arguments:
  - `install`, `Register this application's MCP server with your coding agents.`, with the string option `--agent`, `The agent to register with: claude or codex. Every agent that starts when left out.`, validated to `claude` or `codex`, and the Boolean option `--force`, `Replace a registration of this name that mcp install did not make.`
  - `uninstall`, `Remove this application's MCP server from your coding agents.`, with `--agent`, `The agent to remove it from: claude or codex. Every agent it is registered with when left out.`, validated the same way.
  - `config`, `Print a client configuration that starts this application's MCP server.`, with no options.

  An `--agent` value outside the set is core's usage error for that input, with exit 2. No child declares a result, and none carries `mcpCommand`, so none is a tool.
- **The registration.** An [MCP registration](../glossary.md#product-surface) holds a name and a command line. The name is the application's name with each `.` written as `_`, because Claude Code's server names hold only letters, digits, `-`, and `_`, so `my.app` registers as `my_app` with every agent and in `config`. The command line is [`host.program`](../core/host.md#host-facts)'s words followed by `mcp`, the words that start this application's server again, over stdio: no child writes `--http` into a registration or a configuration, so a client that connects by URL is configured by its operator with the URL the HTTP server prints. Every registration is at the agent's user scope, so one registration serves every directory the agent starts in, and no option names a scope.
- **Agents.** `claude` and `codex`, in that order, which every child follows. Each agent is one program with a registration CLI, so they are not the skills plugin's [agent targets](skills.md), which are folder layouts, and each plugin keeps its own list. `<name>` is the registration's name, and `<command line>` is its words.

  | Agent | Starts | Name check | Register | Remove |
  | --- | --- | --- | --- | --- |
  | `claude` | `claude --version` | none | `claude mcp add -s user <name> -- <command line>` | `claude mcp remove -s user <name>` |
  | `codex` | `codex --version` | `codex mcp get <name> --json` | `codex mcp add <name> -- <command line>` | `codex mcp remove <name>` |
- **The agent's programs.** Each call in the table is a child program started through [`host.spawn`](../core/host.md#child-programs) by the agent's name, which the `PATH` of `host.env` resolves, with `host.env` as its environment and `host.cwd` as its working directory, no shell, no input, and its standard output and standard error captured. It adds no time limit; the run signal ends the child with `SIGTERM`. An agent whose `--version` call comes back `unstarted` is an agent whose CLI cannot start, whatever the reason; one that starts is present, whatever its exit code. The plugin never reads or writes an agent's configuration file, so the agent keeps its format, scope precedence, backups, and approval rules, and a variable such as `CLAUDE_CONFIG_DIR` or `CODEX_HOME` in `host.env` reaches the agent as it would from a shell.
- **The record.** Each agent's registration is recorded in the plugin's file for that agent in the installation record, `mcp.claude.json` and `mcp.codex.json`, through the module [Installed files](../core/installation-record.md#installed-files) defines, as a registration by its name and command line. A child writes the file `pending` before it runs an agent's `add` or `remove`, and `committed` after the call settles. A run that ends before then, such as a killed process, or a record write that fails, as [Installed files](../core/installation-record.md#installed-files) states, leaves the file pending, and a pending file is read as recorded: its registration is the one it intended, or the one it held before when it was removing. Before it starts any program, a child reads the plugin's file of every agent it may act on, the one `--agent` names or every agent in the table, and one that is damaged or holds an unknown `format` fails with `<record> cannot be read, so jsonkit will not change the registration it lists. Remove it, then run jsonkit mcp install again.`, with `uninstall` in place of `install` for that child.

### Checks first

`install` and `uninstall` check, in this order, before they start any program, and fail with a `FatalError` and exit 1 at the first that fails:

- **Not on Windows.** On `win32`: `jsonkit mcp install registers with claude and codex on Linux and macOS. Print a client configuration with jsonkit mcp config and add it to your agent yourself.`, with `uninstall` in place of `install` for that child. `host.spawn` runs no shell, and an agent CLI installed as a `.cmd` file cannot start without one, so a present agent would read as one that cannot start.
- **A control character.** For `install`, a word of the command line that holds a control character: `jsonkit cannot register its MCP server because its path holds a control character. Install jsonkit where its path has none.`
- **The record's directory.** `applicationDirectory('installation', name, host)`, which answering `{ variable }` fails: `jsonkit cannot find its installation record because XDG_STATE_HOME is not an absolute path. Set XDG_STATE_HOME to an absolute path, then run the command again.`, naming the variable the lookup answers.
- **The record.** The plugin's file of every agent the child may act on, as The record states, so a damaged file refuses even when its agent would be skipped.

### Install

- **Which agents.** With `--agent`, `install` acts on that agent, and one whose CLI cannot start fails: `jsonkit mcp install cannot register with codex, because codex could not start. Install codex, or leave out --agent.` With no `--agent`, it acts on every agent whose CLI starts, in table order, and prints `Skipped codex, because codex could not start.` for each other one; with none that starts, it fails: `jsonkit mcp install found no agent to register with, because neither claude nor codex could start. Install one of them, then run jsonkit mcp install again.` It starts every selected agent's `--version` before it writes anything.
- **A name the record does not list.** For each agent it acts on whose plugin's file records no registration, `install` checks whether the agent already holds the name, before it writes to any agent. Only Codex is checked: it holds the name when `codex mcp get <name> --json` exits 0 and does not when it exits 1, and any other exit code, or a check that cannot start, fails the child with nothing written: `jsonkit cannot tell whether codex already has a server named jsonkit, because codex mcp get exited with code 2. Fix what codex reported, then run jsonkit mcp install again.`, after the agent's output through `out.warn`. Claude has no check that does not start the server, so a name Claude holds is found by its own `add`, which refuses it as A failed call states. Without `--force`, when Codex holds the name, the child prints `codex already has an MCP server named jsonkit, which jsonkit mcp install did not register.` through `out.warn`, then fails: `jsonkit mcp install changed nothing, because a registration it did not make is in the way.`, corrected by `Remove it with codex mcp remove jsonkit, or run jsonkit mcp install --force to replace it.`
- **Registering.** For each agent in table order, `install` writes the plugin's file pending, runs the agent's calls, and commits the registration:
  - `claude`, recorded or under `--force`, runs `remove` and then `add`, and a `remove` that fails falls through to `add`; otherwise it runs `add`.
  - `codex` runs `add`, which replaces a registration of that name.

  Each agent registered prints `Registered jsonkit with claude to run /home/me/.local/bin/jsonkit mcp.` Under `--force`, an agent that held a name the record did not list also prints `Replaced the jsonkit server codex had, which jsonkit mcp install did not register.`: for `codex` when its name check exited 0, before it registers, and for `claude` when its `remove` exits 0, before its `add`.
- **A failed call.** An `add` that exits with any code but 0, or that cannot start, prints the agent's captured standard error and then its standard output through `out.warn`, one line each, writes that agent's plugin's file back to what is known to be registered, and fails. What is known is the registration the file recorded before the run, or no file when it recorded none, and no file for `claude` once its `remove` exited 0, so a failed `add` never records a registration the plugin did not make. A call the run signal ends is not a failed call: the agent may have written before it ended, so the file stays pending, as an interrupted run leaves it, and once the run signal aborts no further agent call starts, so the run resolves its cancellation code. A failed call's failure reads `jsonkit could not register with claude, because claude mcp add exited with code 1.`, or `because claude mcp add could not start.` For `claude` the correction is `If claude already has a server named jsonkit, remove it with claude mcp remove jsonkit -s user, or run jsonkit mcp install --force to replace it.`, and for `codex` it is `Fix what codex reported, then run jsonkit mcp install again.` An agent earlier in table order stays registered and recorded, and no later agent is attempted.
- **Any build.** `install` registers from a `source`, `development`, or `distributed` build alike, because an agent starts the server on demand. When the build is not `distributed`, it then prints `jsonkit is a development build, so the registration runs it from this checkout. Run mcp install from an installed jsonkit to register that one instead.`, with `a source build` for a source build. A source build then prints a second line through `out.info`, `The registration keeps no runtime flags, so a loader such as --import tsx is not passed on.`, because `host.program` is the runtime and the script alone.
- **No update.** There is no `update` child, and a self-update refreshes nothing, because it replaces the binary at the path the registration names. A re-run of `install` registers a program that moved.

### Uninstall

- **Which agents.** `uninstall` acts on each agent whose plugin's file records a registration, a pending one included, in table order, or on the one `--agent` names. With none, it prints `jsonkit is not registered with any agent by jsonkit mcp install, so there is nothing to remove.`, or `jsonkit is not registered with codex by jsonkit mcp install, so there is nothing to remove.` under `--agent`, and exits 0. A registration the record does not list is never removed.
- **Removing.** For each agent whose CLI starts, `uninstall` writes the plugin's file pending, runs `remove`, and deletes the file whatever `remove` answers, except a `remove` the run signal ends, which leaves the file pending; once the run signal aborts, no further agent call starts. A `remove` that exits 0 prints `Removed jsonkit from claude.` One that exits with any other code prints the agent's captured standard error and standard output through `out.warn`, then `jsonkit is no longer recorded as registered with claude.` A registration still held is then one the record does not list, which `install --force` takes back. When every agent `uninstall` acts on starts, it exits 0, whatever each `remove` answered.
- **An agent that cannot start.** A recorded agent whose `--version` call comes back `unstarted` keeps its plugin's file as it was and prints `claude could not start, so jsonkit stays registered with it.` through `out.warn`. Once every other agent is done, the child fails: `jsonkit mcp uninstall could not remove every registration.`, corrected by `Make claude available and run jsonkit mcp uninstall again, or remove jsonkit from claude's MCP configuration yourself.`, naming each agent that could not start.

### Config

- **The object.** `config` writes `JSON.stringify({ mcpServers: { [name]: { command, args } } }, null, 2)` and a line feed to stdout, where `command` is the command line's first word and `args` the rest, `mcp` last. The bytes reach stdout as the plugin built them, through `out.render` with a view that escapes the text's markup delimiters, as the [completion](completion.md) plugin's print children write their scripts, and a reader that closes stdout early ends the run with 141.
- **Nothing else.** It starts no program, reads no record, writes no file, and runs from every build and every platform. JSON escapes a control character, so no word is refused.

### Output

The `Registered`, `Removed`, and nothing-to lines go through `out.success`; the `Skipped`, `Replaced`, `no longer recorded`, and build lines through `out.info`; and the held-name, agent-output, and could-not-start lines through `out.warn`, so stdout stays empty for `install` and `uninstall`, and `config` writes stdout alone. The examples above omit the glyph each lane view adds. Every path, name, and line of an agent's output a sentence repeats passes through [`escapeControlCharacters`](../core/styles.md#strings-and-composition), and a command line is shown as its words joined by single spaces. Every refusal and check failure above is a `FatalError` that exits 1.

Each `claude` or `codex` call with `mcp add` or `mcp remove` that exits 0 records `Program run.`, with `arguments` holding the words the plugin passes, such as `['mcp', 'add', '-s', 'user', 'notes', '--', '/home/me/.local/bin/notes', 'mcp']`: the registration's name, `host.program`, and `mcp`, never a secret. A `claude mcp remove` before an `add` that exits otherwise falls through to `add` and records nothing, and the `--version` and `codex mcp get` reads record nothing. A leftover staging file the plugin removes beside a file it writes, which a run that was stopped mid-write left, records `File removed.` too.

Core shows each through its [log-line view](../core/logging.md#at--v) under the run's [verbosity](../core/verbosity.md): `-v -q` shows none, the lines go to stderr whether or not it is a terminal, an [`app.invoke`](../core/invocation.md#invocation-by-name) shows them in its `messages` when its values ask for them, and under an action's `invoke` or an [MCP](mcp.md) tool call they follow the outermost run's verbosity. Each line is a log event, so an installed [logging plugin](logging.md) records it at its level, and each change event the plugin records shows at `-v` too, as every `info` event does. [ADR-0165](../decisions/0165-first-party-plugins-say-what-they-did-at-v-and-record-each-change-they-make-as-a-log-event.md) records the lines and the events, and [ADR-0174](../decisions/0174-v-shows-the-log-through-message-templates-and-out-keeps-what-the-operator-is-told.md) moves the lines onto `log`.

## The protocol package

The protocol is written in this repository, in the private workspace package `@loom/mcp` at `packages/mcp`, which is never published. It knows MCP and nothing of Loom, and the plugin speaks MCP only through it.

- **Two eras.** The package holds two named constants: the per-request revision `2026-07-28`, and the initialize-era revisions `2025-11-25` and `2025-06-18`, latest first, which it serves to a client that opens its connection with `initialize`, such as Codex CLI. A request whose `params._meta` names `io.modelcontextprotocol/protocolVersion` is served on `2026-07-28`, whether or not the connection was initialized. Any other request is served on the revision the connection's `initialize` negotiated. Moving to a later revision is a deliberate change to this package and the plugin's tests, never a dependency update. [ADR-0122](../decisions/0122-the-mcp-server-serves-the-initialize-handshake-beside-the-per-request-revision.md) records the decision.
- **Framing.** The stdio transport reads newline-delimited JSON-RPC 2.0 messages and writes each message as one line of `JSON.stringify` output with no indentation, followed by a line feed, so no message holds an embedded line break. A blank line, one that holds nothing but spaces, tabs, and carriage returns, is ignored. Any other line that is not JSON is answered with `-32700`, and a message that is not a JSON-RPC request or notification, a batch included, with `-32600`. A response from the client is ignored. A last line that ends without a line feed when stdin ends is read as one message.
- **Request ids.** A request whose id matches a call or a subscription still in flight is answered, before every other check, with `-32600`, the id in use as the response's `id`, and the message `The request id is in use by a request still in flight. Send each request with an id no request in flight holds.` The request in flight keeps the id and runs untouched, so its answer stays the only one under that id and shutdown still waits for it. An id is free again once its request settles or the client cancels it.
- **Per-request checks.** A request on `2026-07-28` carries `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in its `params._meta`, and the server relies on no earlier request. A request whose `_meta` names a protocol version that is not a string, or carries no capabilities object, is answered with `-32602`. Before `initialize`, a tool request whose `_meta` names no protocol version is answered with `-32602` too, with a message naming both ways in: the two keys on every request, or `initialize`. A request for any version other than `2026-07-28` is answered with `UnsupportedProtocolVersionError`, `-32022`, whose `data` is `{ supported: ['2026-07-28', '2025-11-25', '2025-06-18'], requested }`.
- **The handshake.** An `initialize` request negotiates the connection's revision once: the `protocolVersion` it asks for when that is `2025-11-25` or `2025-06-18`, and otherwise `2025-11-25`, the latest, as the initialize-era lifecycle requires, so a client asking for `2024-11-05` learns the version it would have to speak. Its result holds `protocolVersion`, `capabilities` `{ tools: {} }`, and `serverInfo`, the server's identity, without its description on `2025-06-18`. An `initialize` whose `protocolVersion` is not a string or whose `capabilities` is not an object is answered with `-32602`, and a second `initialize` with `-32600`. `notifications/initialized` is accepted like every other notification. A client that speaks both eras probes with `server/discover` and never sends `initialize`.
- **An initialized connection.** A request with no per-request `_meta` is served on the negotiated revision, which serves `ping`, `tools/list`, and `tools/call` and answers every other method with `-32601`. `ping` is answered with an empty result at any time, before `initialize` too. Its results carry no `resultType` and no identity in `_meta`, and `tools/list` carries no `ttlMs` or `cacheScope`. Those revisions hold `structuredContent` as a JSON object alone, so a tool result whose structured content is an array, a string, a number, a Boolean, or `null` leaves it out, and its text content, which already carries the same JSON, stands alone: a view that prints an array answers text alone there.
- **Methods.** On `2026-07-28`, the package serves `server/discover`, whose `supportedVersions` lists all three revisions, `tools/list`, `tools/call`, and `subscriptions/listen`, answers every other method, `ping` included, with `-32601` before the per-request checks, and stamps `resultType: 'complete'` and the server's identity in `_meta` on every result. `subscriptions/listen` is acknowledged by `notifications/subscriptions/acknowledged`, its first message, with an empty `notifications` filter and `_meta['io.modelcontextprotocol/subscriptionId']` set to the request's id, and the server sends no other notification on it, because it offers no notification type. It stays open until the client cancels it or the server shuts down. A `tools/call` whose `params.name` is not a string is answered with `-32602`. A throw while the server handles a request is answered with `-32603`, and the server keeps serving.
- **Cancellation.** `notifications/cancelled` aborts the request it names and suppresses its response. A notification for an unknown or settled request is ignored. Every other notification is ignored.
- **Tool-call metadata.** `ToolCall` carries the request's optional `params._meta` object as `_meta`, without interpreting plugin-specific keys. The shared plugin handler reads the caller-zone key from it on stdio and HTTP alike. The protocol package keeps its existing envelope, revision, and progress checks.
- **Progress.** A `tools/call` handler receives a function that sends progress when the request's `params._meta` carries a `progressToken`, a string or a number, and no function otherwise. Each call of it writes one `notifications/progress` whose params hold the token as `progressToken`, the given `progress`, and the given `total` and `message` when present, and the package passes each one on as given, because its caller keeps `progress` increasing as the protocol requires. It writes none once the call is answered, cancelled by the client, or aborted by shutdown or the run's signal.
- **Shutdown.** When stdin ends, the package stops reading, aborts every call in flight, waits for each to settle, sends `notifications/cancelled` naming each open subscription, answers it with its closing result, whose `_meta` carries `io.modelcontextprotocol/subscriptionId` beside the server's identity, and resolves, so the caller returns. A call shutdown aborts answers nothing, as a call the client cancels answers nothing, while a `server/discover` or `tools/list` still pending is answered. A write the client can no longer read, such as one after it closed its end of the pipe, is dropped, and the run still resolves.
- **The run's signal.** `run(input, output, { signal })` takes an optional `AbortSignal`, through which the caller ends the run early. When it aborts, before or after stdin ends, the package stops reading, aborts every call, and answers no call. It then sends `notifications/cancelled` naming each open subscription and the subscription's closing result, as at the end of stdin, because `2026-07-28`'s Cancellation section requires the notification of a server that tears down a subscription, and a write the client can no longer read is dropped. It resolves once each call has settled. This is a change from the earlier rule that the signal ended a subscription with no message, and it ships with the HTTP transport, under [ADR-0184](../decisions/0184-the-mcp-plugin-also-serves-its-tools-over-streamable-http-at-an-address-the-operator-names.md). A signal already aborted when the run starts ends it before it reads anything.
- **Connections.** The package keeps a connection's state apart from its transport: the revision `initialize` negotiated, the calls and subscriptions in flight by request id, and the request-id rule above. One stdio run is one connection. Over HTTP, one initialize-era session is one connection, and one `2026-07-28` POST is a connection of one request, so its id is never in use. A connection is the package's state, never the transport's socket, which this page calls an HTTP connection: one HTTP connection may carry requests of several sessions, and a session outlives each HTTP connection its requests arrive on. Every rule above that names a connection holds for each of them, and the rules that name stdin, its end, and a line are the stdio transport's alone.
- **The HTTP transport.** The package answers one `node:http` request with the rules [Serving over HTTP](#serving-over-http) states from [The endpoint](#the-endpoint) through [Shutdown](#shutdown): it takes each accepted socket through `connection(socket)` for receipt deadlines and shutdown closure, the request and its response, the `onOriginRefused` callback, a callback that judges the headers for authorization, the body limit, the session idle interval, and the run's signal, and it owns the body limit's enforcement, the sessions and their expiry, the metadata-header checks, the event-stream framing, and each status. Listening, the address, and every operator sentence stay with the plugin. The protocol error text the transport answers lives in the package's `messages.ts`, beside the stdio text, worded for a POST body rather than a line.
- **Bundled into the pack.** `@loomcli/plugins` lists `@loom/mcp` as a development dependency alone. The pack keeps `tsc` for every subpath, and its build then bundles the `mcp` subpath's emitted server module, `serve.js`, which the entry loads when the `mcp` Command runs, with Rolldown, inlining `@loom/mcp` and leaving `@loomcli/core` and the pack's own modules external, so the packed tarball names no dependency on the private package. The HTTP server module, `serve-http.js`, which `serve.js` loads only when `--http` is given, receives the package's transport from `serve.js` and imports nothing of the package, so it needs no bundling, and its declarations write the transport's shape rather than name the private package.
