# Completion plugin

This page documents the completion plugin, which prints shell completion scripts and installs, updates, and removes them. An author installs it to give an operator tab completion for the application's Commands and options.

```ts
// @loomcli/plugins/completion
import type { Host, Log, Plugin } from '@loomcli/core';

export interface RefreshContext {
  readonly path: string; // the binary that replaced this one
  readonly host: Host; // the run's host
  readonly signal: AbortSignal; // the run signal
  readonly log: Log; // the run's log
}
export declare function completion(): Plugin;
export declare function refreshCompletion(context: RefreshContext): Promise<void>;
```

```ts
import { Application } from '@loomcli/core';
import { completion, refreshCompletion } from '@loomcli/plugins/completion';
import { help } from '@loomcli/plugins/help';
import { selfUpdate } from '@loomcli/plugins/self-update';

export const jsonkit = new Application('jsonkit', {
  plugins: [help(), completion(), selfUpdate({ afterReplace: refreshCompletion })],
});
```

```text
$ jsonkit completion install
Installed the zsh completion script in /home/me/.local/share/jsonkit/completion/zsh/_loom_jsonkit.
Added a line to /home/me/.zshrc that loads it.
Open a new shell to use it.
$ tail -n 1 ~/.zshrc
fpath=('/home/me/.local/share/jsonkit/completion/zsh' $fpath); if [ -f '/home/me/.local/share/jsonkit/completion/zsh/_loom_jsonkit' ]; then . '/home/me/.local/share/jsonkit/completion/zsh/_loom_jsonkit'; fi # added by jsonkit completion install
$ jsonkit completion uninstall
Removed /home/me/.local/share/jsonkit/completion/zsh/_loom_jsonkit.
Removed the line from /home/me/.zshrc.
```

```sh
# Loading a printed script by hand instead:
source <(jsonkit completion bash)   # in ~/.bashrc
source <(jsonkit completion zsh)    # in ~/.zshrc, after compinit
jsonkit completion fish | source    # in ~/.config/fish/config.fish
jsonkit completion powershell | Out-String | Invoke-Expression   # in $PROFILE
```

```text
$ jsonkit completion __complete -- ke
keys→List the keys at a path.
:4
```

`completion()` is the completion plugin. Its identity is `@loomcli/plugins/completion`, and it declares no settings, no options, no middleware, and no extension; its whole contribution is one [plugin Command](../core/plugin-contract.md#plugin-commands) group. `jsonkit completion install` writes the operator's shell's script to a file and has the shell load it, and `jsonkit completion zsh` prints the script for an operator who loads it another way. From then on, each Tab runs the script, which calls `jsonkit completion __complete` with the words typed so far and inserts what it answers. The script holds no copy of the Command tree, so it never goes stale when the application changes. [ADR-0043](../decisions/0043-shell-completion-follows-cobras-protocol-and-never-evaluates-typed-text.md) records the decision: the scripts and the answer follow [Cobra](https://github.com/spf13/cobra)'s, and nothing typed is ever evaluated. [ADR-0078](../decisions/0078-the-completion-plugin-installs-a-script-and-one-startup-line-per-shell.md) records installing, and [ADR-0101](../decisions/0101-completion-installs-on-linux-and-macos-and-a-startup-line-is-written-or-printed.md) narrows it to Linux and macOS. In the answer above, `→` stands for one tab character.

- **The Commands.** `completion` is a group, `Print or install a shell completion script.`, with these children:
  - `bash`, `zsh`, `fish`, and `powershell`, each `Print the <Shell> completion script.`, where `<Shell>` is `Bash`, `Zsh`, `Fish`, or `PowerShell`, with no argument or option.
  - `install`, `Install completion for your shell.`, with one optional argument, `shell`, `The shell: bash, zsh, fish, or pwsh. Your login shell when left out.`, validated to those four values.
  - `update`, `Bring installed completion up to date with this version.`, with no argument or option.
  - `uninstall`, `Remove completion from your shell.`, with one optional argument, `shell`, `The shell: bash, zsh, fish, or pwsh. Every installed shell when left out.`, validated the same way.
  - the hidden `__complete`, `Answer a completion script.`

  A `shell` value outside the set is core's usage error for that input, with exit 2. No child declares a result, so `--format` never applies. A group cannot declare arguments beside children under [ADR-0004](../decisions/0004-arguments-and-children-are-exclusive.md), so each printed shell is a child, and `jsonkit completion` prints the missing-subcommand error that lists the visible children. `pwsh` is the shell name `install` and `uninstall` take for PowerShell 7, not a print child, because PowerShell runs the script `powershell` prints.
- **Exact bytes.** Each print child and `__complete` write through `out.render` with a view that escapes the text's markup delimiters, so the bytes reach stdout as the plugin built them, with no newline added. A print child writes its script, and `__complete` writes its answer; a failure in either writes nothing to stdout. Because both write through `out`, a reader that closes stdout early, such as `jsonkit completion bash | head -1`, ends the run with 141 under [Signals and cancellation](../core/signals.md). `install`, `update`, and `uninstall` write through `out`, as Output states.
- **The callback.** The script runs `<program> completion __complete -- <words>`, where `<program>` is the first word with its quoting removed and no expansion, and `<words>` are the words after it, the last cut at the cursor and empty when the cursor starts a new word. The words arrive in `passthrough`, so the parser never reads one of them as an option and a typed `--help` activates nothing. `__complete` passes them to [`locate`](../core/graph-inspection.md#locating-a-word) with the action's `graph`. Each Tab is an ordinary run: always-on middleware and the configuration source run as on any run, and the script discards stderr. Stdout that an always-on middleware, or a plugin activated through its environment binding, writes on a `__complete` run is read as offered words, so a plugin that writes to stdout on a run it does not own breaks completion.
- **Offered words.** By the position `locate` reports:
  - `command`: the canonical names of the node's children, each with its description, and directive `4`.
  - `option`: the long spellings of the options in scope, a Boolean's negative spelling included, and also the short spellings when `prefix` is exactly `-`, each with its option's description, and directive `4`. An option the earlier words gave is left out unless another occurrence still adds anything, the rule help's `...` reads too, through one package-internal module outside either subpath that help and completion both import: a multiple string option collects another value and a counted option adds one, so each is offered again, except that the [quiet-marked](../core/verbosity.md) option is not offered once `counts` holds it at 1 and the verbose-marked option is not offered once `counts` holds it at 2, because the verbosity reads neither count higher.
  - `value` and `argument`: the values of the closed set the input's `schema` names, each written after `lead` under `value`, with no description, and directive `4`. The closed set is the one help derives for its [accepted values](help.md#accepted-values), read through one package-internal module outside either subpath, beside `encode.ts`, that help and completion both import. The module returns the whole set, and each reader applies its own bound: help keeps its limit of eight under Bounds, and completion offers every value, so a Command with more than eight view names completes each of them. An input with no closed set, a `null` schema included, offers nothing with directive `0`, so the shell completes file names.
  - `passthrough`: nothing, with directive `0`.
  - `none`: nothing, with directive `1`.

  A string option with an [implied value](../core/options.md#implied-values) has its values offered only after `=`, as `--backup=<Tab>`, or after its short letter in the same word, because `locate` reads a bare spelling as complete: after `--backup` and a space, completion offers what the next word may otherwise be and awaits no value.

  A hidden or deprecated Command or option is never offered, and one typed in full still routes and completes past. An alias, a Command's or an option's, is never offered and never rewritten: `locate` routes through it and reads an option alias's value, and completion reads no alias. Only words that start with `prefix`, compared by code unit, are offered, a value compared before `lead` is added to it, so `--format=j` offers `--format=json`, in graph order with repeats removed.
- **The answer.** One line per offered word: the word, then, when it has a description, a tab and the description. The last line is `:` and the directive. Every line ends with a newline. The directive numbers are Cobra's: `1` error, `2` no space, `4` no file completion, `8` filter by file extension, `16` directories only, `32` keep order, and `0` the shell's default. The plugin writes `0`, `1`, or `4`, and the scripts honor all of them, except that the Fish script, as Cobra's does, completes every file name under `8` and `16`.
- **Exact or omitted.** An offered word that holds a control character or a line separator, U+0000 through U+001F, U+007F through U+009F, U+2028, or U+2029, is left out rather than cut, so completion never inserts a value the graph does not hold. An empty value, a value holding a lone surrogate, which the shell would receive as U+FFFD, and a value that starts with `_activeHelp_ `, which Cobra's scripts read as help text, are left out too. So is a word whose first character is `~`, because Bash 3.2 and Fish insert it unescaped and it would expand when the line runs; a `~` later in a word, such as after `--format=`, is offered. The Bash script escapes every `~` it inserts, because Bash expands a `~` after `=` or `:` in a word shaped like an assignment. A description is display text: each line break in it, CRLF or a single terminator, reads as one space, as help reads it, then every such character is removed, and no tab when nothing is left.
- **The scripts.** The Bash, Zsh, Fish, and PowerShell scripts are ported from Cobra, with Cobra's Apache-2.0 notice and license text kept beside them in the pack and the changes stated. Each inserts an offered word through its shell's own completion call as one exact value. The PowerShell script runs on PowerShell 7, which CI runs on Linux and macOS, registers with `Register-ArgumentCompleter -Native`, and returns each offered word as a `CompletionResult` whose text is the word itself when it holds only ASCII letters, digits, and `-`, `_`, `.`, `/`, `:`, and `=`, and otherwise the word in PowerShell's single quotes as The name states. The script passes an empty last word, and a word holding `"`, to the program as that exact argument. When the program resolves to a `.bat` or `.cmd` file, the script offers nothing and does not call it, because `cmd.exe` reads its arguments again as commands. The Bash script runs on Bash 3.2 and later, with or without the bash-completion package. A Bash without `compopt`, such as 3.2, cannot turn default file completion off, so there the script registers without it and completes file names itself, only when the directive allows files and no word was offered. Without the bash-completion package's `_filedir`, the Bash script lists file names by pathname expansion of the typed word with only a trailing `*` unquoted, and it calls no `compgen -f` or `compgen -d`, because in a completion Bash 3.2 expands the directory part of their word. The Bash script escapes every word it inserts with `printf %q`, and a leading `~` too. With several matches it lists the escaped words, so the common prefix readline inserts is escaped text. The Zsh script's completion function is `_loom_<identifier>`, so no application name shadows a completion system function such as `_describe`.
- **No evaluation.** A script never evaluates text. Every `eval` in Cobra's scripts is removed, and so is the PowerShell script's `Invoke-Expression`, through which Cobra's builds and runs its request as a string, and every construct that expands an operand, such as Bash's `compgen -W`, which expands its word list: a script filters offered words by string comparison, and it honors directives `8` and `16` without evaluating an offered word. It calls the program with an argument array, so a typed word reaches the application as its characters and pressing Tab never runs it. It removes quoting without evaluating, through Zsh's `(Q)` flag, Fish's own tokenizer and `string unescape`, a string-only decoder in the Bash script, and the value of each constant string element in the command PowerShell's parser hands the completer, passing any other element, such as one holding a variable or a subexpression, as the text typed, and it performs no expansion, so `~`, `$HOME`, and `$(…)` reach the application as typed, and the Bash file listing never rewrites them; a Bash with `compopt` leaves the fallback to its own default file completion, which keeps the typed `$HOME/` and may append a file name it finds under the expanded directory. Zsh's default Tab widget, `expand-or-complete`, expands a typed `$(…)` before any completion function runs, so in Zsh pressing Tab runs it whether or not the script is installed; `bindkey '^I' complete-word` binds Tab to completion alone and avoids it. When the word under the cursor holds an unclosed quote, the script offers nothing and does not call the application. A nonzero exit, or an answer whose final line is not `:` followed by decimal digits, offers nothing.
- **The name.** The application name reaches a script only as data: as a single-quoted string in its shell's quoting, for Bash and Zsh with each `'` written as `'\''`, for Fish, whose single quotes read `\'` and `\\` as escapes, with each `\` written as `\\` and each `'` written as `\'`, and for PowerShell, whose single quotes end at `'` and at each of U+2018 through U+201B and read a doubled one as that character, with each of those five written twice; as the suffix of a function identifier in which every character outside `A-Z`, `a-z`, and `0-9`, `_` included, is written as `_` and its code point's lowercase hexadecimal digits and another `_`, so `git-lfs` gives `git_2d_lfs` and no two names give one identifier, and in the Zsh `#compdef` comment and autoload check as it is, because a portable name holds nothing a comment or a double-quoted string can misread. A script takes the Application's name, which `new Application()` already holds to the portable set under `@loomcli/core/portable-name`, so no other name reaches a script. The quoting and the identifier encoding stay, because `.` and `-` are portable and neither is an identifier character, so any name the constructor accepts yields a script that runs nothing but completion.
- **Which applications.** A root that declares arguments cannot hold children, so textstat cannot install the plugin, as [Plugin Commands](../core/plugin-contract.md#plugin-commands) states, and an application installs it once, because a second `completion` collides there.

## Installing completion

`install`, `update`, and `uninstall` act on shells. For each, the plugin writes the shell's script to a file and, for every shell but Fish, has the shell's startup file load it through one [startup line](../core/installation-record.md#installed-files). Both are recorded through the [installed-files module](../core/installation-record.md#installed-files), each shell in its own plugin's file, `completion.<shell>.json`, so an install for one shell never removes another's script or line.

- **The shell.** `install` acts on its `shell` argument. Left out, it reads `SHELL` from `host.env`: when the variable is set and the last segment of its value, after the last `/`, is one of the four shell names, that is the shell. Otherwise the action throws an `InputError` with exit 2, `jsonkit cannot tell your shell from SHELL (/bin/sh). Name it: jsonkit completion install bash, zsh, fish, or pwsh.`, with `(unset)` for a variable that is unset or empty. `uninstall` acts on its `shell` argument, or, left out, on every shell whose plugin's file exists, in the order the four names are listed. `update` acts on every shell whose plugin's file, read as recovery would resolve it, records a file; a shell whose pending file records none keeps it for its next `install` or `uninstall`.
- **The files.** `<home>` is `HOME`; `<data>` is `XDG_DATA_HOME` when it is an absolute path, else `<home>/.local/share`; and `<config>` is `XDG_CONFIG_HOME` when it is an absolute path, else `<home>/.config`; each read from `host.env`. `<app>` is the application's name.

  | Shell | Script | Startup file |
  | --- | --- | --- |
  | `bash` | `<data>/<app>/completion/<app>.bash` | `<home>/.bashrc`; on `darwin`, the first of `<home>/.bash_profile`, `<home>/.bash_login`, and `<home>/.profile` that exists, else `<home>/.bash_profile` |
  | `zsh` | `<data>/<app>/completion/zsh/_loom_<identifier>` | `$ZDOTDIR/.zshrc` when `ZDOTDIR` is an absolute path, else `<home>/.zshrc` |
  | `fish` | `<config>/fish/completions/<app>.fish` | none |
  | `pwsh` | `<data>/<app>/completion/<app>.pwsh.ps1` | the path `pwsh` reports for `$PROFILE` |

  Fish reads `<config>/fish/completions` on every version since 3.0; the vendor folder under `<data>` joined its path only in 3.5. On `darwin`, a terminal opens a login Bash, which reads the first of those three files and never `.bashrc`, so the line goes where that Bash reads it and never creates a `.bash_profile` that would shadow an existing `.profile`; a Bash started from another shell is not a login shell and reads `.bashrc`, where the operator loads the script by hand. `$PROFILE` is the profile of the current user and the console host, so the PowerShell extension of an editor, which reads its own profile, does not load the line. On `win32`, `install`, `update`, and `uninstall` fail for every shell with a `FatalError` and exit 1: `jsonkit completion installs bash, zsh, fish, and pwsh completion on Linux and macOS. Print the script with jsonkit completion powershell and load it yourself.`, naming the print child for the shell asked for, and `powershell` for `pwsh` or when no shell is named.
- **The scripts.** Each file holds the script the shell's print child prints, with two differences: the Zsh file's check for being loaded as a completion function names its own file, `_loom_<identifier>`, and, right after its `#compdef` line, it starts the completion system when no `compdef` function is defined, with `autoload -Uz compinit && compinit -i`, which skips an insecure folder on `fpath` rather than asking at every shell start, and returns before it registers anything when `compdef` is still not defined. The `pwsh` file holds the script `powershell` prints. Each is written with mode `644`, and each folder the module creates for it with mode `755`, whatever the umask, so a later `compinit` never reads the Zsh folder or its parent as insecure.
- **The startup line.** One line that loads the script when the file exists and ends with a comment naming the install Command:

  | Shell | Startup line |
  | --- | --- |
  | `bash` | `if [ -n "${BASH_VERSION-}" ] && [ -f '<script>' ]; then . '<script>'; fi # added by <app> completion install` |
  | `zsh` | `fpath=('<folder>' $fpath); if [ -f '<script>' ]; then . '<script>'; fi # added by <app> completion install` |
  | `pwsh` | `if (Test-Path -LiteralPath '<script>') { . '<script>' } # added by <app> completion install` |

  `<script>` is the script's path and `<folder>` the folder that holds the Zsh script, each in its shell's single quotes as The name states. The Bash line checks `BASH_VERSION` because a `.profile` is also read by other shells. The Zsh line puts the script's folder on `fpath` before it sources the script, so a `compinit` later in `.zshrc` that rebuilds its cache, as it does when the number of completion files on `fpath` changed since the cache was written, finds the script through its `#compdef` line rather than dropping the registration the source made. A later `compinit` that loads a cache written before the install, as `compinit -C` always does and `compinit` does when the number of files is unchanged, such as after one application's completion was uninstalled and another's installed, drops the registration until the cache is rebuilt; removing the cache, `.zcompdump` by default, rebuilds it at the next shell start. Loom never touches the cache, which is the operator's. The file is named `_loom_<identifier>`, with the identifier The name states, so no application name shadows a completion function Zsh ships, such as `_files` for an application named `files`. A shell starts no program to load the script, and a missing script loads nothing, so a line left behind is harmless.
- **Asking PowerShell for its profile.** For `pwsh`, `install` runs the shell with the words `-NoLogo -NoProfile -NonInteractive -Command` and `[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($PROFILE))`, as a child process with `host.env` as its environment, `<home>` as its working directory, no shell, and no input, and reads its standard output. The program is the first file named `pwsh` in an absolute entry of `PATH` from `host.env`, so a program in the working directory or under a relative entry never runs. It adds no time limit; the run signal ends the child with `SIGTERM`. The answer, with a trailing line feed or carriage return and line feed removed, is the profile's path in Base64 of its UTF-8 bytes, which no console code page changes. A shell not found on `PATH`, or that cannot start, fails with a `FatalError` and exit 1: `jsonkit cannot find the profile of pwsh, because pwsh could not start. Install pwsh, or name the shell you use.`; one that exits with any code but 0 fails the same way, `because pwsh exited with code <code>.`, with the same correction. An answer that is not that shape, or whose path is not absolute, fails with `jsonkit cannot find the profile of pwsh, because pwsh reported <answer>.`, corrected by `Check that pwsh -NoProfile -Command $PROFILE prints the path of your profile.`, with the answer passed through [`escapeControlCharacters`](../core/styles.md#strings-and-composition). `uninstall` and `update` read the startup file from the plugin's file and run no shell.
- **Checks first.** Each child checks, in this order, and fails at the first that fails, with the failure each names:
  1. Every child: the platform, which `win32` fails as The files states.
  2. `install`: the shell, as The shell states.
  3. `install`: `<home>`, unless the paths it needs come from absolute variables alone: `jsonkit cannot find your home folder because HOME is not an absolute path. Set HOME to an absolute path, then run the command again.`, a `FatalError` that exits 1.
  4. Every child: the record's directory, `applicationDirectory('installation', name, host)`, which answering `{ variable }` fails as [Skills](skills.md#global-installs) states.
  5. Every child: each selected shell's plugin's file, read through the module. One that is damaged or holds an unknown `format` fails with a `FatalError` and exit 1: `<record> cannot be read, so jsonkit will not change the files and line it lists. Remove it, the files it lists, and the line it added, then run jsonkit completion install again.`, with `uninstall` in place of `install` for that child.
  6. `install` and `update`: every selected shell's script, which Files the record does not list may refuse.
  7. `install`, for `pwsh`: the profile.
  8. Every child: every startup file it would change, under A startup file the plugin cannot change.

  `update`, and `uninstall` with no shell, check every selected shell before they write any, so a refusal changes no file of any shell.

## A startup file the plugin cannot change

Before it writes anything, a child that would add, replace, or remove a startup line reads the startup file, resolved through symbolic links to its real path, and the nearest folder at or above it that exists.

- **Not a file.** A directory or any other file that is not a regular file there, or a symbolic link whose target does not exist, fails `install` with a `FatalError` and exit 1, `<startup> is not a file, so jsonkit cannot add its startup line. Remove it, then run jsonkit completion install again.`, and writes nothing.
- **Cannot change.** The startup file cannot be changed when the process may not write the file, or the folder that holds it, or, for a file that does not exist, the nearest folder at or above it that exists; when the file is owned by another user; or when it is not UTF-8, which Installed files reads. A read-only home configuration manager that links the startup file is the common case. A startup line is then printed and never recorded, and Loom removes only a line it wrote, under [ADR-0101](../decisions/0101-completion-installs-on-linux-and-macos-and-a-startup-line-is-written-or-printed.md).
  - `install` writes the script and records it with no startup line, prints `jsonkit cannot change <startup>, so add this line to it yourself:` through `out.warn`, then the line itself through `out.print`, and exits 0. A line the record held for that file is dropped from the record without writing the file; when its text differs and the file holds it, or cannot be read to tell, `install` first prints the line to remove as `uninstall` does, and the line to add follows `Add this line to <startup> in its place:`. A file that already holds the line prints `<startup> already loads it.` and no line to add.
  - `uninstall` does everything else and drops the recorded line from the plugin's file without writing the startup file, prints `jsonkit cannot change <startup>, so remove this line from it yourself:` through `out.warn` and the line through `out.print`, and exits 0. A file it can read that no longer holds the line prints the no-longer-holds line instead.
  - `update` does everything else and drops the recorded line the same way. When this version changes the line's text and the file holds the old line, or cannot be read to tell, it prints the line to remove, then, unless the file already holds the new line, `Add this line to <startup> in its place:` through `out.warn` and the new line through `out.print`. A line whose text is unchanged is dropped with nothing printed, because no line in the file has to change.

## Install, update, and uninstall

- **`install`.** For the selected shell, the module installs the script file and, for every shell but Fish, the startup line. A script file that is unchanged, recorded with the digest of the script it would write, is not rewritten and prints `<script> is unchanged.`; otherwise it prints `Installed the <shell> completion script in <script>.` A startup line added prints `Added a line to <startup> that loads it.`, and one the startup file already holds prints `<startup> already loads it.` When the script now differs from the one recorded, as after `XDG_DATA_HOME` changed, the module removes the recorded script, which prints as `uninstall` states, and replaces the recorded line where it stands in its startup file, which prints `Updated the line in <startup>.` When the startup file it computes now differs from the one recorded, as after `ZDOTDIR` changed, the module removes the recorded line, which prints as `uninstall` states. When anything changed, it prints `Open a new shell to use it.`
- **Files the record does not list.** A script file the shell's plugin's file does not record, any file or folder at its path, refuses `install` and `update`, and so does a recorded script whose digest changed since it was written. The child prints one line for each through `out.warn`, `<script> was not installed by jsonkit completion install.` or `<script> changed since jsonkit completion install wrote it.`, then fails with a `FatalError` and exit 1: `jsonkit completion install changed nothing, because files it did not install are in the way.`, corrected by `Remove them, then run jsonkit completion install <shell> again.` `update` uses `jsonkit completion update` in the failure sentence and `jsonkit completion install` in the correction. There is no `--force`.
- **`update`.** For each shell it acts on, it rewrites the script at its recorded path with this version's script, printing `Updated the <shell> completion script in <script>.` in place of the installed line, or the unchanged line. When the line `install` would add for the recorded script differs from the recorded line, which happens only when a new version changes the line's text, it replaces each line of the recorded startup file equal to the recorded one where it stands and prints `Updated the line in <startup>.` It reads no variable the paths come from, so a refresh run from another environment never moves a script, and it never adds a line the startup file no longer holds. With no shell recording a file, it prints `jsonkit has no completion installed, so there is nothing to update. Run jsonkit completion install to install it.` and exits 0.
- **`uninstall`.** For each shell it acts on, the module removes the recorded script when its digest is unchanged, removes each line of the startup file equal to the recorded line, removes each directory it created that is then empty, and deletes the plugin's file. It prints `Removed <script>.` and `Removed the line from <startup>.` A changed script is kept and prints `<script> changed since jsonkit completion install wrote it, so it was left in place.` through `out.warn`; a script already gone prints `<script> was already gone.`, and a startup file that no longer holds the line prints `<startup> no longer holds the line jsonkit completion install added, so it was left as it is.` With nothing recorded for the shells it acts on, it prints `jsonkit has no completion installed, so there is nothing to remove.` and exits 0. The startup file itself is never removed.
- **Any build.** Every child acts from a `source`, `development`, or `distributed` build alike, because a script calls the program by the name the operator typed, not by the binary's path.

## Refreshing completion after a self-update

`refreshCompletion` is an `afterReplace` function for the [self-update plugin](self-update.md), which passes it a context that holds every member `RefreshContext` names. A script changes only when a new version of Loom changes it, but the replaced process holds the old version's scripts, so `refreshCompletion` runs the new binary, and `update` decides what to refresh. It runs `path` with the words `completion update` exactly as [`refreshSkills`](skills.md#refreshing-after-a-self-update) runs `skills update`, under the same rules for the child, its output, and the run signal. A child that fails, or that cannot start, adds the `warn` log event `Completion was not refreshed after the update.`, with the same fields, and resolves; one that cannot start writes `Completion was not refreshed because /home/me/.local/bin/jsonkit could not start. Run jsonkit completion update.` to `host.stderr`. An application that also refreshes skills calls both from its own `afterReplace`:

```ts
selfUpdate({
  afterReplace: async (context) => {
    await refreshSkills(context);
    await refreshCompletion(context);
  },
});
```

A binary that a package manager, npm, or the installer script replaced runs no `afterReplace`. Until the operator runs `completion update`, its installed script is the one the earlier version wrote, which keeps completing every Command and option the new binary has, because it asks the binary at every Tab.

- **Output.** The `Installed`, `Updated`, `Added a line`, `Updated the line`, and nothing-to lines go through `out.success`; the `is unchanged`, `already loads`, `Removed`, `already gone`, `no longer holds`, and `Open a new shell` lines through `out.info`; the refused-file, left-in-place, and cannot-change lines through `out.warn`; and a line the operator adds or removes by hand through `out.print`, the only thing `install`, `update`, or `uninstall` writes to stdout. The examples above omit the glyph each lane view adds. Every path a sentence repeats passes through `escapeControlCharacters`. Every refusal and check failure above is a `FatalError` that exits 1, and an unknown shell is the `InputError` above.
- **Names.** `completion`, `refreshCompletion`, and `RefreshContext` are exported from `@loomcli/plugins/completion`. `RefreshContext` is the same declaration `@loomcli/plugins/skills` exports.
