# loom docs

`loom docs <directory>` writes a Markdown reference for every Command of the application that is not hidden. Each Command gets one file named `<application>-<path joined by ->.md`, and `index.md` lists them. The pages are the ones [`skills install`](../plugins/skills.md) writes as a skill's command references, rendered by the same function, without the skill guidance.

```sh
loom docs reference
```

```text
Wrote 4 command reference files to /work/notes/reference.
```

For an application `notes` with the Commands `add` and `list`, the directory holds `index.md`, `notes.md`, `notes-add.md`, and `notes-list.md`.

`<directory>` is required, resolves against the working directory, and is created when it does not exist. The command reads `--application` relative to the working directory, otherwise `paths.application` from `loom.config.json`, otherwise `src/application.ts`, as [`loom skills export`](skills.md) does. It imports the module under Bun, builds the graph, and runs no application action, but importing the module executes author code.

Every generated file ends with a blank line and the line `<!-- Generated by loom docs. -->`, so `index.md` keeps its frontmatter first. A file has the marker when its last non-empty line is exactly that comment.

- A later run overwrites the files it generates, so edits to a generated file are lost. Repeating a run with nothing changed leaves every file's bytes as they were.
- After writing, the run removes only regular `.md` files directly in the directory that have the marker, were not written by this run, and have a name this application owns: `index.md`, `<app>.md`, or a name starting with `<app>-` and ending with `.md`, where `<app>` is the application name. The success sentence counts only those removals. The run does not look in subfolders or remove links.
- A marked file under any other name is yours and is never removed. After an application is renamed, the old application's files stay for you to remove. A directory belongs to one application's reference, because every run writes `index.md`, and an application whose name is another's followed by a hyphen, such as `acme` beside `acme-admin`, owns the other's file names too.
- Deleting the marker line makes a generated file yours, after which the run refuses to write over it. A file without the marker is yours and is never overwritten or removed. When one sits at a path the run would write, the run fails before writing anything and names the file. Move or rename it, then run `loom docs` again.

The command renders with the application's own `@loomcli/plugins`, so the package must depend on it. When it does not resolve, the command says: `The package resolves no @loomcli/plugins that renders command references. Install a current @loomcli/plugins, then run loom docs again.`

A failure partway through writing leaves the files written so far, and running the command again completes the set.

A module that cannot load fails with the application reader's report. A renderer that throws once the module has loaded, or a resolved `@loomcli/plugins` skills module that fails to load, fails with the Developer Diagnostic [`@loomcli/loom/command-references-failed`](../core/diagnostics.md#loomcliloomcommand-references-failed), which names `@loomcli/plugins` rather than the module, and nothing is written. File-system failures name the path and the cause in Loom's words. Failures exit 1, and a missing directory argument or invalid configuration exits 2.
