# ADR-0092 - Core settles each run's background once, and a theme entry may adapt to it

## Context

The [Loom theme](../core.md#loom-theme) has dark foreground defaults only. On a light terminal its dim `#8B93A3` and warning `#E2B93D` almost disappear. [ADR-0022](0022-renderers-return-marked-strings-that-core-resolves-and-a-theme-is-a-palette.md) makes a theme a palette of concrete styles, [ADR-0027](0027-core-resolves-marked-output-and-one-theme-contribution.md) gives a run one theme contribution, and neither knows the terminal's background. [ADR-0029](0029-explicit-color-fallbacks-preserve-theme-hues.md) deferred light colors and background detection.

A terminal can report its background. xterm's OSC 11 query asks for the background color, the color-scheme query `CSI ? 996 n` asks whether the scheme is dark or light, and nearly every terminal answers the Primary Device Attributes query, DA1, `CSI c`. A terminal answers in the order it was asked, so a DA1 reply sent after the other two marks the end: any other reply has arrived, or never will. Reading the replies needs stdin in raw mode before the action runs, which [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md)'s statement that `run()` consumes no stdin does not allow. A pseudo-terminal with no emulator behind it, a stalled SSH link, or a terminal without DA1 never answers, so the wait needs a backstop.

[ADR-0091](0091-live-regions-stack-at-the-bottom-of-stderr-and-progress-reaches-invoke-callers-and-mcp-clients-as-typed-events.md) states the timer rule: "Core never uses a timer to cancel or limit work because it has run too long; that is the author's job, in the author's own action." A deadline on a reply to a query core itself wrote, before any author code runs, bounds no work.

`COLORFGBG`, which rxvt and some other terminals export, names the background's palette index. It is set when the shell starts, so it goes stale when the operator switches the terminal's theme, and many terminals never set it.

## Decision

- **Adaptive theme entries.** `style.adaptive({ dark, light })` returns an adaptive style, a theme entry that holds one concrete style for each background. Each side follows the rules of a plain entry, an unapplied concrete chain with no semantic token, with its own fallbacks. One theme contribution still holds: the mapping is one value, and an entry opts in alone. Core resolves an adaptive entry to the side that matches the run's background when it emits the token, at every depth, and to the dark side when the background is `undefined`. A plain entry looks the same on both backgrounds.
- **One background per run.** Core settles the run's background, `'dark'`, `'light'`, or `undefined`, once, right after the operator's color choice under [ADR-0089](0089-an-operators-color-or-no-color-settles-the-runs-color-right-after-host-capture.md) and before graph build, so the first themed byte already knows it. It never changes within the run: settlement reads the captured environment and the run's color before environment preparation, so a color change during preparation, such as a dotenv file importing `FORCE_COLOR` under the shell's `NO_COLOR`, leaves it as settled.
- **Precedence.** The first source that answers settles it: the operator's background choice; the author's `rendering.background`, `'dark'` or `'light'`, with `'auto'` the default that answers nothing; a background a host override states as `host.terminal.background`, so a test never queries; `undefined` when stdin, stdout, or stderr is not a terminal, as in `app | fzf`, `app | less`, or `app > file`, because a program at the other end of a pipe may read the terminal itself and race core for the replies and the terminal's mode, or when the run's color is off on both stdout and stderr; dark when `TERM` is `linux`; the terminal's answer to the background query; `COLORFGBG`, light when its last field is `7` or `15`; and `undefined`, so a background no source knows never passes for dark. The steps after the host override detect the background, and they run only when an entry of the installed theme is adaptive or an option carries the background mark, as the background plugin's does; otherwise the background stays `undefined`. An invocation by name settles nothing and reads `undefined` whatever the policy holds.
- **The query.** Core writes OSC 11, then `CSI ? 996 n`, then DA1 as the sentinel, in one write to stderr, which the step before leaves a terminal whose color is on. An OSC 11 reply of `rgb:` with 1 to 4 hex digits in each component, ended by BEL or ST, answers light when its relative luminance is above 0.5. When no OSC 11 reply parses, a `CSI ? 997 ; 1 n` reply answers dark and `CSI ? 997 ; 2 n` answers light.
- **The read.** Core puts stdin in raw mode, reads until the DA1 reply, removes the replies to its queries from what it read, and pushes every other byte back onto stdin in arrival order, so keys typed ahead reach the action's own read. It reads through a `data` listener and `resume()`. In a `finally` it restores the mode it found, removes its listeners, and pauses the flowing stream, which emits the `pause` event on which the runtime stops a terminal's handle reading, so stdin keeps no run alive; it then sets the stream's flowing state back to the state it found, so an action's own `data` listener starts it flowing.
- **Interrupt keys.** Raw mode delivers `Ctrl-C`, `Ctrl-\`, and `Ctrl-Z` as the bytes 0x03, 0x1c, and 0x1a instead of signals. Core drops each one read during the wait from the typeahead, and once the mode is restored, it raises SIGINT, SIGQUIT, or SIGTSTP for each on its own process in arrival order, so the run behaves as if the key came a moment later. No signals owner's listener is installed before graph build, so the process's own disposition answers, and with no listener of the author's, the runtime's default ends the run, which a shell reports as status 130 for `Ctrl-C`, or stops it for `Ctrl-Z`.
- **The deadline.** One unref'd timer of 1 second backs the read, and core clears it as soon as the DA1 reply arrives. When it fires, the replies that arrived before it answer as above, so an OSC 11 reply counts even when the DA1 reply never came; with none, settlement continues at `COLORFGBG`. The timer bounds core's own wait for a reply to a query core wrote, before any author code runs. It cancels and limits no work, so it keeps the timer rule [ADR-0091](0091-live-regions-stack-at-the-bottom-of-stderr-and-progress-reaches-invoke-callers-and-mcp-clients-as-typed-events.md) states.
- **Skipped.** Core writes no query and reads no byte when an earlier source settles the background, when the run is already cancelled, when stdin offers no raw mode or refuses it, when `TERM` is unset, empty, or `dumb`, when `STY` or `INSIDE_EMACS` is set and nonempty, because GNU screen and Emacs do not pass the query through, when the host's platform is `win32`, when stdin is a real terminal and the process is not in that terminal's foreground job, and when detection does not run because no theme entry is adaptive and no option carries the background mark. An invocation by name settles nothing and reads `undefined`. A completion request a shell's completion script makes reads `undefined` and writes no query, because the script gives it no terminal; one typed by hand at a terminal settles as any other run does.
- **The foreground check.** A background job that switches its terminal to raw mode is sent SIGTTOU, and one that reads its terminal SIGTTIN, and either stops it. Before the query, when `host.stdin` is a real terminal stream, core compares the process group with the terminal's foreground process group: it reads both from `/proc/self/stat` where it exists, as on Linux, and otherwise runs `ps -o tpgid=,pgid=` for its own process id, as on macOS and the BSDs. A check that cannot tell counts as background, so the run skips the query rather than risk a stop. A stdin stream that is not a real terminal, such as a test's scripted one, is under no job control, so it skips the check.
- **The background mark.** `background: true` on one string global option, the application's or a plugin's, marks the option whose value carries the operator's background choice. Right after host capture, beside the color choice, core reads from argv the last occurrence of a marked spelling, before the first bare `--`, whose value, attached or the next word, is `dark` or `light`. The read is exact without a parse under [ADR-0055](0055-an-invocation-routes-on-global-options-then-parses-the-routed-commands-words-against-one-table.md)'s grammar, because an option word is never a separate value. The marked option takes no short alias, environment variable, configuration binding, default, implied value, or `multiple`, so argv is its one source. `COLORFGBG` stays the environment's standard input for the background with no application-named twin.
- **Where it is read.** `host.terminal.background` holds the settled background for actions, middleware, and hooks, and the view context's `background` holds it for every view, read before each render as `columns` is. Both read `undefined` when no source settled the background, until it settles, and in an invocation by name, so author code can tell an unknown background from a dark one. A host override that states `background` supplies a source; the field reads the settled value.
- **The background plugin.** `@loomcli/plugins/background` exports `background()`, which takes no settings and declares the global string option `background`, validated to `dark` or `light`, with `control: true` and the mark. A theme plugin declares no options, so the spelling lives in its own plugin. Its mark also turns detection on, so an application whose own code reads the background installs it.
- **The light palette.** `loomTheme()` makes its six colored tokens adaptive. The light side is dim `#5F6B7A`, highlight `#9C5A1E`, success `#4E6B50`, warning `#8A6D0E`, error `#C04532`, and info `#4A6B91`, each at least 4.5:1 on a cream background, with the 256-color fallbacks 243, 130, 65, 94, 131, and 60. The 16-color fallbacks keep the dark side's names, because a light terminal remaps its own sixteen colors. `primary` stays `style.resetForeground`. A whole-token override stays whole, so a plain override is one value on both backgrounds.

The contract and its acceptance are in [Background](../core.md#background), [Background plugin](../core.md#background-plugin), and [Loom theme](../core.md#loom-theme).

## Considered options

- **A `{ dark, light }` pair of whole mappings.** Rejected. It doubles the contribution ADR-0027 makes one, and a custom theme could not opt in one entry at a time.
- **An application environment variable for the operator's override.** Rejected. `COLORFGBG` is the environment's standard input for the background, and an argument read beside the color choice settles the first byte the run prints, as `--color` does.
- **The theme plugin declaring `--background`.** Rejected. A theme plugin declares no options, and an application that installs a theme may not want the option.
- **The background on core's internal capabilities.** Rejected. That record is internal and never reaches a view; the host and the view context are the surfaces an author reads.
- **A wait with no deadline.** Rejected. A pseudo-terminal with no emulator behind it would hold the run forever before any author code ran, a defect in what Loom ships.
- **Querying at the first themed byte.** Rejected. A view function is synchronous, so the answer must be known before the first render, and a run that prints before any themed byte would still need it for a later one.
- **`COLORFGBG` before the query.** Rejected. It is fixed when the shell starts, so it goes stale when the operator switches the terminal's theme, while the query reads the terminal as it is now.
- **A short alias, an implied value, or a default on the marked option.** Rejected. A short group needs the parse, an implied value would make a bare spelling ambiguous to a read without one, and the author's default is `rendering.background`.
- **Reading dark when no source knows the background.** Rejected. An action, a hook, or a view that branches on the background would take an unknown for dark, on a light terminal too. `undefined` says that nothing was detected, and an adaptive entry still takes its dark side.
- **Detecting only for an adaptive theme.** Rejected. Author code may read the background with a theme that does not adapt, and a run that skipped the query would hand it a guess. The background mark turns detection on, so an application that reads the background installs `background()`.
- **Settling again after environment preparation.** Rejected. The first themed byte can print before preparation ends, and a second settlement would change the background within the run. A color change during preparation leaves the background as settled.
- **Discarding replies when the DA1 reply never comes.** Rejected. An OSC 11 reply that arrived before the deadline is a real answer, and a terminal that answers OSC 11 without DA1 would otherwise never settle.

## Consequences

An Application whose installed theme holds no adaptive entry and that declares no background mark writes no query and reads no stdin byte, and its `host.terminal.background` and view contexts read `undefined` unless `rendering.background` or a host override states a background. One whose theme adapts or that declares the mark, run at a terminal, writes three short queries and waits for the replies before graph build, usually for a few milliseconds and never more than one second. A reply that arrives after the deadline is not read, so on a link slower than that it reaches the action's stdin or the shell after the run.

A takeover run such as `--help` prints themed text, so it settles the background as any other run does, and on a pseudo-terminal with no emulator behind it that run waits the full second before it prints. That is the backstop case, and the cost is accepted. A completion request a shell's completion script makes writes no query, because every shipped completion script captures its stdout and discards its stderr, so neither is a terminal. A request typed by hand at a terminal settles as any other run does, because settlement runs before routing.

`host.terminal.background` is the one terminal fact core settles rather than captures. `RunOptions.host` accepts a terminal override without it, so a test host written before this record still compiles and settles by the rules above.

This narrows ADR-0009's statement that `run()` consumes no stdin, for the one bounded read the query makes when stdin is a terminal, which returns every byte that is neither a reply nor an interrupt key; [ADR-0081](0081-content-inputs-prepare-lazy-handles-and-one-command-claims-stdin.md)'s stdin targets read nonterminal stdin, which the query never touches. It narrows ADR-0022's and ADR-0027's mapping of names to concrete styles, which may now hold adaptive styles, and ends ADR-0029's deferral of light colors and background detection. It narrows [ADR-0032](0032-environment-and-configuration-map-into-options-through-one-core-input-source-stage.md)'s binding rule for the marked option, which binds no variable and no configuration key. No clause of ADR-0055 or ADR-0089 changes. ADR-0009, ADR-0022, ADR-0027, ADR-0029, and ADR-0032 carry dated entries.

The glossary gains Background, Background choice, Background mark, and Adaptive style.

The read returned to a `data` listener and `resume()`, so `pause()` emits `pause` and the handle stops, and core then sets `readableFlowing` back to the state it found, which keeps a later bare `data` listener working. - 2026-10-20: The query now runs only when stdin, stdout, and stderr are all terminals, and the background reads `undefined` otherwise, whatever `COLORFGBG` names. With stdout piped, a program at the other end, such as fzf, which reads `/dev/tty`, raced core for the terminal's replies and for its mode, and `app | less` and `app > file` now settle the same way, so their adaptive tokens take the dark side.
