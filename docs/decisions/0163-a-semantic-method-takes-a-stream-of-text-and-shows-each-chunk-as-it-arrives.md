description: Each of the seven semantic methods takes an async iterable of text in place of its string message, so text such as a model's output shows as it arrives. A streamed message keeps the method's lane, destination, and verbosity, takes no view, and draws through the lane view; when it ends, what was written is what the method writes for the joined text. On a terminal that redraws, each chunk shows as it arrives: `print` writes what each chunk adds at the cursor, never redraws it, and holds every other write to the terminal until its line ends, and the lanes that wrap keep a permanent finished row that stands alone and an unfinished row redrawn as it grows above any live region, which counts for onLiveRegions. A hidden streamed message is read to its end, a throw keeps the text and rejects the call, open streamed messages are independent, and core runs no timer. At the process's end and a shutdown's end, the text an open streamed message has received is written with the rest of the queue. It widens ADR-0148's signature, narrows ADR-0008's and ADR-0027's string-only signatures, and extends ADR-0090's hidden call, ADR-0110's inert lanes, ADR-0156's span, and ADR-0157's queued writes.

# ADR-0163 - A semantic method takes a stream of text and shows each chunk as it arrives

## Context

[ADR-0148](0148-a-semantic-method-takes-a-view-for-its-message-and-ends-it-with-one-line-break.md) gives each semantic method the form `(message: string, view?: View<string>)`. The message is whole when the call is made, so an action whose text arrives over time, such as a model's answer streamed from a service, either waits for all of it or writes each piece through a call of its own, which ends every piece with a line break. `out.results` and `out.render` already take an async iterable of rows under [ADR-0023](0023-a-command-declares-its-result-and-core-resolves-its-presentation.md), but a row is a unit of a result and carries no message level.

On a terminal, core erases the live regions before every write to stderr, writes it, and draws them again below it, under [ADR-0091](0091-live-regions-stack-at-the-bottom-of-stderr-and-progress-reaches-invoke-callers-and-mcp-clients-as-typed-events.md). The default lane views give a message its glyph, wrap it on a terminal at the columns right of the gutter, and indent continuation rows under [ADR-0086](0086-renders-fit-the-destinations-live-columns-and-tables-shrink-to-fit.md). A text that arrives in chunks has to keep all three: the regions below it, the gutter on its first row, and the wrap of the rows after it.

The resolved text of a message keeps a style open across a line break: `out.print(style.bold('abc\ndef'))` writes `\u001b[1mabc\ndef\u001b[22m\n`. A lane view's wrap is not stable as text grows at one place: a space that ends the text so far can push the word before it to the next row, and the next word pulls it back, as `aaaa bbbbbbb ` and `aaaa bbbbbbb c` wrap differently at 12 columns.

The owner settled the shape in grooming (LM-389): every semantic method takes the stream, a plain iterable is refused, a stream takes no view, the joined text decides what is written, a terminal shows each chunk as it arrives, a pipe receives whole lines, a hidden stream is drained, a throw keeps the text and rejects the call, open streams are independent, a captured run follows the pipe's rule, and core runs no timer.

## Decision

- **The two forms.** `print`, `info`, `success`, `warn`, `error`, `debug`, and `trace` each take `(message: string, view?: View<string>)` or `(message: AsyncIterable<string>)`. Each method declares two signatures: the string form first, and then one over `MessageArguments`, an exported type that is the union of the two argument lists:

  ```ts
  /**
   * The arguments a semantic method takes: a message and an optional view over it, which replaces the
   * lane view for that call, or the message as an async iterable of its text, which takes no view and
   * draws through the lane view as each chunk arrives.
   *
   * @see https://github.com/dbtlr/loomcli/blob/main/docs/core/output.md#a-streamed-message
   * @public
   */
  export type MessageArguments =
    | [message: string, view?: View<string> | undefined]
    | [message: AsyncIterable<string>];

  export interface Out<Result = unknown> {
    /**
     * A message on stdout at every verbosity, or on stderr from the action of a Command that declares
     * a result. Each semantic method draws its message through its lane view, or through `view` when
     * the call passes one, which replaces the lane view for that call, and ends it with exactly one
     * line break. The message may instead be an async iterable of its text, which takes no view: core
     * shows each chunk through the lane view as it arrives, and the call resolves once the iterable
     * has ended and its text is written.
     *
     * @example
     * ```ts
     * import { Application } from '@loomcli/core';
     *
     * import { answer } from './model.js'; // yields the answer's text as the service sends it
     *
     * const app = new Application('ask')
     *   .argument('question', { required: true })
     *   .action(async ({ args, out, style }) => {
     *     async function* text(): AsyncGenerator<string> {
     *       for await (const chunk of answer(args.question)) {
     *         yield style.escape(chunk);
     *       }
     *     }
     *     await out.print(text());
     *   });
     * ```
     */
    print(message: string, view?: View<string>): Promise<void>;
    /** The stream form, or either form when the caller forwards `MessageArguments` whole. */
    print(...call: MessageArguments): Promise<void>;
    // info, success, warn, error, debug, and trace declare the same two signatures.
    // ...the other members, unchanged...
  }
  ```

  The string form comes first, so a generic answer passed straight to a method, such as `out.print(await text(context, settings))` from `@loomcli/prompts`, is inferred as a string, as it was before. The second signature takes either argument list, so a wrapper forwards `MessageArguments` whole, and a test's stated lane typed `(message: string)` stays assignable. The types refuse a view beside a stream, a plain `Iterable`, an array of strings, and a message typed as either form, which the caller narrows first. `MessageArguments` is an input type, `@public`, under [ADR-0137](0137-a-published-export-is-public-and-its-tag-says-whether-it-is-an-input-type-or-an-output-type.md). The `warn` an `onEnvironment` hook receives is `Pick<Out, 'warn'>`, so it takes both forms too. A chunk that is not a string gets no rule, under [ADR-0093](0093-a-value-that-bypasses-the-types-gets-no-rule.md) and [principle 7](../principles.md#7-guide-with-types-then-lint-then-diagnostics): a Node `Readable` iterates as `any` and yields `Buffer` chunks unless its encoding is set, so an author streams one after `setEncoding('utf8')`.
- **The governing rule.** A streamed message keeps the method's lane, its destination, `print` moving to stderr from the action of a Command that declares a result, and its verbosity. When the iterable ends, what was written is what the method writes for the joined text, the chunks joined in the order they arrived: its lane view's text and the one closing line break of ADR-0148. Each chunk is marked text, as a message is, so an author escapes raw text chunk by chunk with `style.escape` and keeps each style call inside one chunk.
- **The lane view.** A streamed message draws through its lane view, the application's override included, and never through a passed view. Core renders the text received so far through it as each chunk arrives and writes what follows what it has already written. It reads the view context once, at the message's first layout, so the whole message lays out at the columns read then. Before the end, the text laid out leaves out its trailing run of spaces, tabs, and carriage returns, with only frame closes after the run, which shows once text follows it or the iterable ends. It also leaves out a high surrogate that ends the text so far, the first half of a character such as an emoji, until the chunk with its second half arrives or the iterable ends, because half a character written alone reaches a terminal as a replacement character, which a `print` never redraws. With that run held back, every default lane view lays out the finished rows of a longer text as it laid out the start of it, so the governing rule holds for each of them. An override that changes its earlier rows as the text grows writes, row by row, the rows of the moment each was finished, and keeping them consistent is the override's, under [principle 1](../principles.md#1-loom-owns-what-it-ships-the-author-owns-what-they-write). For a lane view core ships, each chunk lays out the text after the last line the message has finished, and each finished line is laid out once more to count its rows. The message stops doing so for the rest of its text once a finished line holds a raw terminal control sequence, a lone carriage return or another control character the terminal reads as a command, a pad or no-wrap frame, a style that names a token the application's theme adds, any other header core does not accept, or a stray close; from then on each chunk lays out everything after the last line the message had finished before that, so the cost of laying out that text grows with its square. A lane view the application overrode gets the whole text received so far at every chunk. The bytes written are the same in every case.
- **On a terminal.** Where the message's destination is a terminal that redraws in place, not under `TERM=dumb` and not under CI, as ADR-0091 and [ADR-0114](0114-a-ci-run-is-not-interactive-draws-no-live-region-and-renders-as-the-standard-detectors-do.md) read redrawing, each chunk shows as it arrives, and at every moment the terminal shows what the method would write for the text received so far. The message shows nothing until its text holds more than a trailing blank run. No streamed message on any lane erases or redraws text at a position core computed from grapheme widths across a row the terminal wrapped.
- **`print` only appends.** A streamed `print` writes what each chunk adds at the cursor and never erases or redraws any of it. The `print` lane never wraps, so a paragraph of a model's answer is one line longer than the screen, and the terminal wraps it as it wraps a whole `print`. A resize between two chunks, and a grapheme such as a VS16 emoji or a ZWJ sequence that the terminal draws at another width than core counts, leave the screen as a whole `print` of the same text leaves it. Each line is resolved on its own, so a style or a hyperlink the text keeps open across a line break is closed at the line's end and opened again at the next line's start. Within a line, the control sequences after its last character, such as a style's close, wait for the next chunk's text or the line's end.
  - **The line holds the terminal.** While a streamed `print`'s line is unfinished on the terminal, every other write to that terminal waits for the line to end: a message on either stream when both are on that terminal, a render, an `out.draw`, a lend's start, and a live region's first frame and every frame after it are written at the next line break of the streamed text, or when the message ends or stops. It is the rule a pipe already has: another write lands between two lines and never inside one. While the line holds the terminal, a stdout write joins stderr's order on a terminal both streams share, so the writes held behind it keep the order they were issued in. Where stdout is a terminal and stderr is not, the line holds stdout alone, and a stderr write goes on in its own order. Two streamed `print` messages take the terminal in turn, each holding it until its line ends.
  - **A stop is never held.** A failure or a cancellation ends the streamed message first, under the stop rule below, and that end finishes its line, so a failure report is never held behind it. A streamed `print` a middleware or a configuration source issued is read on when the action fails, so its unfinished line holds a failure report until the line ends or a cancellation ends the message.
  - **An iterable that waits on the terminal.** An iterable that awaits another write to the same terminal while its `print` line is unfinished waits on itself, as a row sequence's source that writes to its own destination does under [ADR-0023](0023-a-command-declares-its-result-and-core-resolves-its-presentation.md); a stop still ends it. The author yields the line break before awaiting the write, or issues the write without awaiting it, which then lands after the line.
  - **Whole lines beside a redrawn screen.** While a live region is open, while another streamed message keeps an unfinished row, or while a row sequence holds the order of either stream on the terminal, a streamed `print` writes a whole line at a time, as off a terminal, and a line it has not started writing waits for its line break. It returns to chunk by chunk at the next chunk once none of those holds, and a line it has started at the cursor goes on growing there until it ends. So a `print` line never grows below a frame it would have to erase, and it holds no stderr write behind a row sequence.
- **The lanes that wrap.** `info`, `success`, `warn`, `error`, `debug`, and `trace` lay out their rows through the lane view, which breaks them at the columns the first layout read, and core redraws the last of them:
  - A row is finished once the method's text holds a row after it. A finished row is permanent: core writes it as it writes a finished message, above every unfinished row and every live region, and never draws it again.
  - Each row stands alone: a style or a hyperlink the text keeps open across a line break is closed at the row's end and opened again at the next row's start, so a write or a frame drawn between the two takes none of it, and the screen shows what the joined text shows.
  - The last row is the unfinished row. Core redraws it as it grows. It sits above every open live region, as a finished message does, and core erases it with the regions before every other write and draws it again below that write, so a message written meanwhile lands between the message's finished rows and its unfinished row. While an unfinished row is shown, a stdout write joins stderr's order on a terminal both streams share, as it does while a region is drawn, apart from a row sequence open on stdout.
  - A word that outgrows the unfinished row moves to the next row when it does, where the lane view's wrapping places it, and the row it left is finished.
  - When the iterable ends, the unfinished row is written as a finished row with the one closing line break, so the screen holds what the method writes for the joined text.
  - An open input region holds the regions' frames and not the unfinished row, which goes on growing above the stack. While the terminal is lent, core draws no unfinished row, as it draws no frame: a row the message finishes is written as it is, as every write through `out` is during a lend, the row drawn before the lend stays on the screen as drawn, and the unfinished row is drawn again above the stack the lend's end draws. A suspend erases the unfinished row with the regions, and the resume draws it again.
  - A finished row stays as it was written when the terminal is resized, as every finished message does. The message keeps the width its first layout read.
  - **A row wider than the screen.** A word longer than the row, or a terminal that narrowed after the message's first layout, makes an unfinished row wider than the screen, which the terminal wraps and no redraw can place. Core never draws or erases such a row. An unfinished row that would be wider than the screen, at the terminal's real width read at that chunk, is not drawn, and the row drawn before it leaves the screen. When a write would have to erase an unfinished row that has become wider than the screen, core leaves every unfinished row on the screen as the terminal shows it and erases only the regions below them, and moves the cursor below them when nothing is. Either way the message follows the line rule for the rest of its text: it draws no unfinished row again and writes each later row once it is finished, the row left on the screen included, so the text that row showed shows again in its finished row below it.
- **The live-region hook.** An unfinished row and a `print`'s unfinished line are not live regions: each shows at every verbosity at which its message is shown and builds no progress event. Each counts for the [ADR-0156](0156-onliveregions-tells-a-plugin-when-a-runs-live-regions-first-hold-a-frame-and-when-none-does.md) span, because a write core cannot see tears it as it tears a frame: `onLiveRegions` reports `'drawn'` at the write that puts a run's first live region frame, unfinished row, or unfinished `print` line on the screen, and `'closed'` at the write after which none is left. So with the [patch-console plugin](../plugins/patch-console.md) installed, a dependency's console write is routed through `out`: it lands above an unfinished row as it lands above a live region, and the message is neither welded to it nor drawn twice, and beside a streamed `print` it waits for the line's end.
- **Off a terminal.** Everywhere else, a pipe, a file, a terminal under `TERM=dumb` or CI, and a captured run, core writes each line of the method's text once it completes, as one write that holds the line and its line break, so another write can land between two of the message's lines and never inside one. A line completes at its `\n`, so a CRLF that two chunks split is one line break. The last line is written when the iterable ends, with the one closing line break, which a text that already ends with one does not gain. The writes, joined, are the bytes the method writes for the joined text: a style the text keeps open across a line break stays open from one write to the next, as it is in the joined text's bytes.
- **A captured run.** A [captured run](../glossary.md#output), an invocation by name, an MCP tool call, or a run on a `mockProcess` whose streams are its recording streams, as they are by default, follows the off-terminal rule, so `invoke`'s `output` and `messages` hold the joined text's plain text. A `mockProcess` whose `terminal` puts a stream on its terminal is a terminal to core, and a message there follows the terminal rule.
- **The order.** The call takes no place in its destination's order itself. Off a terminal each line takes its place when it completes, and on a terminal each chunk's write takes its place when it arrives, as a write issued at that moment does, so a write held behind a row sequence open on stdout waits as any stdout write does. Core reads the next chunk once the writes of the last one have completed. Every write the message makes follows the regions rule of ADR-0091.
- **A hidden streamed message.** One the run's verbosity hides calls no view and writes nothing. Core reads it to its end and discards its text. The call resolves when the iterable ends and rejects when it throws, at every verbosity.
- **A throw.** When the iterable throws partway, the text already received stays: on a terminal the rows shown stay, and off a terminal the line not yet written is written, and the message gets its one closing line break. The call then rejects with the thrown value through the [ordinary failure path](../core/failures.md#the-ordinary-failure-path), as a call whose view throws rejects. Loom writes no marker line.
- **Independent streamed messages.** Each open streamed message keeps its own text and its own unfinished row or line. On a terminal the unfinished rows sit together above the regions, in the order each first showed, and a row any of them finishes is written above all of them.
- **No timer.** Core reads the iterable and writes as chunks arrive. It never writes a partial line off a terminal on a timer, and it never limits how long the iterable may stay open; an application that needs a timeout sets one in its own iterable.
- **The call and the run.** The call resolves once the iterable has ended and every write it made has completed. A run waits for every streamed message it issued, awaited or not, as it waits for every queued write. A write that fails ends the message: core calls the iterator's `return` and the call rejects with the write's failure, which follows the destination row of the ordinary failure path.
- **A stop.** When the action fails while a streamed message it issued is still open, the action's failure stays primary, and when the run's signal aborts, every open streamed message stops; one issued after the abort stops at once. Either way core ends the message at that moment, as a throw does, its text received so far and its one closing line break queued ahead of any failure report, calls the iterator's `return`, and the call resolves once those writes complete. Core waits neither for `return` to settle nor for a chunk it has already asked for, which an async generator suspended at an await settles only when that await does, and a chunk that arrives after the stop is discarded. A streamed message a middleware or a configuration source issued is read on when the action fails, as a row sequence it issued is.
- **At the process's end.** At the process's `exit` event and at a shutdown's end, `SIGQUIT`'s included, the text an open streamed message has received and core has not yet written counts as queued under [ADR-0157](0157-core-writes-every-queued-write-at-the-processs-exit-and-a-shutdowns-end.md). Core writes it in the same step as every other queued write, at the place the message's last write took in the order, as the iterable's end would write it: the text received so far laid out whole, its unfinished row or last line, and the one closing line break. Core reads no further chunk, so text the iterable has not yielded is not written, as a row a source has not yielded is not. A hidden streamed message has nothing queued.
- **The testing builders.** In a context `@loomcli/testing` builds, an unstated semantic lane reads a streamed message to its end and writes nothing, and its promise resolves when the iterable ends and rejects when it throws, as a hidden call does, so an action's streamed message runs in its test as it runs at an operator's terminal.

The contract is in [A streamed message](../core/output.md#a-streamed-message), [Output](../core/output.md), [Verbosity](../core/verbosity.md), [Testing](../libs/testing.md), and the [glossary](../glossary.md#output).

## Considered options

- **A plain `Iterable` as well.** Rejected by the owner's ruling. A string is itself an iterable of strings, so the types could not tell a message from its characters, and a synchronous iterable has every chunk at hand, which one joined string already writes.
- **A view with a stream.** Rejected by the owner's ruling. A passed view owns the whole layout under ADR-0148, and a box or a heading draws rows that depend on the whole text, so no row of it could be final before the iterable ends.
- **A separate method, such as `out.stream(text, { level })`.** Rejected. It gives every level a second spelling, against [principle 5](../principles.md#5-one-system-per-concept) and ADR-0148's rejection of `out.message`.
- **Write each chunk as it arrives off a terminal.** Rejected by the owner's ruling. Another write could land inside a line, and a log reader would read a line torn in two.
- **Flush a partial line on a timer.** Rejected by the owner's ruling and [principle 1](../principles.md#1-loom-owns-what-it-ships-the-author-owns-what-they-write): core runs no timer, and how long an iterable pauses is the application's.
- **The unfinished row as a live region.** Not taken. A region hides under `-q`, CI, and `TERM=dumb` and holds still under an input region, while a streamed message is a message that shows wherever its level shows. It counts for the `onLiveRegions` span as a frame does, because a console write tears it as it tears a frame.
- **Close a style at each line's end off a terminal, and open it again at the next line's start.** Not taken. The writes would then differ from the joined text's bytes whenever a style crosses a line break, as the debug and trace lanes' fade does for a message of more than one line wherever the theme styles it, against the ruling that what was written is what the joined text writes. A write that lands between two lines of a colored pipe takes the open style on. On a terminal each row stands alone, because there the screen is the product and a row's open style would otherwise reach the frames and messages drawn below it.
- **Lay out the text so far as it is, its trailing spaces included.** Not taken. A trailing space that overflows the row moves the word before it down, the row above it is then finished, and the next word moves it back in the joined text, so the final screen would differ from the joined text's.
- **Lay out each chunk at the width read at that chunk.** Not taken. After a resize the text so far lays out into rows that no longer begin with the rows already written, so what follows them is undefined. One width for the whole message keeps the rule whole; the terminal reflows rows as it does for every finished message.
- **Redraw the whole unfinished row of a `print`.** Not taken. A `print` line is never wrapped by its lane, so an unfinished row can be longer than the screen is tall, which an erase cannot reach, and each chunk would rewrite the whole line.
- **Write a `print` line longer than the screen for good a screen row at a time, and redraw only its last screen row.** Not taken, by the owner's ruling on a review finding. Core placed the split with its own grapheme-width table, across a line the terminal wraps, so a resize between two chunks erased text already written, and a grapheme the terminal draws at another width than core counts duplicated or dropped characters. A whole `print` of the same text has neither problem, because the terminal wraps it, so a streamed `print` only appends.
- **Let another write land inside an unfinished `print` line.** Not taken, by the owner's ruling. Core would have to erase or move back over the line to put the write above it, which is the redraw the line gives up, and a write at the cursor would land inside the line, which the pipe's rule forbids.
- **Keep redrawing an unfinished row that became wider than the screen, counted at the new width.** Not taken. The terminal has wrapped it, so the count rests on core's widths across a wrapped row, and an erase that misses erases text already written. Leaving the row as drawn writes some of its text twice and erases none.
- **Wait for the iterator's `return` at a stop.** Not taken. An async generator suspended at an await settles `return` only once that await does, so a Ctrl-C during a stalled network read would hang until the shutdown budget ran out.
- **One signature over `MessageArguments` alone.** Not taken. It types a call's message from the union of the two forms, so a generic answer with a default type parameter, such as `out.print(await text(context, settings))`, is inferred as `string | AsyncIterable<string>` and stops compiling.
- **One generic signature whose view parameter is conditional on the message, or overloads of the two forms alone.** Not taken, though principle 5 prefers a conditional type. Neither accepts a test's stated lane typed `(message: string)`, such as `vi.fn(async (_message: string) => {})` in the [testing reference](../libs/testing.md), so every test written that way would stop compiling. The string form followed by a signature over `MessageArguments` keeps both that lane and a generic answer compiling.
- **A marker line when the iterable throws.** Rejected by the owner's ruling. The failure report already says what went wrong, and a marker would put Loom's voice inside the author's text.
- **Drop an open streamed message's unwritten text at the process's end.** Not taken. The terminal already shows the unfinished row, so a log of the same run would hold less than the screen did, and ADR-0157 writes everything the author handed core.

## Consequences

`Out`'s seven methods each gain a second signature over `MessageArguments`, a new `@public` export of `@loomcli/core`, and its API report changes for each method. A call that compiled before compiles and writes the same bytes, a generic answer passed straight to a method included. A test that states a lane with an annotated string parameter, as the testing reference shows, still compiles, and so does one that writes `(...call: MessageArguments)`. A stated lane whose parameter is typed from the context alone and used as a string, such as `warn: async (message) => { lines.push(message); }`, no longer compiles, because the context types the parameter as either form. The type checker reports every such site, and annotating the parameter, `(message: string)`, fixes it. `@loomcli/testing`'s unstated lanes read a streamed message to its end.

A message's call order on its destination no longer holds for a streamed message: its lines take their places as they complete, so a message issued after a streamed one can land before its later lines, which is the ruling's point. A failure report follows the text an action's open streamed message received, because the stop ends the message first.

ADR-0148's signature, a string message with an optional view, gains the stream form, and its line-break rule applies to the joined text. [ADR-0008](0008-rendered-output-is-a-neutral-call.md)'s and [ADR-0027](0027-core-resolves-marked-output-and-one-theme-contribution.md)'s string-only signatures gain the stream form, and ADR-0008's call order within a destination does not hold for it; the split between a message with a purpose and a value with a presentation holds, because a streamed message is a message's text, not a value. [ADR-0090](0090-an-operators-v-or-q-settles-the-runs-verbosity-right-after-graph-build.md)'s hidden call, which calls no view and resolves, is extended: a hidden streamed message is read to its end, and its call resolves at that end or rejects at a throw. [ADR-0110](0110-a-test-calls-one-author-function-with-a-context-the-testing-package-builds.md)'s unstated lanes, which resolve and do nothing, read a streamed message to its end first. ADR-0157's queued writes gain the text an open streamed message has received and not written. ADR-0156's span gains the unfinished rows and the unfinished `print` lines of a run beside its regions' frames. ADR-0008, ADR-0027, ADR-0090, ADR-0110, ADR-0148, ADR-0156, and ADR-0157 carry dated entries. ADR-0091 is unchanged: an unfinished row lands above the regions as every other write does and is not a region.

On a terminal, a streamed `print` holds every other write to that terminal while its line is unfinished, so an iterable that awaits a write to the same terminal before its line break waits on itself, as a row sequence whose source writes to its own destination does, and the author yields the line break first or does not await that write.

The glossary gains Streamed message, Unfinished row, Unfinished line, and Captured run, and its Semantic output entry names the stream form.

It widens ADR-0148's signature, narrows ADR-0008's and ADR-0027's string-only signatures, and extends ADR-0090's hidden call, ADR-0110's unstated lanes, and ADR-0157's queued writes, each of which carries a dated entry. The contract review found that a trailing space breaks the joined text's layout, that closing a style at each line's end off a terminal departs from the joined text's bytes, that a resize, a line longer than the screen, a stop, and a streamed `print` beside stderr writes were unstated, and that one signature over `MessageArguments` broke a generic answer passed to a method; the decision above states each.
- 2026-11-16: The owner ruled on 2026-11-16 on two review findings held for the owner, and the decision above now states the rulings. On a terminal a streamed `print` only appends: it writes what each chunk adds at the cursor and never erases or redraws it, which drops the split of a line longer than the screen and the style and hyperlink replay that served it, because core placed that split with its own grapheme widths, so a resize between chunks erased written text and a grapheme the terminal draws at another width duplicated or dropped characters. While a `print` line is unfinished, every other write to that terminal, a live region's first frame included, waits for the line to end, as on a pipe, and a stop still ends the message first. While a live region is open, while another streamed message keeps an unfinished row, or while a row sequence holds its destination's order, a streamed `print` writes whole lines, and it returns to chunk by chunk once none does. The lanes that wrap keep their unfinished row; one that is wider than the screen, from a long word or a terminal that narrowed, is never drawn or erased, the rows drawn are left as the terminal shows them, and the message writes each later row once it is finished. An unfinished row and a `print`'s unfinished line count for ADR-0156's `onLiveRegions` span, which carries a dated entry, so a routed console write lands above an unfinished row and waits for a `print` line's end. The rule that stdout's unfinished `print` row is redrawn around other stdout writes where stderr is not a terminal is gone with that row.
- 2026-11-16: The owner ruled on 2026-11-16 that the change ships with the limit the lane view bullet states: a message stops skipping the lines it has finished once one holds a raw escape sequence or one of the other conditions it names, and from then on lays out everything after the last line it had finished before that. Laying out no finished line again when it holds a raw escape sequence is separate work (LM-535).
- 2026-11-16: Amended from a review of the pull request (LM-389). A chunk that ends between the two halves of a character wrote each half alone on a terminal, so a streamed `print` showed two replacement characters for good. The text laid out now holds back a high surrogate that ends the text so far, as it holds back a trailing blank run. A message the run's verbosity hid keeps none of the text it drains.
- 2026-11-16: [ADR-0169](0169-one-plain-switch-turns-off-all-redrawing-so-progress-prints-plain-lines-and-a-question-asks-line-by-line.md), proposed, adds the run's plain switch to what keeps a terminal from redrawing in place. With the switch on, a streamed message on a terminal follows the off-terminal rule, as under `TERM=dumb`, so each line is written once it completes and no unfinished row is drawn. It binds when that record is accepted.
- 2026-11-19: An addendum for LM-535, the separate work the owner's ruling of 2026-11-16 named. The decision text above stays as accepted; this entry replaces the lane view bullet's cost clause, from "each finished line is laid out once more" to "grows with its square", and [A streamed message](../core/output.md#a-streamed-message) states the full rule. A finished line that holds a raw SGR or OSC 8 sequence, a lone carriage return or another terminal control, a pad or no-wrap frame, a style that names a token the application's theme adds, a header core rejects, or a stray close no longer stops the message from skipping the lines it has finished: the row laid out before the text after the split sets up the frames open there, the raw attributes set inside each, and the open hyperlink. Where the rendering policy keeps terminal controls, that row carries every raw SGR command Loom does not track, so a message that sets such a command on every line lays out text that grows with its square. A line break inside a frame header, a terminal control string, or a carried hyperlink is skipped as a split. Two conditions still stop splitting for the rest of the message: a frame header or a terminal control string that never ends, and a style that names a token the application's palette lacks, which line breaking and resolution read as text and the row split reads as a frame. The bytes written are unchanged.
- 2026-11-19: An addendum for LM-579. The decision text above stays as accepted; this entry extends the lane view bullet's sentence that leaves out a high surrogate ending the text so far to an escape sequence the text so far has not finished, and [A streamed message](../core/output.md#a-streamed-message) states the full rule. A chunk that ended inside an escape sequence, such as an OSC 8 link's close, wrote part of the sequence on a terminal. The `print` lane counted that part as text it had written, so it never wrote the text after it, and a terminal that receives part of a sequence reads the text after it as the sequence's own. The text laid out now also leaves out a lone ESC, a CSI without its final byte, or an OSC, DCS, SOS, PM, or APC string without its terminator that ends the text so far, with only frame closes after it, until the chunk that finishes it arrives or the iterable ends. Core finds it by decoding the text after the last line the message has finished from its frame markup, behind the row that sets up what that line leaves open, as line breaking and resolution read it, and scanning the decoded text with the scanner resolution uses. Frame markup between a sequence's bytes, as two chunks that each wrap part of it in a style call leave it, therefore does not part them: such a sequence is held back only while its bytes leave it unfinished, and a sequence after it on the same line is held back as any other is. The text laid out before the end never ends inside an escape sequence as resolution reads the text, for `print` and for the lanes that keep an unfinished row, except after a style that names a token the application's palette lacks, which the decoding reads as a frame and resolution reads as text. Off a terminal the bytes are unchanged. At the end, a streamed message on a terminal, on every lane, also writes the terminal controls after the text's last line break, counted outside every escape sequence, when no text follows them there, such as a title or a bell the rendering policy keeps, and the line break the method adds after them for the joined text. No row holds them, and the message dropped them before. It leaves out the SGR and OSC 8 commands among them, which each row opens and closes for itself.
