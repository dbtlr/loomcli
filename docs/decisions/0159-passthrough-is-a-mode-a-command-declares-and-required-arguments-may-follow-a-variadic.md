# ADR-0159 - Passthrough is a mode a Command declares, and required arguments may follow a variadic

## Context

Every Command has passthrough today. The first bare `--` ends routing and option parsing, and every later word reaches the action in `passthrough`, never an argument. Three things follow from that.

- **A hyphen word cannot fill an argument.** An option word is `--` followed by a character, or `-` followed by an ASCII letter, so `rm -draft.txt` reads `-draft.txt` as an unknown option. The usual fix, `rm -- -draft.txt`, puts the word in `passthrough`, which `rm` never reads, and the run reports the argument missing. The reference tells the operator to write `./-draft.txt`, which works for a path and for nothing else, such as a branch named `-wip` or a search term that starts with a hyphen. POSIX Utility Syntax Guideline 10 states the standard reading: the first `--` that is not an option's value ends the options, and every later word is an operand, even one that starts with `-`.
- **A tail is dropped in silence.** A Command that never reads `passthrough` still accepts a tail, so `textstat one.txt -- two.txt` counts `one.txt` alone. The `loom` bin refuses a tail on every Command by hand, through one helper that each action calls, because core accepts it.
- **A variadic argument is last.** A variadic argument takes every remaining word, so `copy <src...> <dest>` cannot be declared, and an author writes the destination as an option or splits the list in the action. The rule comes from the reference docs, where `argument()` rejects a variadic argument that is not last. [ADR-0034](0034-a-declaration-fault-throws-at-the-earliest-point-that-knows-it.md) lists that fault among those raised at the call, a moment [ADR-0093](0093-a-value-that-bypasses-the-types-gets-no-rule.md) carries forward, and [ADR-0136](0136-a-multiple-string-option-or-a-string-argument-may-be-required-only-when-input-is-not-interactive-and-a-question-may-link-an-argument.md) restates it. The rule that passthrough never satisfies a required argument comes from the reference docs too. No record decides either rule.

The owner settled the shape in grooming (LM-382): passthrough becomes a mode each Command declares, a Command without it reads the words after `--` as plain words, and required scalar arguments may follow a variadic one.

## Decision

- **The mode.** A Command turns passthrough on with the builder method `.passthrough({ description? })`. The call types `passthrough: string[]` onto the action context, as `.argument()` grows `args`. A Command calls it at most once, the types close it at `.action()`, and `description` is a core fact that help and the manifest print. Only a Command with an action declares the mode: a group that declares it is the [`@loomcli/core/command-without-action`](../core/diagnostics.md#loomclicorecommand-without-action) fault, at attach and, for the root, at build, as a group that declares `.stdin()` is. There is no application-wide or subtree switch, because nothing inherits along a path.
- **The first bare `--`.** In both modes, the first bare `--` ends routing and option parsing, and the delimiter itself is no word of the Command. A global option, the color, background, and verbosity choices, and every option spelling are read among the words before it alone, as today.
- **Mode off, the default.** Every word after the first bare `--` is a plain word for the routed Command. It fills the next unfilled argument, after the plain words before the `--`, and a later `--` is an ordinary word. A word with no argument left to fill is the ordinary unexpected-argument error, with exit 2. So `rm -- -draft.txt` fills `rm`'s argument with `-draft.txt`. The action context has no `passthrough` member, so an action that reads one fails to compile.
- **On a Command with children.** Routing ends at the first bare `--` in both modes, so a word after it never names a child. With the mode off, it fills no argument, because a Command with children takes none: `store -- cache` on a `store` group is the unexpected-argument error, a structural fault that ranks ahead of the group's missing subcommand.
- **Mode on.** Every word after the first bare `--` reaches the action in `passthrough`, with its order, values, and word boundaries intact. A later `--` is an ordinary passthrough word. No such word fills an argument, and core never parses, validates, or transforms one. This is the behavior every Command had before.
- **Arguments after a variadic.** Only `required: true` scalar arguments may follow a variadic argument. An optional argument, a second variadic argument, an argument that declares `required: 'non-interactive'`, and a content argument may not follow one. The variadic argument may itself be optional, as in `mv [src...] <dest>`.
- **How the words fill.** Without a variadic argument, the plain words fill the arguments left to right. With one, the plain words fill the arguments after the variadic from the end of the line first, then the arguments before it from the start, and the variadic takes the words between, in order. So with too few words, the arguments after the variadic fill first: `copy a`, with a required `src...` and a required `dest`, fills `dest` with `a` and reports `src` missing. A word after the first bare `--` joins this list only with the mode off.
- **The order rule.** [`@loomcli/core/optional-argument-last`](../core/diagnostics.md#loomclicoreoptional-argument-last) orders the arguments up to and including the variadic. The arguments after it fill from the end, so the variadic before them can always be left out, and its presence rule never blocks them: `mv [src...] <dest>` and a `required: 'non-interactive'` variadic before a required `dest` are both valid.
- **The build rule.** `@loomcli/core/argument-after-variadic` replaces `@loomcli/core/variadic-argument-last`, raised at the same moment, the `argument()` call. Its headline is `Argument after variadic not a required scalar`. Its explanation is `A variadic argument takes the plain words between the arguments before it and the arguments after it, so each argument after it fills from the end of the line with exactly one word. Only a required scalar argument always takes exactly one word: an optional argument, a second variadic, an argument required only when input is not interactive, or a content argument after a variadic would leave the parser unable to tell where the variadic's words end.` Its sentence names the argument and why it cannot follow, such as `Argument "dest" is optional and follows variadic argument "src" on Command "copy".`, with `is variadic`, `is required only when input is not interactive`, and `is a content argument` in place of `is optional` for the other three cases. Its correction is `Declare only required scalar arguments after a variadic argument.`
- **Projections.** `CommandNode` gains `passthrough: { description: string | undefined } | null`, and the manifest's Command entry gains `passthrough: { description: string | null } | null`, each `null` on a Command without the mode. Help's usage line ends with `[-- <args>...]`, and its ARGUMENTS block lists the mode's description, on a Command with the mode alone. A man page follows help. With the mode off, `locate` reads a word after the first bare `--` as an argument position, and with it on as the `passthrough` position. The completion plugin's hidden `__complete` Command declares `.passthrough()`, because it receives the typed words after `--`. The service plugin's check of its `run` words reads a word after a bare `--` as the parser does, so such a word fails the build when it fills no argument on a Command without the mode. The MCP plugin is unchanged, and passthrough is never exposed, under [ADR-0063](0063-the-mcp-plugin-serves-opted-in-commands-as-tools.md).
- **Invocation by name.** `invoke`'s `values.passthrough` reaches `passthrough` on a Command with the mode. On a Command without it, a non-empty `values.passthrough` is an `UnexpectedArgumentError` whose `extra` holds those words, with the sentence `Command "get" declares no passthrough. Remove passthrough from the values.`, and an empty one is no fault. The fault is structural and held, ranked after every other unknown name. A call by name therefore refuses where argv would fill the arguments with the same words.
- **The unknown option's correction.** On a routed Command that declares at least one argument and has the mode off, `UnknownOptionError`'s sentence ends `Supply a declared option, or pass it as an argument after "--".` in place of `Supply a declared option; prefix a hyphenated path with "./".`, as in `Unknown option "-draft.txt". Supply a declared option, or pass it as an argument after "--".` Every other Command keeps today's sentence. The sentence names the spelling and what to do instead, under [ADR-0047](0047-an-operator-message-says-what-went-wrong-and-what-to-do-instead.md).
- **What stays.** The validation context and the middleware `request` keep `passthrough: readonly string[]`, which is `[]` with the mode off. `host.argv` stays intact.

The contract is in [Passthrough](../core/options.md#passthrough), [Application declarations](../core/application.md), [Global consumption and routing](../core/commands.md#global-consumption-and-routing), [Invocation](../core/invocation.md), and [Locating a word](../core/graph-inspection.md#locating-a-word).

## Considered options

- **An application-wide or subtree switch.** Rejected. A Command's parsing would depend on where it is mounted, which is the inheritance [ADR-0003](0003-globals-are-application-owned-and-nothing-inherits.md) removed and [ADR-0026](0026-applications-declare-global-options-through-a-fluent-method.md) carries forward.
- **Passthrough on every Command, with `./` as the escape.** Rejected. The escape works for a path alone, the standard reading of `--` is POSIX's, and a tail a Command never reads is still dropped in silence.
- **With the mode on, fill the arguments first and pass the rest through.** Not chosen. Which words an argument takes would depend on how many arguments the Command declares, and a wrapper that forwards its tail to another program needs the whole tail.
- **Optional arguments after a variadic.** Rejected. With a variadic before them, a parser cannot tell how many words the variadic takes and how many the optional arguments take.

## Consequences

This is breaking. An action that reads `passthrough` adds `.passthrough()` to its Command, or it fails to compile. A tail on a Command without the mode now fills its arguments, or fails with the unexpected-argument error. `@loomcli/core/variadic-argument-last` is renamed, so code that matches a rule identity changes. `CommandNode` and the manifest gain a field, which a consumer that ignores unknown fields reads as before. Arguments after a variadic are a feature. The `loom` bin's own refusal of a tail goes, because core refuses those words.

ADR-0055's second layer, which reads the routed Command's words up to the first bare `--`, is narrowed: with the mode off, the words after it are the routed Command's plain words. ADR-0042's `passthrough` position is narrowed to a Command with the mode, and with the mode off a word after the first bare `--` reads as an argument position. ADR-0059's rule that `values` mirrors the action context, with `passthrough` as the tail after `--`, and its rule that a call by name behaves as the argv that spells it, are narrowed for a Command without the mode. ADR-0028's 2026-10-05 entry, under which an action reaches `passthrough` through its typed inputs, holds on a Command with the mode alone, while the request keeps `passthrough`. ADR-0110's `actionContext` throws for an unstated `passthrough` on a handler whose Command declares the mode, and has no such member otherwise. ADR-0136's sentence that a variadic argument is last, as every variadic argument is, is narrowed to the new rule. ADR-0028, ADR-0042, ADR-0055, ADR-0059, ADR-0110, and ADR-0136 carry dated entries.

Proposed. It moves to accepted in the release PR of the release that ships it.
