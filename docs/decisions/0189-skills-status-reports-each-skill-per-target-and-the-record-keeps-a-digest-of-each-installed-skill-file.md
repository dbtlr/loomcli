# ADR-0189 - Skills status reports each skill per target, and the record keeps a digest of each installed skill file

## Context

[ADR-0076](0076-the-skills-plugin-installs-an-applications-agent-skills-for-claude-and-the-shared-agents-folder.md) installs each skill as one folder, replaced whole. At global scope its record, one plugin's file per agent target in the installation record, lists each folder by its path alone, with no digest, and a recorded folder belongs to the plugin whatever someone changed inside it: local edits do not survive an update, and the skill always matches the binary. It rejected two things: protecting edits inside a recorded folder by digest, because a skill must match the binary and an edit protection would make a self-update's refresh fail after a local tweak, and a `status` Command, because `update` already brings every recorded target current and a report of drift had no caller.

[ADR-0188](0188-the-skills-plugin-generates-each-skills-command-references-from-the-graph-at-install.md) generates a command reference for each Command a skill selects, from the graph of the binary that installs it, at names the plugin owns under `references/commands/`: `index.md`, `<app>.md`, and each `<app>-*.md`, where every other file is the author's. An installed skill now goes stale whenever the graph changes, and `index.md` carries the Application's version, so it changes with every release. Generated content depends on the graph alone, so a run can regenerate what it would write and compare.

The contract is settled. Global installs move to the [installed-files module](0071-an-installation-record-per-application-says-how-it-was-installed-and-what-its-installers-wrote.md) with per-file SHA-256 digests, as completion and the man page use, through a record format bump that reads the old format once. `skills status` reports each declared skill per target in one of five states: missing, no folder; unmanaged, a folder with no record; modified, a generated file's digest differs from the record; stale, the record matches the disk but this binary writes different content; and current, both match. Project installs keep no record and report current, stale, or unmanaged by comparing the disk with regenerated content. The output follows `service status` under [ADR-0074](0074-the-service-plugin-supervises-one-user-unit-per-application-through-the-installation-record.md): one result row per skill and target through `out.results`, with a typed state, and exit 0 whenever it produced a report. `update` and `uninstall` keep a modified generated file as the man page and completion keep a changed one under [ADR-0078](0078-the-completion-plugin-installs-a-script-and-one-startup-line-per-shell.md) and [ADR-0079](0079-the-manpage-plugin-writes-a-roff-page-per-command-and-installs-the-set-in-the-home-folder.md): an install or update refuses a recorded file whose digest changed, and a removal leaves it in place and reports it. The module treats a recorded file that is gone as no change: an install writes it again, and a removal passes over it.

## Decision

- **The record holds every file's digest, and marks the command references.** A global install records each skill folder through the installed-files module with the relative path and SHA-256 digest of every file it wrote there, the author's files and the generated ones alike, because the folder's files are the module's unit and its recovery reads them. Each generated command reference, a file at a name the plugin owns under `references/commands/` in a skill that selects Commands, is marked `generated` in the record, so the record tells the two kinds apart even for a skill this version no longer declares. The digests of the marked files decide whether a skill is modified; every file's digest serves recovery, and the files this version writes decide whether it is stale.
- **Modified means a command reference changed.** A skill is modified when a recorded command reference is on disk in its folder as anything but a regular file holding its recorded digest. Nothing else makes a skill modified:
  - **An author's file.** An edit to `SKILL.md` or any other file the author supplies is not a modification. The skill reads stale, and `update` replaces the folder whole, as ADR-0076 holds: local edits to the author's files do not survive an update.
  - **A file that is gone.** A recorded file that is gone, a command reference included, is not a change, as the module holds for any recorded file. The skill reads stale, and the next install writes it again.
  - **An entry the record does not list.** A file or folder the record does not list, such as a `.DS_Store` or a `__pycache__` a shipped script left, never changes a skill's state and never refuses an install. An update still replaces the folder whole, so it does not survive one.
- **A modified skill is kept, as a changed file is.** A modified folder of a skill this version declares refuses `install` and `update`, which then write nothing to any target, as a changed page refuses `manpage install`, and each changed command reference is named. `uninstall`, and an install that no longer lists the folder, leave the whole folder in place, report it, and drop it from the record, as a removal leaves a changed page. `skills install --force`, whose description already reads `Replace skill files that something else wrote or that you changed.`, replaces a modified folder as it replaces one the record does not list. It replaces only the folders the install lists; a modified folder of a skill no longer declared is left in place under `--force` as without it. `update` keeps no `--force`. The steps offered for a modified skill name the way to keep the change first: copy the changed file elsewhere, then replace the folder.
- **A link at a recorded folder's path.** Whatever is at a folder's path is never read through, so a symbolic link or any other non-directory there holds none of the recorded files: such a skill is never modified and reads stale. `install` and `update` replace it, a link by removing the link alone, and `uninstall` and a removal remove it the same way. A link at a path the record does not list reads unmanaged and refuses an install unless `--force` replaces it, removing the link alone.
- **The folder stays the unit.** An install still writes a skill's folder whole beside the old one and swaps it in, and still removes a folder whole, so a new version may restructure its skill freely. Nothing is written or removed file by file.
- **The record format.** The installed-files module writes `format` 2 for a plugin's file that records an installed folder, whose folder entries each hold `files`, every file's relative path and digest, `generated: true` on a marked one, and keeps `format` 1 for every other plugin's file, so completion, the man page, the service unit, and MCP registrations are unchanged and an older binary still reads them.
- **The old format is read once, and its first rewrite rolls forward.** The module still reads a format-1 plugin's file, whose folders are recorded by their path alone. Such a folder is never modified: it is replaced or removed whole whatever it holds, as ADR-0076 promised when it was written. `install` and `update` always write a target whose plugin's file is format 1, or records any folder by its path alone, so the first of them after the upgrade writes the file in format 2 with the digests of what it wrote. A pending entry for a folder recorded by its path alone holds `prior: "path"`, and recovery records the intended files when every intended file is in the folder as a regular file with its digest, whatever else the folder holds, and otherwise keeps such a folder recorded by its path alone when something is at the path, so an interrupted first update leaves the skill recorded, and the next run replaces it, as [ADR-0071](0071-an-installation-record-per-application-says-how-it-was-installed-and-what-its-installers-wrote.md) rolls an interrupted operation forward. `uninstall` removes a format-1 file's folders whole and deletes the file. `status` reads either format and writes neither.
- **A `status` child.** `skills status`, `Report whether each skill is installed and up to date.`, joins `install`, `update`, and `uninstall`. It takes `--agent`, `--project`, and `--directory` with `-C`, as `install` does, with the same validation and the same `InputError` for `--directory` without `--project`, and no `--force`. It reads the record and the folders and writes nothing.
- **Five states at global scope, in precedence order.** A skill's state at a target is the first that applies: **missing**, nothing at the folder's path, recorded or not; **unmanaged**, something at the path the target's plugin's file does not record as a folder; **modified**, a recorded command reference changed, as above; **stale**, a file this version writes is absent from the folder, is not a regular file, or differs in content, or whether it is executable, its mode holding any execute bit, differs from what this version writes, or a file the record lists that this version no longer writes is still in the folder; **current**, otherwise. Whether a file is executable means any execute bit in its mode, compared with what this version writes, because git keeps only that bit and a checkout's umask sets the rest. A change to an author's file in the new binary makes a skill stale, as a change to its command references does: stale compares every file an install writes. A skill that is modified and stale reads modified, because `update` refuses it.
- **Project scope compares the disk alone.** A project folder has no record, so modified never applies. Its state is **missing** when nothing is at the path, **unmanaged** when something other than a directory is there, such as a symbolic link to a working copy, **stale** when a file this version writes is absent or differs as above, and **current** otherwise. The contract lists current, stale, and unmanaged for project installs; this record extends it with missing, because a repository that holds no copy must report something and the global state of that name fits it, and narrows unmanaged to a non-directory, because without a record no directory can be told from an earlier version's install, and `install --project` replaces either, so every directory reads stale or current by its content. `--project` finds the root as `install --project` does, falling back to the start directory, and a project folder that is the global folder fails as it fails an install.
- **What status reads.** Status runs the checks, reads the skills folder, calls each loader, judges the files, and generates the command references, exactly as `install` does, because stale and current need what this version writes. A loader that throws or rejects, and a fault in a skill's files, fail status through the ordinary failure path with no report, as they fail an install: they are the author's to fix, and a status that reported around them would hide the defect.
- **One row per skill and target.** Status sends its rows through `out.results` under a `rows` declaration of `SkillStatus`, with the views `text`, its default, and `json: json()`, so an installed formatter adds `jsonl`. A row holds `skill`, `target`, `scope`, the typed `state`, the absolute `folder`, `files`, the relative paths that differ, and `notes`, the sentences that say what to do next, none for a current skill, as `service status` carries its `notes`. Rows follow the targets in `claude`, `agents` order and each target's skills in install order. The text view prints a block per row in the shape of `service status`: `<skill> for <target>: <state>`, then the `folder`, each changed command reference of a modified skill, and each note. A note never sends the operator to a Command that refuses: a note whose step `install` or `update` would refuse adds `once no skill reads modified or unmanaged`, and each note names its own row's target with `--agent`, and `--project` for a project row, so its step never acts on the other target.
- **A skill the binary no longer declares.** A row reports each declared skill, as the contract states, so a folder the record lists for a skill this version no longer declares gets no row. Status names each such folder that is on disk in an `out.info` line after the rows: one whose command references are unchanged says `update` removes it, under the same clause, and a modified one says `update` leaves it in place and names the manual step, copying what to keep and removing the folder.
- **Exit 0 whenever it reported.** Every state, at either scope, exits 0. The checks before loading, a record that cannot be read, a project folder that is the global folder, the option errors, a loader's failure, a fault in a skill's files, and a cancelled run fail it.
- **Lines and events.** Status writes the left-out `-vv` line ADR-0188 gives `install` and `update`, because it computes the same file set, and no other line. It records no change event, because it changes nothing; the other children's events are unchanged, and a format-1 file they rewrite records `File written.` as any write does.
- **The refresh is unchanged.** `refreshSkills` still runs the new binary's `skills update`. While a command reference is modified, that update refuses, so the child exits 1, its warning lines and failure sentence reach `host.stderr`, the refresh adds its `warn` event, and the self-update still succeeds, as it does for any child that fails.

The contract and its acceptance are in [Skills](../plugins/skills.md) and [Installation record](../core/installation-record.md#installed-files).

## Considered options

- **Every installed file decides modified.** Rejected. A refusal writes nothing to any target, and `index.md` changes with every release, so one edit to an installed `SKILL.md` would leave every skill at every target unrefreshed after every release, the cost ADR-0076 named in full. The contract's modified state concerns a generated file, and an author's file stays the binary's, replaced by each update.
- **Digests of the command references alone in the record.** Rejected. The module records a folder's files, and recovery reads them to tell a finished swap from an unfinished one; a record that left the author's files out would lose that. Marking the command references keeps one record and says which digests decide modified.
- **Telling the command references apart by their names at read time.** Rejected. A skill that selects no Commands owns no name, so an author's file named `references/commands/index.md` there is the author's; for a skill this version no longer declares, only the record still knows which kind each file was.
- **Counting an entry the record does not list as a change.** Rejected. A `.DS_Store` a file browser writes, or a `__pycache__` a shipped script leaves, would make a skill modified and block every update at every target, for a file nobody edited.
- **A gone command reference as a change.** Rejected. The module rewrites a gone recorded file and passes over it on removal, and a deleted reference holds no edit to keep.
- **Installing file by file through the module's writer of files.** Rejected again, for ADR-0076's reasons: it cannot replace a folder whose shape changed, it would leave an edited file beside a new version's files, and an agent reads a skill as one folder.
- **An uninstall that removes the unchanged files and keeps only the changed ones,** as the man page keeps a single changed page. Rejected. A skill folder kept in part is still a skill an agent loads when `SKILL.md` stays, now missing the references it names, and is debris when `SKILL.md` goes. Keeping the folder whole keeps the operator's edited skill working and leaves one unmanaged folder that status names.
- **An update that skips a modified skill and updates the rest.** Rejected. The man page and completion refuse the whole install for one changed file, and one rule for a changed digest across the installers is the point of the move.
- **Bumping every plugin's file to format 2.** Rejected. Only installed folders change shape, and a bump for every installer would make an older binary refuse its completion, man page, service, and MCP records for a change that is not theirs.
- **Recording the old format's folders with the digests on disk, without replacing them.** Rejected. The format-1 record promised that an update replaces the folder whatever it holds, and a folder edited under that promise would otherwise become a protected baseline that never matched any binary.
- **A pending entry with `prior: null` for a folder recorded by its path alone.** Rejected. Recovery drops an entry with no prior record when the swap did not finish, so an interrupted first update would turn the skill unmanaged and refuse it, where ADR-0071 rolls an interrupted operation forward.
- **Stale and unmanaged at project scope told apart by a marker,** such as the generated `index.md` frontmatter naming the application. Rejected. A skill that selects no Commands has no `index.md`, so every earlier version of it would read unmanaged; the frontmatter records the version an agent reads, not who wrote the folder.
- **A sixth state for a recorded skill the binary no longer declares.** Rejected. The contract sets five states for each declared skill; an info line serves the case without a row an agent must learn.
- **A status that reports around a loader that fails, or that never calls the loaders.** Rejected. Stale and current need what this version writes, and a defect in the author's loader belongs on the ordinary failure path.
- **A status that recovers a pending record or rewrites the old format.** Rejected. A report that writes would change what it reports and could fail where reading cannot; status reads a pending file as recovery would resolve it and leaves the write to the next install.
- **A `--force` on `update`.** Rejected. An update runs unattended after a self-update, and discarding an operator's edits stays a choice made on the command line through `install --force`.
- **A `-vv` line for each record file read.** Rejected. The rows already say what status found, and ADR-0165 gives the skills Commands no line of their own beyond the left-out line ADR-0188 adds.

## Consequences

An operator's edit to an installed command reference now survives every update until they choose `install --force`, and status names the changed files; an edit to an author's file is still replaced by the next update, which status reports as stale beforehand. A self-update's refresh fails, harmlessly, only while a command reference is modified, and the child's failure sentence names the fix. The installed-files module gains a second format, written only for a plugin's file that records a folder, a `generated` mark on a folder's file, and a recovery that reads a folder's files and keeps a folder recorded by its path alone. A binary older than this record refuses a format-2 plugin's file with the sentence it already has, `<record> cannot be read, so notes will not change the folders it lists. Remove it and the folders it lists, then run notes skills install again.`, so an operator who moves back to one removes the file and the folders it lists. The first `install` or `update` after the upgrade rewrites each target and prints its install or update line even when no folder changed. The skills plugin gains a fourth child and a result row type, `SkillStatus` and `SkillState`. ADR-0188's consequence that a status report tells generated files from the author's holds: the install tells them apart by their names, and the record keeps the mark. ADR-0071, ADR-0076, ADR-0165, and ADR-0188 carry dated entries.

## Changelog

- 2026-11-18: Proposed for skills status and per-file digests (LM-558). It supersedes three rules of ADR-0076: that a global install records each folder by its path with no digest, its rejection of protecting edits inside a recorded folder by digest, for the generated command references alone, and its rejection of a `status` Command. It narrows a fourth, that a recorded folder belongs to the plugin with edits included, which stands for the author's files and no longer holds for a folder whose command references changed. It narrows ADR-0071's installed folders, which gain per-file digests, a `generated` mark, a second record format, and the changed-file rule ADR-0076 had lifted for them, triggered by a marked file, and gives the skills Commands a fourth child under ADR-0165.
