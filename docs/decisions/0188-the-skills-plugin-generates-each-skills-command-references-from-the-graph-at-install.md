# ADR-0188 - The skills plugin generates each skill's command references from the graph at install

## Context

An agent skill that teaches the application's Commands needs a reference for each one: how to invoke it, what it accepts, what it returns, and what can fail. Mimir writes that reference by hand, and a hand-written copy drifts from the binary the moment a Command changes. [ADR-0076](0076-the-skills-plugin-installs-an-applications-agent-skills-for-claude-and-the-shared-agents-folder.md) installs a skill as the author supplies it, through a loader, and [ADR-0133](0133-the-skills-plugin-reads-a-skills-folder-that-loom-build-carries-into-the-artifact.md) adds the skills folder, whose consequences name generated command references as the next extension. The graph already holds every fact a reference needs, and help, the man page, and the manifest each project it at run time.

The owner settled the direction: the plugin generates each skill's references at install from the running binary's graph, as help and the manifest project it at run time, with no committed source to keep in sync, no source receipt, and no drift gate at build. An application declares several skills, each selects its own Commands, and each keeps the author's own files, `SKILL.md`, references, scripts, and assets, beside the generated ones, where the workflow prose lives.

The owner then settled four forks. A skill selects Commands by path arrays. A `skillCommand` extension on the `command` target, in a new declarations-only module, carries guidance as Markdown. Generated files live under `references/commands/` in each installed skill, one per selected Command named as the [man page plugin](0079-the-manpage-plugin-writes-a-roff-page-per-command-and-installs-the-set-in-the-home-folder.md) names its pages, plus an `index.md` that carries the binary's version; each file shows arguments and options in their long spellings, with no alias; hidden Commands are skipped and deprecated ones marked. A later status report compares regenerated content with what is on disk, so generation must be deterministic.

Three later pieces read what this record defines: a status report that tells generated files from the author's and regenerates content to compare, an export command in the `loom` bin and a test assertion that each produce exactly what an install writes from an Application without running the install, and a `loom docs` command that renders the same per-Command file for the whole application without skill guidance. Core keeps a plugin's settings private, and the graph carries only plain data, so a loader or a folder setting cannot reach a tool through the graph. [ADR-0060](0060-ongraphbuilt-judges-the-built-graph-and-never-contributes.md) lets an `onGraphBuilt` hook judge the graph and says it stores nothing. [ADR-0168](0168-a-command-or-an-option-may-declare-a-visible-alias-that-every-listing-shows-beside-its-canonical-name.md) has every listing show a visible alias beside its member's canonical name.

## Decision

- **A skill selects Commands by path.** A `Skill` entry gains `commands`, a list of paths, such as `[['note'], ['cache', 'clear']]`. A path is the canonical names of the Commands from the root down, never an alias, and it selects that Command and every Command under it; the path `[]` selects the root and so the whole application. Paths may overlap, and a Command two paths select is selected once.
- **A skills-folder skill selects through a list entry without `files`.** `SkillsSettings` keeps its shape, and `skills()` also takes `FolderSkillsSettings`, whose `folder` is required. Settings that name a `folder` take, in `skills`, either a `Skill`, whose `files` stays required, or a `FolderSkillCommands` entry, `{ name, commands }` with no `files`, which names the folder's skill of that name and adds the Commands it selects, so `skills({ folder, skills: [{ name: 'notes', commands: [['note']] }] })` selects for the folder's `notes`. Settings without a `folder` take only `Skill` entries, so an entry without `files` and no folder is a compile error, and a value that bypasses the types gets no rule under [ADR-0093](0093-a-value-that-bypasses-the-types-gets-no-rule.md). An entry that names a skill the folder does not hold is a folder fault when the folder is read, at install, in `skillFolders`, and at `loom build`. A `Skill` that holds a folder skill's name stays a fault. A `FolderSkillCommands` entry changes nothing about which skills install or their order.
- **No Commands selected, nothing generated.** A skill that leaves out `commands`, or gives the empty list, generates nothing and installs exactly the files it supplies, as before. A non-empty list whose every Command is hidden, or under a hidden Command, generates nothing either, `index.md` included.
- **Judged at build.** The plugin's `onGraphBuilt` hook judges the Commands every skill selects on every build, so `inspect()` throws and a run reports the fault, as the ruling asks. A path whose names do not lead to a Command is `@loomcli/plugins/skills/commands`. Two selected Commands that give one file name, as `config-set` beside `config set` does, or a root whose file would be `index.md`, is `@loomcli/plugins/skills/reference-name-taken`. A path that leads to a hidden Command, or into one, is not a fault: it selects nothing an operator can find, so it gives no file.
- **Which Commands get a file.** A selected Command gets a file when it is neither hidden nor under a hidden Command, the man page's page set rule. The files follow graph order: the root first, then each Command's children depth first in authoring order.
- **Guidance.** `skillCommand({ guidance })` from `@loomcli/plugins/skills/extension` is an ordinary extension on the `command` target with the identity `@loomcli/plugins/skills/command`. Its value is Markdown under the pack's Markdown rule, and the module holds declarations alone, as the MCP and manifest extension modules do. `skills()` lists the descriptor. The guidance appears in the Command's file in every skill that selects the Command.
- **The plugin owns the generated names.** In a skill whose `commands` is not empty, the plugin owns three names directly under `references/commands/`: `index.md`, `<app>.md`, and every `<app>-*.md`, where `<app>` is the application name. An author's file at one of those names, from the folder or a loader, is left out of the install, and the run says so at `-vv`, so a file an export wrote for a Command since removed never survives. Every other author file under `references/commands/`, such as `overview.md`, installs unchanged, like any author file, and the plugin changes none of the author's files. A skill whose `commands` is left out or empty owns no name.
- **Names.** A Command's file is the application name, then each name on its path, joined with `-`, and `.md`: `notes.md` for the root and `notes-note-list.md`, under ADR-0079's naming.
- **One rendering of a Command's facts.** A file holds, in order: an `#` heading of the application name and the path; the Command's visible aliases as help's masthead shows them, `Alias: ls`; `Needs a terminal: stdin and stderr, outside CI.` for a Command that needs one, the line help's masthead shows under [ADR-0181](0181-a-command-may-declare-that-it-needs-a-terminal-and-runs-only-at-one.md); `Deprecated: <message>` for a deprecated Command; the description; a Usage block holding each usage form help prints; the arguments as help's ARGUMENTS rows; help's INPUT lines for a standalone stdin declaration; the visible local options as help's OPTIONS rows, followed by help's option-group sentences; the result's kind and views, the default marked; the `skillCommand` guidance; then the `manifestCommand` details, examples, and failures. An option's label is help's left cell without its short spelling, and its text is help's right cell without the alias fact, so no option alias appears anywhere. A part with nothing to show is left out with its heading. Defaults, environment variables, configuration keys, required marks, accepted values, and deprecated options read exactly as help states them, because they come from help's cells.
- **An option with no long spelling.** A `shortOnly` option keeps its short spelling as its label. The ruling names long spellings because an option has one; an option without one would otherwise have no label, so this is the reading the ruling needs, not a rule beside it.
- **A Command's visible aliases are shown.** The owner's ruling against aliases concerns arguments and options. A Command's visible alias is a listing fact under ADR-0168, so its file shows it under the heading and its index entry shows it as help's Command rows do, `(alias: ls)`. An alias that is not visible appears nowhere. An option's visible alias appears nowhere either: the ruling keeps every option to its one long spelling, so the command reference is the one listing that leaves out the alias fact [ADR-0168](0168-a-command-or-an-option-may-declare-a-visible-alias-that-every-listing-shows-beside-its-canonical-name.md) puts in help's option blocks and the man page's OPTIONS entries. This narrows ADR-0168 for options in a command reference alone.
- **Global options in the index, once.** A skill that selects a subtree gets no root file, so `index.md` lists the visible global options after its Command entries, with the cells the option entries use, and no Command's file lists them. An application with no visible global gets no such section.
- **CommonMark, escaped where Loom shows text.** The file is CommonMark. Text Loom shows, a description, a right cell, a note, or a failure's meaning, is one line, escaped so it renders as written: a backslash before each `\`, `` ` ``, `*`, `[`, and `<`, before an `_` without an ASCII letter or digit on both sides, and before an `&` that an ASCII letter or `#` follows, and at the start of a paragraph before a leading `#`, `>`, `-`, or `+`, before a leading run of three or more `~`, and before the `.` or `)` after leading digits. A label, a view name, a failure code, and an example's command line are code spans, delimited by CommonMark's rule, and the usage forms sit in a fenced `text` block. Guidance and details are Markdown the author wrote, inserted as written, with line breaks normalized to LF and the blank lines at their start and end removed. The page states the bytes exactly, because a golden fixture pins them.
- **The index.** `index.md` opens with YAML frontmatter holding `application` and `version`, each as `JSON.stringify` writes it, then a `# <name> commands` heading, one list item per file, a link to the file whose text is the path, with the description and the alias, needs a terminal, and deprecated facts, and then the global options.
- **Deterministic.** A file depends on the graph alone: its name, its version, its nodes, and their extension values. It reads no clock, host, or environment, so a build, a run of the same graph on any host, and a tool that inspects the application in its own process write the same bytes. The version is `graph.version`, the Application's declared version, which does not depend on the release version a build bakes, so a test and an export agree with an installed binary.
- **Install writes one file set.** For a selecting skill, `install`, `update`, and a project install write the author's files and the generated files as one folder, under the rules ADR-0076 sets, each generated file with mode 644, generated from the graph of the run that installs, after the author's files are judged. Unchanged compares the whole set, so a binary whose graph changed updates the skill and one whose graph did not leaves it unchanged. `uninstall` removes the folder whole, and a self-update's refresh regenerates through the new binary. `loom build` carries the author's folder alone; nothing generated is carried or committed.
- **Two public functions.** `commandReferences(graph, { commands, guidance })` from `@loomcli/plugins/skills` renders the files the given paths select, the index first, without the folder prefix, and with or without guidance, and it judges the paths with the build's two rules; `commands: []`, or paths that select only hidden Commands, gives `[]`. `skillFolders(graph, { moduleDirectory })` returns each declared skill, in install order, with every file an install writes for it, reading the folder and calling the loaders as an install does, resolving a relative folder against `moduleDirectory` as `loom build` does. A tool that writes or checks a skill outside an install calls the second, and a tool that documents the application's Commands calls the first with `[[]]` and no guidance. So the folder is read and the loaders are called outside a skills Command too, whenever a tool calls `skillFolders`.
- **`skillFolders` finds the declaration through a shared weak map.** The plugin's `onGraphBuilt` hook, which already judges the selected Commands, records, for each graph it receives, an entry `{ format: 1, read }`, where `read` is the reader of the `skills()` call that built it, in a `WeakMap` keyed by the graph object, so the graphs a test builds are collected. A change to the entry's shape raises its format, and a copy that finds a format it does not know fails under `@loomcli/plugins/skills/folder`, as a carried folder of an unknown format does. The map lives on the global object under `Symbol.for('@loomcli/plugins/skills/graphs')`, as the registry `loom build` reads lives under its own symbol, so a second copy of `@loomcli/plugins` in the process, such as a nested dependency of a test library or the `loom` bin's own copy, finds what the application's copy recorded, and calls that copy's reader, so the copy that would install the skills reads and generates them. `skillFolders` returns `undefined` exactly when the graph's application installed no skills plugin, the graph did not come from a build, or the application's copy of the package is older than the record and so recorded nothing. This narrows ADR-0060: a plugin's `onGraphBuilt` hook may record the graph object against that plugin's own declaration, outside the graph, adding nothing to it.

The contract and its acceptance are in [Skills](../plugins/skills.md).

## Considered options

- **Command values in place of paths.** Rejected by the owner: core maps no Command value to a graph node, and `extend()` returns a new value, so the value an author holds may not be the one attached. Paths also carry over to the ports in other languages.
- **A per-Command opt-in.** Rejected by the owner: a Command would have to know every skill that documents it, where the Commands a skill selects belong to the skill.
- **Guidance keyed per skill.** Rejected by the owner until someone needs it: one guidance per Command serves every skill that selects it.
- **A committed copy kept in sync, a source receipt, or a drift gate at build.** Rejected by the owner: generation at install from the running binary's graph cannot drift, as help and the manifest cannot.
- **A folder skill's paths in its `SKILL.md` frontmatter.** Rejected. The folder is read only when a skills Command, `skillFolders`, or `loom build` reads it, so a bad path could not fail the graph build, and the plugin would read a file it otherwise never interprets.
- **A `commands` record on the settings, keyed by skill name.** Rejected. A listed skill would then declare its paths in a second place apart from its entry, two lanes for one concept.
- **An optional `Skill.files` with a call-time fault for an entry without it and no folder.** Rejected. A union of the settings makes the mistake a compile error, types before diagnostics under principle 7, and keeps `files` required for code that reads a `Skill`.
- **The plugin owning all of `references/commands/`.** Rejected. It would drop an author's hand-written reference, such as an overview beside the generated files, without telling the author. A fault for an author's file under the folder was rejected too: a skill folder that holds an exported copy of its own references, committed so that a repository's readers have the whole skill, would then break the next install. Replacing only the files the current graph generates was rejected as well: a file an export wrote for a Command since removed would survive every install, so the installed folder would no longer match the binary.
- **The author's file winning at a generated name.** Rejected. The installed reference would then describe the surface the author last exported, not the binary's.
- **No alias at all, a Command's included.** Rejected. ADR-0168 has every listing show a visible alias, and the owner's ruling concerns arguments and options; a reference that hid `ls` would teach an agent less than help does.
- **Global options on the root's file alone, as on the man page.** Rejected. A skill that selects a subtree has no root file, so its agent would never learn the globals.
- **Finding a skill's declaration through the registry `loom build` reads.** Rejected. The registry holds every `skills()` call the process made, so a test run that loads several applications could not tell which call built the Application it checks.
- **A fact on the root that holds a key into the registry.** Rejected. The graph describes the built product, as ADR-0133 holds when it rejects the folder as a graph fact, and a key is not a fact about it.
- **A map in each copy's own module.** Rejected. A test library or the `loom` bin that resolves another copy of `@loomcli/plugins` would find nothing the application's copy recorded.
- **A tool that takes the `Plugin` value, or a hidden Command that writes the files.** Rejected. The `loom` bin finds the module's one exported Application and nothing else, and the owner ruled that writing a skill's files into a repository is an author tool, never a hidden Command.
- **No escaping, or every ASCII punctuation character escaped.** Rejected. Unescaped, a description such as `Read <path> from disk` loses `<path>` wherever Markdown renders; escaping everything makes the raw file, which an agent reads, hard to read. Escaping what CommonMark would read as markup keeps both.
- **A fact format of the reference's own.** Rejected. Help and the man page already state an input's facts through help's cells, and a second rendering would let the three disagree.
- **The version from the release facts.** Rejected. The baked release version belongs to a build, while the Application's declared version is the same in a test, an export, and the installed binary.
- **A child listing in each group's file.** Rejected. The index lists every selected Command, so the listing would repeat it.

## Consequences

A skill's installed folder now holds files the plugin generates beside the author's, so a later status report tells them apart by path and name: in a skill that selects Commands, `index.md`, `<app>.md`, and each `<app>-*.md` directly under `references/commands/` are generated, and every other file is the author's. `skills()` takes `SkillsSettings` or the new `FolderSkillsSettings`, so an entry that names a folder skill compiles only beside a folder, `Skill` keeps `files` required, and code that extends `SkillsSettings` still compiles. The folder is read and the loaders are called whenever a tool calls `skillFolders`, not only when a skills Command runs. The registry `loom build` reads keeps its format, because its entry's shape is unchanged; its read judges `FolderSkillCommands` entries as an install does. Every build of an application that installs the plugin runs its `onGraphBuilt` hook, which makes the graph frozen on every run, the cost [Lifecycle hooks](../core/lifecycle-hooks.md#judging-the-built-graph) states. The guidance module adds one subpath export, `@loomcli/plugins/skills/extension`. The skills Commands gain one `-vv` line, for an author's file left out. ADR-0060, ADR-0076, ADR-0133, ADR-0165, and ADR-0168 carry dated entries.

## Status

Proposed. It moves to accepted in the release PR of the release that ships it.
