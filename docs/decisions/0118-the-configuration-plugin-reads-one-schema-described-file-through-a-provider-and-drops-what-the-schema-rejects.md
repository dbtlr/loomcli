# ADR-0118 - The configuration plugin reads one schema-described file through a provider and drops what the schema rejects

## Context

The configuration plugin answers one tier of option values, under [ADR-0032](0032-environment-and-configuration-map-into-options-through-one-core-input-source-stage.md) and [ADR-0054](0054-the-configuration-plugin-reads-one-file-per-run-found-by-the-authors-file-pattern.md). Options take only strings, string lists, Booleans, and counts, so structured configuration had no lane. Heimdall's three applications read four configuration sections, `sessions`, `updates`, `delivery`, and `conditions`, by re-implementing the plugin's lookup, finding `--config` through `'config' in options`, validating two sections with zod, and failing through a hand-written `log.fatal`. A table of transcript sources, `[[sessions.sources]]`, cannot be an option.

[ADR-0108](0108-an-action-receives-provided-values-from-the-providers-its-command-opts-in-to.md) gave application code a typed value through a provider a Command opts in to, and named "the configuration plugin's structured values" as its first consumer. A plugin's value is opaque and frozen, and no plugin installs a provider.

The owner's rulings on LM-269 set the shape:

- **One schema.** "Multiple schemas is absurdly difficult for an author to reason about. There are better ways to do this with one schema and not 'Fail' the whole schema, but rather ignore invalid fields."
- **No required fields.** "Does it even remotely make sense for a CLI app to have 'required' fields? how would it ever get created if the app keeps failing?"
- **Configuration stands alone, and a link prefills an option.** "At most, config is like prompts are for options. Config may standalone, it might also prefill an option that could be set. This is a rule of specificity. default -> config -> env -> option."
- **Forgiving and quiet.** "Config files don't generally report on that level, they just ignore unknowns. We need to be forgiving where it makes sense, otherwise the tool will be unnecessarily noisy." A dropped value is named at `-v`, because "someone might be trying to figure out why the value in their config file is being ignored."
- **The schema is required.** "The schema allows for easy typing. Someone who wants to keep it loose can just make the types loose."
- **No provenance for the action.** "The action doesn't need to know this."

## Decision

- **`configuration()` replaces `config()`.** `configuration({ schema, file, short, env, directory, notice })` takes one settings object and returns `{ plugin, values }` from it, so the file pattern and the schema are written once. `plugin` is the configuration plugin the Application installs, with the identity `@loomcli/plugins/config`, the `--config` option, the directory option when declared, and the configuration source. `values` is a provider. `file` and `short` keep ADR-0054's meaning and faults, and [ADR-0119](0119-the-configuration-lookup-walks-to-home-reads-an-author-named-variable-and-the-xdg-user-file-and-never-falls-back-after-a-broken-file.md) defines `env`, `directory`, and `notice`.
- **One schema for the whole file.** `schema` is one Standard Schema for the file's top-level object, and it is required. Its types accept only a schema whose input accepts an empty file: every object key is optional at every depth outside an array item and a record's values. Inside an array item a key may be required, because an item is a unit: a `[[sessions.sources]]` entry without `harness` is not a source. The rule holds at every depth, because a file that holds an optional table without its required key would lose the whole table. The contract's probes showed the type check holds alike for zod 4, valibot 1, and ArkType 2. An author who wants a loose file writes loose types.
- **Drop and validate again.** The plugin validates the parsed file with the schema's `~standard.validate`. When the result holds issues, it removes the value at each issue's path and validates again, until the file passes. Each round removes at least one value, so the loop ends. An issue whose path ends inside an array item removes that whole item. An issue whose path ends at a value the file does not hold removes the nearest enclosing value it does hold. An issue with no path removes the whole file, which then validates as an empty file. A key whose value is removed falls back to its schema default or to absence. A schema that still rejects an empty file is the author's defect and fails the run with code 1, because the types cannot see a refinement.
- **Named at `-v`.** Each removed value writes one `out.debug` line naming its key, the file, and the first issue's message, so it shows at `-v` alone and never at the default verbosity.
- **Unknown keys are ignored.** A key the schema does not describe is never reported at any verbosity. Whether it reaches the output is the schema library's choice for a loose object.
- **A strict schema is advised against.** A strict object reports an unknown key as an issue, and zod names the object that holds the key rather than the key, so the drop rule removes the whole object, the whole file at the top level. Standard Schema's types cannot tell a strict schema from a loose one, so `@loomcli/eslint-plugin` gains a rule, `strict-configuration-schema`, that reports a zod strict object it can trace into `configuration()`'s `schema`. valibot and ArkType name the unknown key itself, which the probes showed, so the drop rule removes that key alone and the rule leaves their strict objects alone. The owner: "It gives author's provenance to ignore the rule, but can advise against using it." An author who disables the rule gets what the schema reports, under the ordinary drop rule.
- **`provided.config`.** `values` is an ephemeral provider named `config` whose value is the schema's output for the passed file. A Command opts in with `uses: [config]` and reads `provided.config`. The provider reads `--config` and the directory option as global options, so a Command that opts in fails to compile where it meets an Application that does not install the plugin, under ADR-0108. A run with no configuration file provides the output of an empty file. The name carries no package prefix, because the application's own call creates the provider and an application has one configuration source.
- **One read per run.** The source and the provider share one lookup, one read, and one validated result per run, so each warning and each `-v` line is written once. A Command that does not opt in and fills no linked option reads no file, and a takeover such as `--help` builds no provider.
- **A link stays on the option.** An option links to a key with `configInput({ path })`, beside `env`, as today. The order of tiers is unchanged: argv, the environment, the configuration, then the declared default. A linked option takes the value the file holds at its path once the file has passed the schema, so a dropped value fills nothing, and a schema default or transform never reaches the option: the option's own default and validator decide, as for every tier. A value that does not fit the option's raw type, under ADR-0054's value shapes, is not answered and writes one `-v` line, in place of ADR-0039's usage failure. A value the option's validator rejects falls back under [ADR-0117](0117-a-configuration-value-its-validator-rejects-falls-back-and-validates-against-its-files-directory.md), while `provided.config` keeps it.
- **A link the schema cannot hold is a build fault.** When the schema implements `StandardJSONSchemaV1`, the plugin's `onGraphBuilt` hook reads its input-side JSON Schema and throws a `DeclarationError` for a linked option whose path the schema's shape does not hold, or whose type at that path the option cannot take. A schema that publishes no shape, or a shape open at the path, gets no check. `configuration()` cannot see the Application's options in its types, so the check runs where the graph is built.
- **File-relative paths for linked options.** Every answer the source gives carries the file's `directory`, under ADR-0117, so a linked option's validator, such as `path()`, resolves a relative value against the file's directory. `provided.config` keeps every path as the file wrote it, because a Standard Schema library passes no options to the validators nested inside it; the owner chose paths as written over a plugin helper for schema transforms and over a list of path keys. The plugin expands no `~`.

## Considered options

- **A schema per section, each read as its own value.** Rejected by the owner: "absurdly difficult for an author to reason about."
- **A required key fails the run, or the file.** Rejected. A configuration file is written after the application already runs, so a required key would fail every run until the operator writes it.
- **An invalid value fails the run, as ADR-0039 holds.** Rejected. A file is state every later run reads, and the owner: "ignore invalid fields."
- **Unknown keys warned about, or reported at `-v`.** Rejected by the owner: "they just ignore unknowns."
- **Requiring Standard JSON Schema in the types and stripping unknown keys before validation.** Rejected. It would refuse a schema that publishes no shape, and the lint rule covers the strict case without narrowing which libraries an author may use.
- **The option's link declared in the schema, or the schema keyed by option names.** Rejected. The schema describes the whole file and is the author's, and a plugin cannot type the Application's options. The option is what is filled, so the link stays beside `env`.
- **The plugin installs the provider, or the plugin's value carries it.** Rejected. ADR-0108 has no plugin-installed provider, and `plugin()`'s value is frozen and opaque.
- **A linked option takes the schema's output.** Rejected. A schema default would then fill the option ahead of its own default, and a transform would hand the option's validator a value no operator wrote.
- **Provenance on the action context or in the `-v` lines.** Rejected by the owner: "the action doesn't need to know this."
- **Named profiles.** Out. No CLI framework ships them, and the owner: "I don't have a good vision for this."

## Consequences

`configuration()` replaces `config()`, the schema is required, and a wrong value in the file no longer fails the run, so the implementation carries breaking fragments with the migration: an application calls `configuration({ schema })` with a schema for its file, installs `plugin`, and keeps every `configInput` link. textstat migrates in the implementation, and Heimdall's three applications replace `readConfigSection` through a seed on its board. The bet is the drop loop over an opaque Standard Schema and the empty-file type check; the contract's probes against zod, valibot, and ArkType ground both. A schema that implements `StandardJSONSchemaV1` and an application with a linked option convert the schema once per graph build for the link check. LM-377 publishes the file's JSON Schema, LM-379 reads JSONC, and LM-367 shows bindings in help, each after this record's implementation. [Configuration plugin](../plugins/config.md) and [ESLint plugin reference](../libs/eslint-plugin.md) carry the contract.

## Status

Proposed. It moves to accepted in the release PR of the release that ships `configuration()` with the schema, the drop rule, `provided.config`, the link check, and the `strict-configuration-schema` lint rule, with textstat migrated.
