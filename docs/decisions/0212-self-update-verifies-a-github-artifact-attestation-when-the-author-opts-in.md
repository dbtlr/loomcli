title: ADR-0212 - Self-update verifies a GitHub artifact attestation when the author opts in
description: An author who passes selfUpdate({ attestation: attestation({ workflow }) }), from the subpath @loomcli/plugins/self-update/attestation, makes self-update verify a GitHub artifact attestation of the release asset before it downloads the asset. The Command asks GitHub's attestations API for the digest SHA256SUMS lists, brings Sigstore's trust root current over TUF in the application's cache directory, reads each SLSA provenance bundle, verifies it in full with sigstore-js, and checks the issuer, the signing workflow and repository, that the run was on the release's own tag, and a statement subject with the asset's name and digest. It never falls back to the digest alone. The setting is a branded value only attestation() makes. The sigstore-js packages are optional peer dependencies that only the subpath loads. It supersedes ADR-0073's HTTPS alone clause for the attestation case, and names exceptions to ADR-0093's removal of a check TypeScript already makes, ADR-0107's one-module read of the process, and ADR-0165's one event per change.

# ADR-0212 - Self-update verifies a GitHub artifact attestation when the author opts in

## Context

[ADR-0073](0073-the-self-update-plugin-replaces-a-script-installed-binary-with-a-verified-release.md) verifies a release asset against the release's `SHA256SUMS`. The digest proves that the asset is the file the release lists, not who published the release. Anyone who can write to the repository's releases, such as a leaked token or a compromised maintainer account, can upload a binary and a `SHA256SUMS` that agree. Its **HTTPS alone** clause limits the Command to HTTPS requests under the repository on `github.com`, with no API and no token. It rejected the REST API for resolving prereleases because an unauthenticated caller gets 60 requests an hour.

GitHub artifact attestations narrow that gap. A release workflow that runs `actions/attest-build-provenance` gets a short-lived certificate from Sigstore's public certificate authority, Fulcio, for the workflow run's identity, signs an in-toto statement that names each asset's name and SHA-256 digest, records the signature in Sigstore's transparency log, Rekor, and stores the bundle with GitHub. The certificate names the workflow file, the repository the run belongs to, and the ref the run was triggered on. A verifier that checks the bundle against Sigstore's trust root, and checks those names, knows that the pinned workflow, run on that ref in that repository, built those bytes. Upload access to releases alone cannot forge that. It does not show who started the run: anyone who can push a tag the workflow runs on, or dispatch the workflow, gets an attestation for what the run builds. Loom's own release attests its npm packages through `--provenance`, but not binaries, and an application's release workflow is the author's under [principle 1](../principles.md).

Reading the sigstore-js packages and GitHub's live endpoint, as they stood on 2026-11-19 (`@sigstore/verify` 4.1.3, `@sigstore/bundle` 5.0.1, `@sigstore/tuf` 5.0.1, `tuf-js` 6.0.2), established these facts:

- **The endpoint.** `GET https://api.github.com/repos/{owner}/{repo}/attestations/sha256:{digest}` answers an unauthenticated caller for a public repository. It counts against the 60-an-hour limit per address, and it takes `predicate_type` and `per_page` parameters and pages through a `Link` header. A digest with no attestation answers `200` with `{"attestations":[]}`, not `404`. Asked for `X-GitHub-Api-Version: 2026-03-10`, it answers `200` and reports `x-github-api-version-selected: 2022-11-28`, with a `deprecation` date of 2026-03-10 and a `sunset` of 2028-03-10 for that older version; an unknown version answers `400`. Each attestation carries `bundle`, which GitHub now omits or returns as `null`, and `bundle_url`, a signed URL on `tmaproduction.blob.core.windows.net` that expires within the hour and answers `application/x-snappy`: the bundle's JSON compressed in Snappy's block format, not its framing format. Reading a bundle therefore costs a second request, to a host outside GitHub's domains. The GitHub CLI reads `bundle_url` the same way and falls back to an inline `bundle`.
- **The bundles.** A provenance bundle from `actions/attest-build-provenance` in a public repository is a Sigstore bundle of media type `application/vnd.dev.sigstore.bundle.v0.3+json`, a few kilobytes of JSON. It holds a DSSE envelope, a Fulcio certificate, and a Rekor entry with an inclusion proof, and its statement's `predicateType` is `https://slsa.dev/provenance/v1`. Each statement subject's `name` is the attested file's base name. `@sigstore/bundle` reads that media type, and `@sigstore/verify` verifies it once it is decoded. The same digest can also have a release attestation, which GitHub signs on its own Sigstore instance with no Rekor entry. It does not verify against Sigstore's public trust root, and the provenance filter leaves it out.
- **The certificate.** Fulcio writes the run's facts as certificate extensions, each a DER `UTF8String`. Among them are the issuer (`1.3.6.1.4.1.57264.1.8`), the Source Repository URI (`.1.12`), `https://github.com/<owner>/<name>` of the repository the run belongs to, the Source Repository Ref (`.1.14`), the ref that triggered the run, such as `refs/tags/v1.5.1`, and the numeric Source Repository Identifier and Owner Identifier (`.1.15` and `.1.17`). The subject alternative name is the URI of the workflow file that ran the signing job, `https://github.com/<owner>/<name>/<path>@<ref>`. For a reusable workflow, that is the reusable workflow's own repository and path, while `.12` and `.14` still name the calling run's repository and ref.
- **Verification.** `@sigstore/verify`'s `Verifier` makes no network request. With its defaults, which are thresholds of one, it requires all of these at once: a certificate that chains to a Fulcio authority in the trust root at every verified time; at least one signed certificate timestamp from a certificate-transparency log in the trust root; at least one transparency-log entry whose body matches the signature and whose inclusion verifies, by a signed entry timestamp or by an inclusion proof against a signed checkpoint; at least one verified timestamp, from a log entry with a signed entry timestamp or from a timestamp authority in the trust root; and the signature by the certificate's key. Its constructor takes other thresholds. `verify` returns the signer, whose identity lists every certificate extension's OID with its DER value. Its policy compares the issuer extension exactly, but it matches the subject alternative name as an unanchored regular expression, and it compares extension values as exact bytes. It checks no statement subject: for a DSSE bundle, the caller checks the digest and the name.
- **The trust root.** `@sigstore/tuf`'s `getTrustedRoot` keeps Sigstore's `trusted_root.json` current through TUF from `https://tuf-repo-cdn.sigstore.dev`, its one host. It ships a seed `root.json`, version 16 in 5.0.1, and seed targets. Its `cachePath` option sets the directory, which defaults to `$XDG_DATA_HOME/sigstore-js`, or `~/.local/share/sigstore-js`, which other tools share. Under it, the directory `tuf-repo-cdn.sigstore.dev` holds `root.json`, `timestamp.json`, `snapshot.json`, `targets.json`, and `targets/` with `trusted_root.json` and a seeded npm key file. It creates the folders and writes the seed synchronously when it is called, writes the metadata in place with `writeFileSync`, not through a rename, and stages each download in a folder under `os.tmpdir()` that it removes afterwards.
- **What the cache decides.** tuf-js trusts a cached `root.json` that is signed by its own keys, and checks the cached `snapshot.json` against that root without its hash. Whoever can write the cache can therefore name the keys the next run trusts, unless the root is seeded again. Its `forceInit` option writes the shipped seed root and targets over the cached ones at every call, so the walk to the current root starts from the root the package ships. Cached metadata that the seeded chain does not sign is then discarded and fetched again, and a cached target whose hash the current targets metadata does not list is downloaded again. `forceInit` writes the seed targets too, so once Sigstore's `trusted_root.json` has changed since the one the installed `@sigstore/tuf` ships, every call downloads it again: one more request of a few kilobytes per call, until a newer `@sigstore/tuf` ships the current one. On 2026-11-19 the seed of 5.0.1 matched the current target, and a call with a warm cache made two requests.
- **Requests.** A warm cache makes two requests per call: the next `root.json` version, which answers `404`, and `timestamp.json`. A changed timestamp adds `snapshot.json` and `targets.json`, a changed trust root adds the `trusted_root.json` target, and each root version after the cached one adds one request. Each request has a 5-second limit through `AbortSignal.timeout` and two retries after a network error or a `5xx`. `timeout` and `retry` can change both, and no option takes an outside abort signal. The platform's `fetch` follows redirects on its own. tuf-js loads `debug`, which reads `DEBUG` from the process environment when it loads and writes its lines to the process's own stderr.
- **Faults.** `getTrustedRoot` rejects with a `TUFError`, which `@sigstore/tuf` exports, whose `code` names the stage, such as `TUF_REFRESH_METADATA_ERROR`, `TUF_DOWNLOAD_TARGET_ERROR`, or `TUF_READ_TARGET_ERROR`, and whose `cause` is the fault beneath, or, when the cache cannot be created or seeded, with the system error itself. For the root and the timestamp, the cause is the fault itself: a `DownloadHTTPError` with a numeric `statusCode` for a response, the platform's `fetch` rejection, a `TypeError` or a `DOMException` named `TimeoutError`, for no response, a system error with `code` and `path` for the staging folder, or one of tuf-js's other classes, such as `RepositoryError` for metadata that does not verify or has expired and `PersistError` for a write. None of the three packages exports tuf-js's classes, and none of them sets `name`, so the subpath cannot tell those apart. The snapshot and targets faults, whatever caused them, are a `RuntimeError` that carries only message text.
- **An offline mode.** `forceCache` uses the cached timestamp without a request while it holds, and goes to the network when the cache is missing, damaged, or expired.
- **The packages.** The `sigstore` package wraps the three and loads `@sigstore/sign`, with `make-fetch-happen`, at import, even to verify. Each package declares Node `^22.22.2 || ^24.15.0 || >=26.0.0`.

## Decision

- **An opt-in value from a subpath.** `@loomcli/plugins/self-update/attestation` exports `attestation({ workflow })`, and the author passes its value as `selfUpdate({ attestation: attestation({ workflow: '.github/workflows/release.yml' }) })`. `workflow` pins the path, in the application's repository, of the workflow file that runs the attestation job, which may be a reusable workflow in that repository: `.github/workflows/`, then a file name with no `/` that ends in `.yml` or `.yaml`. `attestation()` throws a `DeclarationError` at the call for any other value. Only that subpath imports sigstore-js, and `@loomcli/plugins/self-update` declares the value's type without it. A costly capability lives in a subpath and its packages are optional peers; this is the package's first optional-peer subpath.
- **A setting only `attestation()` makes.** The type is `AttestationSetting`. It carries a member keyed by an unexported `unique symbol`, so an object literal cannot satisfy it and a hand-written `{ workflow }` is a compile error. `selfUpdate()` throws a `DeclarationError` at the call, with the diagnostic code `@loomcli/plugins/self-update/attestation-setting`, for an `attestation` that is not `undefined` and is not a value `attestation()` made, so the same value from JavaScript or through `any` fails before the application ships. This goes past [principle 7](../principles.md), which leaves a value that bypasses the types to the platform's own error, because no platform error would follow: a plugin that read a hand-written value as unset would turn the check off in silence. For the same reason it is an exception to [ADR-0093](0093-a-value-that-bypasses-the-types-gets-no-rule.md)'s **A check needs a reason a type cannot carry**, under which a rule whose fault TypeScript already rejects at the call goes: TypeScript rejects a hand-written setting at the call, and the check stays anyway. ADR-0093 carries a dated entry. A set attestation is never treated as unset. When the Command cannot run it, for any reason, the update fails. "Attestation" stays the glossary's word for the signed statement, and the setting is named for what it is, under [principle 5](../principles.md).
- **The verifying packages are optional peers.** `@sigstore/verify`, `@sigstore/bundle`, and `@sigstore/tuf` are optional peer dependencies of `@loomcli/plugins`. An application that imports the subpath installs them, and every other application carries none of their code. The `sigstore` umbrella is not used, because it loads the signing stack.
- **Verified before the asset is downloaded.** With an attestation set, once the release's `SHA256SUMS` lists the asset, the Command verifies an attestation for the digest it lists, then downloads the asset and checks it against that digest as before. Nothing is placed whose SHA-256 and name the verified attestation does not name, and a release that fails is not downloaded. `--check`, the update notices, and `--refresh-notice` make no attestation request, resolve no cache directory for it, and read no trust root.
- **The order of the requests.** The Command first resolves `applicationDirectory('cache', name, host)`; when it answers `{ variable }`, the Command refuses before any request, as the other refusals do. After `SHA256SUMS`, it makes these requests, in this order:
  1. **The list.** One unauthenticated request to `https://api.github.com/repos/<owner>/<name>/attestations/sha256:<digest>?per_page=10&predicate_type=provenance` for the repository it resolved, with `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2026-03-10`. The Command reads that one page and follows no `Link`: every further page would spend another of the address's 60 requests an hour, and a release attests a digest once per run of its workflow, so ten holds every run a release plausibly has, re-runs included. The page also bounds the attestations tried at ten. A run whose list holds none fails here, with no trust-root request.
  2. **The trust root.** Sigstore-js brings the trust root current from `https://tuf-repo-cdn.sigstore.dev`, once. It comes before the first bundle because every attestation is verified against the same trust root: a fault there fails the run with one sentence, rather than being ranked among the attestations' faults, and each bundle is then read and verified in one step.
  3. **The bundles.** For each attestation, in the order GitHub lists them, the Command reads its bundle inline when GitHub gives one as an object, and otherwise requests its `bundle_url`, then verifies it, and stops at the first that passes. An attestation whose `bundle` is not an object and whose `bundle_url` is missing or not an absolute HTTPS URL makes no request and fails the first check, **The bundle reads**.

  The Command follows each redirect of its own requests itself, only to HTTPS, under ADR-0073's rules, and the run signal cancels it. A bundle request that fails, by a status other than `200`, no response, or a redirect fault, fails the run under the ordinary request rows: the URL comes fresh from GitHub's answer moments before, so a failure there is the storage's, not the attestation's, and the step is to run self-update again later.
- **Reading a bundle.** The body is decoded as Snappy's block format by a small decoder of Loom's own in the subpath, which reads nothing else, such as the framing format, and takes no dependency. It reads the declared uncompressed length first and refuses a length above 1 MiB before it allocates; a bundle is a few kilobytes. It also refuses an element that would write past the declared length or copy from before the output's start. The decoded bytes then parse as JSON and as a Sigstore bundle through `@sigstore/bundle`, with a DSSE envelope.
- **Full verification, then identity, then the release, then the statement.** An attestation passes when every check holds, in this order:
  1. **The bundle reads.** It decodes and parses as above.
  2. **Sigstore's checks.** `@sigstore/verify`'s `Verifier`, built with no options, so each threshold is its default of one, verifies the bundle in full against the trust root. It requires all of these at once: a certificate that chains to a Fulcio authority in the trust root, at least one signed certificate timestamp, at least one transparency-log entry whose inclusion verifies, at least one verified timestamp, from a log entry with a signed entry timestamp or from a timestamp authority in the trust root, and the signature by the certificate's key. The setting offers no way to lower them.
  3. **The identity.** The certificate's issuer is `https://token.actions.githubusercontent.com`. Its subject alternative name starts with `https://github.com/<owner>/<name>/<workflow>@`, with any ref after the `@`. Its Source Repository URI, OID `1.3.6.1.4.1.57264.1.12`, read from the signer the `Verifier` returns and decoded as a DER `UTF8String`, is `https://github.com/<owner>/<name>`. The Command compares both itself and does not hand the name to sigstore-js as a pattern. In each, `<owner>/<name>` is either the repository the release facts hold, `host.release.repository`, or the one the Command resolved through GitHub's redirect, compared without regard to case as ADR-0073's release-channel clause compares them, so an update across a rename or a transfer passes. Every other character compares exactly. The Source Repository URI check refuses a run of another repository that calls the pinned workflow as a reusable workflow: its subject alternative name names the pinned file, but `.12` names the caller.
  4. **The release.** The Source Repository Ref, OID `1.3.6.1.4.1.57264.1.14`, decoded the same way, is exactly `refs/tags/v<version>` for the version being installed. The attestation then comes from a run on the release's own tag.
  5. **The statement.** The envelope's payload type is `application/vnd.in-toto+json`, the statement's `_type` is `https://in-toto.io/Statement/v1`, its `predicateType` is `https://slsa.dev/provenance/v1`, and one subject has both a `name` equal to the asset name in the release facts, `host.release.asset`, and a `sha256` digest equal, in lowercase, to the digest `SHA256SUMS` lists.

  A missing extension, or one that does not decode as a `UTF8String`, fails the check that reads it.
- **No fallback.** A rate-limit response, no attestation, an attestation that fails, a trust root that cannot be brought current, and a bundle that cannot be read each fail the update with exit 1. None falls back to the digest alone, because an attacker who can force any of them would otherwise turn the check off. When none of the listed attestations passes, the sentence names the fault of the one that went furthest through the checks above, the first of those when several tie.
- **The failure sentences.** Each sentence is a named export of the plugin's messages module under [ADR-0164](0164-looms-operator-messages-live-in-message-modules-and-a-voice-test-per-package-reads-them.md), names the fault and a step, and quotes no Node.js, engine, or library reason. The trust-root faults are told apart only by facts: the `TUFError` class and its `code`, the `statusCode` its `cause` carries and the class of the platform's `fetch` rejection, and a system error's `code` and `path`, which says whether the fault is in the trust root's folder or the staging folder. Never by message text, which rule 6 forbids, so a read of `cause` to test what it is is pinned in the voice test with that reason. A `cause` that is a `TypeError` is always the platform's `fetch` rejection, and so an unreachable host, even when it carries a `code` and a `path`, as Bun's does for `ENOTFOUND` or `ECONNREFUSED`; a system error is one with a string `code` and `path` that is not a `TypeError`. tuf-js's own classes, a `RuntimeError` among them, cannot be told apart from those facts, so every fault the facts do not name shares one sentence that names the host, the clock, and both folders a fault could be in. The sentences are stated in [Self-update](../plugins/self-update.md#attestation).
- **The trust root in the cache directory.** The subpath calls `getTrustedRoot` with `cachePath` set to `sigstore` in `applicationDirectory('cache', name, host)`, the kind [ADR-0080](0080-the-self-update-plugin-tells-an-interactive-operator-about-a-newer-release-from-a-daily-cache.md) adds to [ADR-0071](0071-an-installation-record-per-application-says-how-it-was-installed-and-what-its-installers-wrote.md)'s lookup, and with `forceInit: true` and `forceCache: false`, so every update starts from the root the binary ships and checks for a new trust root.
- **The cache is security state.** What the trust root says decides which signatures verify, so the cache is not merely data that can be lost. Seeding at every call keeps it from deciding anything: a planted or damaged file in it is replaced by the seed, discarded because the seeded chain does not sign it, or downloaded again, so the most it can do is stop updates. A folder that cannot be written, or a file in its place, fails with a sentence that names it, and removing the folder always recovers, because the next update seeds it again.
- **No token.** No request carries a token. A public repository's attestations need none, and the operator who runs `self-update` has none to configure.
- **No new time limit.** The Command adds no time limit, as ADR-0073 adds none. The TUF requests are sigstore-js's own. They keep its 5-second limit per request and its two retries, because no abort signal reaches them. When the run signal aborts, the Command stops waiting and propagates the reason, and the limit bounds how long a request the signal cannot reach stays open after that.
- **The rate limit.** One API request per update that replaces a binary, and only when the author opts in, spends one of an address's 60 an hour. ADR-0073 rejected the API because resolving a channel would spend that limit on every lookup, every update notice's daily refresh included, for every application, without the author choosing it. Here a run that is limited fails with the time the limit resets, and the operator runs it again then.
- **At -v and in the log.** `-vv` names the API request and each bundle request with ADR-0165's `Requested <url>.` line, which leaves out the bundle URL's query and its signature. `-v` writes `Checked Sigstore's trust root in <folder>.` once the trust root is current, which is ADR-0165's line for a cache used, and `Verified <asset> against its attestation from <workflow>.` once an attestation passes. Sigstore-js makes the TUF requests and writes the cache files, and reports neither to Loom, so no `Requested` line names a TUF request and no `File written.` event records a cache file. That is an exception to ADR-0165's **One event per change**, which ADR-0165 carries as a dated entry.
- **The process outside the handle.** Sigstore-js reads `os.tmpdir()`, and the `debug` package it loads reads `process.env.DEBUG` and writes to the process's own stderr, not the run's host. That is an exception to [ADR-0107](0107-a-run-reads-the-process-through-one-process-handle.md)'s **Core reads the global `process` in one module**, of the same kind as the `yaml` package's debug variables that the configuration plugin names at `packages/plugins/src/config/yaml.ts:14`: a dependency reading the process environment for its own debug output. Loom adds no guard for `DEBUG`, as it does for the YAML parse, because `debug` reads it once when it loads, not during a call a guard could wrap, and what tuf-js writes under it is its own requests and cache paths, not an operator's data. ADR-0107 carries a dated entry.
- **Without the setting, nothing changes.** An application that leaves `attestation` unset makes the same requests, in the same order, with the same outcomes as under ADR-0073 with ADR-0211's amendment applied: the early package-manager refusal and the ownership check of the recorded path, which make no request.
- **The proof.** The implementation is held to these, with recorded fixture bundles and a recorded trust root, under the plan beside its tests that [ADR-0100](0100-acceptance-plans-live-beside-the-tests.md) requires:
  - A valid attestation from the pinned workflow, run on the release's tag, passes, and the update completes.
  - Each of these fails with its own sentence and places nothing: another workflow; another repository, including a run of another repository that calls the pinned workflow as a reusable workflow; a run on another ref than `refs/tags/v<version>`; a subject with the digest under another name; another digest; a tampered signature; a bundle that does not decode, including a declared length above the bound; no attestation; and a rate-limit response. None falls back to the digest.
  - An attestation whose certificate names the repository the release facts hold passes after GitHub redirects that repository to a new name, and so does one that names the new name.
  - Each trust-root sentence follows from the facts that classify it: an unreachable host, a cache folder that cannot be written, a file in place of that folder, a staging folder that cannot be written, metadata that does not verify, and a `RuntimeError`. Under Bun, a `fetch` rejection that is a `TypeError` carrying `code` and `path` names the unreachable host, not a folder. A planted `root.json`, `snapshot.json`, or `targets/trusted_root.json` in the cache does not change what verifies.
  - A hand-written `attestation` value fails `selfUpdate()` with the diagnostic code, and a value from `attestation()` passes.
  - `--check` with an attestation set and an unresolvable cache directory still reports, and makes no attestation request.
  - Without the attestation set, self-update's requests and behavior are unchanged.
  - The subpath has an API report under `check:api`.
  - A bundle test shows that an application which does not import the subpath holds no sigstore code.
  - A compiled Bun binary that imports the subpath verifies a recorded attestation and updates itself in CI. A compiled binary is the only place self-update runs, so this is part of the proof, not a step after it, under ADR-0100's rule that support no CI entry runs is not shipped.

The contract is in [Self-update](../plugins/self-update.md#attestation).

## Considered options

- **Not pinning the ref.** Rejected. An earlier draft pinned the issuer, the repository, and the workflow, but no ref, so that a workflow run from a branch, a tag push, a release event, or a dispatch would all verify. Then any attestation the workflow ever made verifies any release whose `SHA256SUMS` lists its digest. Someone with write access to releases could publish an older, attested binary as a new release, a downgrade the operator never asked for, or replay a binary the workflow built from a branch. Binding the attestation to `refs/tags/v<version>` and the subject to the asset's name closes both, and costs the author one rule: attest from the tag.
- **Pinning the numeric repository and owner identifiers.** Not chosen. The certificate's `.15` and `.17` extensions name the repository and owner by number, which a re-registered name does not inherit. The binary would have to bake those numbers, which no release fact holds today, and an author who transfers the repository would change the owner's number. Identity by name matches how the release facts and ADR-0073 already name the repository.
- **An embedded trust root.** Not chosen. Loom would bake Sigstore's `trusted_root.json` into the subpath, and verification would make no request beyond GitHub's. Sigstore rotates its certificate authorities, transparency logs, and timestamp authorities, and TUF is how it publishes those changes. A binary built before a rotation could not verify attestations signed after it. Its operators then could not update to the release that would fix that, the case self-update exists for. TUF is Sigstore's own standard for distributing its root, under [principle 6](../principles.md). Seeding at every call keeps the part of this option that matters, a trust anchor fixed in the binary, and lets TUF walk forward from it.
- **Trusting the cached root, sigstore-js's default.** Rejected. A warm cache would save one request for each root version since the build, but whoever could write the cache could choose the keys the next update trusts.
- **Seeding the root alone.** Not chosen. Writing the shipped `root.json` over the cached one before each call, without `forceInit`, would keep a cached `trusted_root.json` whose hash the current targets metadata lists, and save the request `forceInit` adds once Sigstore's trust root has changed since the seed. `@sigstore/tuf` exports neither its seeds nor a way to seed the root alone, so the subpath would read the package's `seeds.json` and write into its cache layout itself, both internal to a package whose versions it does not pin. One request of a few kilobytes per update costs less than that coupling.
- **The `sigstore` umbrella package.** Rejected. It is the documented entry, but it loads `@sigstore/sign` and `make-fetch-happen` at import, so every application that verifies would carry the signing stack.
- **sigstore-js's default cache directory.** Rejected. `~/.local/share/sigstore-js` is a data directory that other tools share. The application's own cache directory, which ADR-0080 already gives it, holds nothing another tool writes.
- **`forceCache`.** Rejected. It would save the TUF requests while a cached timestamp holds, but a key Sigstore revokes would then stay trusted until that timestamp expires. An update is rare, and a warm cache costs two small requests.
- **Following the list's pages.** Not chosen. Each page is another request against the address's 60 an hour, and a release plausibly has far fewer than ten attestations of one digest.
- **Moving to the next attestation when a bundle request fails.** Not chosen. The fault is the storage's, the same for every bundle URL in that answer, and the furthest-fault sentence would then report a transport fault as a bundle that cannot be read.
- **A Snappy package.** Not chosen. The block format needs a decoder of a few dozen lines. One of Loom's own reads only the format GitHub serves, applies the bound above before it allocates, and adds no dependency to the subpath.
- **Falling back to the digest when the API is limited or no attestation exists.** Rejected. Anyone who can exhaust an address's limit, or strip an attestation, could then turn the check off.
- **A token from the environment, such as `GITHUB_TOKEN`.** Rejected. A token raises the limit, but it would send a credential that the operator set for another tool, and ADR-0073 keeps self-update free of secrets.
- **Running `gh attestation verify`.** Rejected. It needs the GitHub CLI installed and signed in on every machine that updates.
- **Disabling sigstore-js's time limit and retries.** Not chosen. That would match ADR-0073's requests exactly, but the run signal cannot reach these requests. A hung request would then outlive a cancelled run in an embedding host or an `app.invoke`.

## Consequences

This supersedes ADR-0073's **HTTPS alone** clause for an application that sets `attestation`. Such an application also requests `api.github.com`, the bundle's host, and `tuf-repo-cdn.sigstore.dev`. It calls an API and keeps a cache. Every request it makes starts at an HTTPS URL, and every redirect it follows itself stays HTTPS. Sigstore-js's TUF requests follow redirects through the platform's `fetch`, which Loom cannot hold to HTTPS. TUF's signatures, not the transport, decide what those files may say. ADR-0073 stays accepted and carries a dated entry. Every other clause of ADR-0073 stands, and without the setting this one does too.

An author who opts in adds the three peer packages and an attestation step to the release workflow for each binary asset. The step runs in a run on the release's tag, from a push of the `v*` tag, a `release` event, or a dispatch on the tag. A workflow that attests from a branch and tags afterwards produces attestations that do not verify. Every release from then on needs an attestation, so an operator on that binary cannot self-update to a release published without one. The pinned workflow must live in the application's repository, because a reusable workflow from another repository signs with that repository's path. A private repository cannot use this, as it cannot use self-update at all, because both read without a token.

What remains open, each failing closed:

- **Who can start the workflow.** An attestation shows that the pinned workflow, run on the release's tag in the repository, built the bytes. Anyone who can push a `v*` tag, or dispatch the workflow on one, can have it build and attest their own commit. The protection is the author's: a tag ruleset that limits who creates `v*` tags, and an environment with required reviewers on the job that attests, so the job gets no signing identity until someone approves it. The reference tells the author both.
- **A tag made again.** The release check compares the ref by name. When a maintainer deletes a `v*` tag and creates it again on another commit, an attestation from the first tag's run still names `refs/tags/v<version>`, so it verifies for any release whose `SHA256SUMS` lists the first build's digest. Maintainers publish a new version rather than re-tag one, and the reference says so. Pinning the commit, OID `1.3.6.1.4.1.57264.1.13`, was considered and not taken: no release fact holds the tag's commit, and reading it would cost another API request against the same hourly limit.
- **A name someone else takes.** Identity is by name. When a repository or its owner is deleted or renamed and someone else registers the old name, that party's workflow at the same path signs as the old name, and a binary that bakes it fetches their releases. Pinning the numeric identifiers was considered and not taken.
- **GitHub's formats.** An opted-in binary stops updating if GitHub retires the API version it pins, changes the bundle's media type beyond what its `@sigstore/bundle` reads, or changes the blob encoding from Snappy's block format. Each fails with a sentence whose step is `install.sh`, which checks no attestation and installs a release whose own reader is current. On 2026-11-19 GitHub answered the pinned `2026-03-10` with its `2022-11-28` behavior, whose stated sunset is 2028-03-10.
- **Releases from before the step.** `self-update <version>` to a release published before the repository attested its assets fails with the no-attestation sentence. `install.sh <version>` installs it.
- **Node.** Sigstore-js's Node range, `^22.22.2 || ^24.15.0 || >=26.0.0`, leaves out Node 23, 25, and 24 before 24.15, which `@loomcli/plugins` accepts. It limits only the subpath: an application that does not import it keeps the package's range. Self-update runs only in a compiled Bun binary, so the range binds an author who runs the subpath's tests under Node.

The ADR-0093, ADR-0165, and ADR-0107 exceptions above are the plugin's only departures from those records.
