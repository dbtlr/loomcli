# ADR-0213 - An opt-in npm target writes a launcher package and a platform package per binary

## Context

An application reaches npm today as the package its author builds and packs, which is usually a `loom build --target node` bundle. That package runs only where a Node.js runtime runs it, and it starts as slowly as Node loads the bundle. A compiled binary from `loom build --target bun-<os>-<arch>` starts at once and needs no runtime, and the [installer script](../toolchain/install.md) already installs one from a GitHub Release. An operator who installs command-line tools with `npm install -g` cannot get that binary from npm.

The npm ecosystem has a settled pattern for native binaries, which esbuild, Biome, Turborepo, and SWC follow. A small launcher package lists one package per platform as optional dependencies. Each platform package declares the `os`, `cpu`, and, on Linux, `libc` it runs on, so the package manager installs only the one that matches the host. The launcher's bin finds that package and runs its binary. No install script runs and no download happens outside the package manager, so `--ignore-scripts`, offline mirrors, lockfile integrity, and provenance all cover the binary.

Three facts constrain how Loom adopts the pattern:

- [ADR-0099](0099-an-assembly-check-from-loomcli-testing-replaces-loom-check.md) carries forward [ADR-0066](0066-the-toolchain-acts-on-one-package-directory.md)'s rule that `loom build` builds one target per call. ADR-0066 rejected several targets in one call because a failed target would leave the set half-built.
- Publishing is release orchestration, which stays with each repository under ADR-0099 and [principle 1](../principles.md#1-loom-owns-what-it-ships-the-author-owns-what-they-write). [ADR-0075](0075-the-release-workflow-runs-a-pinned-published-loom-cli.md) keeps Loom's own publishing in its repository's workflow, and an application's publishing stays in its author's.
- npm attaches a trusted publisher only to a package name that already exists on the registry, one package at a time. [ADR-0037](0037-validators-ship-in-their-own-package-as-standard-schema-values.md) records that cost for one new package: a placeholder `0.0.0` published by hand, then the publisher card. The launcher pattern multiplies it by the number of platforms.

How an application was installed is the installation group's question, under [ADR-0065](0065-release-facts-on-the-host-say-how-the-running-application-was-built.md) and [ADR-0071](0071-an-installation-record-per-application-says-how-it-was-installed-and-what-its-installers-wrote.md), and not the build's. ADR-0211, proposed in the same release, has core derive the method `npm` when no `install.json` matches and the running executable's real path lies under npm's global root, `<prefix>/lib/node_modules`. Update notices then name `npm install -g <pkg>@<version>`, and self-update refuses with the command for the version asked for. ADR-0211 takes `<pkg>` from the release fact `release.npmPackage`, which the build bakes.

A launcher that runs the binary as a child stands between the binary and the shell. The shell reads the launcher's status, and terminal signals reach both processes. [The shutdown](../core/signals.md#the-shutdown) promises that an application Ctrl-C ends dies by `SIGINT`, so a shell that runs it in a loop stops the loop. A launcher that exits with a code in its place breaks that promise, and one that forwards a terminal's signal makes the child read one keypress as two.

## Decision

- **The opt-in.** The toolchain configuration file gains a top-level `npm` object:

  ```jsonc
  // loom.config.json
  {
    "npm": {
      "launcher": true,
      "platforms": ["darwin-arm64", "linux-x64", "linux-x64-musl"]
    }
  }
  ```

  `launcher` is a Boolean, `false` when absent. `platforms` is optional and names the platform packages to write. Each entry is one of the six release asset platforms: `darwin-arm64`, `darwin-x64`, `linux-arm64`, `linux-arm64-musl`, `linux-x64`, and `linux-x64-musl`. When `platforms` is absent, all six are written. An empty list, an entry outside the six, a repeated entry, and a `platforms` key whose `launcher` is not `true` are values the schema rejects, so the run fails with code 2 under [ADR-0158](0158-the-loom-bin-reads-loom-config-json-strictly-so-a-broken-file-or-a-rejected-value-fails-the-run.md). The file turns the mode on, and it changes nothing else: `loom build --target node`, `bun`, and every compile target write what they wrote before.

- **One target, `npm`.** `loom build --target npm` builds the mode's artifact, which is a set of package directories. It is still one target per call. Within the call, the build compiles one binary for each listed platform from the compile target `bun-<platform>`, as `loom build --release --target bun-<platform>` compiles it, so each binary carries the release group and the asset name `<name>-<platform>`. Each binary also bakes `release.npmPackage` as `<pkg>`, the launcher package's name, under ADR-0211, so the binary's update notice and self-update refusal name the package the operator installed. `--target npm` in a package whose file does not set `npm.launcher` to `true` fails with code 2. The failure sentence says to set `"npm": { "launcher": true }` in `loom.config.json`, or to build a bundle with `--target node`.

- **Options under `--target npm`.** `--release` is implied, and passing it changes nothing. `--repository`, `--name`, `--entry`, and `--out` apply as they do for a compile target. `--application`, `--build development`, `--watch`, `--facts`, and `--define` are option errors, and each error names the reason. The packages hold distributed binaries, `--application` applies to a bundle, and the facts differ per platform, so a custom build reads each platform's facts with `--target bun-<platform> --release --facts`.

- **The layout.** The build writes the package directories into one directory, `<out>/npm` by default, where `<out>` is `paths.out`, or the directory `--out` names. Each package's directory is named for the package without its scope:

  ```text
  dist/npm/
    notes/                    the launcher package, @acme/notes
      package.json
      bin/notes               the launcher, mode 755
      README.md               copied from the package directory, when present
      LICENSE                 copied from the package directory, when present
    notes-darwin-arm64/       the platform package, @acme/notes-darwin-arm64
      package.json
      bin/notes               the compiled binary, mode 755
      LICENSE
    notes-linux-x64/
    notes-linux-x64-musl/
  ```

  Before anything compiles, the build checks `<pkg>` against npm's package name rule, which `@loomcli/core` exports as `isNpmPackageName` under ADR-0211: at most 214 characters, a segment, or `@`, a scope segment, `/`, and a segment, where a segment is lowercase letters, digits, `-`, `.`, and `_`, starting with a letter or a digit, and never `node_modules` or `favicon.ico`, the whole names npm reserves. Each directory is named for the last segment, so the rule keeps a name such as `..`, `.`, or `@acme/..` from naming the output directory's parent or the output directory itself. A name outside the rule fails with code 2, a usage error as the other `--target npm` refusals are. The build also checks `<name>` against `isPortableName` before it compiles, so a `--name` or a `bin` key with a path separator, such as `../package.json` or `x/y`, or a name of `.` or `..`, fails with code 2 and cannot redirect a binary over `package.json` or out of the staging directory.

  The build owns only the directories it wrote. It may replace or remove a package directory only when the entry at that name is absent, or is a directory, read with `lstat` so that a link is not followed, whose `package.json` has a `name` equal to the package the build writes there: `<pkg>` for the launcher's directory and `<pkg>-<platform>` for a platform's. Every directory the build writes carries that name, so a rebuild owns what an earlier build wrote, and an output directory that others share, such as `--out ../shared`, keeps every entry the build did not write. Before anything compiles, an entry at a name the build would write that it does not own, such as a folder that holds only `draft.txt`, a file, or a link, fails the build with exit 1, as a binary's `--out` that names a directory does, with a sentence that names the entry, and nothing changes. The build replaces each package directory it writes as a whole. It also removes a sibling directory named `<base>-<platform>` for one of the six platforms that the current build does not write, where `<base>` is the launcher's directory name, so a platform dropped from the list leaves no stale package. It removes only an entry it owns: a file, a link, or a directory whose `package.json` does not name that platform package stays, as does every other entry in the directory. Because the build replaces whole directories, an output directory that is the package directory or holds it fails with code 2 before anything compiles. With `--out ..` in `packages/notes`, the launcher's directory would be the package directory itself. An output directory inside the package directory, as `dist/npm` is, is where the packages belong.

- **One build or none.** Every binary and every package is written into the temporary directory beside the output that every build uses. The build moves them into place only after all of them succeed. A failed compile for one platform fails the build, and the directories from an earlier build stay as they were. The move is staged in a fixed order: every platform package's directory first, then the launcher package's directory, then the removal of dropped platforms' directories. A move that is interrupted part way can leave new platform directories beside the old launcher, but never a new launcher beside an old platform directory. Platform directories keep their names across builds, so such a set is mismatched: the old launcher checks the version in each platform package's `package.json` against its own, so on each platform already replaced it fails with the missing-package step, and it runs only on the platforms the move had not reached. The set stays mismatched until the next build writes it whole. Cancellation and shutdown follow the rules that every build follows. This answers ADR-0066's objection that several targets leave a set half-built: the set moves into place as a whole after every compile succeeds, and only an interrupted move leaves a mismatched set, which never runs a binary of another version and which the next build replaces.

- **The names.** The launcher package's name is `<pkg>`, the `name` field of the author's `package.json`. A build with no `name` fails and names the field. Each platform package's name is `<pkg>-<platform>`, such as `notes-linux-x64` or `notes-linux-arm64-musl`. A scoped `<pkg>` keeps its scope, so `@acme/notes` gives `@acme/notes-darwin-arm64`, which the same npm organization owns and publishes. One rule names the package an operator upgrades: every binary the target compiles bakes `release.npmPackage` as `<pkg>` under ADR-0211, and nothing reads a package name from a platform package's name or path. The binary inside each platform package, and the launcher's bin key, is the application's name `<name>`, read from `bin` or `--name` by the rule a binary build uses.

- **The launcher's `package.json`.** Its fields are written in this order, with two-space indentation and a final newline, so golden files pin the bytes:

  | Field | Value |
  | --- | --- |
  | `name` | `<pkg>` |
  | `version` | the author's `version`. A build with no `version` fails and names the field, as `--release` does. |
  | `description`, `keywords`, `homepage`, `bugs`, `license`, `author`, `repository` | copied as written from the author's `package.json`, each only when present |
  | `bin` | `{ "<name>": "bin/<name>" }` |
  | `files` | `["bin"]` |
  | `optionalDependencies` | each written platform package at the exact version, `"<pkg>-<platform>": "<version>"`, in the order of the six platforms above |
  | `publishConfig` | copied as written, only when present |

  The launcher carries no `dependencies`, `scripts`, `main`, `exports`, `type`, or `engines`. Its README and license files are the files npm always packs from the package directory, `README*`, `LICENSE*`, and `LICENCE*`, copied unchanged.

- **A platform package's `package.json`.** Its fields are written in the same way:

  | Field | Value |
  | --- | --- |
  | `name` | `<pkg>-<platform>` |
  | `version` | the author's `version` |
  | `description` | `The <platform> binary of <pkg>.` |
  | `license`, `repository` | copied as written, only when present |
  | `os` | `["darwin"]` or `["linux"]` |
  | `cpu` | `["arm64"]` or `["x64"]` |
  | `libc` | `["glibc"]` for a Linux platform without `-musl`, and `["musl"]` for one with it. A darwin package has no `libc`. |
  | `files` | `["bin"]` |
  | `preferUnplugged` | `true`, so Yarn Plug'n'Play extracts the binary to disk where it can run |
  | `publishConfig` | copied as written, only when present |

  A platform package has no `bin`, so the package manager links only the launcher onto `PATH`. It has no `dependencies` and no `scripts`. Its license files are copied as the launcher's are.

- **The launcher.** `bin/<name>` is a CommonJS file with the line `#!/usr/bin/env node`. Loom renders it, and it requires only Node's built-in modules, so the launcher package has no dependencies. It reads none of `process.stdin`, `process.stdout`, and `process.stderr`, and asks whether a descriptor is a terminal with `tty.isatty`, so Node leaves the three descriptors as the shell gave them. Before the binary runs, it writes nothing, a warning from Node included. When it runs, it does these steps in order:
  1. **The platform.** It reads `process.platform` and `process.arch`. On Linux it reads the C library the way core reads `host.libc`: `glibc` when the runtime's report, `process.report.getReport().header.glibcVersionRuntime`, names a glibc version, and `musl` otherwise. Where the runtime has `process.report.excludeNetwork`, it sets it to `true` before reading the report and restores the earlier value after, as core's process handle does, because Node otherwise resolves the peer of every open socket to fill the report. A musl Linux host appends `-musl`. A platform outside the written list, Windows included, fails and names the platforms the package supports.
  2. **The package.** It calls `require.resolve('<pkg>-<platform>/package.json')` from its own file, and the binary is `bin/<name>` in that file's directory. It then reads that `package.json` and requires its `name` to be `<pkg>-<platform>` and its `version` to be the launcher's own. A package that does not resolve fails, and so does one that resolves with another name or version, such as a copy of another version hoisted into an ancestor `node_modules` or found through `NODE_PATH`, so a launcher never runs a binary it was not built with. This happens, for example, after `npm install --omit=optional` or `--no-optional`, or on an older npm that skipped the dependency. The sentence names `<pkg>-<platform>@<version>` as the package to install beside `<pkg>`, and says to install `<pkg>` again without omitting optional dependencies.
  3. **The exec.** Where `process.execve` is a function, which Node provides on Linux and macOS from 22.15 and 23.11, the launcher calls `process.execve(<binary>, [<binary>, ...process.argv.slice(2)], process.env)`. The binary replaces the launcher in the same process: the same process ID, process group, terminal, working directory, environment, and descriptors. Every signal then reaches the binary alone, and the status the shell reads is the binary's own, a death by signal included, so no step below applies. The binary's own path is the executable, so core reads its release facts and ADR-0211 reads its path.
  4. **The spawn, on a Node without `process.execve`.** The launcher first adds its signal listeners, under **Signals**, so a signal that arrives while the child starts is held rather than ending the launcher. It then spawns the binary asynchronously, never with `spawnSync`, with `process.argv.slice(2)` as its arguments, inherited stdio, and the launcher's own environment and working directory, unchanged.
  5. **A binary that cannot start.** Before either path starts the binary, the launcher checks the file: it must exist, be a regular file, have execute permission, and start with a program's magic number, the four bytes of ELF (`7f 45 4c 46`) or of Mach-O (`cf fa ed fe`, `ce fa ed fe`, `ca fe ba be`, `fe ed fa ce`, or `fe ed fa cf`). A file that fails the last check fails with `ENOEXEC`, a shell script included, because a spawn would run it through `/bin/sh` and a failed exec ends Node before 26. A Node from 26 throws when the exec fails, and the launcher catches the error. A missing file, a directory, a file without execute permission, a file that is no program, a file inside an archive that Yarn Plug'n'Play left unextracted, and an exec or spawn error fail and name the binary's path and its package. One case stays outside the sentence: a binary with a valid magic number for another architecture, on the exec path of a Node before 26, ends Node with `SIGABRT` and Node's own report. The sentence names the cause from the error's `code` in Loom's words, under **The launcher's sentences**, and says to install `<pkg>-<platform>@<version>` again so its binary is an executable file on disk.
  6. **The end, on the spawn path.** When the child exits with a code, the launcher exits with that code. When a signal ends the child, the launcher removes its signal listeners and raises that signal on its own process, so it dies by the same signal and the shell reads the same status as if it had run the binary directly. Node starts every program with each signal's default action, so the raise ends the launcher. Three signals keep only the numeric status: Node opens its inspector on `SIGUSR1` and ignores `SIGPIPE` and `SIGXFSZ`, so for a child ended by one of them the launcher does not raise it and exits with 128 plus the signal's number, read from `os.constants.signals`. The shell reads the same `$?` as for a death by that signal, but a parent that tells an exit from a death by signal sees an exit. If the launcher is still running 100 ms after any other raise, it exits with the same status as a guard.

- **Signals, on the spawn path.** The launcher listens for `SIGINT`, `SIGTERM`, `SIGHUP`, and `SIGQUIT` from before the spawn until the child ends, so none of them ends the launcher first. It forwards each arrival to the child with `child.kill(signal)` under one rule. `SIGTERM` is always forwarded, because no terminal sends it. `SIGINT`, `SIGHUP`, and `SIGQUIT` are forwarded only when none of the launcher's stdin, stdout, and stderr is a terminal. When one of them is a terminal, Ctrl-C, Ctrl-\\, and a hangup reach the whole foreground process group, so they reach the child directly. A forwarded copy would reach the child as a second signal, which ends a Loom application's [shutdown](../core/signals.md#the-shutdown) at once, without its budget. In that case the launcher holds the signal and waits for the child. A second arrival of a forwarded signal is forwarded again, so a supervisor that escalates still reaches the child.

- **The limits of the spawn path.** Three cases stay wrong on a Node without `process.execve`, and the exec path has none of them:
  - **Ctrl-Z during a raw-mode prompt.** A raw-mode reader turns Ctrl-Z into `SIGTSTP` on its own process, under [Raw-mode readers](../core/signals.md#raw-mode-readers). The child stops, and the launcher, which the shell waits on, keeps running, so the shell gets no prompt back until the child is continued from another terminal.
  - **A signal sent to the process group.** `kill -TERM -<pgid>` reaches the launcher and the child. The launcher forwards its copy, so the child reads two `SIGTERM`s and its shutdown ends at once, without its budget.
  - **A terminal signal sent to the launcher alone.** When any of stdin, stdout, and stderr is a terminal, a `SIGINT`, `SIGHUP`, or `SIGQUIT` sent only to the launcher's process ID, such as `kill -HUP <pid>` or `docker kill -s HUP` on a container run with `-t`, is held and never reaches the binary. The child keeps running until it is signalled by process group or by `SIGTERM`.

- **Node versions.** Loom supports Node.js 22.23.2 and later. Every 22.x release from 22.23.2 and every release from 23.11 provides `process.execve` on Linux and macOS, so a launcher run under one of them takes the exec path. Node 23.0 through 23.10 lies inside the supported range and lacks the call, so a launcher run under it takes the spawn path, with the limits above. The launcher package declares no `engines`, so npm installs it under an older Node too, and the spawn path serves that Node the same way. The proof below runs both paths.

- **The launcher's sentences.** A failure the launcher raises prints one line to stderr that starts with `<name>: `, says what went wrong and what to do, under [ADR-0047](0047-an-operator-message-says-what-went-wrong-and-what-to-do-instead.md), and exits 1. The launcher is dependency-free CommonJS, so it cannot import a messages module at run time. Under [ADR-0164](0164-looms-operator-messages-live-in-message-modules-and-a-voice-test-per-package-reads-them.md), each sentence is a named export of `loom build`'s messages module, and `loom build` renders them into the launcher at build time:
  - **Build-time values.** The build calls each sentence's function with the values it knows, `<name>`, `<pkg>`, `<version>`, and the written platforms, which pass through `escapeControlCharacters` as every message's values do. Each value the build cannot know becomes a named placeholder, `{platform}`, `{path}`, or `{cause}`, which escaping leaves unchanged and which no package name or version can hold. The launcher holds the result as a string constant.
  - **Run-time values.** The launcher fills `{platform}` with the host's platform, such as `linux-riscv64`, and `{path}` with the binary's path, each escaped by a copy of core's `escapeControlCharacters` that the build renders into the launcher. A path that holds a line break therefore prints as `\u000a` on the one line.
  - **Causes.** The build renders a table from the error code to the cause's words from the bin's `systemCause`, for the codes an exec or spawn of an installed file meets: `ENOENT`, `ENOTDIR`, `EACCES`, `EPERM`, and `ENOEXEC`. `ENOEXEC` gains its own line in `systemCause`, `, because it is not a program this system can run`. Any other code fills `{cause}` as `systemCause` does for a code it does not name, the bare code in parentheses, escaped, and an error with no string code fills it with nothing. The launcher never reads an error's `message`, `stack`, or `cause`.

  The template the build renders the launcher from holds no sentence of its own, and the loom package's voice test reads the messages module as it reads every other.

- **Which targets produce packages.** Only the six release asset platforms produce packages. A `-baseline` or `-modern` x64 variant produces none, because it is not a release asset either. No Windows target produces one, because `loom build` offers none, under [ADR-0100](0100-acceptance-plans-live-beside-the-tests.md), and the installer script does not run on Windows either.

- **Publishing stays with the author.** `loom build --target npm` writes directories and publishes nothing. The author's workflow publishes each directory with `npm publish --provenance <directory>`. It publishes every platform package before the launcher, so a launcher on the registry never pins a version that is not there yet. A prerelease version publishes every package with `--tag <channel>`, where `<channel>` is the release channel core derives from the version, its first prerelease identifier, because npm 11 refuses to publish a prerelease without `--tag`, and so that `latest` keeps naming the newest stable release. The newest stable version publishes with no `--tag`. A stable backport, such as 1.4.3 published after 1.5.0, publishes with a tag of its own, such as `--tag v1-latest` or `--tag backport`, because npm 11 refuses to publish a version lower than `latest` without one, and `--tag latest` would move `latest` back to it. ADR-0211's refusal for `self-update --channel <channel>` names that tag. Each new name's bootstrap placeholder, `0.0.0`, publishes by hand under its own tag, `--tag bootstrap`. A registry may still set `latest` on a name's first publish, so the author checks `npm dist-tag ls` and deprecates the placeholder when `latest` names it. `npm install -g <pkg>` installs the application from the first stable release, which moves `latest`. The [build reference](../toolchain/build.md#publishing-the-packages) walks through the order, the tag, provenance, the trusted publisher of each package, and the bootstrap first publish of each new name.

- **The installation method.** The mode adds no record kind and writes no `install.json`. After `npm install -g <pkg>`, the binary runs from its platform package beneath npm's global root, `<prefix>/lib/node_modules/<pkg>/node_modules/<pkg>-<platform>/bin/<name>`, so ADR-0211's path rule reads the method `npm`, and the binary's baked `release.npmPackage` names `<pkg>`. An update notice and self-update's refusal name the launcher package, which the operator installed, and never the platform package. A launcher installed as a project dependency or run through `npx` derives no installation under ADR-0211.

- **The proof.** The implementation is held to these checks. Under ADR-0100, they become the plan beside the build tests that run them, and the [build reference](../toolchain/build.md) carries no acceptance list:
  1. **The packages.** A fixture application whose file sets `npm.launcher`, built with `loom build --target npm`, yields the expected directories and `package.json` files, compared with golden files. The fixture covers a scoped name, a `platforms` list, and a removed platform's stale directory. A file or a link named for a removed platform stays. A failed compile leaves the earlier directories byte for byte as they were, a move cut short leaves the earlier launcher, whose version check refuses each platform package already replaced, and an output directory that is or holds the package directory fails with code 2.
  2. **No key.** `--target npm` in a package whose file has no `npm` key, and in one whose `launcher` is `false`, fails with code 2 and the pinned sentence, and writes nothing under `<out>`.
  3. **Other targets.** A package with no `npm` key builds `--target node` and every compile target exactly as before.
  4. **The exec path.** The launcher, run through a Node that has `process.execve` on linux-x64, passes its arguments, stdio, environment, working directory, and the child's exit code through. The binary runs with the launcher's process ID, and stderr holds only the binary's bytes.
  5. **The spawn path.** The launcher, run through the same Node with `process.execve` removed before it loads, passes its arguments, stdio, and exit code through. With no terminal on any descriptor, a `SIGINT`, a `SIGTERM`, and a `SIGHUP` sent to the launcher's process ID each reach the child once, and the launcher then dies by that signal. With a pseudo-terminal on all three descriptors, and on each one alone, a `SIGINT`, `SIGHUP`, and `SIGQUIT` sent to the launcher's process ID are held and not forwarded. A child ended by `SIGUSR1`, `SIGPIPE`, or `SIGXFSZ` ends the launcher with 128 plus the signal's number, and the inspector does not open.
  6. **The shell loop.** Under a pseudo-terminal, `while true; do <name> wait; done`, where `wait` waits until cancelled, stops at the first Ctrl-C, on both paths, and the shell reads the status it reads for the bare binary's loop, 130 on Linux.
  7. **The npm global layout.** A binary that `--target npm` compiled, installed by `npm install -g` from the packed directories into a temporary prefix and run through its launcher, reads the installation method `npm` and `release.npmPackage` `<pkg>`, as the version plugin's extended output prints them.
  8. **An unsupported platform.** A launcher built for `platforms: ["darwin-arm64"]` and run on linux-x64 fails with exit 1 and the sentence that names `linux-x64` and the supported platforms.
  9. **A missing package.** With its platform package removed, or resolved at another version or name from an ancestor `node_modules` or `NODE_PATH`, the launcher fails with exit 1 and the sentence that names the package to install. With musl faked in the runtime's report, it runs the `-musl` package.
  10. **A binary that cannot start.** With the platform binary's execute permission removed, the launcher fails with exit 1 and the cannot-start sentence that names the path and the `EACCES` cause, on both paths, and so does a directory in its place. A shell script and a file that is no program fail with the `ENOEXEC` cause, on both paths. With the binary under a directory whose name holds a line break, the sentence prints the path escaped on one line.

## Considered options

- **A postinstall download, as older esbuild did.** The launcher package would run an install script that downloads the platform's binary from the GitHub Release or the registry. Rejected. `--ignore-scripts`, which security-minded operators and many CI systems set, leaves no binary. pnpm 10 and Bun skip dependency install scripts by default. An offline mirror or a registry proxy cannot serve a download that bypasses the package manager. The binary falls outside the lockfile's integrity check and npm's provenance. esbuild moved to optional dependencies for these reasons.
- **A single fat package that holds every binary.** One package would carry all six binaries, and the launcher would pick one. Rejected. Every install downloads six binaries to run one, which is tens of megabytes per platform for a Bun-compiled application, and each platform added grows every install.
- **The binary in the launcher package, one launcher per platform.** Each platform's build would publish the binary under the one launcher name, or under names chosen at install. Rejected. One name and version holds one tarball on npm, so the package manager cannot pick a platform's tarball by name and version. Distinct names are what `os`, `cpu`, and `libc` select among, and that is what platform packages are.
- **A separate command, such as `loom pack`.** Rejected. The build's job is the artifact, and the mode's artifact is the package set. `--target` already names what a build writes, and every build rule applies to the package set unchanged: the temporary directory, the move into place, cancellation, and `--out`.
- **Turning the mode on with `--target npm` alone, with no file key.** Rejected. Turning the mode on is a lasting fact about the package, and the platform list belongs with it. The file is the package's own record of how it ships to npm, and a CI run that forgets a flag must not publish a different shape.
- **The launcher replacing its own bin with the binary at install.** esbuild does this as an optimization, so later runs skip Node. Rejected. It needs an install script, which the first option rejects. It also breaks when the package manager links bins before scripts run or keeps the store read-only, as pnpm does.
- **Always spawning the binary as a child.** The draft of this record did. A child leaves the launcher between the shell and the binary, so job control, process-group signals, and the shell's status all pass through Node, and the two limits above hold on every run. `process.execve` removes the launcher from the process, so the binary behaves as if the shell had started it. The spawn path stays only for a Node that lacks the call.
- **Exiting with 128 plus the signal's number when a signal ends the child.** The draft of this record did. A shell reads a status of 130 from a program that exited and a death by `SIGINT` differently: Bash and Zsh stop a script's loop only for the death, so a loop that runs the application would carry on after Ctrl-C, against [The shutdown](../core/signals.md#the-shutdown)'s promise. Raising the signal on the launcher keeps it, and the exit code stays for the three signals Node reserves or ignores and as a guard for a launcher the raise does not end.
- **Forwarding every signal unconditionally.** Rejected. A terminal's Ctrl-C reaches both processes, so the child would read one keypress as two signals and skip its shutdown budget.
- **Musl detection by `ldd --version`, as the installer script does.** Rejected for the launcher. It starts a process on every launch. The runtime's report gives the same answer in-process, and core and `loom build`'s host target already read the C library that way. The installer script keeps `ldd`, because a shell has no runtime report.
- **Reading the package name from the platform package's name.** A launcher's name follows from a platform package's name by removing the platform suffix, so core could read it from the path. Rejected. That would be a second rule beside the baked `release.npmPackage`, and the two could disagree for a binary that reaches npm another way. The build already knows `<pkg>` and bakes it.
- **Sentences written into the launcher's template.** The launcher could carry its sentences as literal text. Rejected. ADR-0164 keeps every operator sentence in a messages module that the voice test reads, and the build already holds the module, so rendering from it costs nothing at run time.

## Consequences

An author ships a binary through npm with one file key and one build call. The author also gains N more package names to own and to publish in order. Each name needs a bootstrap publish and a trusted publisher card once, and so does each platform added later, before the release that first carries it.

A package manager that does not honour `libc` installs both the glibc and musl packages for one architecture on Linux, and the launcher still picks the right one. A Yarn Plug'n'Play install extracts each platform package because of `preferUnplugged`.

On a supported Node, the launcher adds the start-up time of Node and one `require.resolve` before the exec, and nothing after it: the binary is the process. On an older Node, the launcher stays as the binary's parent for the whole run, with the limits the spawn path names. Operators who need the bare binary install it with the installer script.

A prerelease published under its channel's tag leaves `npm install -g <pkg>` on the newest stable version, and an operator follows a prerelease channel with `npm install -g <pkg>@<channel>`.

## Status

Proposed. It moves to accepted in the release PR of the release that ships it.
