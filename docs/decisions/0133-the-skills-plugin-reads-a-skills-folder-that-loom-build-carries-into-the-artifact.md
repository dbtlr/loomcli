# ADR-0133 - The skills plugin reads a skills folder that loom build carries into the artifact

## Context

[ADR-0076](0076-the-skills-plugin-installs-an-applications-agent-skills-for-claude-and-the-shared-agents-folder.md) hands the skills plugin each skill as a name and a loader of its files, and documents a root `skills/<name>/` folder read through text imports. Every application that ships a skill writes that loader by hand: Mimir imports ten files one by one, and a new reference file reaches the binary only when someone adds its import. Text imports are Bun's, so a Node source run and a test under a Node worker cannot read them at all. ADR-0076 rejected the alternative, a `skills/` folder that `loom build` embeds, because development runs and tests never pass through the build, so the plugin would need a second path that reads the folder from disk, and the build would gain a file-embedding seam for one plugin.

The owner directed that the build read operator skills in 0.17.0 ([ADR-0130](0130-the-loom-toolchain-reads-loom-config-json-from-the-package-directory-and-every-path-it-owns-is-a-key.md) reserved `paths.skills` for it), and ruled on the shape: a source run and a test install the skills too ("Why would it not work in development for testing the skill? Why impose this limitation?"), and the author names the folder in the declaration and nothing else ("The author should just provide a relative path OR a URL path and we should do the rest").

Each way an application runs knows a different place for the folder. A source run and a test, under Node or Bun, resolve `new URL('../skills/', import.meta.url)` against the module that wrote it. A bundle keeps that expression as it is, so it resolves against the bundle's chunk. A compiled binary's `import.meta.url` is inside Bun's embedded file system, which holds only what `bun build --compile --asset` embedded. Core keeps a plugin's settings to itself and the built graph names no plugin, so nothing outside the application can ask an Application which folder its skills plugin was given. `loom init` already imports the application module under Bun in a process of its own to learn its exports.

## Decision

- **A folder setting.** `skills()` takes `folder`, a `file:` URL or a path, beside `skills`, the list of named loaders ADR-0076 defines. A string that starts with `file:` reads as that URL. Either setting may be left out, and a call with neither is a settings fault at the call; an empty list with no folder declares no skill, as it did before. Each directory directly inside the folder is one skill, named for the directory, and so is a symbolic link there that names a directory, read through the link. An entry whose name starts with `.`, directly inside the folder or at any depth inside a skill, is skipped by its name before it is read, whether it is a file, a directory, or a symbolic link, so a `.DS_Store` or an editor's lock link never reaches an operator and is never a fault. A skill holds every other file below its directory, at its path relative to the skill's directory, executable when its mode has an execute bit, and a symbolic link to a file reads as that file. Directly inside the folder, a file or a symbolic link to one is ignored, so a `README.md` beside the skills does not count; a symbolic link there that names nothing is a fault. The bundle and the binary carry the folder as `loom-skills/`, a name no application's binary takes. A skill directory whose name is not a skill name, a symbolic link inside a skill that names a directory or nothing, an entry that is neither a file nor a directory, a folder that holds no skill when the list is empty, and a folder skill that holds a listed skill's name are faults. A folder skill's name and files meet the rules ADR-0076 sets for a loader's; a folder skill's name is judged when its files load and at the build, not at the call, because only the folder knows it.
- **The plugin reads the folder when a skills Command loads files.** `install` and `update` read and judge the folder at the point they call loaders, so every other run reads nothing and a fault never removes an installed skill. An unbuilt run reads the folder a URL or an absolute path names. A relative path resolves against the application module, which only `loom build` knows, so an unbuilt run whose setting is a relative path fails and says to name the folder with a URL resolved against the module that calls `skills()`. A folder that does not exist fails and names its path.
- **The build learns the folder from the declaration.** Before it bundles, for every target, `loom build` loads the application module, `--application` or `paths.application` for a bundle and `paths.application` for a compile target, under Bun in a process of its own, as `loom init` reads it, and reads the folder that `skills()` was given while the module loaded. `skills()` records each call in a registry keyed by a global symbol, which the build's process reads after the import, and each entry resolves its call's folder against the module's directory and reads and judges it, so the rule that reads the setting lives in the plugin alone; the registry is a channel between `@loomcli/plugins` and `@loomcli/loom`, which publish at one version, it carries a format number, and no export names it; a registry, define, or index whose format the reader does not know fails the build or the run, names both packages, and says to install them at one version. The build reads the registry alone and applies none of init's checks of the module's exports. A relative path resolves against that module's directory. The build reads and judges the folder as the plugin does and fails before it bundles on any fault, naming the folder, so a bad skill fails the build rather than an operator's install. Two calls that each name a folder fail the build. The build does not load a module that is also the entry, which would run the application.
- **A build that cannot read the declaration warns.** When the package does not resolve `@loomcli/plugins`, has no application module, or its application module is the entry, the build reads nothing, and when the module loads but `skills()` does not run while it loads, as when a function the entry calls makes the Application, the build learns no folder. When the bundle it then makes holds the skills plugin, as Bun's module list for the build shows, the build warns that it carried no skills folder, says which of the two happened, and names `paths.application`, and the build succeeds, because the plugin may have been given only loaders. A `skills()` call that ran and named no folder gives no warning.
- **What the artifact carries.** The build bakes a second define, `__LOOM_SKILLS__`, which the skills plugin alone reads and which carries a format number:
  - **A development build** names the source folder by its absolute path, with nothing copied, so a skill edited during `--watch` installs as it now stands, read and judged when it loads.
  - **A distributed bundle** writes the judged files, links followed, into `loom-skills/` in the output directory, beside the chunks, replacing that folder whole so a skill the source dropped leaves the output, with an index, `loom-skills/index.json`, that carries a format number and names each skill's files with their executable bits. A skill name holds no `.`, so no skill takes the index's name. The define says only that the build carried a copy, so no file and no file name passes through it.
  - **A distributed binary** embeds the same staged copy, index included, with `--asset`, so the files read inside the binary at `loom-skills/` beside the program through the runtime's file functions, and the index names their executable bits, because an embedded file keeps no mode.
  - **A build that read nothing** says so, and **a build that read the module but found no folder**, because no call named one or `skills()` did not run, says that, and a run of either whose setting names a folder fails and says which, naming `paths.application`.

  A run with no `__LOOM_SKILLS__`, an unbuilt run or a custom build, reads the setting as an unbuilt run does; when such a run is built, by its release facts, and the folder is missing, the failure says the build carried no skills folder. The plugin reads every form through `node:fs`, under Node and Bun alike, so the second path ADR-0076 feared is one reader with a different base folder. `loom build --define` and `--facts` keep printing the release facts alone, so a custom build carries no folder.
- **The build never writes into the source folder.** Every bundle build that carries no copy, a development build or one that read no folder, removes `loom-skills/` from the output directory, so no stale copy outlives the folder that made it. A bundle, development or distributed, whose `loom-skills/` would be the skills folder, inside it, or hold it, as `--out skills` does in a package whose folder is `skills/`, fails before it builds.
- **`paths.skills` leaves the configuration file.** The folder is named once, in the declaration, so ADR-0130's `skills` key is removed before it ships, and `loom.config.json` names no skills folder.
- **The managed changelog skill is not an operator skill.** `.agents/skills/loom-changelog/` teaches the author's agent, and nothing here reads it.

## Considered options

- **Unbuilt runs carry no folder skills, as they carry no release facts.** Rejected by the owner: a skill is tested in development, and a run that cannot install it from source imposes a limitation nothing requires.
- **A helper the author calls to read the folder.** Rejected by the owner: the setting takes the folder and Loom does the rest.
- **A relative path against the working directory.** Rejected. A test runner in a monorepo runs from the repository's root, so the path would read a different folder there. The owner chose the application module as the base, which reads the way the URL does.
- **The folder in `loom.config.json` and in the declaration.** Rejected. The two can disagree in exactly the monorepo case the key existed for, and nothing short of loading the module could see it, so development would read one folder while the binary carried another.
- **The plugin reading `loom.config.json` in an unbuilt run.** Rejected. It would make `@loomcli/plugins` parse the toolchain's file, against [ADR-0131](0131-the-post-install-declaration-moves-from-the-application-into-loom-config-json.md)'s rule that a fact only the toolchain reads lives in the toolchain's file.
- **The folder as a graph fact.** Rejected. The graph describes the built product, under [ADR-0010](0010-one-graph-serves-runtime-and-projections.md), and a folder on the build machine is where it came from; the manifest would print an author's path.
- **The file contents or the file names in the define.** Rejected. A define passes through one command-line argument, which Linux limits to 128 KiB, so a skill with large references, or a folder of a few thousand files, would fail to build.
- **A Bun bundler plugin that serves the files as a virtual module.** Rejected. `bun build --watch` runs through the command line, which takes no plugin, and one `node:fs` reader serves every form without a module the bundler invents.

## Consequences

`loom build` loads the application module for every build of a package that resolves `@loomcli/plugins`, so every build pays for one Bun process that imports the module, and a module that throws while it loads fails the build with the toolchain's load failure. A change to the `folder` setting during `--watch` takes a restart, and a change inside a development build's folder does not. An author who builds with Bun directly carries no folder and names the files through a loader, and so does a skill that means to carry a file whose name starts with `.`, such as `.env`, which the folder skips. ADR-0076's loader stays the way to supply generated or computed files, which the generated command references planned for 0.20.0 can extend. The skills plugin no longer acts from every build alike: a source run whose setting is a relative path cannot read its folder. ADR-0076 and ADR-0130 carry dated entries.

## Status

Proposed. It moves to accepted in the release PR of the release that ships the skills folder.
