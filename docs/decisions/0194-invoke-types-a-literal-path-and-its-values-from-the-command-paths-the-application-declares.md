# ADR-0194 - invoke types a literal path and its values from the Command paths the Application declares

## Context

[ADR-0059](0059-a-command-runs-by-name-through-invoke.md) typed `invoke`'s values loosely and left its path untyped: `invoke(['gte'], { options: { flie: 'x' } })` compiles and fails at run time with an `UnknownCommandError` or an `UnknownOptionError`. Principle 7 puts a mistake a type can express in the type. A `Command` value held its arguments, options, and globals at the type level, but not its name or its children, so nothing could say which paths an Application declares or what each Command's values take. The contract settled on 2026-11-18: new type parameters on Command and Application collect a path-keyed map of each declared Command's argument and option types; a literal path the Application declares types its values against that Command, every global option included; a plain `readonly string[]` keeps the dynamic form for MCP and graph-driven callers; canonical names only; a depth cap of four; and an editor-latency gate on textstat and a 50-Command fixture. The owner confirmed two further rulings on 2026-11-19: typed paths ship as a breaking change with a migration, because existing calls that name an undeclared input or an option an attach hook adds no longer compile (LM-q78); and an action's `invoke` reads the registered paths only if hover with paths registered stays within the +20% gate, and otherwise stays dynamic (LM-q79).

## Decision

- **Command paths.** A Command carries its entry under its canonical name, a literal type when the name is written as one: the value an invocation by name may supply for each argument and local option, by declared name, and each child's entry, by canonical name. `argument()`, `option()`, and `options()` add to it, and `command()` joins the child's entry to the parent's. The Application carries the root's entry, its global options and each installed plugin's joined. `PathsOf<typeof app>` reads it, and `CommandPaths` names one entry's shape.
- **The value an input takes is what lowering accepts, not what the action reads.** The entry holds the input side, read from each declaration's configuration: a string or a number on a string option or a scalar argument, a list of them on a multiple option or a variadic argument, `true` as well on an option with an implied value, a Boolean on a Boolean option, a count on a counted option, and a list of words on an arity option, whose length the run checks. A validator's output type never reaches it, because a validator receives the token, so an option whose validator transforms `'debug'` to `'DEBUG'` still takes `'debug'`.
- **One signature, a conditional over the path.** `invoke` is one generic signature whose path and values parameters are conditional types over the inferred path, rather than a stack of overloads. A literal path is checked one name at a time, and a name its level does not declare is replaced in the expected type by the names it does, so the error reads `Type '"gte"' is not assignable to type '"get" | "remote"'` at that element. Overloads would let a mistyped literal fall through to the dynamic overload and compile, or report `No overload matches this call` over both forms, so the conditional gives the clearer error principle 5 asks for.
- **Typed values.** The values of a literal path are the routed Command's arguments and local options and every global option, each optional. An undeclared name is an excess property and a wrongly typed value a type error. Required inputs stay optional in the type, because an input source may supply an option and a missing argument is the run's missing-input problem. `passthrough` is accepted on every path. An option a plugin's `onCommandAttach` hook adds, such as the formatter's `--format` and `--fields` on every Command with a result, is in no declaration's type, so a literal path rejects it: a call selects the view with `view`, or passes its path dynamically. Typing such options would need each hook to state its additions at the type level, which no hook does.
- **The dynamic form.** A path typed as an array, or as a tuple with an element typed as the wide `string`, takes `InvocationValues`. So do a path deeper than four Commands, a path through a Command whose name is typed as the wide `string`, from its level on, and on an Application that installs any plugin a first name it does not declare, because a plugin may contribute Commands at the root that no type names. An alias routes at run time, so a literal path checked against canonical names takes canonical names alone, and a call that names an alias passes its path dynamically. A union of literal paths, such as a conditional's two branches, names no one Command whose values could type the call, so it is dynamic too, and so is a call with an explicit `Mapped`, which leaves the path at its default.
- **An action's `invoke` reads the registration.** A Command declared in its own module cannot name its Application, so `ActionContext['invoke']` reads `Register.paths`, which the Application registers as `PathsOf<typeof app>` beside `Register.environment`, and is dynamic where none is registered. The paths are read only inside an action's body, never in a declaration's type, so registering the completed Application creates no circular dependency, unlike the environment. The context's `invoke` is a non-generic interface that names the registered paths only in its base type, which TypeScript resolves when a call reads it, so an action resolves the completed Application's type only at a typed `invoke` call, never elsewhere in its body or at its declaration.
- **Nothing changes at run time.** The typing narrows what a call compiles with. Routing, lowering, and every failure a call that compiles can meet are ADR-0059's.

## Considered options

- **Two overloads, a typed one and a dynamic one.** Rejected. A literal path that names no declared Command would match the dynamic overload, so the mistake the contract targets would still compile, or the dynamic overload would need its own rejection of literal paths, whose error lists both overloads.
- **Typing the values from the action's own types.** Rejected. An action reads each value after its validator, and a call supplies it before, so a transforming validator would type the call against the wrong side.
- **Rejecting an undeclared first name on an Application with plugins.** Rejected. A plugin's Commands attach at the root with no type that names them, so this would reject a valid call such as `invoke(['completion'], …)`; the Commands the Application declares stay typed.
- **Typing the plugin's Commands too.** Out of scope: a `Plugin` carries its options at the type level but not its Commands, and changing that reaches every first-party plugin's factory type.

## Consequences

- An Application's type and a Command's type carry their Command paths, so two Applications that declare different Commands have different types, as two Commands with different names do. A variable or a parameter that holds either takes the `Application` or `Command` annotation, whose paths are unstated and whose calls are dynamic.
- A call that passes a literal path with values typed as `InvocationValues`, or with a name the routed Command does not declare, no longer compiles; it passes its path as a `readonly string[]`.
- Hover and completion at a typed `invoke` call resolve the completed Application's type, as at a typed `app.invoke` call; elsewhere in an action, registration costs nothing measurable.
- A call that names an option a plugin's attach hook adds, such as `format: 'json'`, on a literal path no longer compiles; it passes `view`, or its path as a `readonly string[]`.
- [ADR-0059](0059-a-command-runs-by-name-through-invoke.md)'s **Values mirror the action context**, which types the values loosely and leaves the path untyped, is superseded in part: the dynamic form keeps those values, and a literal path types them. ADR-0059 carries a dated entry.
- The reference amends with it: [Typed paths](../core/invocation.md#typed-paths), [Modular authoring](../core/commands.md#modular-authoring), and the glossary's **Application registration** and **Command paths**.

- 2026-11-19: Proposed and implemented (LM-399). Measured with `scripts/measure-editor-latency.mjs`, seven runs each before and after on one shared host, medians: on textstat's action, warm hover 386 ms before and 181 ms after, warm completion 5.0 and 1.9 ms, instantiations 268,912 and 270,800; on a 51-Command fixture, at an action, warm hover 20.7 and 17.3 ms and warm completion 3.2 and 1.5 ms, at a typed `app.invoke` call's values, warm hover 232 and 263 ms and warm completion 4.3 and 1.4 ms, and instantiations 104,547 and 172,934, 1.65 times. With the fixture's paths registered, in `packages/core/tests/type-consumer/fifty-registered`, which is the fixture with `Register.paths` added, medians of seven runs against the unregistered fixture in the same session: warm hover at an action that calls `invoke` 9.4 ms registered and 16.4 ms unregistered, and at an action that does not 27.8 and 24.9 ms; warm completion 1.0 and 2.3 ms, and 1.7 and 1.7 ms. Both registered action sites are within the +20% gate the owner confirmed on 2026-11-19 (LM-q79). Before the context's `invoke` became an interface that defers the registration, the first site measured 158 ms registered against 17.2 ms. At the typed `invoke` call inside the action, warm hover is 251 ms registered against 42 ms for the same call unregistered, which is dynamic: that is the cost of resolving the Application's type, which a typed `app.invoke` call pays as well.
