# ADR-0164 - Loom's operator messages live in message modules, and a voice test per package reads them

## Context

[ADR-0047](0047-an-operator-message-says-what-went-wrong-and-what-to-do-instead.md) states the voice every operator message Loom ships follows, in [Failure message voice](../core/failures.md#failure-message-voice). Nothing holds a sentence to it except review, and review reads a sentence only where it was written. Core builds its sentences as template literals in about 20 failure classes in `packages/core/src/failures/errors.ts`, and inline in `inputs/validation.ts`, `inputs/missing-input.ts`, `inputs/option-groups.ts`, `inputs/content.ts`, `invocation/lower.ts`, `output/lanes.ts`, and `failures/form.ts`. `commands/command.ts` raises only Developer Diagnostics and defects, and writes the `-v` line validation builds. The plugins write theirs inline across about 14 files, though six plugins (completion, man pages, MCP, self-update, service, and skills) already keep most of theirs in a `messages.ts` that groups them into objects such as `lines` and `refusals`. `@loomcli/prompts` and the `loom` bin write theirs inline in a few more files. `packages/validators/src/codes.ts` is already one catalog, but its sentences are members of the public issue-code descriptors under [ADR-0048](0048-a-validator-package-declares-one-issue-code-per-sentence.md).

Three of the voice's rules are mechanical enough for a test to hold. Rule 5 asks that every repeated value is escaped, rule 6 that no message quotes text Loom did not write, and the [glossary](../glossary.md) names words a sentence avoids. A test can read them only where the sentences are gathered, and gathered sentences also let a reviewer read one module's voice in one place.

ADR-0047 rejected "a lint or a runtime check on message text", because no check can tell whether a sentence states a fix, and because an application's messages are its own. Both reasons hold for what that record weighed. A test of Loom's own repository checks no application's text, and it holds only the mechanical rules, so rule 2 stays with review. This record narrows that rejection rather than superseding it.

The owner settled the shape in grooming (LM-352): one `messages.ts` per concept module, the four kinds of sentence that move, no operator byte changed, one voice test per package with four checks and pinned exceptions, the banned-word table on the voice page, internal modules, no localization, and a small launch cost, measured below.

## Decision

- **Message modules.** A Loom package keeps the operator messages one concept module's code raises or writes in one `messages.ts` beside that code, such as `packages/core/src/failures/messages.ts`, `packages/core/src/inputs/messages.ts`, and `packages/plugins/src/config/messages.ts`. A concept module is a folder directly under the package's `src`. A package whose `src` has no folders, such as `@loomcli/prompts`, `@loomcli/validators`, and `@loom/mcp`, keeps one at `src/messages.ts`. In `@loomcli/plugins`, each plugin keeps its own in its folder, and the files at the top of `src`, which several plugins share, keep theirs in `src/messages.ts`. In the `loom` bin, each command's folder under `src/commands` is a concept module: `src/commands/<command>/messages.ts` holds that command's sentences, with those of the helpers under `src/helpers` that do its work, so they load only on a route that reaches that work. A helper that serves more than one command keeps its sentences with the command whose work it does, such as the fragment reader's with `loom changelog`, and another command's route that calls it, such as `loom pr check`, loads that module too. A launch loads every command declaration and no command's work, as `packages/loom/tests/application.test.ts` pins, so the issues the declarations' validators report, the sentences of the helpers a declaration imports, and the package-directory helper's one sentence, `noPackageJson`, which build and changelog share, live in `src/helpers/messages.ts`, the one message module every launch loads, which holds no other sentence. The same test fails when a launch that routes to no command's work loads a command's message module. Each sentence is a named export: a function of the values it repeats, or a constant when it takes none. A message function returns the sentence as a string. It constructs no failure and writes nothing: the code that raises the failure or writes the line calls it. The six plugin message modules that group their sentences into objects export each sentence by its own name instead.
- **What moves.** Four kinds of sentence move into message modules: a failure's sentence; a hint line a plugin adds under a failure through `onFailure`; a line written at `-v` or `-vv`, through `out.debug` or `out.trace`; and a notice, a warning, or a confirmation a plugin or the `loom` bin prints. A failure's sentence includes each part of it Loom writes: an issue Loom's own code reports, such as a content input's `Expected piped or redirected stdin.` or the issue of a value an invocation by name cannot lower, the line a question shows under an answer it rejects, and the error text an MCP server returns to its client. Core's one warning line, the line of a result sequence that stopped early, moves with them. Fixed labels stay where they are: help headings, the `repeatable` fact, the key hints under a question, and table and record labels. Developer Diagnostics, which address the author, do not move: a rule's headline and explanation stay in its rules registry, and a fault's sentence and correction stay where the code that raises it writes them. A log event's message, which a logging plugin records, is not an operator message under ADR-0047 and does not move.
- **No byte changes.** A sentence prints exactly as it did, and no existing test's expected string changes. The one exception is a sentence one of the four checks shows to be wrong, such as a repeated value that is not escaped. That sentence is fixed, and the change carries a fix fragment under `.changes/` that says the change happened without naming each changed sentence, so the changelog is not specific about the different sentences. A change with no changed sentence carries no fragment.
- **One voice test per package.** Each package whose sentences reach an operator holds one voice test, `tests/message-voice.test.ts`, beside its other tests: `@loomcli/core`, `@loomcli/plugins`, `@loomcli/validators`, `@loomcli/prompts`, `@loomcli/loom`, and `@loom/mcp`, whose protocol errors `@loomcli/plugins` ships to an MCP client. `@loom/json`, `@loomcli/testing`, and `@loomcli/eslint-plugin` hold none, because none writes an operator message. A voice test reads only its package's message modules, the files named `messages.ts` under its `src`, plus one plain text scan of the package's other `.ts` files under `src` for the gathering check. It builds no type-checked program and imports no TypeScript compiler. The four checks share one reader, `scripts/test-voice.ts`, as the tests share `scripts/test-process.ts`. Each voice test reads the banned words from [Failure message voice](../core/failures.md#banned-words), so each carries the `docs` module tag.
- **The reader.** The reader of a message module is a small scanner of its own. It reads comments, string literals, and template literals, nested `${...}` and nested templates included, and it knows each module-level declaration's parameter list. A message module holds functions, constants, imports, and types, with no regular-expression literal and no division, so every `/` outside a literal opens a comment. The reader refuses a module where one does not, and the test fails on it, so the reader never has to tell a pattern from a quotient in a message module. The gathering scan reads the package's other files with the same scanner, where a `/` that opens no comment is a division after a value, such as a name, a number, or a closing bracket, and a pattern after anything else, as a JavaScript parser reads it.
- **Banned words.** No string or template literal in a message module contains a word the [banned-word table](../core/failures.md#banned-words) lists in its "Do not write" column. A word matches without regard to case at the start of a word, so `presentation` also matches `Presentations` and `presentational`. The table's only entry is `presentation`, whose "Write" column reads "view, formatter, or request, whichever is meant".
- **Rule 5, escape what is repeated.** Every `${...}` in a message module's template literals is one of three forms. The first is a call to an escaping helper, core's `quoted(...)` or `escapeControlCharacters(...)`, whatever its argument holds, so a template inside the call is escaped whole. A style's `escape(...)` alone is not one, because it escapes Loom's markup delimiters and no control character; a style's `escape(...)` whose argument is a call to an escaping helper is, because a line an out call writes needs both escapes. The second is a call to another message function: a function the module declares, or binds with `const` to a function or to an escaping helper, or one it imports from another message module of its package. The third is a value typed as a number: an identifier, bare or as the argument of `String(...)`, that the module-level function holding the interpolation declares as a parameter of type `number`, or destructures from a parameter whose inline object type declares that member as `number`. The reader reads a conditional expression's two branches by the same rule, and a string literal, or a template literal whose own interpolations pass, repeats no value. A called message function's own interpolations are checked where it is declared, so a helper with no template literal of its own, such as `const shown = escapeControlCharacters`, passes, and review judges what it returns. An issue's sentence, which core and the configuration plugin repeat after an input's name as its validator wrote it under [Issues and validator failures](../core/validation.md#issues-and-validator-failures), is the known exception the rule has by design: the calling code reads the issue's `message` and passes it to the message function as a parameter, and its interpolation is pinned with that reason, so a multi-line issue prints as before.
- **Rule 6, quote no outside text.** The check reads message modules only. No message module reads a member named `message`, `stack`, or `cause`, by a dot, an optional chain, or a bracket with a string literal, so a message function takes the facts its sentence names, never the error that carried them. The check cannot see what a caller passes in: code outside a message module that reads an error's text and hands it to a message function as a value passes the check, because a parameter holds whatever its caller passes. The `loom` bin's sentences that repeat such text are listed under Scope.
- **Gathering.** Outside a message module, no failure constructor and no out call is handed a literal sentence. A failure constructor is a `new` expression whose class name ends in `Error` and is not one of JavaScript's own error classes (`Error`, `AggregateError`, `EvalError`, `RangeError`, `ReferenceError`, `SyntaxError`, `TypeError`, and `URIError`), a `super(...)` call inside a class that extends a class whose name ends in `Error`, and an assignment to a member named `message`. An out call is a call of a member named `print`, `info`, `success`, `warn`, `error`, `debug`, `trace`, or `fatal` on any receiver except a style (a receiver named `style` or ending in `Style`) and the log (`log`). A literal sentence is a string or template literal outside any bracket of the call's arguments, or of the assigned value, whose literal text, or that of a literal inside its interpolations, holds a space; a conditional's branches and a fallback after `??` are outside any bracket. A literal inside an object argument, such as a Developer Diagnostic's `correction`, is not one, nor is a literal inside a nested call, and neither is a failure's kind, such as the `'insecure'` of `new RequestError('insecure', url)`. The scan skips comment blocks and comment lines, so a doc comment's example never counts.
- **A package's own routes.** A package whose sentences reach an operator by a route of its own names that route in its voice test, as a value of the `VoiceSinks` type `scripts/test-voice.ts` exports, and gathering reads it as it reads a failure constructor: a call of a named function, such as the `text(...)` that builds the content of a tool execution error the MCP plugin's server returns, or self-update's `fatal(...)` and `conflict(...)` and the skills plugin's `directoryProblem(...)`, which each wrap a sentence in a failure; a call of a named member on a named receiver, such as the `run.line(...)` that writes each line `loom init` prints for a file it writes; a `return` inside the arguments of a call of a named function, and a concise arrow body that is itself one of those arguments, such as the `loom` bin's `report(...)`, which prints what a command's work returns, its confirmation included; a `return` and a concise arrow body inside a function declared with a name the test lists, whose returned text such a call prints; an assignment to a named variable or member, such as the issue line `@loomcli/prompts` assigns to a question; a named member of an object literal, such as the `message` of a validators issue-code descriptor; and a named error class counted as a failure constructor, such as JavaScript's own `Error` in the `loom` bin, whose `report()` prints a thrown error's message through `out.fatal`. Gathering reads only the routes a package's voice test names, so a sentence built in a helper those routes do not name is judged in review. The `loom` bin names the helpers whose returned text `report(...)` prints, `stableNotes`, `prereleaseNotes`, `packageNotes`, `recordRelease`, `renderPlan`, and `cutSummary`, and `lines.push(...)`, the call that collects each line of a release record, which is the route the lines of `readUpload` take. The changelog section `loom release cut` prints, which `renderSection` builds around the fragments' own prose, and the facts and `--define` pair of `loom build`, are data and a document, not a sentence the bin words, and no route names them.
- **Known exceptions.** A site that breaks a check and is right is pinned in that package's voice test, per check and per file, by the site's source text and the count of sites in the file that have it, with the reason it holds, as `packages/core/tests/assertions.test.ts` pins each surviving type assertion by its count per file. A site's source text is the literal for the banned words and gathering, as written with its quotes, the whole `${...}` for rule 5, and the member read, such as `error.message`, for rule 6. Every site no pin covers fails the test, and so does a pin whose count differs from the sites found, so a new site with the text of a pinned one fails as well, and a pin that covers no site fails, so the table shrinks as the sentences improve. The pins of one package are one value of this type, which `scripts/test-voice.ts` declares and exports:

  ```ts
  /** One of the four checks a voice test holds over a package's sources. */
  type VoiceCheck = 'banned-words' | 'escaping' | 'gathering' | 'outside-text';

  /** One known exception: the reason it holds, and how many sites in the file have its text. */
  interface VoicePin {
    readonly reason: string;
    readonly sites: number;
  }

  /**
   * A package's known exceptions: for each check, the files under the package's `src` that hold
   * one, by path under `src`, and in each file the source text of each excepted site with its pin.
   */
  type VoiceExceptions = {
    readonly [check in VoiceCheck]?: Readonly<Record<string, Readonly<Record<string, VoicePin>>>>;
  };
  ```

- **Each check fails on a bad sentence.** The reader's own test, `packages/core/tests/voice-reader.test.ts`, runs each of the four checks over a bad sentence written for it, a module text with a banned word, an unescaped interpolation, a read of `error.message`, and a source file that hands `new InputError` a literal sentence, and shows each check report it.
- **Internal.** A message module is internal. No package entry point exports one, and the API reports do not change. A plugin's message module belongs to its subpath, and no subpath imports a sibling's, under the [plugin pack's](../plugins/README.md) rule.
- **Not localization.** A message module is plain functions. Loom adds no locale provider, no message keys, no lookup indirection, and no extension point, and an author rewords a Loom sentence as before, through a view override.
- **A small launch cost, in bytes and no measurable time.** A message module imports only what its sentences call, escaping and text helpers and other message modules of its package, and types. A message module adds no import to a launch path that did not have it: a plugin's entry that loads its message module for a hint line loads no middleware, no Node built-in, and no other library through it. A launch of the `loom` bin loads `src/helpers/messages.ts` and no command's message module. A launch does newly load message modules, each a named function per sentence beside the caller that now calls it. `loom --help` newly loads the message modules of core and `@loomcli/validators`, the help plugin's, and `src/helpers/messages.ts`. An application's launch newly loads core's and the validators' and the message modules of the plugins it installs: the built `examples/textstat` application's `--help` loads those of the configuration, format, help, and suggestions plugins and the pack's shared `src/messages.ts`. So a launch reads about 9 KB more than it did without them: 9,130 bytes more for `loom --help` and 9,629 more for the built `examples/textstat` application's `--help`, as the 2026-11-16 entry measured them with the totals of that day. The bundles hold no comments, so those bytes are the modules' own code. The time that costs is below what the machine's noise shows: see the 2026-11-16 entry for the measured launch times. Every sentence in `src/helpers/messages.ts` was on the launch path already, held inline, except `noPackageJson`, the package-directory helper's one sentence, which a launch now loads because the command declarations import that helper.
- **The application readers.** The `loom` bin's two application-reading scripts, `dist/read-application.js` and `dist/read-skills.js`, each bundle only their own two modules and no copy of core, as `packages/loom/tests/readers.test.ts` pins. They return what they found as facts in the result file they write, and the `loom` process words each through its own message module, so each script still bundles only its own modules. A Developer Diagnostic the package's own core formats still passes through as it does today.
- **The validators catalog.** `packages/validators/src/codes.ts` keeps its name and its issue-code descriptors, which the package's root export publishes under [ADR-0048](0048-a-validator-package-declares-one-issue-code-per-sentence.md). Because they are public, `codes.ts` is not a message module. Each descriptor's `message` calls a sentence of the internal `packages/validators/src/messages.ts`, as each public failure class in core's `failures/errors.ts` calls one of `failures/messages.ts`. A descriptor whose sentence is the author's own, such as `text-pattern`'s `message` parameter, passes it through unchanged.
- **Review.** The voice test holds the banned words, rule 5, rule 6, and gathering. Rules 2, 3, and 4 need judgment, whether a sentence states its fix, depends on a plugin, or repeats a secret, so review judges them.
- **Scope.** The voice's rules bind `@loomcli/prompts` and the `loom` bin as they bind core, `@loomcli/plugins`, and `@loomcli/validators`, which ADR-0047's Two parts and No leaks clauses each name, except that how far rule 6 binds the `loom` bin is an open question, which the changelog's dated entry records. `@loom/mcp` ships inside `@loomcli/plugins`, so the plugins' binding covers it. Today the bin quotes text it did not write in two ways, both as it did before this change:
  - **Another program's output, and an author's module error, whole.** Nine sentences repeat text whole as `output`, unescaped and with its lines, most of it another program's, and the bin's voice test pins each site per file with the reason it holds. `gitFailed` repeats git's stderr. `bunCouldNotRead` repeats Bun's report of reading the author's application module, which carries the error the module threw, and `bunBuildFailed` Bun's build output. `skillsFolderJudged` repeats the plugin pack's judging of a skills folder. `skillMissing` repeats the bin's sentence about the file, which may repeat git's report, `skillInvalidYaml` the YAML parser's report, and `skillVersionUnset` the bin's own sentence about the frontmatter. `lockfilePreparationFailed` repeats pnpm's output, and `refusedRequest` the body of a GitHub or registry response.
  - **A reason a caller reads from an error.** These sentences take a value their caller read from an error's `message`, which the rule 6 check cannot see, and they escape it. `cannotWrite` and `cannotRemove`, which `loom init` prints, and `sharedFileUnreadable`, which the shared-version reader prints, repeat a Node.js reason, so `loom init` prints `Cannot write .changes/README.md: EEXIST: file already exists, mkdir '<path>'.` `unloadedApplication`, the warning of `loom init`, repeats the first line of the error the author's application module threw.

The contract is in [Failure message voice](../core/failures.md#failure-message-voice), [Core source modules](../maintaining/core-modules.md), the repository's [AGENTS.md](../../AGENTS.md#operator-messages), and the [glossary](../glossary.md#failures).

## Considered options

- **A lint rule.** Rejected by the owner's ruling. The voice binds Loom's own sentences, not an author's, so a lint rule an author installs is the wrong reach, and [principle 7](../principles.md#7-guide-with-types-then-lint-then-diagnostics) keeps lint for steering an author.
- **A type-checked reader.** Not taken. A program built with the TypeScript compiler would tell a number from a string exactly, but building one for each package is far slower than reading a few files, and message modules are plain enough for a scanner to read exactly. A value the scanner cannot type is pinned with its reason.
- **One table of every operator message per package.** Not taken; the owner's ruling places a message module beside each concept's code. A table far from its code turns each change into two edits in two places, and a sentence beside its concept keeps the concept's voice in one module.
- **`codes.ts` as the validators package's message module.** Not taken. Its descriptors are public, so it cannot be an internal module, and its sentences are descriptor members, not named exports. Renaming it would give a public module the name the internal ones carry.
- **Message keys and a locale provider.** Rejected by the owner's ruling. Localization is a separate decision, and an indirection that nothing uses gives the reviewer one more place to look.

## Consequences

This is an internal change. No public export, no type, and no operator byte changes, apart from a sentence a check shows to be wrong, which is fixed under its own fix fragment. Core gains `failures/messages.ts`, `inputs/messages.ts`, `invocation/messages.ts`, and `output/messages.ts`, and every other concept module whose code raises an operator failure or writes an operator line gains its own. Each plugin with operator sentences keeps one `messages.ts` in its folder, and the six existing ones export each sentence by name. `@loomcli/validators`, `@loomcli/prompts`, and `@loom/mcp` each gain `src/messages.ts`, and the `loom` bin gains one `messages.ts` in each command's folder under `src/commands` and `src/helpers/messages.ts`, which holds the sentences every launch loads. The application readers return facts in place of sentences.

Six voice tests and their shared reader join the suite, and a later change writes each new sentence into a message module. The binding of [ADR-0047](0047-an-operator-message-says-what-went-wrong-and-what-to-do-instead.md)'s Two parts and No leaks clauses, each of which names core, `@loomcli/plugins`, and `@loomcli/validators`, widens to `@loomcli/prompts` and the `loom` bin, and its rejection of a check on message text is narrowed: a repository test holds Loom's own sentences to the mechanical rules, while a lint rule or a runtime check stays rejected and rule 2 stays with review. ADR-0047 carries a dated entry.

## Status

Proposed. It moves to accepted in the release PR of the release that ships it.
