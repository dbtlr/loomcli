# ADR-0164 - Loom's operator messages live in message modules, and a voice test per package reads them

## Context

[ADR-0047](0047-an-operator-message-says-what-went-wrong-and-what-to-do-instead.md) states the voice every operator message Loom ships follows, in [Failure message voice](../core/failures.md#failure-message-voice). Nothing holds a sentence to it except review, and review reads a sentence only where it was written. Core builds its sentences as template literals in about 20 failure classes in `packages/core/src/failures/errors.ts`, and inline in `inputs/validation.ts`, `inputs/missing-input.ts`, `inputs/option-groups.ts`, `inputs/content.ts`, `invocation/lower.ts`, `output/lanes.ts`, and `failures/form.ts`. `commands/command.ts` raises only Developer Diagnostics and defects, and writes the `-v` line validation builds. The plugins write theirs inline across about 14 files, though six plugins (completion, man pages, MCP, self-update, service, and skills) already keep most of theirs in a `messages.ts` that groups them into objects such as `lines` and `refusals`. `@loomcli/prompts` and the `loom` bin write theirs inline in a few more files. `packages/validators/src/codes.ts` is already one catalog, but its sentences are members of the public issue-code descriptors under [ADR-0048](0048-a-validator-package-declares-one-issue-code-per-sentence.md).

Three of the voice's rules are mechanical enough for a test to hold. Rule 5 asks that every repeated value is escaped, rule 6 that no message quotes text Loom did not write, and the [glossary](../glossary.md) names words a sentence avoids. A test can read them only where the sentences are gathered, and gathered sentences also let a reviewer read one module's voice in one place.

ADR-0047 rejected "a lint or a runtime check on message text", because no check can tell whether a sentence states a fix, and because an application's messages are its own. Both reasons hold for what that record weighed. A test of Loom's own repository checks no application's text, and it holds only the mechanical rules, so rule 2 stays with review. This record narrows that rejection rather than superseding it.

The owner settled the shape in grooming (LM-352): one `messages.ts` per concept module, the four kinds of sentence that move, no operator byte changed, one voice test per package with four checks and pinned exceptions, the banned-word table on the voice page, internal modules, no localization, and a small launch cost, measured below.

## Decision

- **Message modules.** A Loom package keeps the operator messages one concept module's code raises or writes in one `messages.ts` beside that code, such as `packages/core/src/failures/messages.ts`, `packages/core/src/inputs/messages.ts`, and `packages/plugins/src/config/messages.ts`. A concept module is a folder directly under the package's `src`. A package whose `src` has no folders, such as `@loomcli/prompts`, `@loomcli/validators`, and `@loom/mcp`, keeps one at `src/messages.ts`. In `@loomcli/plugins`, each plugin keeps its own in its folder, and the files at the top of `src`, which several plugins share, keep theirs in `src/messages.ts`. In the `loom` bin, each command's folder under `src/commands` is a concept module: `src/commands/<command>/messages.ts` holds that command's sentences, with those of the helpers under `src/helpers` that do its work, so they load only on a route that reaches that work. A helper that serves more than one command keeps its sentences with the command whose work it does, such as the fragment reader's with `loom changelog`, and another command's route that calls it, such as `loom pr check`, loads that module too. A launch loads every command declaration and no command's work, as `packages/loom/tests/application.test.ts` pins, so the issues the declarations' validators report, the sentences of the helpers a declaration imports, and the package-directory helper's one sentence, `noPackageJson`, which build and changelog share, live in `src/helpers/messages.ts`, the one message module every launch loads. Beside them it holds the sentences every command's work shares, which no one command's module can hold: the wording of a system error, which is the cause table `systemCause`, the code in parentheses `codeNote`, `cannotUseFile`, which names a file from a system error's facts with the verb `systemVerb` reads from its system call, and `systemFailure`, the general sentence for a system error that carries no path, all of which `report()` prints and every command's work prints through `report()`; the sentences of a git or Bun that cannot start, `gitMissing` and `cannotRun`; and the issue `useHttpUrl`, which the release commands' `--registry` and `--github-api` validator reports. The same test fails when a launch that routes to no command's work loads a command's message module. Each sentence is a named export: a function of the values it repeats, or a constant when it takes none. A message function returns the sentence as a string. It constructs no failure and writes nothing: the code that raises the failure or writes the line calls it. The six plugin message modules that group their sentences into objects export each sentence by its own name instead.
- **What moves.** Four kinds of sentence move into message modules: a failure's sentence; a hint line a plugin adds under a failure through `onFailure`; a line written at `-v` or `-vv`, through `out.debug` or `out.trace`; and a notice, a warning, or a confirmation a plugin or the `loom` bin prints. A failure's sentence includes each part of it Loom writes: an issue Loom's own code reports, such as a content input's `Expected piped or redirected stdin.` or the issue of a value an invocation by name cannot lower, the line a question shows under an answer it rejects, and the error text an MCP server returns to its client. Core's one warning line, the line of a result sequence that stopped early, moves with them. Fixed labels stay where they are: help headings, the `repeatable` fact, the key hints under a question, and table and record labels. Developer Diagnostics, which address the author, do not move: a rule's headline and explanation stay in its rules registry, and a fault's sentence and correction stay where the code that raises it writes them. A log event's message, which a logging plugin records, is not an operator message under ADR-0047 and does not move.
- **No byte changes.** A sentence prints exactly as it did, and no existing test's expected string changes. The one exception is a sentence one of the four checks shows to be wrong, such as a repeated value that is not escaped. That sentence is fixed, and the change carries a fix fragment under `.changes/` that says the change happened without naming each changed sentence, so the changelog is not specific about the different sentences. A change with no changed sentence carries no fragment. The `loom` bin's sentences listed under The bin's reworded sentences change too, on the owner's ruling of 2026-11-16, under one fix fragment of the same kind.
- **One voice test per package.** Each package whose sentences reach an operator holds one voice test, `tests/message-voice.test.ts`, beside its other tests: `@loomcli/core`, `@loomcli/plugins`, `@loomcli/validators`, `@loomcli/prompts`, `@loomcli/loom`, and `@loom/mcp`, whose protocol errors `@loomcli/plugins` ships to an MCP client. `@loom/json`, `@loomcli/testing`, and `@loomcli/eslint-plugin` hold none, because none writes an operator message. A voice test reads only its package's message modules, the files named `messages.ts` under its `src`, plus one plain text scan of the package's other `.ts` files under `src` for the gathering and rule 6 checks. It builds no type-checked program and imports no TypeScript compiler. The four checks share one reader, `scripts/test-voice.ts`, as the tests share `scripts/test-process.ts`. Each voice test reads the banned words from [Failure message voice](../core/failures.md#banned-words), so each carries the `docs` module tag.
- **The reader.** The reader of a message module is a small scanner of its own. It reads comments, string literals, and template literals, nested `${...}` and nested templates included, and it knows each module-level declaration's parameter list. A message module holds functions, constants, imports, and types, with no regular-expression literal and no division, so every `/` outside a literal opens a comment. The reader refuses a module where one does not, and the test fails on it, so the reader never has to tell a pattern from a quotient in a message module. The scan of the package's other files, for gathering and rule 6, reads them with the same scanner, where a `/` that opens no comment is a division after a value, such as a name, a number, or a closing bracket, and a pattern after anything else, as a JavaScript parser reads it.
- **Banned words.** No string or template literal in a message module contains a word the [banned-word table](../core/failures.md#banned-words) lists in its "Do not write" column. A word matches without regard to case at the start of a word, so `presentation` also matches `Presentations` and `presentational`. The table's only entry is `presentation`, whose "Write" column reads "view, formatter, or request, whichever is meant".
- **Rule 5, escape what is repeated.** Every `${...}` in a message module's template literals is one of three forms. The first is a call to an escaping helper, core's `quoted(...)` or `escapeControlCharacters(...)`, whatever its argument holds, so a template inside the call is escaped whole. A style's `escape(...)` alone is not one, because it escapes Loom's markup delimiters and no control character; a style's `escape(...)` whose argument is a call to an escaping helper is, because a line an out call writes needs both escapes. The second is a call to another message function: a function the module declares, or binds with `const` to a function or to an escaping helper, or one it imports from another message module of its package. The third is a value typed as a number: an identifier, bare or as the argument of `String(...)`, that the module-level function holding the interpolation declares as a parameter of type `number`, or destructures from a parameter whose inline object type declares that member as `number`. The reader reads a conditional expression's two branches by the same rule, and a string literal, or a template literal whose own interpolations pass, repeats no value. A called message function's own interpolations are checked where it is declared, so a helper with no template literal of its own, such as `const shown = escapeControlCharacters`, passes, and review judges what it returns. An issue's sentence, which core and the configuration plugin repeat after an input's name as its validator wrote it under [Issues and validator failures](../core/validation.md#issues-and-validator-failures), is the known exception the rule has by design: the calling code reads the issue's `message` and passes it to the message function as a parameter, and its interpolation is pinned with that reason, so a multi-line issue prints as before.
- **Rule 6, quote no outside text.** The check reads every `.ts` file under the package's `src`, its message modules and its other files alike, with the one reader, so it reaches the code that calls a message function as well as the function. A site is a read of a member named `message`, `stack`, or `cause`, by a dot, an optional chain, or a bracket with a string literal. Its source text is the member read with the identifier before it, such as `error.message` or `error['cause']`, or the member alone, such as `?.message` or `.message`, after anything that is not an identifier. An assignment to such a member, such as `this.cause = cause`, writes it and reads nothing, so it is no site; gathering reads an assignment to `message`. In a message module no site is right: a message function takes the facts its sentence names, never the error that carried them. Outside one, a site is code that can hand an error's text to a sentence, so the code reads a fact in its place, such as a system error's `code`, or the site is pinned in that package's voice test with the reason the read is right. The rule concerns what a sentence says, not what a failure carries, so the reasons are of the kinds the 2026-11-16 scan found, and a pin states which one holds: a failure's own message that the package prints, such as core's default text, a `ProtocolError`'s message the MCP server writes, or the bin's own sentence a caller passes on, such as the fragment reader gathering each fragment's sentence into one failure; an issue's sentence a validator or a schema wrote, repeated after its input's name or its key; what the `loom` bin relays under Scope, another program's output or the error an author's application module threw; a Developer Diagnostic's text, which addresses the author; a log event's field, which ADR-0047 and [ADR-0069](0069-core-hands-log-events-to-onlog-hooks-and-writes-no-log-record.md) count as no operator message; and a cause read to carry it on to the failure that wraps it, or to test what it is, which quotes nothing. The scan reads no types, so it cannot tell an error from another value with a member of one of those names, and a read of one, such as a question's own `message` setting or the post-install message an author declares, is pinned with that reason. A read the three forms do not cover, such as `const { message } = error`, is judged in review, as a sentence built in a helper no route names is under gathering. The check builds no type-checked program and imports no TypeScript compiler, as the other three do not.
- **Gathering.** Outside a message module, no failure constructor and no out call is handed a literal sentence. A failure constructor is a `new` expression whose class name ends in `Error` and is not one of JavaScript's own error classes (`Error`, `AggregateError`, `EvalError`, `RangeError`, `ReferenceError`, `SyntaxError`, `TypeError`, and `URIError`), a `super(...)` call inside a class that extends a class whose name ends in `Error`, and an assignment to a member named `message`. An out call is a call of a member named `print`, `info`, `success`, `warn`, `error`, `debug`, `trace`, or `fatal` on any receiver except a style (a receiver named `style` or ending in `Style`) and the log (`log`). A literal sentence is a string or template literal outside any bracket of the call's arguments, or of the assigned value, whose literal text, or that of a literal inside its interpolations, holds a space; a conditional's branches and a fallback after `??` are outside any bracket. A literal inside an object argument, such as a Developer Diagnostic's `correction`, is not one, nor is a literal inside a nested call, and neither is a failure's kind, such as the `'insecure'` of `new RequestError('insecure', url)`. The scan skips comment blocks and comment lines, so a doc comment's example never counts.
- **A package's own routes.** A package whose sentences reach an operator by a route of its own names that route in its voice test, as a value of the `VoiceSinks` type `scripts/test-voice.ts` exports, and gathering reads it as it reads a failure constructor: a call of a named function, such as the `text(...)` that builds the content of a tool execution error the MCP plugin's server returns, or self-update's `fatal(...)` and `conflict(...)` and the skills plugin's `directoryProblem(...)`, which each wrap a sentence in a failure; a call of a named member on a named receiver, such as the `run.line(...)` that writes each line `loom init` prints for a file it writes; a `return` inside the arguments of a call of a named function, and a concise arrow body that is itself one of those arguments, such as the `loom` bin's `report(...)`, which prints what a command's work returns, its confirmation included; a `return` and a concise arrow body inside a function declared with a name the test lists, whose returned text such a call prints; an assignment to a named variable or member, such as the issue line `@loomcli/prompts` assigns to a question; a named member of an object literal, such as the `message` of a validators issue-code descriptor; and a named error class counted as a failure constructor, such as JavaScript's own `Error` in the `loom` bin, whose `report()` prints a thrown error's message through `out.fatal`. Gathering reads only the routes a package's voice test names, so a sentence built in a helper those routes do not name is judged in review. The `loom` bin names the helpers whose returned text `report(...)` prints, `stableNotes`, `prereleaseNotes`, `packageNotes`, `recordRelease`, `renderPlan`, and `cutSummary`, and `lines.push(...)`, the call that collects each line of a release record, which is the route the lines of `readUpload` take. The changelog section `loom release cut` prints, which `renderSection` builds around the fragments' own prose, and the facts and `--define` pair of `loom build`, are data and a document, not a sentence the bin words, and no route names them.
- **Known exceptions.** A site that breaks a check and is right is pinned in that package's voice test, per check and per file, by the site's source text and the count of sites in the file that have it, with the reason it holds, as `packages/core/tests/assertions.test.ts` pins each surviving type assertion by its count per file. A site's source text is the literal for the banned words and gathering, as written with its quotes, the whole `${...}` for rule 5, and the member read, such as `error.message`, for rule 6. Every site no pin covers fails the test, and so does a pin whose count differs from the sites found, so a new site with the text of a pinned one fails as well, and a pin that covers no site fails, so the table shrinks as the sentences improve. The pins of one package are one value of this type, which `scripts/test-voice.ts` declares and exports:

  ```ts
  /** One of the four checks a voice test holds over a package's sources. */
  type VoiceCheck = 'banned-words' | 'escaping' | 'gathering' | 'outside-text';

  /** One known exception: the reason it holds, and how many sites in the file have its text. */
  interface VoicePin {
    readonly reason: string;
    readonly sites: number;
  }

  /**
   * A package's known exceptions: for each check, the files under the package's `src` that hold
   * one, by path under `src`, and in each file the source text of each excepted site with its pin.
   */
  type VoiceExceptions = {
    readonly [check in VoiceCheck]?: Readonly<Record<string, Readonly<Record<string, VoicePin>>>>;
  };
  ```

- **Each check fails on a bad sentence.** The reader's own test, `packages/core/tests/voice-reader.test.ts`, runs each of the four checks over a bad sentence written for it, a module text with a banned word, an unescaped interpolation, a read of `error.message`, and a source file that hands `new InputError` a literal sentence, and shows each check report it. It also runs the rule 6 check over a source file outside any message module that reads `error.message` and passes it to a message function: the check reports that read, and passes once a pin names its text, its file, and its count. An assignment to a member named `cause` in such a file is reported by no check.
- **Internal.** A message module is internal. No package entry point exports one, and the API reports do not change. A plugin's message module belongs to its subpath, and no subpath imports a sibling's, under the [plugin pack's](../plugins/README.md) rule.
- **Not localization.** A message module is plain functions. Loom adds no locale provider, no message keys, no lookup indirection, and no extension point, and an author rewords a Loom sentence as before, through a view override.
- **A small launch cost, in bytes and no measurable time.** A message module imports only what its sentences call, escaping and text helpers and other message modules of its package, and types. A message module adds no import to a launch path that did not have it: a plugin's entry that loads its message module for a hint line loads no middleware, no Node built-in, and no other library through it. A launch of the `loom` bin loads `src/helpers/messages.ts` and no command's message module. A launch does newly load message modules, each a named function per sentence beside the caller that now calls it. `loom --help` newly loads the message modules of core and `@loomcli/validators`, the help plugin's, and `src/helpers/messages.ts`. An application's launch newly loads core's and the validators' and the message modules of the plugins it installs: the built `examples/textstat` application's `--help` loads those of the configuration, format, help, and suggestions plugins and the pack's shared `src/messages.ts`. So a launch reads about 9 KB more than it did without them: 9,130 bytes more for `loom --help` and 9,629 more for the built `examples/textstat` application's `--help`, as the 2026-11-16 entry measured them with the totals of that day. The bundles hold no comments, so those bytes are the modules' own code. The time that costs is below what the machine's noise shows: see the 2026-11-16 entry for the measured launch times. Every sentence in `src/helpers/messages.ts` was on the launch path already, held inline, except `noPackageJson`, the package-directory helper's one sentence, which a launch now loads because the command declarations import that helper.
- **The application readers.** The `loom` bin's two application-reading scripts, `dist/read-application.js` and `dist/read-skills.js`, each bundle only their own two modules and no copy of core, as `packages/loom/tests/readers.test.ts` pins. They return what they found as facts in the result file they write, and the `loom` process words each through its own message module, so each script still bundles only its own modules. A Developer Diagnostic the package's own core formats still passes through as it does today.
- **The validators catalog.** `packages/validators/src/codes.ts` keeps its name and its issue-code descriptors, which the package's root export publishes under [ADR-0048](0048-a-validator-package-declares-one-issue-code-per-sentence.md). Because they are public, `codes.ts` is not a message module. Each descriptor's `message` calls a sentence of the internal `packages/validators/src/messages.ts`, as each public failure class in core's `failures/errors.ts` calls one of `failures/messages.ts`. A descriptor whose sentence is the author's own, such as `text-pattern`'s `message` parameter, passes it through unchanged.
- **Review.** The voice test holds the banned words, rule 5, rule 6, and gathering. Rules 2, 3, and 4 need judgment, whether a sentence states its fix, depends on a plugin, or repeats a secret, so review judges them.
- **Scope.** The voice's rules bind `@loomcli/prompts` and the `loom` bin as they bind core, `@loomcli/plugins`, and `@loomcli/validators`, which ADR-0047's Two parts and No leaks clauses each name. `@loom/mcp` ships inside `@loomcli/plugins`, so the plugins' binding covers it. Rule 6 binds the `loom` bin with one exception, on the owner's ruling of 2026-11-16: the bin may relay what another program or the author's code said, because it is a toolchain that runs them, and its voice test pins each site with the reason it holds, the interpolation under rule 5 and the caller's read under rule 6. The bin's own sentences never quote a Node.js or engine reason. It relays in two ways:
  - **Another program's output, whole.** Nine sentences repeat text whole as `output`, unescaped and with its lines, most of it another program's. `gitFailed` repeats git's stderr. `bunCouldNotRead` repeats Bun's report of reading the author's application module, which carries the error the module threw, and `bunBuildFailed` Bun's build output. `skillsFolderJudged` repeats the plugin pack's judging of a skills folder. `skillMissing` repeats the bin's sentence about the file, which may repeat git's report, `skillInvalidYaml` the YAML parser's report, and `skillVersionUnset` the bin's own sentence about the frontmatter. `lockfilePreparationFailed` repeats pnpm's output, and `refusedRequest` the body of a GitHub or registry response.
  - **The author's module error.** `unloadedApplication`, the warning of `loom init`, repeats, escaped, the first line of the sentence the read of the author's application module failed with: Bun's report, which carries the error the module threw, the Developer Diagnostic of a declaration fault, or one of the bin's own sentences, such as `missingBun`, `coreUnresolved`, or a schema issue's. A system error that reaches its catch, such as a scratch folder the reader cannot make, passes the reason `it could not be read (ENOSPC)`, the general reason with the system error's code, in place of its text, and a Bun that cannot start passes the bin's sentence for it below.
- **The bin's reworded sentences.** On the owner's ruling of 2026-11-16, two kinds of the `loom` bin's sentences change, each keeping the part that names what went wrong, and the bin's tests run each command on `mockProcess` in a sandbox and assert the whole sentence.
  - **A Node.js reason, in Loom's words.** A sentence about a file the bin cannot write, remove, or read, a program it cannot start, or a request that gets no response names the cause from the system error's code in Loom's words, with a step the operator can take. The code that catches the error passes the message function the code, and any fact it determines itself, such as the folder on the way that is a file, and never the error's text. The thrown error keeps the `cause` it carries today. The paths are the ones each sentence names today, relative to the package directory with `/` between segments. A code no line names, such as `EIO`, takes the general sentence, which names the bare code in parentheses, as the editor question's `Cannot write the editor's file in "/tmp" (EACCES).` does, and a throw that carries no string `code` takes the same sentence without the parentheses. `loom init` prints these when it cannot write a file:
    - `ENOTDIR`, or `EEXIST` from creating a folder, when a path on the way to the file is a file: `Cannot write .changes/README.md, because .changes is a file. Remove or rename it, then run loom init again.`, naming the first path on the way, from the package directory, that exists and is not a directory, so `.agents/skills` when it is a file and init writes `.agents/skills/loom-changelog/SKILL.md`. When the code finds none, `EEXIST` takes the general sentence and `ENOTDIR` the line below.
    - `ENOTDIR` when the code finds no file on the way: `Cannot write src/main.ts, because a path on the way is a file. Remove or rename the file on the way, then run loom init again.`
    - `EISDIR`: `Cannot write src/main.ts, because it is a folder. Remove or rename the folder, then run loom init again.`
    - `EACCES` or `EPERM`: `Cannot write src/main.ts, because permission was denied. Give your user write access to it and its folder, and execute access to each folder above it, then run loom init again.`, since a folder above it without search permission denies a file that is itself writable.
    - `EROFS`: `Cannot write src/main.ts, because the file system is read-only. Run loom init in a package on a writable file system.`
    - `ENOSPC`: `Cannot write src/main.ts, because no space is left. Free some space, then run loom init again.`
    - Any other: `Cannot write src/main.ts (EIO). Check that you can write to it and its directory, then run loom init again.`

    When it cannot remove a file it no longer renders, or a folder that removal left empty:
    - `EACCES` or `EPERM`: `Cannot remove .agents/skills/loom/old.md, because permission was denied. Give your user write access to its folder, and execute access to each folder above it, then run loom init again.`
    - `EROFS`: `Cannot remove .agents/skills/loom/old.md, because the file system is read-only. Run loom init in a package on a writable file system.`
    - Any other: `Cannot remove .agents/skills/loom/old.md (EBUSY). Check that you can write to its directory, then run loom init again.`

    Init reads a managed path that exists before it writes it, so a directory at a managed path is met when init reads it, and the write's `EISDIR` line only when a directory appears between the check and the write. When it cannot read a file it manages that exists, which it reads to learn whether init wrote it, or a Markdown file of the authoring skill's folder that the sweep reads:
    - `EISDIR`: `Cannot read .changes/README.md, because it is a folder. Remove or rename the folder, then run loom init again.`
    - `EACCES` or `EPERM`: `Cannot read .changes/README.md, because permission was denied. Give your user read access to it, and execute access to each folder above it, then run loom init again.`
    - Any other: `Cannot read .changes/README.md (EIO). Check that you can read it, then run loom init again.`

    A program the bin starts that cannot start, and a request that gets no response, fail in the bin's words, for every command that starts git or Bun or sends a request:
    - git, with `ENOENT`: `git is not on the PATH, and loom reads the repository with it. Install git and run the command again.`, as `missingBun` says of Bun.
    - git or Bun, with any other code: `Cannot run git (EACCES). Check that git is installed and that you can run it, then run the command again.`
    - A request that fails before any response, other than on its deadline, which `requestTimedOut` names: `GET https://api.github.com/repos/owner/name could not be reached. Check your network connection, then run the command again.`, the method and the address as `requestTimedOut` names them.

    One table in `src/helpers/messages.ts`, `systemCause`, words each cause from the code, so one cause reads the same at every site, and each site keeps its own subject and its own step: `ENOENT`, it does not exist; `EISDIR`, it is a folder; `ENOTDIR`, a path on the way is a file; `EACCES` and `EPERM`, permission was denied; `EROFS`, the file system is read-only; `ENOSPC`, no space is left; any other code, the bare code in parentheses. Init's write, remove, and read sentences, the shared-version reader, the fragment reader, the read of `--plan`, and `report()` word a cause through it. A step for a denied permission names the file and the folders above it, because a folder without search permission denies a file that is itself readable. Two sites keep words of their own where the table's would mislead. The shared-version reader reads a listed entry whose path passes through a file as an entry that does not exist, because either way the entry names no file and the fix is the same. `loom release plan` says of an `--output` whose folder is missing `Cannot write out/plan.json, because its folder does not exist. Create the folder, then run the command again.`, naming the path as the operator typed it, because a write that finds no entry lacks the folder and not the file.

    A system error is a thrown `Error` that carries a string `code`, and the bin's own failures carry none. Where the bin's code passes on what a throw said, a system error no line above names passes no text of its own. The fragment reader, which gathers each fragment's sentence into one failure, names the fragment: `Cannot read .changes/fix.md, because permission was denied. Give your user read access to it, and execute access to each folder above it, then run the command again.` for `EACCES` or `EPERM`, and `Cannot read .changes/fix.md (EIO). Check that you can read it, then run the command again.` for any other code. `unloadedApplication` takes the general reason Scope names.

    `report()` prints the failure a command's work throws, and what it prints depends on the throw:
    - **The bin's own failure.** A failure the bin raises carries one of its message modules' sentences as its `message`, and `report()` prints that sentence.
    - **A system error.** A throw that carries a string `code` and a string `syscall`, other than a runtime's internal `ERR_*` code such as `ERR_INVALID_URL`, which names no file error, is worded from those facts and never its text. One that carries a `path` names the path, escaped, as the error carries it, what the call was doing to it, which `systemVerb` reads from `syscall` (`open` for an open, which a read and a write both make, `read`, `write`, `create`, `remove`, and `use` for any other call), the cause from the table, and a step: `Cannot open /work/notes/notes.md, because it does not exist. Check the path and each folder on the way to it, then run the command again.` One that carries no path, such as a read of a folder, prints `The command failed on a system error (EISDIR). Check the files it reads and writes, then run it again.`
    - **Any other throw.** `report()` prints its `message`, which is a runtime's or engine's text, because no such throw is the bin's own. The throws that still reach it this way are defects of the bin's own inputs, not of an operator's: a runtime error with an internal `ERR_*` code, a Bun metafile or the result file the bin's application reader writes that does not parse as JSON, and a GitHub answer whose upload address does not parse as a URL.

    So `report()` prints the bin's own sentences for every failure the bin raises and every system error, and its read of `message` is pinned with that reason and the defects that still print a runtime's text.

    The bin parses an operator's or a dependency's JSON file with its own sentence, never a bare `JSON.parse`. A dependency's `package.json`, which `loom build` reads to learn which package holds a module and `loom release cut` reads for pnpm, takes the manifest's sentence, which names the file's path, the line and the column where the JSON breaks, and the fix, as `manifestNotJsonAt` words it. `loom release record` names the `--plan` file as the operator typed it: one it cannot read takes the table's cause, as in `Cannot read plan.json, because it does not exist. Check the path and each folder on the way to it, then run the command again.`, and one that is not JSON reads `plan.json is not valid JSON: line 1, column 1 needs a value, so write the plan again with loom release plan, then run loom release record again.` A provenance statement the registry's attestation carries that is not JSON names the request: `GET https://registry.npmjs.org/-/npm/v1/attestations/@acme/core@1.2.0 answered with a provenance statement that is not JSON, so check that --registry names an npm registry, then run the command again.`, and a response whose body breaks off after its status arrived reads `GET https://registry.npmjs.org/@acme/core stopped before its answer ended. Check your network connection, then run the command again.`, beside the sentence of a request that gets no response.

    `--registry` and `--github-api` on `loom release plan` and `loom release record` take an http or https URL, checked by a validator on the option's declaration as the bin's other options state what they accept, so a value with no scheme, such as `registry.npmjs.org`, is a usage error before any request: `loom: Option "--registry": Use an http or https URL.` with exit 2, in place of a request named as unreachable.

    The shared-version reader of `loom changelog write`, its dry run included, names the entry as `sharedVersion` lists it:
    - An entry that names something other than a regular file, such as a directory or a symbolic link: `sharedVersion lists ../hub/package.json, which is not a regular file, so correct the entry or the file and cut again.` The code tells it from the entry's own file type, not from a thrown sentence.
    - `ENOENT` or `ENOTDIR`, when the file is gone by the time it is read: the sentence of a missing file, `sharedVersion lists ../hub/package.json, which does not exist, so correct the entry or the file and cut again.`
    - `EACCES` or `EPERM`, from reading the file or its own file type: `sharedVersion lists ../hub/package.json, which cannot be read, because permission was denied. Give your user read access to it, and execute access to each folder above it, then cut again.`
    - Any other: `sharedVersion lists ../hub/package.json, which cannot be read (EIO). Check that you can read it, then cut again.`

    `sharedFileUnparsed` keeps repeating the bin's own sentence about a manifest that does not parse, which `parseManifest` throws, and its caller's read of that sentence is pinned with that reason.
  - **A fix in each failure sentence.** A failure sentence of the bin that says what went wrong and states neither a step nor what is accepted gains a step, against voice rule 2. `tagExists`, which `loom release cut` and `loom pr check` raise, reads `Tag v1.2.0 already exists, so cut a version no tag names with loom release cut --target <version>.`, and `checkoutChanged` reads `Checkout changed during release preparation, so nothing was written. Wait for any other writer to finish, then run loom release cut again from a clean checkout.` The same miss holds in `noVersionCommit`, `noFragments`, `lockfileInvalidYaml`, `lockfileTimedOut`, `lockfilePreparationFailed`, `invalidJsonAnswer`, `refusedRequest`, `requestTimedOut`, `neverAppeared`, `tagObjectMissing`, `uploadOriginRefused`, `provenanceElsewhere`, `provenanceWithoutSource`, `unsupportedIntegrity`, `integrityMismatch`, `noChangelogSection`, `sectionWithoutNotes`, `provenanceConflict`, `tagWithoutProvenance`, `tagAwayFromPublication`, `planWithoutNotes`, `provenanceNotOurs`, `commitOutsideCheckout`, `uploadsDisagree`, and `changedDuringPreparation` of `src/commands/release/messages.ts`; `versionCannotAdvance`, `unclosedBlock`, and `noPendingFragments` of `src/commands/changelog/messages.ts`; `outsideCut` of `src/commands/pr/messages.ts`; `bunCouldNotRead`, `bunBuildFailed`, `skillsFolderJudged`, and `watchExited` of `src/commands/build/messages.ts`; and `gitFailed`, `symlinkedPackage`, and `noLibraries` of `src/helpers/messages.ts`. Each gains a step the operator can take there, such as running the command again once a service's write has propagated, and a sentence that relays another program's output gains the step in the bin's own part, as the MCP plugin's `Fix what codex reported, then run jsonkit mcp install again.` does. A sentence that states what is accepted, such as `Release target must be a stable 0.x version.` or `PR checks require full Git history.`, already has its second part and does not change.

The contract is in [Failure message voice](../core/failures.md#failure-message-voice), [Core source modules](../maintaining/core-modules.md), the repository's [AGENTS.md](../../AGENTS.md#operator-messages), and the [glossary](../glossary.md#failures).

## Considered options

- **A lint rule.** Rejected by the owner's ruling. The voice binds Loom's own sentences, not an author's, so a lint rule an author installs is the wrong reach, and [principle 7](../principles.md#7-guide-with-types-then-lint-then-diagnostics) keeps lint for steering an author.
- **A type-checked reader.** Not taken. A program built with the TypeScript compiler would tell a number from a string exactly, but building one for each package is far slower than reading a few files, and message modules are plain enough for a scanner to read exactly. A value the scanner cannot type is pinned with its reason.
- **One table of every operator message per package.** Not taken; the owner's ruling places a message module beside each concept's code. A table far from its code turns each change into two edits in two places, and a sentence beside its concept keeps the concept's voice in one module.
- **`codes.ts` as the validators package's message module.** Not taken. Its descriptors are public, so it cannot be an internal module, and its sentences are descriptor members, not named exports. Renaming it would give a public module the name the internal ones carry.
- **Message keys and a locale provider.** Rejected by the owner's ruling. Localization is a separate decision, and an indirection that nothing uses gives the reviewer one more place to look.

## Consequences

This is an internal change. No public export, no type, and no operator byte changes, apart from a sentence a check shows to be wrong, which is fixed under its own fix fragment, and the `loom` bin's reworded sentences, which carry one fix fragment that says the bin's own sentences no longer quote a Node.js reason and now name the cause and a fix, without listing each sentence. Each package's voice test pins the reads of `message`, `stack`, and `cause` its code outside the message modules makes, with the reason each is right, and a new read fails the test until it is pinned or replaced by a fact. Core gains `failures/messages.ts`, `inputs/messages.ts`, `invocation/messages.ts`, and `output/messages.ts`, and every other concept module whose code raises an operator failure or writes an operator line gains its own. Each plugin with operator sentences keeps one `messages.ts` in its folder, and the six existing ones export each sentence by name. `@loomcli/validators`, `@loomcli/prompts`, and `@loom/mcp` each gain `src/messages.ts`, and the `loom` bin gains one `messages.ts` in each command's folder under `src/commands` and `src/helpers/messages.ts`, which holds the sentences every launch loads. The application readers return facts in place of sentences.

Six voice tests and their shared reader join the suite, and a later change writes each new sentence into a message module. The binding of [ADR-0047](0047-an-operator-message-says-what-went-wrong-and-what-to-do-instead.md)'s Two parts and No leaks clauses, each of which names core, `@loomcli/plugins`, and `@loomcli/validators`, widens to `@loomcli/prompts` and the `loom` bin, with the bin's exception under Scope for what another program or the author's code said, and its rejection of a check on message text is narrowed: a repository test holds Loom's own sentences to the mechanical rules, while a lint rule or a runtime check stays rejected and rule 2 stays with review. ADR-0047 carries dated entries.
