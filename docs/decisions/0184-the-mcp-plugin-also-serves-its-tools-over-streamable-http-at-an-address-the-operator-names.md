# ADR-0184 - The MCP plugin also serves its tools over streamable HTTP at an address the operator names

## Context

[ADR-0063](0063-the-mcp-plugin-serves-opted-in-commands-as-tools.md) serves an application's tools over stdio: `mcp()` attaches the Command `mcp`, "whose action runs a stdio server until stdin ends or the run's signal aborts". A client that reaches a server by URL cannot use it. Such a client runs on another machine or in a container, or connects to a server that outlives each agent session. The protocol's other standard transport, streamable HTTP, serves those clients. `@loom/mcp` assumes one newline-framed stream per client. `McpServer.run(input, output, { signal })` keeps one connection's state: the revision `initialize` negotiated under [ADR-0122](0122-the-mcp-server-serves-the-initialize-handshake-beside-the-per-request-revision.md), the calls in flight by request id, and their cancellation. Here a connection is that state, and an HTTP connection is the transport's socket.

The transport differs between the revisions Loom serves. On `2026-07-28` ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)), each request is its own POST and is served statelessly. Closing the response stream cancels the request, and a server that tears down a subscription must send `notifications/cancelled` for it. The GET stream and protocol-level sessions are gone. The client mirrors `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` into headers that the server must check against the body, and an unsupported version is answered 400. On `2025-11-25` and `2025-06-18` ([Transports: Streamable HTTP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#streamable-http)), a server may issue a cryptographically secure `MCP-Session-Id` at `initialize`, may end a session at any time and answer its id with 404, and may offer a GET stream. A dropped HTTP connection is not a cancellation, and a client cancels with `notifications/cancelled`. Both versions require the server to validate `Origin` against DNS rebinding and to answer an invalid one with 403. A server running locally should bind to 127.0.0.1. The protocol's [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning#backward-compatibility-with-initialization-based-versions) lets a dual-era server serve both eras on one endpoint. It scopes the legacy semantics an `initialize` selects "to the stdio process (stdio) or the session (HTTP)".

The protocol's [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) is optional. When an HTTP server supports it, it is OAuth 2.1 over HTTPS, with the server as a resource server that publishes Protected Resource Metadata. A stdio server takes its credentials from its environment instead. A bearer token sent without TLS can be read and replayed, and [RFC 6750, section 5.2](https://www.rfc-editor.org/rfc/rfc6750#section-5.2) requires TLS for it.

The owner ruled that a tool call over HTTP runs on the server's host and time zone, as it does over stdio, and that the contract says so. An author who needs a caller's time zone takes it as an ordinary input, and core does not change. The owner also settled what a bind tells the operator. A loopback address reaches every user and process on the machine, and an `authorize` hook is how an author restricts it. A non-loopback bind always warns, about open access without a hook and about cleartext credentials with one.

## Decision

- **An option on `mcp` selects the transport.** `mcp` declares the string option `--http <address>`, marked `control: true` under [ADR-0062](0062-a-control-option-is-marked-by-the-plugin-that-declares-it-and-core-never-reads-the-fact.md). Without it, `mcp` serves over stdio as before, except the subscription teardown its signal now sends (below). The address is a port or `host:port`, with an IPv6 host in brackets. A port alone binds 127.0.0.1, and port 0 takes any free port. `:8080` is refused, because other tools read it as every interface. A non-loopback host binds only when the operator names it, an unspecified address included, and Loom refuses no address the operator names.
- **What a bind tells the operator.** A loopback bind writes no warning. A non-loopback bind always writes one warning before the URL line. Without a hook, the warning says any host that reaches the address can call the tools. With a hook, it says requests and their credentials cross the network unencrypted, and tells the operator to put TLS in front. Installing `authorize` supplies no encryption.
- **Stdout carries the URL.** Once the server listens, the run writes one line to stdout, `http://<host>:<port>/mcp`, with the port it bound and, for an unspecified address, IPv4 or IPv6, the loopback address that reaches it from this machine. A supervisor that starts `app mcp --http 0` reads the endpoint from it. Stdout carries nothing else. Stderr carries what it carries over stdio, and adds the warning, the report of the `authorize` hook's first throw, the `-v` lines for refused requests, and an `error` event for an HTTP connection the server could not accept, after which it keeps serving.
- **One endpoint, checked in a fixed order.** The server answers the path `/mcp` alone. It checks every request in this order: `Origin`, authorization, path, method, then a POST's content type and body. Every response sent before the body is consumed carries `Connection: close`: 401, 403, 404, 405, 415, the 500 of a throwing `authorize` hook, and 413. After writing it, the server half-closes and discards unread body bytes for up to 2 seconds, then closes, so the client reads the answer instead of a reset, under [RFC 9112, section 9.6](https://www.rfc-editor.org/rfc/rfc9112#section-9.6). The server enforces receipt deadlines with its own timers under Node and Bun alike, 60 seconds for the headers and 300 for the whole request, and answers a request not received whole by then with 408.
- **Any `Origin` is refused.** A request that carries an `Origin` header is answered 403. Loom serves no page and answers no CORS preflight, so every request a browser sends to the endpoint is cross-origin, and Loom keeps no allow-list.
- **The author authorizes; Loom stores nothing.** `mcp()` takes an optional setting, `authorize(request)`, which receives a copy of the request's `Headers` before the body is read and returns a Boolean or a promise of one. `false` answers 401 with `WWW-Authenticate: Bearer`. The hook runs before any header is checked against the body, and `Mcp-Method` and `Mcp-Name` are verified only on a `2026-07-28` request, so a hook that decides by them refuses any other version. Without the hook, every request that passes the `Origin` check is served. The author compares a secret in constant time and refuses an empty one, and the contract's example does both. Loom holds no token, implements none of the protocol's OAuth authorization, and never calls the hook over stdio.
- **A hook that throws is a defect, reported when the server stops.** Core offers a plugin no way to report a defect while the run goes on, so the plugin follows how core reports a throwing `onLog` hook. Each request is answered 500 with `-32603`, the server keeps serving, and each throw is an `error` log event that carries the thrown value, seen at `-v` and in a log file. When the server stops, the action fails the run once with the first throw, as an `InternalError` through the ordinary failure path. So `override(InternalError)`, `onFailure` hints, failure encoders, and the generic message's once-per-run latch all apply, and a development build writes the Developer Diagnostic `@loomcli/plugins/mcp/broken-authorize-hook`, which names the hook. The run returns 1, except a cancelled run, which keeps its signal's code and still writes the report, as with `onLog`. A server stopped by `SIGINT` therefore exits 130 with the report.
- **The body has a limit.** `mcp()` takes `maxBodyBytes`, 4 MiB by default. The server counts the bytes as they arrive, whatever `Content-Length` says and with chunked coding included, and answers a body past the limit with 413 under [RFC 9110, section 15.5.14](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.14).
- **`2026-07-28` is served per request.** A request whose `params._meta` names a protocol version belongs to no session. Its `MCP-Protocol-Version`, `Mcp-Method`, and, on `tools/call`, `Mcp-Name` headers must be present and match the body, or the request is answered 400 with `-32020`. A session id or `Last-Event-ID` the request carries is ignored.
- **The initialize era gets a session.** An `initialize` without a session id that the package answers with an `InitializeResult` opens a session, and that response alone carries an `MCP-Session-Id` from `crypto.randomUUID()`. A failed `initialize` opens none. The session holds what one stdio connection holds: the negotiated revision, the calls in flight, and the request-id rule. So an `initialize` with a known session id is a second `initialize`, answered `-32600`, and it never replaces the session. Every request with an unknown session id, `ping` included, is answered 404, and a request without one is answered 400, except `initialize` and `ping`. A session ends by DELETE, which aborts its calls, or when it has had no request or notification with its id and no call in flight for `sessionIdleMs`, 30 minutes by default. It also ends when the server stops. `notifications/cancelled` within a session aborts the call it names. A closed stream does not cancel on those revisions: the call runs to its end and its answer is dropped.
- **Refusals come back as JSON; handlers stream.** The package's checks that run before a handler run before the transport picks a status and a content type: the `_meta` envelope, an unsupported version included, the method, the request id, and the tool name's type. A refused request is answered as JSON with its mapped status. On `2026-07-28`, `-32602` for a required `_meta` key that is missing or of the wrong type is 400, as that revision's `_meta` rule requires on HTTP, and `-32022` is 400. `-32601` is 404 on `2026-07-28` and 200 in a session. Only a `tools/call` or `subscriptions/listen` that reaches its handler is answered as `text/event-stream`. Its headers go out at once, an SSE comment line follows every 15 seconds, and the server turns off the runtime's idle timeout on the stream's socket while the stream is open, restoring it when the stream ends. Progress notifications go on the call's stream, before its result. Every other request is answered with one `application/json` response. GET and every method but POST and DELETE are answered 405. No event carries an id, and no stream resumes. No revision is batched.
- **Calls overlap, and shutdown aborts.** Calls from every POST, session, and client overlap, each through its own `invoke`, with no queue under [ADR-0059](0059-a-command-runs-by-name-through-invoke.md). When the run's signal aborts, the server stops listening and aborts every call. On each `2026-07-28` subscription stream still open, it sends `notifications/cancelled` naming the `subscriptions/listen` request, then the completion result. It answers nothing more and closes every HTTP connection. The stdio run's signal now sends the same subscription teardown, because the revision requires it on any transport, where it used to end a subscription with no message. Stdin plays no part.
- **A call runs where the server runs.** A tool call over HTTP runs on the server's host and time zone, environment, and working directory, as over stdio. Nothing from the HTTP request reaches the run. An author who needs the caller's time zone declares it as an ordinary input.
- **`node:http`, loaded lazily.** The server is `node:http`, which Node, Bun, and a compiled Bun binary all provide. The plugin imports it only when `--http` is given.
- **Registration is unchanged.** `mcp install`, `uninstall`, and `config` keep writing stdio registrations under [ADR-0111](0111-the-mcp-plugin-registers-its-server-with-claude-code-and-codex-through-each-agents-cli.md).

[MCP plugin](../plugins/mcp.md#serving-over-http) carries the full contract.

## Considered options

- **A separate Command, `app mcp serve-http`.** Rejected. The transport is how one server runs, not a different job. A child would sit beside `install` and `config` while serving stays the parent's action, and ADR-0063's command line would gain a sibling that does the same work.
- **An Origin allow-list, with or without loopback origins.** Rejected for now. Without CORS a listed origin still cannot read an answer from a browser, so the list would look like support it does not give. Serving browser clients means a preflight, exposed headers, and an allow-list together, and that is a later change if a client needs it. A page at `http://localhost:3000` is a page Loom did not serve, so loopback earns no exception either.
- **Built-in token checking, such as a `--token` option or a variable Loom reads.** Rejected. Loom would hold a credential and choose its scheme, header, and rotation for every application. The hook leaves those to the author, and the common case, one bearer token from a variable compared in constant time, is a few lines in it.
- **The protocol's OAuth authorization, or TLS in the server.** Rejected for Loom. A resource server's metadata and token validation belong to the author's identity provider and deployment, and a certificate belongs to the operator's. An author who needs OAuth, or an operator who needs TLS, puts a gateway that provides it in front of the server.
- **Warning only when a non-loopback server has no hook.** Rejected by the owner. A hook leaves the credentials it checks readable on the network, and an operator who installed one would take the silence for safety.
- **A warning on a loopback bind.** Rejected by the owner. Every local server shares that reach, and the contract states it once for the author instead.
- **An unbounded body.** Rejected. Passing the `Origin` and authorization checks says who may call, not what a request may cost, so one request could take any amount of memory.
- **Stateless initialize-era serving that reads the revision from `MCP-Protocol-Version`.** Rejected. Without a session, a `notifications/cancelled` names a request id that any client may be using, so it could cancel another client's call or none. The protocol scopes legacy semantics to the session.
- **Sessions that last until DELETE or shutdown.** Rejected. A client that exits without DELETE would leave its session for the life of the server, and the session ids would accumulate. The idle interval ends such a session, and a call in flight keeps its session alive.
- **An `initialize` with a session id replaces that session.** Rejected. A client that holds an id would silently lose the calls in flight under it, and over stdio the same request is answered `-32600`.
- **Aborting an initialize-era call when its stream closes.** Rejected. Those revisions say a disconnection should not be read as a cancellation, and a client there cancels explicitly. Loom follows the revision the client negotiated.
- **Answering every request as JSON.** Rejected. A JSON answer sends no bytes until the call settles, so a call longer than an HTTP client's response timeout fails. Node's fetch, for one, waits five minutes. Progress also needs a stream. A stream whose headers go out at once and whose comment lines keep it busy serves calls of any length.
- **Opening an event stream before the package's checks.** Rejected. A 200 stream could not carry the 400 or 404 that the `2026-07-28` transport requires for an unsupported version or method.
- **A GET stream on the initialize-era revisions.** Rejected. The server sends no request and no unprompted notification, so a GET stream would stay empty, and those revisions allow 405.
- **`Bun.serve`, or a fetch-style handler adapted to each runtime.** Rejected. `Bun.serve` runs under Bun alone, and a fetch handler needs an adapter on Node. `node:http` is one implementation for Node, Bun, and a compiled binary, and its request and response are the Node stream shapes `@loom/mcp` already takes.
- **Per-call caller facts, such as the caller's time zone or locale from headers.** Rejected by the owner's ruling. A caller's facts are inputs the author declares, and core does not change.

## Consequences

`@loom/mcp` splits its per-connection state out of `run()`, and the stdio run's signal gains the subscription teardown described above. One stdio stream is one connection, one initialize-era session is one connection, and one `2026-07-28` POST is a connection of one request. The stdio transport is unchanged except the signal path, whose subscription test now expects the teardown. The package gains an HTTP transport that answers one `node:http` request. It takes each accepted socket through `connection(socket)` for receipt deadlines and shutdown closure, the request and its response, the `onOriginRefused` callback and the authorization callback, the body limit, the session idle interval, and the run's signal. The plugin keeps the option, the bind, its failures, the warnings, the hook's throw report at stop, and the URL line, and its messages live in its `messages.ts` under [ADR-0164](0164-looms-operator-messages-live-in-message-modules-and-a-voice-test-per-package-reads-them.md).

[MCP plugin](../plugins/mcp.md) stated that `mcp()` takes no settings and that the `mcp` action owns stdout as the transport. `mcp()` now takes optional settings, `authorize`, `maxBodyBytes`, and `sessionIdleMs`, and stdout is the transport over stdio alone. An application global option named `http` now collides with the MCP Command's local option; rename the application option and update its readers. The `mcp` Command declares its first option, and its description names both transports. Progress under [ADR-0091](0091-live-regions-stack-at-the-bottom-of-stderr-and-progress-reaches-invoke-callers-and-mcp-clients-as-typed-events.md) and the log lines under [ADR-0174](0174-v-shows-the-log-through-message-templates-and-out-keeps-what-the-operator-is-told.md) behave as they do over stdio.

There is no aggregate budget across concurrent bodies. `maxBodyBytes` bounds each body, and the 300-second receipt deadline bounds how long each upload lives, so concurrent uploads may together hold their count times the limit for that long. An application that needs a total bound puts something that sets one in front of the server.

A loopback address is reachable by every user and every process on the machine, not by the operator alone. The `Origin` rule keeps browser pages out, and an `authorize` hook is how an author restricts every other local caller. A loopback bind writes no warning, so the contract says this instead. A non-loopback server always warns. Without a hook it serves anyone who reaches it. With a hook, its credentials still cross the network in the clear until the operator puts TLS in front. The operator named the address, so Loom refuses neither. ADR-0063 notes that the protocol asks a server to rate limit tool invocations. Over HTTP a server may serve several clients, and Loom still adds no limit, so an application that needs one applies it in its own actions or in front of the server.

This narrows ADR-0063's clause that the `mcp` action "runs a stdio server until stdin ends or the run's signal aborts": with `--http`, it runs an HTTP server until the run's signal aborts. It also narrows ADR-0063's consequence that "A stdio server serves the one client that launched it", because an HTTP server serves every client that reaches it. Each holds unchanged for stdio. It narrows ADR-0122's connection scope too: over HTTP an initialize-era revision is scoped to a session, as the protocol states. ADR-0063 and ADR-0122 carry dated entries. ADR-0111's registrations are unchanged. A client configuration that connects by URL is not part of this record.

## Status

Proposed. It moves to accepted in the release PR of the release that ships it.
