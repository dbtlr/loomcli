# ADR-0091 - Live regions stack at the bottom of stderr, and progress reaches invoke callers and MCP clients as typed events

## Context

An action draws on stderr only through `out.draw`, which [ADR-0082](0082-an-action-asks-through-the-prompts-library-and-one-interaction-decision-governs-questions-and-conditional-requiredness.md) added so a question could draw its frames and erase them by the row count the call resolves. Nothing coordinates any other write with a drawn frame. An `out.info` line, a debug line, or a result row that reaches the terminal while a frame is drawn lands inside it, each stream has its own write queue, and stdout and stderr share no order. A frame drawn before a terminal resize reflows, so the count the caller erases by is stale after the resize.

An author who wants a spinner around awaited work, or progress with counts, writes the frames, the timer, the erase, and the plain output for a pipe by hand, and the same work shows nothing to a program. An [invocation by name](0059-a-command-runs-by-name-through-invoke.md) captures its output with no terminal and has no progress path, and the [MCP](0063-the-mcp-plugin-serves-opted-in-commands-as-tools.md) server sends no `notifications/progress`, although a client that passes a progress token asks for them.

Only core sees every write, so only core can keep a drawn frame intact. How an indicator looks, its characters and how often its frame changes, changes faster than core should.

## Decision

- **One region call.** `Out` gains `region(options?)`, which opens a live region at the bottom of stderr and returns its handle at once: `draw(data, view)`, `end(state?, label?)`, `signal`, `report(progress)`, and the read-only facts `live` and `closedBy`. Questions and progress lines both draw in regions. `out.draw` stays, as a region of one frame that core writes as every other write to stderr, above the open regions, with no line break added and never held by an input region, and it keeps resolving its row count, so no caller breaks.
- **Stacked below every other write.** Open regions sit at the bottom of stderr in the order they opened. Before any other write to stderr, core erases the drawn regions, writes, and redraws them below it: the semantic lanes, the debug and trace lines of [ADR-0090](0090-an-operators-v-or-q-settles-the-runs-verbosity-right-after-graph-build.md) included, `out.draw`, a failure report, and what an `onLog` hook writes to its destination's stderr under `run()`. When stdout is a terminal too, a stdout write does the same, so the two streams share one order while a region is drawn. A closing region's last frame moves into scrollback, and the regions below it close the gap.
- **Frames are views.** `draw` renders a bare or declared view through the registry, with stderr's view context, as `out.draw` does under [ADR-0021](0021-every-rendered-byte-passes-through-one-registry-of-replaceable-views.md), and core keeps the frame's text.
- **Drawn only at a terminal.** A region is live when stderr is a terminal and the region takes input or the run's verbosity is 0 or more. A region that is not live draws nothing, so a pipe, a log file, and an invocation by name's captured output never hold a frame. `live` tells a library to write plain lines instead.
- **The signal.** Core aborts a region's `signal` whenever the region closes: `end()`, the completion of what opened it, a failure about to be reported, or the run's cancellation. It sets `closedBy` to `'end'`, `'completion'`, `'failure'`, or `'cancellation'` first, and a frame an abort listener draws is the region's last frame.
- **Completion follows the opener.** A region the action opens and leaves open closes when the action returns. A region a middleware or a configuration source opens stays open through the action and closes when the middleware chain has unwound, so a middleware can show a line around the whole run.
- **The report is last.** Before core renders any failure report, it closes every open region with `'failure'`, so each region draws its failed frame above the report and the report is the last thing on stderr.
- **Input regions.** `out.region({ input: true })` opens a region that reads the operator's keys. While it is open, core draws no frame of any other region: their timers keep running, core keeps each latest frame, and it draws them once when the input region closes. One input region is open at a time, and a second opens when the first closes.
- **Quiet.** At verbosity -1, core draws no region opened without `input: true`. A question still draws. Only `out.region` follows the verbosity: `out.draw` draws at every verbosity, because its caller decides when to draw.
- **Resize.** Before it erases, core recounts each region's last frame at stderr's current width, so a frame a reflowing resize rewrapped is erased whole.
- **Typed progress events.** `report({ completed?, total?, label? })` draws nothing. It builds a progress event, `{ id, label, state, completed?, total? }`, whose state is `started` for a region's first report, `updated` after it, and `ended`, `failed`, or `cancelled` when the region closes. The end event carries the label `end(state, label)` received, and the last reported label without one; no extra event is built. The label draws nothing, so a caller that wants the terminal to show it, as a progress line does, draws it as the last frame. A region that never reported builds none. `InvokeOptions.onProgress` receives each event of the call's run in order, and a call with no observer collects nothing. A progress event is not a log event under [ADR-0069](0069-core-hands-log-events-to-onlog-hooks-and-writes-no-log-record.md).
- **MCP progress.** For a tool call that carries a progress token, the MCP plugin sends each event as one `notifications/progress` on that token: `progress` is always a per-call counter that every event increments, so every event is sent and `progress` always increases, as the protocol requires. The notification carries no `total`, and `message` carries the label, the counts, and the state, such as `Fetching packages 3/8 (updated)`. Lines that run at once share the token and the counter. The protocol package sends none after the call is answered or cancelled, and the protocol stays pinned to 2026-07-28. `onProgress` still receives the typed event unchanged.
- **The timer rule.** Core never uses a timer to cancel or limit work because it has run too long; that is the author's job, in the author's own action. A timer that animates a frame is plain JavaScript an author or a library runs, and it stops when the region's `signal` aborts. Core runs no timer for a region.
- **Progress lines in the prompts library.** `@loomcli/prompts` ships `progress(context, { label, total?, spinner? })`, which opens a region and returns a handle with `update`, `end(message?)`, `fail(message?)`, and `track(work, { done?, failed? })`. Each end message passes to the region's `end` as its label, so the end event and MCP's `message` read it, such as `Fetched 3 records. (ended)`. Without a total the line is a spinner, and with one a bar with counts. Its failure line draws core's `error` glyph, `✘`, whose compat form is `×`. The library animates the line on its own unref'd timer, draws the cancelled line when core cancels the region, and draws the failed line when core closes it for a failure. Off a terminal, under an invocation by name, and at verbosity -1 it writes one start line through `out.info` and, unless the run is cancelled, one end line through `out.success` or `out.error`, so the quiet rule hides the start and success lines with their lanes and a failure still prints. It reads `live` and never the verbosity.
- **The progress style.** `progressStyle({ spinner?, bar? })` is an optional plugin from `@loomcli/prompts` whose spinner has the cli-spinners shape, `{ frames, interval }`, so any cli-spinners entry drops in. It contributes one extension value that `progress()` reads from the context, and one call may pass its own spinner. The line renders through the library's declared view `@loomcli/prompts/progress`, which an application overrides through `views`.
- **Questions on input regions.** Each question draws in an input region, and core erases and redraws it, so the library no longer erases by `out.draw`'s count.

The contract and its acceptance are in [Live region](../core.md#live-region), [Progress events](../core.md#progress-events), [Invocation by name](../core.md#invocation-by-name), [MCP](../core.md#mcp), and the [prompts reference](../prompts.md#progress).

## Considered options

- **`out.progress` on `Out`, drawn by a core-declared view.** Rejected. Core would own the frames, the interval, the bar characters, custom indicators, and the plain output off a terminal, so every change to how an indicator looks would be a change to core. Core supplies the region, its signal, and its reports, and a library draws the indicator.
- **A core frame timer that animates a spinner.** Rejected. Loom needs no timer to animate a frame: an indicator is plain JavaScript that runs its own interval and stops it when the region's signal aborts.
- **Each library erasing and redrawing its own frames, as questions do.** Rejected. Only core sees every write, so only core can keep a frame whole when a lane, a result row, or a failure report reaches the terminal.
- **Erasing an open line before a failure report.** Rejected. The operator loses which step was running. Each line ends in its failed state above the report, and the report stays last.
- **A cancellation method on the progress handle.** Rejected. Cancellation is the run's, and the region's signal already carries it to the library.
- **Progress events as log events.** Rejected. A log event is a record for a reader later, while a progress event reaches the caller of this run now, and ADR-0069 keeps the two apart.
- **Two input regions drawn at once.** Rejected. Keys reach one reader, so a second question waits for the first, as an operator answers them.
- **Hiding questions at verbosity -1.** Rejected. A question asks for the operator's input, and `-q` asks for less output, not for fewer answers.
- **MCP `progress` as the event's `completed`.** Rejected. An update that changes only the label, a spinner line, and an end at the count already sent would not increase `progress`, so the server would drop them, and a client would miss the line's end. A per-call counter sends every event, and the counts travel in `message`.
- **Closing every region when the action returns.** Rejected. A middleware that opens a line around the whole run, before `next()`, would lose it before the chain unwound.
- **Erasing by the count measured at the draw.** Rejected for regions. A terminal that reflows after a resize leaves rows above the count. `out.draw` keeps that count because its callers erase by it.

## Consequences

`Out` gains `region`, and `@loomcli/core` exports `Region`, `RegionOptions`, `RegionCloser`, `ProgressReport`, and `ProgressEvent`. `InvokeOptions` gains `onProgress`. Each is a new member of an object core builds or an optional member of one an author builds, so no application changes. An application that opens no region and reports no progress writes the same bytes as before, except that two questions asked at once now take turns.

While a region is drawn, writes to stdout and stderr share one order when both are terminals, and a write that does not pass through core, such as `console.log`, can still land inside a frame. A stack taller than the terminal cannot be erased above its top row, so a view keeps its frame within the terminal's rows.

A tool call's progress lines write their start and end lines into the captured `messages`, which an MCP result returns as text, beside the notifications.

This narrows [ADR-0008](0008-rendered-output-is-a-neutral-call.md)'s call order, which holds within a destination alone: while a region is drawn and both streams are terminals, stdout and stderr share one order. It extends [ADR-0021](0021-every-rendered-byte-passes-through-one-registry-of-replaceable-views.md)'s registry to region frames and to the progress view. It narrows [ADR-0059](0059-a-command-runs-by-name-through-invoke.md)'s invocation options with an observer. It narrows [ADR-0063](0063-the-mcp-plugin-serves-opted-in-commands-as-tools.md)'s server, which sends `notifications/progress`. It narrows [ADR-0082](0082-an-action-asks-through-the-prompts-library-and-one-interaction-decision-governs-questions-and-conditional-requiredness.md)'s questions, which draw in input regions rather than through `out.draw`, its library, which gains an optional plugin, and its rule that nothing guards against two questions at once. It adds each region's `draw` to [ADR-0086](0086-renders-fit-the-destinations-live-columns-and-tables-shrink-to-fit.md)'s render calls that build a fresh context, and core redraws a region's kept frame text without rendering it again. It narrows [ADR-0069](0069-core-hands-log-events-to-onlog-hooks-and-writes-no-log-record.md)'s hooks: the stderr an `onLog` hook writes to under `run()` is coordinated with the open regions, so a hook's line lands above them. It extends [ADR-0090](0090-an-operators-v-or-q-settles-the-runs-verbosity-right-after-graph-build.md)'s verbosity to `out.region`: at verbosity -1 a region without input draws nothing. ADR-0008, ADR-0021, ADR-0059, ADR-0063, ADR-0069, ADR-0082, ADR-0086, and ADR-0090 carry dated entries.

The glossary gains Live region, Frame, Input region, Progress event, Progress line, and Progress style.
