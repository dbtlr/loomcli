# ADR-0106 - A signal ends the process within one bounded shutdown

## Context

[ADR-0105](0105-core-is-the-only-process-listener-and-cleanup-runs-on-every-path-out.md) made core the only process listener and gave runs a cleanup lane, but its core lane met three problems in review before it shipped.

- **Ctrl-C could wait without bound.** A cooperative claim made the first signal only cancel the run, and core then waited for the run to unwind, however long that took. A listener outside core made core leave the end to that listener, and `signal-exit`, which libraries such as execa and ora install, leaves the end to any listener it does not own. So with both installed, each waited for the other and Ctrl-C never ended the process.
- **A cleanup behaved two ways.** `defer` awaited an asynchronous cleanup at a run's unwind and only started it on a signal, so the same cleanup finished in one case and was cut off in the other.
- **The terminal users were left for later.** The prompts reader, live regions, and the background query were to move onto the lane in a later task, so the rules for what they write and restore on a signal were never stated. A region's cancelled line was lost on the immediate path, because core queues every write and re-raised in the same tick.

An operator presses Ctrl-C to stop now. Winding down must feel instant and must not spend time on work, and a lane that permits waiting is a broken contract with the operator. Standard practice in graceful shutdown, such as Go's `Shutdown(ctx)` with a deadline and `close-with-grace` in Node, gives the wind-down a short fixed budget and then ends the process regardless.

## Decision

- **One shutdown for every ending signal.** `SIGINT`, `SIGTERM`, and `SIGHUP` each start the process's shutdown while core listens. Core aborts the signal of every live run, `run()` and `app.invoke` alike, with the signal's name as the source, so work that honors cancellation winds down, a middleware's `finally` and an action's own cleanup included.
- **The budget bounds it.** The shutdown ends at the first of three points: every live run has resolved, the shutdown budget has run out, or a second ending signal arrives. The budget is 500 ms from the first signal unless the Application sets another with `shutdown: { timeout }`, a whole number of milliseconds from 0 through 2147483647, the longest a timer waits; any other value is a declaration error. The budget is fixed at the first signal: with several runs live, the process takes the longest timeout among them, and with no live run the shutdown ends at once. A run that starts during the shutdown starts cancelled and does not extend it. When the last run resolves first, the shutdown ends on the next turn of the event loop, so code that awaited `run()` runs its synchronous part.
- **The end.** Core calls every pending `onShutdown` handler synchronously, newest first, each once, then removes its listeners and re-raises the first signal, so the default action ends the process with the shell's status: 129, 130, or 143. Work still running is cut off.
- **`SIGQUIT` ends at once.** It cancels the runs, calls the handlers, and re-raises with no budget, so the core dump it asks for still happens. A `SIGQUIT` during a shutdown ends it the same way.
- **`onShutdown` is the one cleanup registration.** The action and middleware contexts carry `onShutdown(handler)`, scoped to the run: a handler is removed when its run ends while no shutdown is under way. `@loomcli/core` exports `onShutdown(handler)` for a library or an embedding host, scoped to the process. Both return a function that removes the handler. A handler receives the cause, a signal's name or `'exit'`, and the status the shell sees.
- **Handlers are synchronous by type.** A handler that returns a promise does not compile. A handler restores what must not outlive the process, such as raw mode, the cursor, a child process, or a scratch file, and does it synchronously. Cleanup at a run's ordinary end belongs in the code's own `finally`, which also runs within the budget.
- **The process's own end.** At the process's `exit` event, for a normal end, a `process.exit()` call, or an uncaught exception, core calls every pending handler synchronously, newest first, with `'exit'` and the exit status.
- **A failing handler.** A handler that throws is caught, and the rest still run. A run-scoped handler's throw is an `error` log event, `A shutdown handler failed.`, naming the plugin whose middleware registered it, or none. A process-scoped handler's throw is dropped, because no run is there to log it.
- **Core listens only while asked.** Core listens for `SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`, and the process's `exit` event only while a `run()` is live or an `onShutdown` handler is registered, process-scoped or in a run whose outermost run is `run()`. A live `run()` asks because the application that calls it owns the process for that run, so every run started on argv unwinds within the budget on Ctrl-C, whatever it has open. It listens for `SIGTSTP` and `SIGCONT` only while an `onSuspend` or `onResume` handler is registered. Otherwise every signal has its default effect, so a library still installs nothing nobody asked for, under [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md). An `app.invoke` touches no process, so its handlers never start core listening, though a shutdown under way calls them.
- **Core never waits on another listener.** Core always re-raises once its own listeners are removed. A listener outside core, a raw `process.on` or `signal-exit`'s, receives the re-raised signal and decides what happens next: `signal-exit` then finds itself alone, runs its own handlers, and re-raises, and an embedding host that keeps the process alive does so. Core still cancelled the runs and called the handlers, and a later ending signal starts a new shutdown.
- **Suspend and resume.** `@loomcli/core` exports `onSuspend(handler)` and `onResume(handler)`. On `SIGTSTP` core calls each suspend handler synchronously, newest first, then removes its listener and re-raises `SIGTSTP`, so the default action stops the process, as the glibc manual describes and vim and less do; it listens again once the process continues. On the `SIGCONT` that follows it calls each resume handler in registration order. A `SIGCONT` with no suspend before it calls none.
- **A raw-mode reader raises the signal its key stands for.** In raw mode a key arrives as a byte, so a reader that reads keys from the process's own terminal, `process.stdin` when it is a TTY, raises the signal on its own process: `SIGINT` for Ctrl-C (0x03), `SIGQUIT` for Ctrl-\ (0x1c), and `SIGTSTP` for Ctrl-Z (0x1a). A key then means at a question what it means at a cooked terminal. A reader whose stdin is another stream, which an embedding host or a test supplies, raises no signal, because the process is not that terminal's: Ctrl-C and Ctrl-\ call the action's `cancel()`, and Ctrl-Z does nothing. End of input cancels the run through `cancel()` on any stream.
- **The terminal users.** A question leaves raw mode at the abort and also registers a run-scoped `onShutdown` handler that leaves raw mode and shows the cursor, plus suspend and resume handlers that restore the terminal and redraw it. A live region draws its cancelled line at the abort, and at the shutdown's end, `SIGQUIT`'s included, core writes every region frame still in its write queue straight to the terminal and shows the cursor. The background query restores raw mode through a handler while its read is open, and an interrupt key ends its wait at once.
- **One lane per process.** The lane lives under `globalThis[Symbol.for('loomcli.processLane')]`. The first copy of `@loomcli/core` to load creates it and every later copy uses it, so two installed copies listen once and re-raise once. Its shape is a contract across versions that only grows: no version removes a member or changes what one accepts, and arguments are objects. A copy that finds a member missing goes without what it provides and never creates a second lane.
- **Codes.** `SIGHUP` resolves 129 and `SIGQUIT` 131, beside 130 for `SIGINT` and 143 for `SIGTERM`. `ExitCode`, a cancelled invocation outcome's `exitCode`, and `CancellationReason`'s `source` widen to match, and the manifest's exit-code table gains the two rows. A run that resolves inside the shutdown resolves its signal's code and sets `process.exitCode`, and the process still dies by the signal.
- **What goes.** The cooperative claim and the plugin `signals` field, the signals slot and its `@loomcli/core/slot-taken` case for it, `defer`, `processEvents` and its types, and the exit backstop's re-raise. ADR-0018's run signal, its causes, its first-cause rule, and its cancellation codes carry forward.

## Considered options

- **Keep ADR-0105's cooperative claim.** Rejected. A signal that only cancels lets an action that ignores its signal hold the process for as long as it runs, so Ctrl-C has to be pressed twice.
- **Defer to a listener outside core, as `signal-exit` does.** Rejected. Two libraries that each defer to the other never end the process, and `signal-exit` is the most common one an application installs.
- **Await asynchronous cleanup within the budget.** Rejected. The budget then has to cover work of unknown length, and a cleanup that returns a promise teaches authors to do slow work on the way out. A synchronous handler restores state at once, and the budget covers only the runs' own unwind.
- **No budget: call the handlers and re-raise at once.** Rejected. A run then never unwinds on a signal, so a middleware's `finally`, a region's cancelled line, and a closing write never happen.
- **Listen only while a handler is registered.** Rejected. Whether a middleware's `finally` ran on Ctrl-C would then depend on whether a spinner happened to be open, and a daemon with no handler would end on `SIGTERM` with no unwind at all.
- **Raise the signal from any raw-mode stream.** Rejected. A key from a stream an embedding host or a test supplies would signal that host's whole process, the reason [ADR-0082](0082-an-action-asks-through-the-prompts-library-and-one-interaction-decision-governs-questions-and-conditional-requiredness.md) rejected a self-delivered `SIGINT`.
- **A budget per run.** Rejected. One process ends once, so its runs share one deadline, and the longest declared timeout keeps every run's author whole.

## Consequences

Ctrl-C ends a Loom application within its budget whatever its action does, and a second press ends it at once. A plugin that declared `signals` no longer compiles, which is a breaking change with a migration: remove the field, and move any wind-down into the run's own cancellation handling inside the budget. A daemon that needs a longer drain under a supervisor raises `shutdown.timeout`, whose documentation warns that a larger budget makes a cancelled run take longer to end. The shutdown budget is a timer in core by design. Core's prompts reader, live regions, and background query register handlers, and so will any later first-party terminal user. [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md), [ADR-0018](0018-one-run-signal-carries-cancellation-and-one-owner-brackets-process-signals.md), [ADR-0059](0059-a-command-runs-by-name-through-invoke.md), [ADR-0069](0069-core-hands-log-events-to-onlog-hooks-and-writes-no-log-record.md), [ADR-0082](0082-an-action-asks-through-the-prompts-library-and-one-interaction-decision-governs-questions-and-conditional-requiredness.md), [ADR-0092](0092-core-settles-each-runs-background-once-and-a-theme-entry-may-adapt-to-it.md), [ADR-0095](0095-the-type-bounds-a-declared-exit-code.md), and [ADR-0097](0097-one-ordinary-failure-path-where-an-authors-catch-is-final.md) carry dated entries, and ADR-0105 is superseded whole.

## Status

Proposed. It moves to accepted with the release that ships the shutdown, `onShutdown`, `onSuspend`, and `onResume`, with the prompts reader, live regions, and the background query on them. Process and pseudo-terminal tests prove under Node and Bun that a question sent `kill -TERM` or `SIGHUP` leaves the terminal cooked with the cursor shown, that an action ignoring its signal still ends within the budget, that a second signal ends the shutdown at once, that `signal-exit` and core together still end the process, that a region's cancelled line reaches the terminal, and that Ctrl-Z and `fg` at a question suspend and redraw under a job-control shell.

A later `run()` or a handler from the exported `onShutdown` makes core listen again. Every other clause stands.
- 2026-10-24: Resume follows the re-raise. Once the re-raise returns, core listens for `SIGTSTP` again and then calls the resume handlers in registration order, so a later Ctrl-Z, a resume handler's included, suspends again. The decision is unchanged: suspend handlers run newest first, then `SIGTSTP` is re-raised, then resume handlers run.
- 2026-10-24: The budget holds while the action leaves the event loop free. A process whose main thread is blocked, by a long synchronous loop or a call such as `execSync`, handles no signal until the loop is free, so every signal, `SIGQUIT` included, waits for it; `kill -9` ends such a process at once. Core keeps listening for `SIGQUIT`, so Ctrl-\ still restores the terminal and calls `onShutdown` handlers, rather than leaving a question raw or the cursor hidden. The decision is unchanged.
