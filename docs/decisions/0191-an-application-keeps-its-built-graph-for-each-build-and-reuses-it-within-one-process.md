# ADR-0191 - An Application keeps its built graph for each build and reuses it within one process

## Context

[ADR-0134](0134-a-built-application-builds-its-graph-at-launch-and-loom-build-carries-no-graph.md) keeps graph build at launch for every artifact form: a command-line invocation is one process, so a graph one process builds cannot serve the next, and carrying a graph across processes or building only the routed path were measured and rejected. That record leaves a second case open. A test suite and an embedding host call `run()`, `app.invoke()`, and `inspect()` many times on one Application in one process, and each call runs graph build again: every Command's build, every `onCommandAttach` hook, the option compilation, the frozen graph, the converter check in a development build, and every `onGraphBuilt` hook. On Mimir's command-line application, about 50 Commands and several plugins, one build costs about 7 ms and a whole run 8 to 10 ms, so a usage refusal or `--version` in a test spends nearly all its time rebuilding a graph the previous call already built.

Core already reuses a built graph in one place. An action's `invoke` runs another Command of the graph its own run built and judged, and runs no hook again ([ADR-0059](0059-a-command-runs-by-name-through-invoke.md)). The same reuse can reach every later call on the Application when nothing a call supplies can change the graph a build produces.

Nothing does, for one Application value and one build. Graph build reads the Application's declarations and its installed plugins, which an authoring call never changes on an existing value, since every authoring call returns a new Application. It reads no host fact, environment variable, working directory, or time zone. The one input that differs between calls is the build, development or distributed: a development build asks every validated input's converter and fails a converter that breaks, and a distributed build reads a failing converter's schema as `null` ([Input schema](../core/validation.md#input-schema)). The hooks are author code that core calls with the declarations alone, so under principle 1 a hook that answers differently on a second graph build, or reads a run's state, is the author's defect, as any other mistake in a hook is.

[ADR-0010](0010-one-graph-serves-runtime-and-projections.md) rejected caching the built graph across calls so that a consumer never reads a graph a later declaration change invalidated, and [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md) has each run build the graph anew. That reason does not reach a graph kept on one Application value. A declaration change is an authoring call, which returns a new Application that keeps nothing, and the value that kept the graph never changes, so nothing a kept graph depends on can change after it is built.

The owner settled the shape on 2026-11-18: the key is the Application and its build, so each Application holds at most two built graphs; `check()` always rebuilds, because it collects converter and `onGraphBuilt` faults during the build; a declared default's asynchronous validation still runs on every `run()`, because it reads the run's host; and the record extends ADR-0134 without superseding its launch decision. The rulings named `run()` and `inspect()`, and the owner confirmed on 2026-11-19 that `app.invoke()` reuses the kept graph too (LM-q66).

## Decision

- **An Application keeps the graph it built, one for each build.** The first graph build on an Application value for a development build keeps its graph, and the first for a distributed build keeps its own, so one Application holds at most two. A later `run()`, `app.invoke()`, or `inspect()` on that value in the same build reuses the kept graph: it builds no Command, calls no `onCommandAttach` or `onGraphBuilt` hook, compiles no option table, and runs no converter check. A kept graph holds the table a run routes and parses against, and renders the frozen graph `inspect()` returns at most once, when a reader first asks for it, so a distributed build with no `onGraphBuilt` hook may render it on a later call or never; nothing in it belongs to one run.
- **Each door picks its build as it does today.** `run()` and `app.invoke()` pick the graph their host's [release facts](../core/release-facts.md) name, whether the real process's baked facts or a facts override on a test's process handle. `inspect()` picks the one the baked facts name. A source run, a development artifact, and an artifact with no facts share the development graph. A run whose host names a distributed build and an `inspect()` that reads development facts in the same process use different graphs.
- **One graph object.** Two `inspect()` calls in one build return the same frozen object, and an `inspect()` after a run in that build returns the object the run's middleware, actions, and `onFailure` hooks read. [`locate`](../core/graph-inspection.md#locating-a-word) and the skills plugin's record, which read a graph by its identity, find it on every later call.
- **Only a successful graph build is kept.** A graph build that ends in a fault, from a build rule, a hook that rejects the graph or breaks, or a failing converter in a development build, keeps nothing. The next call builds again, calls the hooks again, and meets the same fault.
- **`check()` keeps nothing and reuses nothing.** It builds the graph anew on every call, calling every hook, whatever an earlier call kept, and its graph never becomes the kept one. It continues past each converter fault and each rejecting hook, so its graph may read a failed converter's `schema` as `null` in a development build, which no run reads.
- **Each run's own work stays each run's.** Host capture, environment preparation, the background, verbosity, routing, parsing, the input-source stage, validation, middleware, and the action run on every call. Every `run()` and every `app.invoke()` still passes every declared default and implied value through its validator, because that validation reads the run's host; an action's `invoke` keeps reusing its run's validated values as before.
- **Hooks answer from the declarations alone.** An `onCommandAttach` and an `onGraphBuilt` hook give the same result on every graph build of one Application in one build, and read no host, environment, clock, or per-run state; a hook receives nothing else to read. A third-party hook that breaks this is the author's code under principle 1, and Loom adds no detection for it.
- **A launch is unchanged.** A command-line invocation is one process whose one `run()` builds the graph, as ADR-0134 decides. Nothing is carried between processes, and `loom build` carries no graph.

## Considered options

- **Building anew on every call, as ADR-0010 and ADR-0009 had it.** Rejected for repeated calls in one process. ADR-0010's reason, that a later declaration change could invalidate a kept graph, cannot arise: an authoring call returns a new Application with nothing kept, so a kept graph always matches the declarations of the value that holds it. Building anew would cost every test and embedded call a whole graph build for a graph identical to the last.
- **A cache keyed by the Application alone.** Rejected. A development build's graph has run the converter check and holds each converter's schema, and a distributed build's reads a failed converter's schema as `null`, so one graph cannot answer both builds, and a test that runs one Application under both facts would read the wrong one.
- **Keeping the graph `check()` builds.** Rejected. `check()` continues past faults a run stops at, so its graph is one no run may read, and a caller that calls `check()` to collect the faults expects every hook to judge the declarations on that call.
- **Keeping a faulted build's fault.** Rejected. A fault is the failure path, where a second build's cost does not matter, and replaying a kept fault would make a hook's second call unobservable for no gain.
- **Keeping the validated declared defaults too.** Rejected by the owner. A default's validator reads the run's host, such as a `path()` resolved against the working directory, so its verdict belongs to each run.
- **Only `run()` reuses, and `app.invoke()` builds per call.** Rejected. `app.invoke()` is the embedding host's door, shares `run()`'s run body and build, and picks its build from its host's release facts as `run()` does, so a different rule would serve the embedded callers this record exists for worse and keep two build paths.
- **A cache across processes or a routed-path build.** Out of scope: ADR-0134 rejected both for a launch, and this record changes nothing about a launch.

## Consequences

- A second `run()` on one Application reads its kept graph, so a usage refusal or `--version` costs only the run's own work. A test suite that runs many cases against one Application pays one graph build per build it uses.
- A test that counts hook calls sees one `onCommandAttach` call per Command and one `onGraphBuilt` call per build across any number of `run()`, `app.invoke()`, and `inspect()` calls on one Application, and a fresh count on every `check()`. A test that needs a fresh build calls `check()` or builds a new Application value.
- A kept graph lives as long as its Application value, so a process holds at most two graphs for each Application it keeps.
- Two runs of one Application that overlap in one process read one graph object, as an action's `invoke` and its run already do, which holds because the graph and its tables carry no per-run state.
- A consumer that changes a declared default's wrapped value or a `schema` object, the two parts of the graph that are not frozen, changes what every later call on that Application reads. Their types are read-only, so only a value that bypasses the types does this, and [ADR-0093](0093-a-value-that-bypasses-the-types-gets-no-rule.md) gives it no rule.
- This record supersedes in part [ADR-0010](0010-one-graph-serves-runtime-and-projections.md): its sentence that `inspect()` caches nothing, and its rejection of caching the built graph across calls, for calls on one Application value in one build within one process. ADR-0010's other rules stand, a graph build still applies every rule before any token is read, and `inspect()` and `run()` still build from the same declarations in the same order.
- It extends ADR-0134 and narrows clauses of seven records. ADR-0134's consequence that the lifecycle hook reference stays as it is, with `onCommandAttach` and `onGraphBuilt` run at every graph build: they still run at every graph build, and a graph build now happens once per Application and build within one process. [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md)'s sentence that each run captures the host and builds the graph anew: each run still captures the host, and builds the graph only when its Application keeps none for the run's build. [ADR-0060](0060-ongraphbuilt-judges-the-built-graph-and-never-contributes.md)'s **When**, which calls the hook on every `run()`, `inspect()`, and `app.invoke()`, and its consequence that each converter runs once per run: both now hold per graph build. [ADR-0028](0028-plugins-run-code-at-lifecycle-hooks-and-middleware-reads-the-request.md)'s consequence that a plugin with a hook pays one call per Command on every invocation, since the graph builds on every run. [ADR-0030](0030-an-input-carries-its-json-schema-as-a-core-graph-fact.md)'s 2026-09-19 entry, which calls each converter on every `inspect()` call and on every run with a middleware chain, and its 2026-09-29 acceptance entry, in which `inspect()` and every `run()` of a development build call every converter at build: each converter is called once per graph build that renders the frozen graph, and a development build's check runs on every graph build. [ADR-0188](0188-the-skills-plugin-generates-each-skills-command-references-from-the-graph-at-install.md)'s consequence that the skills plugin's hook makes the graph frozen on every run: it does so once per graph build. ADR-0059's decision that `app.invoke` builds the graph for each call and runs every hook: it does so as `run()` does, which now reuses a kept graph. ADR-0009, ADR-0010, ADR-0028, ADR-0030, ADR-0059, ADR-0060, ADR-0134, and ADR-0188 carry dated entries.
- The reference amends with it: [Graph inspection](../core/graph-inspection.md), [Lifecycle hooks](../core/lifecycle-hooks.md), [Invocation by name](../core/invocation.md#invocation-by-name), and the glossary's **Graph build** and **Invocation**.

## Status

Proposed. It moves to accepted in the release PR of the release that ships it. The implementation adds a dated entry with the measured cost of a usage refusal on a second run.

- 2026-11-19: Implemented. A kept graph also holds where each input was declared and the list of local inputs, each derived once from the graph, which every run's validation of declared defaults reads. Measured in process on Node 24 with a mock process handle, on an Application of 50 Commands, each with three options, one of them with a declared default, and an argument, with `help()`, `version()`, and `format()` installed: a usage refusal for an unknown option on a repeated `run()` took a median of 3.3 to 8.5 ms per run before, across three runs of 300 rounds on a shared host, and 0.52 to 0.63 ms after. What a reused run still spends goes mostly to validating the 50 declared defaults and rendering the failure.
- 2026-11-19: [ADR-0193](0193-invoke-takes-a-per-call-time-zone-and-mcp-reads-it-from-request-metadata.md), proposed, narrows **Each run's own work stays each run's** for an action's invocation: declared defaults and implied values validate anew against the call's host when its effective zone differs from their validation zone. Same-zone calls reuse them, and no graph or lifecycle hook rebuilds. It binds when that record is accepted.
