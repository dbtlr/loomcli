# ADR-0105 - Core is the only process listener, and cleanup runs on every path out

## Context

[ADR-0018](0018-one-run-signal-carries-cancellation-and-one-owner-brackets-process-signals.md) settled two concerns with one rule. What a signal means for the run has one answer per process, so it needs one owner. What must happen before the process ends has many contributors and needs no arbitration. Node's `process.on` takes over a signal's default disposition, so a plugin that only wanted cleanup had to own the policy, and with no owner nothing could clean up on a signal at all.

The cost is visible to the operator. No first-party plugin claims the signals slot, so a shipped application gets the default disposition and cleans up nothing. A question puts stdin in raw mode and hides the cursor. A `kill -TERM`, a supervisor, or a closed terminal window ends the process with the terminal still raw and the cursor still hidden. Ctrl-Z mid-question is a byte the reader ignores, so the operator cannot suspend, and nothing redraws after `fg`. The help pager needs to end its child on a signal, and its own listeners would conflict with the single-owner rule.

The ecosystem's answer is `signal-exit`. It holds one listener per signal, calls every registered exit handler synchronously, removes its listeners, and re-raises, so the process ends as it would have, only with its cleanup done. It coordinates several installed copies through a global and re-raises only when no other listener remains.

## Decision

- **Core is the only listener, and it listens lazily.** Core listens for `SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`, and the process's own `exit` event only while an `exit` listener is registered, a cleanup is pending in a run whose outermost run is `run()`, a live `run()` holds a cooperative claim, or a `run()` a signal cancelled has set `process.exitCode`, until the process ends. It listens for `SIGTSTP` and `SIGCONT` only while a `suspend` or `resume` listener is registered. With none of these, core holds no listener and every signal has its default effect, so [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md)'s rule that a library installs nothing nobody asked for still holds: a subscriber is someone asking. An `app.invoke` call touches no process, so its cleanups never start core listening.
- **One process event object.** `@loomcli/core` exports `processEvents`, an `EventTarget` typed by an event map of `exit`, `suspend`, and `resume`. It lives under `globalThis[Symbol.for('loomcli.processEvents')]`. The first copy of core to load creates it and every later copy uses the one it finds, so two installed copies never both listen or both re-raise, and the object's shape is a contract across versions. `exit` carries a `ProcessExitEvent` with `cause`, a signal name or `'exit'`, and `code`, the status the shell sees. It fires at most once per process, and its listeners run synchronously, newest registration first. `suspend` and `resume` carry no payload.
- **A run-scoped cleanup.** The action and middleware contexts gain `defer(cleanup)`, which returns a function that runs the cleanup now, once, and removes it. A cleanup runs exactly once, at the first of three points: the returned function, the run's unwind, or the immediate path or the `exit` backstop. Runtime hook contexts get none, and build-time hooks never will. Every caller outside a run uses `processEvents`.
- **The immediate path is the default.** A signal takes the immediate path unless a live run that is not yet cancelled claims it cooperatively, or a listener outside core also receives it, as Going around the lane states. Core aborts every live run's signal with the signal as its source, so each abort listener runs, each region draws its cancelled line, and each question leaves raw mode. Then core calls every pending cleanup, then every `exit` listener, each synchronously and newest first. A returned promise is started, not awaited. Core removes its listeners and re-raises the signal. Writes on this path are best effort, so a write to a terminal that has hung up is dropped.
- **A signal never waits on cleanup.** Waiting happens only at a run's own unwind. On a signal, restoration must be synchronous, and the operator's next press is the only bound. Core sets no timer.
- **A cooperative claim per signal.** The plugin field `signals` lists the cooperative signals, a subset of `SIGINT`, `SIGTERM`, and `SIGHUP`. An unlisted signal stays immediate, and `SIGQUIT` cannot be listed. The slot keeps one owner, a second claim stays the Application constructor's declaration error naming both plugins, and an empty list claims nothing. The pack ships `signals({ cooperative? })`, defaulting to all three.
- **One process-wide decision.** A signal is cooperative while at least one live run claims it and is not yet cancelled. Core then cancels every live run not yet cancelled, claimant or not, with that signal as the source, absorbs the signal, and lets each run unwind. Otherwise the signal takes the immediate path, which is also the force path: a second Ctrl-C after a cooperative cancel finds every claimant cancelled. `SIGQUIT` always takes the immediate path, and the re-raise keeps its core dump.
- **The unwind order.** At a run's own end, on a normal end and after a cooperative cancel, the chain settles, core closes the open regions, awaits the pending cleanups one at a time, newest first, renders the failure report, and resolves the code. An invocation by name follows the same order inside the call, and its cleanups finish before it resolves its outcome.
- **A failing cleanup.** Every cleanup runs, whatever an earlier one did. At the unwind, the first cleanup that throws or rejects in a run that would otherwise succeed becomes the run's failure, as if the action had thrown it, under [ADR-0097](0097-one-ordinary-failure-path-where-an-authors-catch-is-final.md). Any other throw, in a run that already failed or was cancelled, after that first one, or on the immediate path or the `exit` backstop, changes no outcome: core publishes it as an `error` log event and writes no report.
- **The `exit` backstop.** At the process's own `exit` event, for a normal end, a `process.exit()` call, or an uncaught exception, core calls every pending cleanup synchronously, newest first, then fires `exit`, then re-raises when `process.exitCode` still holds the code of a run a signal cancelled and no listener outside core is installed for that signal. It fires `exit` only when the immediate path has not.
- **A cooperative run ends by its signal.** A run cancelled by a signal resolves that signal's code and sets `process.exitCode`, and the author's code after `run()` runs. When the process then ends on its own and `process.exitCode` still holds that code, core's `exit` backstop calls the `exit` listeners and re-raises the signal, so the process dies by it. A calling shell that follows wait-and-cooperative-exit then stops its script, as it does for any program interrupted by Ctrl-C. A host that sets another code, or keeps running, is unaffected.
- **Suspend and resume.** On `SIGTSTP`, core calls the `suspend` listeners synchronously, newest first, and then stops the process with `SIGSTOP` on itself. On the `SIGCONT` that follows, it calls the `resume` listeners in registration order. A suspend cancels no run, and a `SIGCONT` with no suspend before it fires nothing. A raw-mode reader joins by raising `SIGTSTP` on the process for a Ctrl-Z byte. `SIGWINCH` is not a process event, because a terminal stream's `resize` serves redraws, and neither is `SIGPIPE`, because [ADR-0104](0104-a-closed-reader-on-stdout-ends-the-run-with-141.md)'s closed pipe ends the run.
- **Codes.** `SIGHUP` resolves 129 and `SIGQUIT` 131, beside 130 for `SIGINT` and 143 for `SIGTERM`. `ExitCode`, a cancelled invocation outcome's `exitCode`, and `CancellationReason`'s `source` widen to match, and the manifest's exit-code table gains the two rows.
- **What carries forward from ADR-0018.** One run signal per run. Its causes: a caller-supplied signal, a process signal, the action's `cancel()`, and a closed pipe. The rule that the first cause to abort it fixes the reason and the code. Core keeps awaiting what already runs and starts nothing new after cancellation. A cancelled run resolves its code whatever the action did afterward. Cancellation outranks a broken failure view, `onFailure` hook, or destination. An invocation by name has its own run signal, derived from its parent's, and an action's `cancel()` cancels only its call. Core never calls `process.exit()`.
- **Going around the lane stays allowed.** A raw `process.on` listener is the author's choice, and core never forbids it. Its documented cost is that it takes over that signal's default disposition. A signal that a listener outside core also receives, from a raw `process.on`, takes neither path's end: core cancels every live run not yet cancelled with that signal as the source, lets each unwind with its cleanups awaited, fires no `exit`, and does not re-raise, so that listener decides whether the process ends, and `exit` fires once, when it does. This is how `signal-exit` treats a listener it does not own.

## Considered options

- **Keep ADR-0018 and add cleanup listeners per plugin.** Rejected. Each plugin would install its own listener, which is the ad hoc arbitration ADR-0018 rejected, and two plugins that both want cleanup would still fight over the default disposition.
- **Any subscriber makes the run cooperative.** Rejected. Installing the prompts library would silently change what Ctrl-C does for the whole application.
- **Await async cleanup on a signal, and let a second signal force.** Rejected. The first press would feel dead, and the second would skip the restoration that matters. An operator presses Ctrl-C again, so a signal never waits.
- **Everything through contexts, with no exported object.** Rejected. A library and an embedding host have no Loom context, so they would be shut out of cleanup.
- **The policy as an Application setting.** Rejected. Every other policy in Loom arrives through a plugin, and a plugin could not bring its own.
- **Each run decides for itself, as ADR-0018's several-runs rule did.** Rejected. It needs a listener per run again, and it cannot express an immediate run beside a cooperative one without ending the cooperative run's process.
- **Exit 130 normally after a cooperative unwind.** Rejected. A shell script loop that runs the application keeps looping through every Ctrl-C, because the shell reads a normal exit as a handled interrupt.
- **Re-raise as the cooperative run settles.** Rejected. The author's code after `run()` would never run, and core does not own the process.

## Consequences

Core gains its one piece of process-wide state, shared across copies through `globalThis`. Every first-party feature that changes terminal state moves onto the lane: the prompts reader, live regions, the background query, and the help pager. Under the immediate default, a middleware's `finally` never runs on a signal, so restoration belongs in `defer`. `ExitCode` and `CancellationReason` widen, which is an ordinary change because both are produced unions. The `exit` backstop's re-raise depends on the runtime honoring a signal a process raises on itself during its `exit` event. The implementation proves it under Node and Bun, and if either refuses, a cooperative run exits normally with its code and this record carries a dated entry saying so. [ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md), [ADR-0018](0018-one-run-signal-carries-cancellation-and-one-owner-brackets-process-signals.md), [ADR-0059](0059-a-command-runs-by-name-through-invoke.md), [ADR-0069](0069-core-hands-log-events-to-onlog-hooks-and-writes-no-log-record.md), and [ADR-0097](0097-one-ordinary-failure-path-where-an-authors-catch-is-final.md) carry dated entries.

## Status

Proposed. It moves to accepted with the release that ships `processEvents`, `defer`, lazy listening, the immediate path, the cooperative claim with `SIGHUP`, `SIGQUIT`, suspend, and resume, and the `signals()` plugin. Process and pseudo-terminal tests prove, under Node and Bun, that a real process with a question open, sent `kill -TERM` or `SIGHUP`, leaves the terminal cooked with the cursor shown. They also prove that core holds no listener with no subscriber, the immediate and cooperative orders, the force path, the end by signal after a cooperative unwind, each code, suspend and `fg` under a job-control shell, and two copies of core sharing one object.
