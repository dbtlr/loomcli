# ADR-0107 - A run reads the process through one process handle

## Context

[ADR-0009](0009-core-captures-the-host-and-resolves-an-exit-code.md) has `run()` capture the host from the process and accept whole-field overrides, and [ADR-0059](0059-a-command-runs-by-name-through-invoke.md) gives `app.invoke` five of those overrides. Every field a caller omits falls back to the process the run happens to be in. So a test that states `argv` alone reads the developer's `NO_COLOR`, `COLUMNS`, `HOME`, and every bound variable, and the real stdin, terminal facts, platform, and time zone, and its result changes with the machine. Loom's own process-test helper strips a list of known variables before each child starts for that reason.

Core also reaches the process directly, outside the host. `run()` writes `process.exitCode`, core's signal listeners and re-raise act on the global `process`, environment preparation writes `process.env`, and first-party code reads `process.getuid()`, `process.arch`, and `process.report`. A host override cannot reach any of these, so none of them can be stated by a test, and an in-process test changes the exit status of the test runner's own worker.

The process also reaches a run outside both. Core's `applicationDirectory` and the configuration, completion, logging, manpage, service, and skills plugins read `HOME` from the environment, the toolchain asks `os.tmpdir()` for its scratch folders, and the service and completion plugins, the update notices, and the toolchain's `git`, `pnpm`, and `bun` start child programs through `node:child_process`. So a test of the service plugin runs the machine's `systemctl`, a test of `loom` runs its `git`, and a test that leaves `HOME` out writes under the developer's home. An application's own source can do the same, and nothing tells its author.

Replacing the global `process` in a test does not answer it. The test runner lives in the same worker and writes to the same `process`, the only practical replacement is a runner's own stubbing API, which a runner-neutral testing package cannot depend on, and tests running concurrently in one worker share the one global.

## Decision

- **One process handle per run.** A process handle holds every process fact core reads and receives every process effect core makes. `run({ process })` and `app.invoke(path, values, { process })` bind one handle when the run enters, and core never replaces it during the run. A run given none binds the real process's handle, and an action's `invoke` binds its own run's.
- **The facts.** The handle holds `argv`, `program`, `env`, a `cwd()` read that throws when the working directory cannot be read, `home`, `tmpdir`, `platform`, `arch`, `libc`, `uid`, `timeZone`, `release`, an optional `readSource`, the three streams, and their terminal facts. Core copies them into the run's Host at entry, as ADR-0009 captures them today, and the Host gains `arch`, `libc`, `uid`, `home`, `tmpdir`, `raise`, and `spawn`. Terminal width and height stay live reads, as [ADR-0086](0086-renders-fit-the-destinations-live-columns-and-tables-shrink-to-fit.md) states, through the handle's terminal facts.
- **The effects.** The handle's `exitCode` is the one member core writes, and `run()` writes it once the run's code is final; `app.invoke` never does. The handle's `signals` is the signal source core listens on and re-raises on, and its `exit` event is the process's own end. An optional `publishEnv` receives the variables environment preparation copies out, under [ADR-0084](0084-dotenv-prepares-an-allowlisted-environment-before-inputs.md). The handle's `spawn` starts each child program the run starts.
- **The home and temporary folders.** `home` is the operator's home folder and `tmpdir` the folder for temporary files. Both follow the handle's environment, as `os.homedir()` and `os.tmpdir()` do: `home` is the handle's `env.HOME` when it is set and absolute, and otherwise, for the real process, the home the user database holds for its user, which is `os.homedir()`'s fallback, or the empty string when there is none; `tmpdir` is the handle's `env.TMPDIR` when it is set and absolute, and otherwise `/tmp`, on Linux and macOS alike, so the machine's `TMP` and `TEMP` never reach a run whose `env` was supplied. A supplied `home` or `tmpdir` wins over both, so an absolute `HOME` in the handle's environment and `home` never disagree unless `home` is supplied. Every read of the home in Loom's packages moves from `HOME` in `env` onto `host.home`, so there is one way: core's `applicationDirectory`, whose `from` gains `home`, the log destination an `onLog` hook receives, which gains `home`, the configuration, completion, logging, manpage, service, and skills plugins, and the toolchain, whose scratch folders move onto `host.tmpdir`. The XDG base-directory variables and zsh's `ZDOTDIR` are environment facts, so they are still read from `host.env`, and an absolute one still wins over the folder under the home wherever it does today. A home that is empty or not an absolute path is unresolved, named by `HOME`, the variable an operator sets to fix it. Core copies both folders into the Host at entry, before environment preparation adds variables, so a `HOME` or `TMPDIR` that a `.env` file adds changes neither folder. Code that wants who the user is reads `host.uid`, and the name to show for them `host.env.USER`, so nothing calls `os.userInfo()`.
- **Child programs.** `spawn(command, args, options)` is the run's one way to start a child program, and the one method for it: a child the run waits for, one whose output streams to a run's stream, and one released to outlive the run are options of one call. It runs no shell. `cwd` and `env` default to the run's, and core fills them before it calls the handle. `input` is the child's whole stdin, or `stdin: 'inherit'` gives it the run's own, never both, so an interactive child such as `$EDITOR` can run; each of `stdout` and `stderr` is captured, ignored, inherited from the run's own stream, or piped into a `Writable`. Core passes `inherit` to the handle only when the run's stream is the handle's own, and the run's stream as a `Writable` otherwise, as under an invocation by name; the real process's handle passes its own standard streams as their descriptors. It returns at once a child whose `exited` never rejects and answers the exit code, 128 plus the signal's number for a child a signal ended, and the captured output, or that the child could not start. An abort of `signal` ends the child with `SIGTERM`, `kill(signal)` delivers a signal to it, and `detached: true` starts it in its own process group with every stream ignored, and the process does not wait for it. It sets no time limit. The service plugin's `systemctl`, `loginctl`, and `launchctl`, the completion plugin's profile query, the skills, completion, and manpage refreshes, the update notices' refresh, and the toolchain's `git`, `pnpm`, and `bun` move onto it, so the toolchain's synchronous calls become asynchronous. The toolchain's Bun signal forwarding goes through the child's `kill` until it moves onto `onShutdown`. Its types are stated in the [host reference](../core/host.md#child-programs).
- **Core reads the global `process` in one module.** That module builds the real process's handle. Every other read of a process fact and every process effect goes through the run's handle, in core and in the libraries that run inside an author's run: `@loomcli/plugins`, `@loomcli/prompts`, and `@loomcli/validators`, in `@loomcli/testing`, whose mock reads nothing from the process, and in the `loom` toolchain, an Application Loom ships. A repository lint rule bans the `process` global in their source, and `homedir`, `userInfo`, and `tmpdir` from `node:os` and every import of `node:child_process` beside it, each message naming its replacement. The exceptions are named in the rule's configuration. The real handle's module is the one exception for the `node:os` calls and `node:child_process`. For the `process` global the exceptions are that module; the configuration plugin's guard of the YAML library's debug variables, which must touch the global because the library reads it; the toolchain's application reader, which is its own child program; and the toolchain's Bun signal forwarding, until it moves onto `onShutdown`.
- **`processHandle(fields)` builds the real process's handle.** `@loomcli/core` exports it. A supplied field replaces its whole field, apart from `signals`, `spawn`, and `publishEnv`, which it does not take, as ADR-0009's overrides do, so an environment map replaces the process's map rather than merging into it, and `home` and `tmpdir` follow the supplied map: `processHandle({ env: { HOME: '/srv/notes' } })` has the home `/srv/notes`. Every handle it builds shares the real process's signal source, writes `exitCode` to `process.exitCode`, and supplies `publishEnv`, which writes `process.env`, only when neither `env` nor `cwd` was supplied, and starts real children through `node:child_process`.
- **`mockProcess(fields)` builds a sealed handle.** `@loomcli/testing` exports it. Every fact has a fixed default that reads nothing from the process, a supplied field replaces its default, the streams record what a run writes, and the handle has a signal source of its own. Its `home` and `tmpdir` follow its `env` as the real handle's do, and fall back to `/loom-test/home` and `/loom-test/tmp`, neither of which exists, so a test that writes files supplies a real folder. Its `programs` field scripts each child program by the command the run names, answering the exit code and output from the call without running anything, and a command with no script throws from `spawn` with a sentence that names the command, so the run fails. Its defaults and members are stated in the [testing reference](../libs/testing.md#mockprocess). A test runs an Application through `app.run({ process: mockProcess(...) })` and reads the mock, so the package adds no second way to run one.
- **One lane per signal source.** [ADR-0106](0106-a-signal-ends-the-process-within-one-bounded-shutdown.md)'s lane belongs to a signal source, not to the process. The real process's source keeps its lane under `globalThis[Symbol.for('loomcli.processLane')]`, shared by every copy of core and every handle `processHandle` builds, so one process still listens once and re-raises once. That global object also holds the real process's one signal source, which every copy's `processHandle` uses, and a `WeakMap` from every other source to its lane, so every copy of core resolves the same lane for any source and a mock's lane goes once nothing holds the mock. A mock's source has a lane of its own, so a signal raised on a mock reaches only the runs that hold it, and a shutdown on the real process never reaches them. A `run()` asks its source's lane to listen from the moment it is called, before its first await.
- **A raw-mode reader raises through the host.** A reader that reads keys in raw mode calls `host.raise(signal)` for the key it read. It raises the signal on the run's signal source when `host.stdin` is that source's own terminal, `process.stdin` for the real process, and answers `true`; for any other stdin, a mock's included, it raises nothing and answers `false`, and the reader cancels the run as ADR-0106 states. So the prompts library and an author's reader follow the rule without reading the handle.
- **Checks only the real process can answer.** Two checks read the real process and live in the module that builds the real handle. The background query's check that the process is in its terminal's foreground applies when the run's stdin is a real terminal stream, a terminal device of the process such as `process.stdin` or a stream opened on `/dev/tty`, whatever the handle; for any other stdin, such as a mock's, there is no job control to compare, so core skips the check and the query runs whenever [ADR-0092](0092-core-settles-each-runs-background-once-and-a-theme-entry-may-adapt-to-it.md)'s skips allow it. The check that a content input's path in an invocation by name does not resolve to the process's own stdin, macOS's included, applies to every such call, whatever its handle, because a path reaches the real file system.
- **What the handle leaves out.** The handle owns a process's facts, its effects, and the child programs it starts. Clocks, timers, randomness, the network, and the file system stay outside it, so a mock does not seal them, and a test masks timestamps and elapsed times in what it compares.
- **The author's lint rule.** `@loomcli/eslint-plugin` ships `host-bypass` in its recommended set, under [ADR-0098](0098-lint-is-the-author-guidance-lane.md)'s contract rule. It reports the global `process`, `globalThis.process`, `global.process`, an import of `process` or `node:process`, `homedir`, `tmpdir`, and `userInfo` from `os` or `node:os`, and an import of `child_process` or `node:child_process` in an application's source, and each message names its replacement: `host.env`, `host.home`, `host.tmpdir`, `host.uid`, `host.spawn`, `out`, or the host member for what was read. An entry module needs no exception, because `app.run()` given no handle binds the real process. A test file, whose name holds `.test.` or `.spec.`, is left alone, because a test runs outside any run and is where a real folder or a machine fact is handed to a mock. Its forms are stated in the [plugin reference](../libs/eslint-plugin.md#host-bypass).
- **What goes.** `RunOptions.host`, the `HostOverrides` type, and `app.invoke`'s `host` option. `RunOptions` keeps `rendering` and `signal`.

## Considered options

- **Keep host overrides and add sealed defaults in the testing package.** Rejected. The direct reads of `process.exitCode`, signals, `getuid`, and the architecture stay out of reach, and two ways remain to give a run its facts.
- **Replace the global `process` in tests.** Rejected, for the reasons in the context: the runner shares it, only a runner-specific API replaces it, and concurrent tests share it.
- **Keep `host` beside `process`, applied on top of the handle.** Rejected. Two places would set the same fact, and their precedence would need its own rule.
- **A run entry in the testing package that wraps `run()` and returns the exit code and captured streams.** Rejected. It is a second way to run an Application, and everything the mock gains, such as raising a signal, would have to be threaded through the entry's options.
- **One lane per process for every handle.** Rejected. A signal a test raises on a mock would shut down every run in the worker, and the real process's shutdown would reach a test's runs.
- **One lane per handle object.** Rejected. Two handles `processHandle` built over the same process would each listen on it and each re-raise.
- **The real machine's platform, time zone, and working directory as the mock's defaults.** Rejected. The test's result would change with the machine, which is the leak the handle removes.
- **The home read from `HOME` in `host.env` at each lookup, as before.** Rejected. Each lookup would repeat the absolute-path rule, a `.env` file could move every folder Loom writes, and an unset `HOME` would give no home where `os.homedir()` answers from the user database.
- **A home that ignores the handle's environment.** Rejected. A caller that states `HOME` would get a home that disagrees with it, and would have to state the same fact twice.
- **Two child methods, one that runs a child to completion and one that streams it.** Rejected. Both start one child the same way and differ only in where its output goes, which the stream options state, so one method serves them, and a mock scripts one call shape.
- **A synchronous `spawn`, beside the asynchronous one or chosen by an option.** Rejected. A synchronous child blocks the event loop for as long as it runs, so the run signal, the shutdown's budget, and the live regions stand still behind it, and the toolchain's synchronous `git`, `pnpm`, and `bun` calls become asynchronous instead.
- **The clock in the handle.** Rejected. The handle owns the process, not the machine: a test that compares a timestamp or an elapsed time masks it, and the same holds for timers, randomness, the network, and the file system.
- **An exception for the entry module in the author's lint rule.** Rejected. `app.run()` given no handle binds the real process, so an entry module has no reason to read it.

## Consequences

Every fact and effect of a run can be stated, so a test runs in the test's own process with nothing taken from the machine, and the shutdown, `onShutdown` order, and re-raise of ADR-0106 are testable in-process through a mock's signal source. A real signal on a real terminal, a pseudo-terminal, a real shell, and a process's own exit status remain what a process test proves, under [ADR-0103](0103-process-acceptance-comes-from-looms-own-pipeline-and-the-packed-consumer.md).

Removing `RunOptions.host`, `HostOverrides`, and `app.invoke`'s `host` is a breaking change with a migration: `run({ host: fields })` becomes `run({ process: processHandle(fields) })`, and a test that wants nothing from the machine uses `mockProcess(fields)` instead. `ProcessHandle` is a type a caller may implement by hand, so a required member a later release adds to it is breaking for such a caller; `processHandle` and `mockProcess` build complete handles. Adding `arch`, `libc`, `uid`, `home`, `tmpdir`, `raise`, and `spawn` to the Host, and `home` to the log destination, is not breaking, because core builds both. `applicationDirectory`'s `from` gaining `home` is breaking for a caller that passes its own `{ env, platform }`, with a migration: pass the run's host, or add `home`. An operator whose `HOME` is unset or relative now has a home from the user database, where every lookup that needed one used to refuse. A new lint rule reports what it did not before, so an application that adopts the release meets `host-bypass` reports in source that reads the process.

ADR-0009, ADR-0051, ADR-0054, ADR-0059, ADR-0065, ADR-0070, ADR-0071, ADR-0079, ADR-0080, ADR-0084, ADR-0086, ADR-0089, ADR-0092, ADR-0098, ADR-0100, ADR-0102, ADR-0103, and ADR-0106 carry dated entries naming what this record changes in each.

## Status

Proposed. It moves to accepted with the release that ships the process handle, `processHandle`, `mockProcess`, `host.spawn`, and the `host-bypass` rule, once the repository lint rule holds over the six packages with only the named exceptions, every child program Loom starts goes through `host.spawn` apart from the foreground check's `ps`, the real handle's own child, run inside the real handle's module, and a mock's run is proven to read nothing from the test's process and start no real program under Node and Bun.
