# Installation record

```ts
type ApplicationDirectory = 'installation' | 'logs' | 'cache';
type DirectoryLookup =
  | { readonly path: string } // the absolute directory
  | { readonly variable: string }; // the variable it needs that is unset, empty, or not absolute
declare function applicationDirectory(
  kind: ApplicationDirectory,
  application: string,
  from: { readonly env: Host['env']; readonly platform: string },
): DirectoryLookup;
```

```sh
# The installer script, once the verified binary of notes is at /home/me/.local/bin/notes,
# writes ~/.local/state/notes/installation/install.json:
{"format":1,"method":"script","path":"/home/me/.local/bin/notes","digest":"sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"}
```

```ts
// src/commands/about.ts: the binary at that path reads it
const { installation } = host.release;
return out.print(installation === undefined ? 'Installed some other way.' : `Installed by ${installation.method} at ${installation.path}.`);
```

The installation record is one directory per application and per user that says how the application was installed and which files its installers wrote. It holds `install.json`, the installation, and one file for each first-party plugin that installs files, named for the plugin, such as `service.json`, or one for each of its targets when a plugin installs into independent targets, named for the plugin and the target, such as `skills.claude.json`. Each file has its own writers, and each writer replaces only its own file, whole, through a temporary file in the same directory and a rename, so no writer reads or merges another's. Core reads `install.json` and writes nothing. [ADR-0071](../decisions/0071-an-installation-record-per-application-says-how-it-was-installed-and-what-its-installers-wrote.md) records the decision.

- **The directory.** `applicationDirectory('installation', name, host)` resolves it from `env` and `platform` alone, `applicationDirectory('logs', name, host)` resolves the [logging plugin's](../plugins/logging.md) default directory, and `applicationDirectory('cache', name, host)` resolves the directory of data the application can lose, such as the [update notices'](../plugins/self-update.md#update-notices) cache:

  | Platform | `installation` | `logs` | `cache` |
  | --- | --- | --- | --- |
  | `darwin` | `$HOME/Library/Application Support/<app>/installation/` | `$HOME/Library/Logs/<app>/` | `$HOME/Library/Caches/<app>/` |
  | any other | `$XDG_STATE_HOME/<app>/installation/` | `$XDG_STATE_HOME/<app>/` | `$XDG_CACHE_HOME/<app>/` |

  On any other platform, an `XDG_STATE_HOME` that is unset, empty, or not an absolute path is replaced by `$HOME/.local/state`, and such an `XDG_CACHE_HOME` by `$HOME/.cache`. A `HOME` that is unset, empty, or not an absolute path cannot give the directory, and the lookup answers `{ variable }` with its name. `<app>` is the application's name, which the [portable name](../glossary.md#names-and-routing) grammar keeps safe as one path segment. The platform chooses the row and its variables; the running process's path rules judge an absolute path and join the segments. The function reads no file and creates nothing. `win32` takes the row for any other platform, under [ADR-0100](../decisions/0100-acceptance-plans-live-beside-the-tests.md).
- **`install.json`.** One line: `{"format":1,"method":"<method>","path":"<path>","digest":"sha256:<hex>"}` and a newline, the members in that order, where `path` is the absolute path of the installed binary and `<hex>` the 64 lowercase hexadecimal digits of its SHA-256 digest. The method `script` means an installer script put the binary there, and a plugin that replaces the binary may replace it. Two writers write the file: the installer script, after it moves a verified binary into place, and self-update, after it replaces the binary, each through the recipe's temporary file and rename.
- **The shell recipe.** An installer script writes `install.json` with POSIX `sh` under `set -e` and no JSON parser, on Linux and macOS:

  ```sh
  # $app is the application's name; $target is the installed binary's absolute path.
  case $target in
    *[\"\\]* | *[[:cntrl:]]*) echo "$app: The install path holds a quote, a backslash, or a control character. Choose another install directory." >&2; exit 1 ;;
    /*) ;;
    *) echo "$app: The install path is not absolute. Choose an absolute install directory." >&2; exit 1 ;;
  esac
  case $(uname -s) in
    Darwin) home_needed=1; state="$HOME/Library/Application Support" ;;
    *) case ${XDG_STATE_HOME:-} in /*) home_needed=; state=$XDG_STATE_HOME ;; *) home_needed=1; state="$HOME/.local/state" ;; esac ;;
  esac
  if [ -n "$home_needed" ]; then
    case ${HOME:-} in /*) ;; *) echo "$app: HOME is not an absolute path. Set it to your home directory, then run the installer again." >&2; exit 1 ;; esac
  fi
  record="$state/$app/installation"
  mkdir -p "$record" 2>/dev/null || { echo "$app: The installation record's directory $record cannot be created. Make it a directory you can write to, then run the installer again." >&2; exit 1; }
  # Once the verified binary is at $target:
  if command -v sha256sum >/dev/null 2>&1; then digest=$(sha256sum "$target"); else digest=$(shasum -a 256 "$target"); fi
  staging=$(mktemp "$record/.install.json.XXXXXX")
  printf '{"format":1,"method":"script","path":"%s","digest":"sha256:%s"}\n' "$target" "${digest%% *}" >"$staging"
  mv -f "$staging" "$record/install.json"
  ```

  The lines above the `# Once the verified binary is at $target:` comment check the path and the environment, set `record`, and create the record's directory, and they write no file, so an installer runs them before it downloads the binary, where a directory it cannot create fails with nothing installed, and the rest once the binary is in place. The [installer script](../toolchain/install.md) runs it that way.
- **Names.** `applicationDirectory`, `ApplicationDirectory`, and `DirectoryLookup` are exported from `@loomcli/core`.

## Reading the installation

Core fills `host.release.installation` during host capture for `run()` and `app.invoke`, once per run:

- **When it reads.** Only when the run has no `release` override and the baked facts hold a release with an `asset`, which a compiled binary built with `loom build --release` alone carries. Every other run reads no file and has no installation.
- **What it reads.** `install.json` in the directory `applicationDirectory('installation', name, host)` gives for the run's `env` and `platform`, read synchronously when it is a regular file no larger than 1 MiB. Its content must be a JSON object whose `format` is `1`, whose `method` is a nonempty string, whose `path` is an absolute path, and whose `digest` is `sha256:` and 64 lowercase hexadecimal digits. Core ignores every other member, in any order.
- **Whom it trusts.** Core sets `installation` to `{ method, path, digest }` as recorded only when `path` and `process.execPath`, each resolved through symbolic links, are the same path. A copy of the application run from another path, through Node or Bun, or from source has no installation.
- **What never fails.** A variable the directory needs, a missing file, a read that fails, content that is not that object, a `format` core does not know, and a path that is not the running executable each leave `installation` absent. Core reports none of them, and the run continues.
- **No hashing.** Core never computes the running binary's digest. A plugin that replaces the binary compares it with `digest` first.

An application with no `installation` was installed some other way, such as by a package manager, from npm, or by copying the file, and that installer owns its updates.

## Installed files

A first-party plugin that installs files outside the application, such as a completion script, a man page, an agent skill, or a service unit, records them in its own file in the installation record through one module of `@loomcli/plugins` that every such plugin shares. The module is internal to the pack. Each plugin states to the operator what the module reports, under its own contract.

```json
{"format":1,"state":"pending","directories":["/home/me/.local/share/notes","/home/me/.local/share/notes/completion"],"files":[{"path":"/home/me/.local/share/notes/completion/notes.bash","prior":null,"intended":"sha256:…"}],"lines":[{"path":"/home/me/.bashrc","prior":null,"intended":"if [ -n \"${BASH_VERSION-}\" ] && … # added by notes completion install"}]}
{"format":1,"state":"committed","directories":["/home/me/.local/share/notes","/home/me/.local/share/notes/completion"],"files":[{"path":"/home/me/.local/share/notes/completion/notes.bash","digest":"sha256:…"}],"lines":[{"path":"/home/me/.bashrc","line":"if [ -n \"${BASH_VERSION-}\" ] && … # added by notes completion install"}]}
{"format":1,"state":"committed","directories":["/home/me/.claude/skills"],"files":[],"folders":[{"path":"/home/me/.claude/skills/notes"}]}
```

- **The file.** It holds the directories the module created, each file it installed with that file's digest, under `folders`, each [installed folder](#installed-files) by its path alone, and, under `lines`, each [startup line](#installed-files) by its startup file's path and its text, in a `pending` file and a `committed` one alike; a pending line holds the text recorded before, `null` for none, and the text it will hold, `null` when it is being removed; a file with no installed folder may omit `folders`, and one with no startup line may omit `lines`. Before every install and uninstall whose plugin's file reads cleanly or is missing, the module removes leftover staging files of the plugin's file. A `pending` file lists the directories the module created and will create, and holds, for each path, the digest it held before, `null` when it held nothing, and the digest it will hold, `null` when the file is being removed. A plugin's file that is not that shape, or whose `format` the module does not know, refuses the install or uninstall: the module reports its path and writes nothing. A missing plugin's file records nothing.
- **Before writing.** An install checks every target first. A target that is absent, or a regular file the plugin's file records at that path with its digest unchanged, may be written. A target that is any other file, a file whose digest changed since it was recorded, a symbolic link, or a directory refuses the whole install, and the module writes nothing and reports each such path. The module never takes over a file it did not record. Each target is an absolute, normalized path listed once, as the first-party plugins build it.
- **Writing.** The module writes the plugin's file as `pending`, creates each missing parent directory, with the permission bits a plugin names for created directories, whatever the umask, when it names any, writes each target to a staging file it creates exclusively in the target's directory, named `.<name>.<random>.loom-staging` and unique to the attempt, with the permission bits a plugin names for that target, whatever the umask, when it names any, and renames it into place, removes each recorded file the install no longer lists when its digest is unchanged and keeps and reports one whose digest changed, and then writes the plugin's file as `committed`. It reads the run signal before the pending write and, once it has begun, does not stop between targets.
- **Uninstalling.** The module removes each recorded file whose digest is unchanged, keeps and reports each whose digest changed, removes each recorded directory that is then empty, deepest first, and deletes the plugin's file. It reads the run signal before the first removal. A file or directory that is already gone is not an error.
- **Installed folders.** A plugin may list folders instead of files, each an absolute, normalized path with the files it holds, as the [skills plugin](../plugins/skills.md) does; the plugin's file then records each folder's path under `folders`, with no digest, and the folder is the plugin's whole. An install writes each listed folder complete in a staging folder it creates exclusively beside it, named `.<name>.<random>.loom-staging`, then moves what is at the path aside to `.<name>.<random>.loom-retired`, renames the staging folder into place, and removes the retired one whole, so a reader of the path sees the old folder, the new one, or, between the two renames, nothing. A recorded folder is replaced, and removed by an uninstall or by an install that no longer lists it, whatever is inside it; a symbolic link at its path is removed alone, never followed. Anything at a listed path that the plugin's file does not record refuses the whole install, unless the plugin passes the force mode, which the skills plugin alone passes and only for an operator's `--force`: a forced install replaces what is there, a link by removing the link alone, and records the folder. Removing a folder whole, a retired folder, a leftover, or a recorded folder, removes each symbolic link inside it as a link and never follows one. A folder's staging and retired names hold its own name, so cleanup touches nothing of another folder's or another application's. Whether a folder holds exactly its files is read without following a symbolic link inside it.
- **Startup lines.** A plugin may list startup lines beside its files, each the absolute, normalized path of a shell's startup file and one line of text with no line break, as the [completion plugin](../plugins/completion.md#installing-completion) does. A startup file is the operator's, so the module records the line and never the file's digest, changes only the lines it adds or removes, and never removes the file. The plugin decides beforehand that it may change the file, as [A startup file the plugin cannot change](../plugins/completion.md#a-startup-file-the-plugin-cannot-change) states, and lists no line for one it may not; a startup file that resolves to anything but a regular file or nothing still refuses the whole install as a file does.
  - **Encoding.** The module reads a startup file as UTF-8, with or without its byte order mark. A file that starts with any other byte order mark, or that is not valid UTF-8, is one the plugin cannot change. A line the module adds is UTF-8, and a byte order mark is never part of a line.
  - **Holding a line.** A startup file holds a line when one of its lines, split at each line feed with a carriage return before it removed, equals the line exactly.
  - **Adding.** An install adds a listed line the file does not hold by appending it to the file in place, through any symbolic link, after a line break when the file is not empty and does not end with one, so the file keeps its owner, its permission bits, its links, and every other byte, and two runs appending at once both land. The line ends with the file's own line ending, a carriage return and a line feed when its first line break is one, and a line feed otherwise. A line the file already holds is not added again: it stays recorded when the plugin's file already records that text, and is otherwise reported and never recorded, because the operator added it. A file that does not exist is created exclusively in place for appending, with mode `644`, whatever the umask, with each missing parent directory, which the plugin's file records as directories the module created, as UTF-8 without a byte order mark, so a line another run appends at that moment lands whole beside this run's. A run that finds the file created by another run since it looked appends its line instead.
  - **Releasing.** A plugin may release a recorded line it cannot change: an install or uninstall drops it from the plugin's file without reading or writing the startup file, and reports it. A line is either added and recorded, or released, under [ADR-0101](../decisions/0101-completion-installs-on-linux-and-macos-and-a-startup-line-is-written-or-printed.md).
  - **Replacing and removing.** A recorded line whose text the plugin now lists differently replaces each line equal to the recorded text where it stands. An uninstall, and an install that no longer lists a recorded line, removes each line equal to the recorded text with its line ending. Both write the real path through a staging file the module creates exclusively in its directory and a rename, keeping every other byte, the encoding, and the permission bits, so a link stays a link; the file is then the process's user's, as it already was. A recorded line the file no longer holds is added again by an install that lists it, unless the plugin marks the install as an update, as `completion update` does, which adds no line and records none for that file. A file that no longer holds the line is not an error, and the module reports it.
- **Recovery.** Before any install or uninstall, a `pending` file is resolved by what is on disk: a path whose digest is the intended one was written, one whose digest is the prior one was not, one that is gone was removed, and one with any other digest was changed by someone else and is no longer recorded. A listed directory that exists stays recorded, and one that is gone is dropped. A listed folder stays recorded whether or not it is there: a recorded folder that is gone is written again by the next install and passed over by an uninstall. A pending startup line is resolved by reading its file: a file that holds the intended text has that text recorded, one that holds the prior text has the prior text recorded, and one that holds neither records no line. The module removes leftover staging files, of targets and of the plugin's file, and each leftover `.<name>.<random>.loom-staging` and `.<name>.<random>.loom-retired` folder beside a listed folder, for that folder's own `<name>` and a `<random>` of 16 lowercase hexadecimal digits, and nothing else, writes the result as `committed`, and then does what was asked. It keeps no backup, so an interrupted install finishes on the next run rather than restoring the files it replaced.
- **No lock.** Two runs that replace or remove a line in one startup file at once, of one application or two, or an editor that saves the file between the module's read and its rename, can lose the other's change; a record that then lists a line the file no longer holds is reported by the next uninstall and added again by the next install. Two runs of one plugin at once may each find the other's `pending` file and recover it, and the recovery of one can remove a staging file the other is still writing, so one run can fail with the runtime's error. Each target still holds whole content, the last commit wins, and the next run recovers. A file one wrote that the other's commit does not list is no longer recorded, so a later install refuses it until the operator removes it.
- **A failed write.** A file system call that fails throws the runtime's error, which the plugin's Command reports as any failure. A failed write or rename of a staging file removes that staging file first. A `pending` file it leaves is recovered on the next run.

## Installation record acceptance

The installation record is proven when public APIs, process runs, and the module's tests alone produce these results:

- **The directory.** `applicationDirectory` gives each table cell from an overridden `env` and `platform`, `$HOME/.local/state` for an `XDG_STATE_HOME` that is unset, empty, or relative, `$HOME/.cache` for such an `XDG_CACHE_HOME`, and `{ variable: 'HOME' }` for a `HOME` that is unset, empty, or relative whenever the cell needs it, while an absolute `XDG_STATE_HOME` or `XDG_CACHE_HOME` needs no `HOME` for its kinds, with no file read or created.
- **The recipe.** The shell recipe runs under `/bin/sh` on Linux and macOS against a fixture binary in a temporary home and writes `install.json` with the pinned bytes. It refuses a target path holding a quote, a backslash, or a newline, and a relative `HOME` whenever the directory needs it, with exit 1 and nothing written. On Linux, an absolute `XDG_STATE_HOME` writes the file with `HOME` unset.
- **Reading.** A compiled fixture binary built with `--release` and recorded by the recipe prints its `installation` under the temporary home. A symbolic link to the binary, and a recorded path that is a symbolic link to it, read the same installation. The same binary prints none when copied to another path, when `install.json` is missing, empty, not JSON, an array, `format` `2`, an empty `method`, a relative `path`, or an uppercase `digest`, or a directory, and when the directory's variable is unset; each run exits with its own code and writes nothing to stderr. A bundle built for Node with `--release`, and the source run, print none and read no file. `install.json` with an extra member and its members reordered reads the same installation. `run({ host: { release } })` reads the override and no file.
- **Installing.** Installing two files into a temporary directory writes both and a `committed` file with their digests and the created directory. A second install with new content replaces both, and one that lists only the first removes the second. An install over an unrecorded file, a recorded file changed since, a symbolic link, or a directory refuses, writes nothing, and reports the path, and so does an install whose plugin's file is damaged or holds an unknown `format`. Installing a folder writes it whole and records its path; a second install whose folder drops a file and moves another into a subfolder leaves exactly the new files, even after someone edited and added files inside it; an install that no longer lists it removes it whole. An install over an unrecorded folder, a file, or a symbolic link at a listed folder's path refuses and writes nothing, and the force mode replaces each, removing a link without touching its target. A process killed between moving the old folder aside and renaming the new one into place leaves a `pending` file whose next install writes the folder and removes the leftovers.
- **Uninstalling.** Uninstall removes unchanged files and the created directory, keeps and reports a changed file, passes over a file already gone, and deletes the plugin's file.
- **Startup lines.** Installing a line into a missing startup file creates it with mode `644` and records the line; into a file that holds it, adds nothing and records nothing unless the plugin's file already recorded that line; into a file that does not end with a line break, adds one first; into a file with CRLF endings, adds a CRLF line; into a UTF-8 file with a byte order mark before the line, finds it; and into a symbolic link or a file with a second hard link, appends to the one file both name, keeping its inode, owner, and permission bits. Two installs appending different lines to one file at once leave both. A link to a missing file and a directory at the path refuse and write nothing. An install listing new text replaces the recorded line where it stands, and one marked as an update adds no line the file no longer holds. Uninstall removes every line equal to the recorded text and leaves every other byte, reports a file that no longer holds it, and never removes the file. A released line is dropped from the plugin's file and the startup file is neither read nor written. A process killed after a first line is appended and before the commit leaves a `pending` file whose next run records the line, and one killed before the append records none; one killed before the rename that replaces a line records the prior line, and one killed after it records the new one.
- **Recovery.** A process killed between two targets leaves a `pending` file, and the next install finishes with both targets written and a `committed` file. A process killed before it creates a listed directory leaves a `pending` file whose next install creates the directory and records it. A pending path changed by hand before the next run is kept and no longer recorded. A leftover staging file is removed. Two installs writing one target at once never rename one's partial staging file into place.
- **Logging.** The logging plugin's default directory follows the `logs` column, and a relative `HOME`, for the default directory and for a `file` under `~/`, calls `onError` with `unresolved-directory` and `variable` `HOME`.
- **Packaging.** `pnpm check:packed` compiles a consumer that calls `applicationDirectory` against core's emitted declarations and runs it under Node and Bun.
