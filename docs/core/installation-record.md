# Installation record

This page states the installation record, the per-application directory that says how the application was installed and which files its installers wrote. An author reads it when code needs the installation or the files an install wrote.

```ts sketch
type ApplicationDirectory = 'installation' | 'logs' | 'cache';
type DirectoryLookup =
  | { readonly path: string } // the absolute directory
  | { readonly variable: string }; // the variable it needs that is unset, empty, or not absolute; HOME for the home
declare function applicationDirectory(
  kind: ApplicationDirectory,
  application: string,
  from: { readonly env: Host['env']; readonly home: string; readonly platform: string },
): DirectoryLookup;
```

```sh
# The installer script, once the verified binary of notes is at /home/me/.local/bin/notes,
# writes ~/.local/state/notes/installation/install.json:
{"format":1,"method":"script","path":"/home/me/.local/bin/notes","digest":"sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"}
```

```ts
import { Command } from '@loomcli/core';

// src/commands/about.ts: the binary at that path reads it
export const about = new Command('about').action(({ host, out }) => {
  const { installation } = host.release;
  if (installation === undefined) {
    return out.print('Installed some other way.');
  }
  // Package-managed runs carry an installation too, with no digest, so check the method.
  return out.print(
    installation.method === 'script'
      ? `Installed by install.sh at ${installation.path}.`
      : `Installed by ${installation.method} at ${installation.path}, which updates it.`,
  );
});
```

The installation record is one directory per application and per user that says how the application was installed and which files its installers wrote. It holds `install.json`, the installation, and one file for each first-party plugin that installs files or registers with an agent, named for the plugin, such as `service.json`, or one for each of its targets when a plugin installs into independent targets, named for the plugin and the target, such as `skills.claude.json`. Each file has its own writers, and each writer replaces only its own file, whole, through a temporary file in the same directory and a rename, so no writer reads or merges another's. Core reads `install.json` and writes nothing. A file the application writes there under a name no first-party writer uses, such as `<app>.json`, is the application's own: no Loom writer reads, replaces, or removes it, so it survives a self-update, and an application's [post-install command](../toolchain/install.md#the-post-install-command) can record what it binds at install there, under [ADR-0113](../decisions/0113-an-application-declares-a-post-install-message-and-command-that-the-installer-script-prints-and-runs.md). [ADR-0071](../decisions/0071-an-installation-record-per-application-says-how-it-was-installed-and-what-its-installers-wrote.md) records the decision.

- **The directory.** `applicationDirectory('installation', name, host)` resolves it from `env`, `home`, and `platform` alone, `applicationDirectory('logs', name, host)` resolves the [logging plugin's](../plugins/logging.md) default directory, and `applicationDirectory('cache', name, host)` resolves the directory of data the application can lose, such as the [update notices'](../plugins/self-update.md#update-notices) cache:

  | Platform | `installation` | `logs` | `cache` |
  | --- | --- | --- | --- |
  | `darwin` | `<home>/Library/Application Support/<app>/installation/` | `<home>/Library/Logs/<app>/` | `<home>/Library/Caches/<app>/` |
  | any other | `$XDG_STATE_HOME/<app>/installation/` | `$XDG_STATE_HOME/<app>/` | `$XDG_CACHE_HOME/<app>/` |

  `<home>` is `from.home`, the run's [`host.home`](host.md#the-home-and-temporary-folders), never `HOME` in `env`. On any other platform, an `XDG_STATE_HOME` in `env` that is unset, empty, or not an absolute path is replaced by `<home>/.local/state`, and such an `XDG_CACHE_HOME` by `<home>/.cache`, so an absolute XDG variable still wins over the home. A `home` that is empty or not an absolute path cannot give the directory, and the lookup answers `{ variable: 'HOME' }`, the variable an operator sets to fix it. `<app>` is the application's name, which the [portable name](../glossary.md#names-and-routing) grammar keeps safe as one path segment. The platform chooses the row and its variables; the running process's path rules judge an absolute path and join the segments. The function reads no file and creates nothing.
- **`install.json`.** One line: `{"format":1,"method":"<method>","path":"<path>","digest":"sha256:<hex>"}` and a newline, the members in that order, where `path` is the absolute path of the installed binary and `<hex>` the 64 lowercase hexadecimal digits of its SHA-256 digest. The method `script` means an installer script put the binary there, and a plugin that replaces the binary may replace it. Two writers write the file: the installer script, after it moves a verified binary into place, and self-update, after it replaces the binary, each through the recipe's temporary file and rename.
- **The shell recipe.** An installer script writes `install.json` with POSIX `sh` under `set -e` and no JSON parser, on Linux and macOS:

  ```sh
  # $app is the application's name; $target is the installed binary's absolute path.
  case $target in
    *[\"\\]* | *[[:cntrl:]]*) echo "$app: The install path holds a quote, a backslash, or a control character. Choose another install directory." >&2; exit 1 ;;
    /*) ;;
    *) echo "$app: The install path is not absolute. Choose an absolute install directory." >&2; exit 1 ;;
  esac
  case $(uname -s) in
    Darwin) home_needed=1; state="$HOME/Library/Application Support" ;;
    *) case ${XDG_STATE_HOME:-} in /*) home_needed=; state=$XDG_STATE_HOME ;; *) home_needed=1; state="$HOME/.local/state" ;; esac ;;
  esac
  if [ -n "$home_needed" ]; then
    case ${HOME:-} in /*) ;; *) echo "$app: HOME is not an absolute path. Set it to your home directory, then run the installer again." >&2; exit 1 ;; esac
  fi
  record="$state/$app/installation"
  mkdir -p "$record" 2>/dev/null || { echo "$app: The installation record's directory $record cannot be created. Make it a directory you can write to, then run the installer again." >&2; exit 1; }
  # Once the verified binary is at $target:
  if command -v sha256sum >/dev/null 2>&1; then digest=$(sha256sum "$target"); else digest=$(shasum -a 256 "$target"); fi
  staging=$(mktemp "$record/.install.json.XXXXXX")
  printf '{"format":1,"method":"script","path":"%s","digest":"sha256:%s"}\n' "$target" "${digest%% *}" >"$staging"
  mv -f "$staging" "$record/install.json"
  ```

  The lines above the `# Once the verified binary is at $target:` comment check the path and the environment, set `record`, and create the record's directory, and they write no file, so an installer runs them before it downloads the binary, where a directory it cannot create fails with nothing installed, and the rest once the binary is in place. The [installer script](../toolchain/install.md) runs it that way.
- **Names.** `applicationDirectory`, `ApplicationDirectory`, and `DirectoryLookup` are exported from `@loomcli/core`.

## Reading the installation

Core fills `host.release.installation` during host capture for `run()` and `app.invoke`, once per run. It does so when there is a baked release group and the process handle supplies no `release` override.

1. **Resolve the application path.** Core resolves symbolic links in the executable's path when the build is compiled or its release group carries an asset. Otherwise it resolves the bundle's entry script path. For a bundle, the script is the second word of [`host.program`](host.md), after the runtime. An absent path or failed realpath leaves the installation absent.
2. **Check for a matching record.** For a release binary with an `asset`, core reads `install.json` in the directory `applicationDirectory('installation', name, host)` gives, synchronously, when it is a regular file no larger than 1 MiB. Its content must be a JSON object with `format` equal to `1`, a nonempty string `method`, an absolute `path`, and a `digest` of `sha256:` and 64 lowercase hexadecimal digits. Core ignores every other member, in any order. If the recorded path resolves to the executable's realpath, core keeps the recorded `method`, `path`, and `digest`, and nothing else, whatever the method.
3. **Derive the installation when no record matches.** Core matches complete directory components of the application realpath, excluding the root and the file name, with case-sensitive names and the running process's path rules. A missing directory, unreadable or malformed record, or record for a different path all reach the same fallback.

   | First matching layout | Installation |
   | --- | --- |
   | `.../Cellar/<formula>/<version>/...` with the application file beneath the version directory | `{ method: 'brew', path, formula }`. The nearest qualifying `Cellar` ancestor wins. Its next component is the formula name. The version directory can have any name. |
   | `<prefix>/lib/node_modules/...` | `{ method: 'npm', path }`. npm on Linux and macOS. |
   | `.../global/<number>/.pnpm/<package-folder>/node_modules/...` | `{ method: 'pnpm', path }`. pnpm 9 and 10, with an all-digit global directory version. |
   | `.../v<number>/links/<scope>/<name>/<version>/<hash>/node_modules/...` | `{ method: 'pnpm', path }`. The global virtual store from pnpm 11 on. The store defaults to `$PNPM_HOME/store`, and the scope folder is `@` for an unscoped package. |
   | `$BUN_INSTALL/install/global/node_modules/...` | `{ method: 'bun', path }`. Bun, with `BUN_INSTALL` defaulting to `~/.bun`. |
   | `.../yarn/global/node_modules/...` | `{ method: 'yarn', path }`. Yarn 1, as in `~/.config/yarn/global/node_modules` or `$XDG_DATA_HOME/yarn/global/node_modules`. |
   | Any other path | The installation is absent. |

   A Homebrew formula that wraps an npm package still matches the Cellar row first. Each global root must end at the outermost `node_modules`. This covers an entry script in an unscoped or scoped package and a binary in a launcher's platform package, such as `.../lib/node_modules/@acme/notes/node_modules/@acme/notes-linux-x64/bin/notes`. Project dependencies, npx and pnpm dlx caches, a pnpm global that the hoisted linker or a turned-off global virtual store leaves at `global/<version>/node_modules`, a global folder moved by Bun's `globalDir` or Yarn's `--global-folder`, and a Bun global installed with `--backend=symlink` derive nothing. A project folder laid out as `install/global/node_modules` or `yarn/global/node_modules` reads as Bun or Yarn, because the path cannot tell it from a global root. Windows derives nothing.

   Core infers ownership from layout alone. A project with a matching layout, such as `~/code/lib/node_modules/` or a pnpm project using the global virtual store, also matches and can get a notice whose command would install a second copy globally.

The derived `path` is the realpath. `packageManagerInstallation(path, platform)` from `@loomcli/core` applies the layout rules to an absolute realpath without reading a record. Core reports no lookup failures, writes no record, and computes no digest. Only a matching record carries a digest. Before replacing a script-installed binary, the self-update plugin checks the recorded path's package-manager ownership and verifies the digest. Each package manager owns its updates. [ADR-0211](../decisions/0211-update-notices-name-the-package-managers-upgrade-command.md) records the derivation.

## Installed files

A first-party plugin that installs files outside the application, such as a completion script, a man page, an agent skill, or a service unit, or that registers with an agent, records them in its own file in the installation record through one module of `@loomcli/plugins` that every such plugin shares. The module is internal to the pack. Each plugin states to the operator what the module reports, under its own contract.

```json
{"format":1,"state":"pending","directories":["/home/me/.local/share/notes","/home/me/.local/share/notes/completion"],"files":[{"path":"/home/me/.local/share/notes/completion/notes.bash","prior":null,"intended":"sha256:…"}],"lines":[{"path":"/home/me/.bashrc","prior":null,"intended":"if [ -n \"${BASH_VERSION-}\" ] && … # added by notes completion install"}]}
{"format":1,"state":"committed","directories":["/home/me/.local/share/notes","/home/me/.local/share/notes/completion"],"files":[{"path":"/home/me/.local/share/notes/completion/notes.bash","digest":"sha256:…"}],"lines":[{"path":"/home/me/.bashrc","line":"if [ -n \"${BASH_VERSION-}\" ] && … # added by notes completion install"}]}
{"format":2,"state":"pending","directories":["/home/me/.claude/skills"],"files":[],"folders":[{"path":"/home/me/.claude/skills/notes","prior":"path","intended":[{"path":"SKILL.md","digest":"sha256:…"},{"path":"references/commands/index.md","digest":"sha256:…","generated":true}]}]}
{"format":2,"state":"committed","directories":["/home/me/.claude/skills"],"files":[],"folders":[{"path":"/home/me/.claude/skills/notes","files":[{"path":"SKILL.md","digest":"sha256:…"},{"path":"references/commands/index.md","digest":"sha256:…","generated":true}]}]}
{"format":1,"state":"pending","directories":[],"files":[],"registrations":[{"name":"notes","prior":null,"intended":["/home/me/.local/bin/notes","mcp"]}]}
{"format":1,"state":"committed","directories":[],"files":[],"registrations":[{"name":"notes","command":["/home/me/.local/bin/notes","mcp"]}]}
```

- **The file.** It holds the directories the module created, each file it installed with that file's digest, under `folders`, each [installed folder](#installed-files) by its path and the files it holds, and, under `lines`, each [startup line](#installed-files) by its startup file's path and its text, in a `pending` file and a `committed` one alike; a pending line holds the text recorded before, `null` for none, and the text it will hold, `null` when it is being removed; a file with no installed folder may omit `folders`, and one with no startup line may omit `lines`. Before every install and uninstall whose plugin's file reads cleanly or is missing, the module removes leftover staging files of the plugin's file. A `pending` file lists the directories the module created and will create, and holds, for each path, the digest it held before, `null` when it held nothing, and the digest it will hold, `null` when the file is being removed. A plugin's file that is not that shape, or whose `format` the module does not know, refuses the install or uninstall: the module reports its path and writes nothing. A missing plugin's file records nothing.
- **Formats.** The module reads `format` 1 and `format` 2. It writes `format` 2 for a plugin's file that records at least one installed folder, and `format` 1 for every other, so a file with no folder reads the same in every version that knows format 1. The two differ only in `folders`: a format-2 folder entry holds `files`, unless recovery kept it recorded by its path alone, and a format-1 entry holds its path alone, the old format, which only the skills plugin's earlier versions wrote. A format-2 file whose pending folder entry lacks `prior` or `intended`, or one of whose folder files holds a `generated` value other than `true`, is not that shape, and refuses as any malformed plugin's file does. [ADR-0189](../decisions/0189-skills-status-reports-each-skill-per-target-and-the-record-keeps-a-digest-of-each-installed-skill-file.md) records the second format.
- **Before writing.** An install checks every target first. A target that is absent, or a regular file the plugin's file records at that path with its digest unchanged, may be written. A target that is any other file, a file whose digest changed since it was recorded, a symbolic link, or a directory refuses the whole install, and the module writes nothing and reports each such path. The module never takes over a file it did not record. Each target is an absolute, normalized path listed once, as the first-party plugins build it.
- **Writing.** The module writes the plugin's file as `pending`, creates each missing parent directory, with the permission bits a plugin names for created directories, whatever the umask, when it names any, writes each target to a staging file it creates exclusively in the target's directory, named `.<name>.<random>.loom-staging` and unique to the attempt, with the permission bits a plugin names for that target, whatever the umask, when it names any, and renames it into place, removes each recorded file the install no longer lists when its digest is unchanged and keeps and reports one whose digest changed, and then writes the plugin's file as `committed`. It reads the run signal before the pending write and, once it has begun, does not stop between targets.
- **Uninstalling.** The module removes each recorded file whose digest is unchanged, keeps and reports each whose digest changed, removes each recorded directory that is then empty, deepest first, and deletes the plugin's file. It reads the run signal before the first removal. A file or directory that is already gone is not an error.
- **Installed folders.** A plugin may list folders instead of files, each an absolute, normalized path with the files it holds, as the [skills plugin](../plugins/skills.md) does, and may mark some of a folder's files as generated. The plugin's file then records each folder under `folders` as `{ path, files }`, where `files` lists each file the install wrote in it, `{ path, digest }`, with `generated: true` after the digest on a marked file and no `generated` member on any other, which is the author's, its path relative to the folder, using `/`, with no empty, `.`, or `..` segment, in the order the plugin listed them; a pending entry is `{ path, prior, intended }`, where `prior` is the files recorded before, `null` for none, or `"path"` for a folder recorded by its path alone, and `intended` the files it will hold, `null` when the folder is being removed. The folder is the plugin's unit: an install writes each listed folder complete in a staging folder it creates exclusively beside it, named `.<name>.<random>.loom-staging`, then moves what is at the path aside to `.<name>.<random>.loom-retired`, renames the staging folder into place, and removes the retired one whole, so a reader of the path sees the old folder, the new one, or, between the two renames, nothing, and a removal removes a folder whole. Nothing in a folder is written or removed file by file.
  - **A changed folder.** A recorded folder has changed when one of its marked files is in the folder as anything but a regular file holding its recorded digest, read without following a symbolic link inside the folder, as a recorded file has changed. Nothing else changes a folder: not an unmarked file, not a recorded file that is gone, not an entry the record does not list, and not a mode. A folder that is gone has not changed, and neither has anything at its path that is not a directory, which holds none of its files. A folder recorded by its path alone has no files and never changes.
  - **Writing.** A listed folder that is absent, or recorded and not changed, may be replaced, whatever else it holds. Anything at a listed path that the plugin's file does not record, and a listed recorded folder that has changed, refuses the whole install, and the module reports each with its reason and, for a changed folder, each marked file that changed, unless the plugin passes the force mode, which the skills plugin alone passes and only for an operator's `--force`: a forced install replaces what is there, a link by removing the link alone, records the folder, and reports each folder it replaced with its reason. The install records each listed folder with the files it wrote and their marks.
  - **Removing.** A recorded folder that an uninstall removes, or that an install no longer lists, is removed whole when it has not changed, and anything at its path that is not a directory, a symbolic link included, is removed alone and never followed; a changed folder is kept and reported. Either way the plugin's file no longer records it. A recorded folder that is gone is passed over. A changed folder an install no longer lists never refuses it, and the force mode does not remove it.
  - **Links and cleanup.** Removing a folder whole, a retired folder, a leftover, or a recorded folder, removes each symbolic link inside it as a link and never follows one. A folder's staging and retired names hold its own name, so cleanup touches nothing of another folder's. Cleanup matches leftovers by that name alone, so two runs that write the same folder at once, of one application or of two, can remove each other's staging folder, or files inside it while the other run is still writing them, so either run can fail or publish the folder with files missing. Run one install of a folder at a time. A folder's files are read without following a symbolic link inside it.
- **Startup lines.** A plugin may list startup lines beside its files, each the absolute, normalized path of a shell's startup file and one line of text with no line break, as the [completion plugin](../plugins/completion.md#installing-completion) does. A startup file is the operator's, so the module records the line and never the file's digest, changes only the lines it adds or removes, and never removes the file. The plugin decides beforehand that it may change the file, as [A startup file the plugin cannot change](../plugins/completion.md#a-startup-file-the-plugin-cannot-change) states, and lists no line for one it may not; a startup file that resolves to anything but a regular file or nothing still refuses the whole install as a file does.
  - **Encoding.** The module reads a startup file as UTF-8, with or without its byte order mark. A file that starts with any other byte order mark, or that is not valid UTF-8, is one the plugin cannot change. A line the module adds is UTF-8, and a byte order mark is never part of a line.
  - **Holding a line.** A startup file holds a line when one of its lines, split at each line feed with a carriage return before it removed, equals the line exactly.
  - **Adding.** An install adds a listed line the file does not hold by appending it to the file in place, through any symbolic link, after a line break when the file is not empty and does not end with one, so the file keeps its owner, its permission bits, its links, and every other byte, and two runs appending at once both land. The line ends with the file's own line ending, a carriage return and a line feed when its first line break is one, and a line feed otherwise. A line the file already holds is not added again: it stays recorded when the plugin's file already records that text, and is otherwise reported and never recorded, because the operator added it. A file that does not exist is created exclusively in place for appending, with mode `644`, whatever the umask, with each missing parent directory, which the plugin's file records as directories the module created, as UTF-8 without a byte order mark, so a line another run appends at that moment lands whole beside this run's. A run that finds the file created by another run since it looked appends its line instead.
  - **Releasing.** A plugin may release a recorded line it cannot change: an install or uninstall drops it from the plugin's file without reading or writing the startup file, and reports it. A line is either added and recorded, or released, under [ADR-0101](../decisions/0101-completion-installs-on-linux-and-macos-and-a-startup-line-is-written-or-printed.md).
  - **Replacing and removing.** A recorded line whose text the plugin now lists differently replaces each line equal to the recorded text where it stands. An uninstall, and an install that no longer lists a recorded line, removes each line equal to the recorded text with its line ending. Both write the real path through a staging file the module creates exclusively in its directory and a rename, keeping every other byte, the encoding, and the permission bits, so a link stays a link; the file is then the process's user's, as it already was. A recorded line the file no longer holds is added again by an install that lists it, unless the plugin marks the install as an update, as `completion update` does, which adds no line and records none for that file. A file that no longer holds the line is not an error, and the module reports it.
- **Registrations.** A plugin may list registrations, each an application's name and the command line an agent starts, as the [MCP plugin](../plugins/mcp.md#registering-with-an-agent) does, one plugin's file per agent; the plugin's file then records each under `registrations` as `{ name, command }`, and a pending one as `{ name, prior, intended }`, the command line recorded before, `null` for none, and the one it will hold, `null` when it is being removed. The module records a registration and never applies one: the agent's own command-line interface writes it, which the plugin runs between the pending write and the committed one, and a call that fails has the plugin commit what is known to be registered rather than what it intended. A file with no registration may omit `registrations`.
- **Recovery.** Before any install or uninstall, a `pending` file is resolved by what is on disk: a path whose digest is the intended one was written, one whose digest is the prior one was not, one that is gone was removed, and one with any other digest was changed by someone else and is no longer recorded. A listed directory that exists stays recorded, and one that is gone is dropped. A pending folder is resolved by reading it. When every intended file is in the folder as a regular file with its digest, the intended files are recorded, whatever else the folder holds, because an entry the record does not list changes no folder. Otherwise, when something is at its path, its prior files are recorded, so a folder someone changed during the install reads as changed; a prior `"path"` keeps the folder recorded by its path alone, so an interrupted first write of a folder an earlier format recorded rolls forward on the next install; and an entry with no prior files is dropped, so a takeover stopped before its swap stays unrecorded. When nothing is at its path, its intended files are recorded, or the entry is dropped when it was being removed. A recorded folder that is gone is written again by the next install and passed over by an uninstall. A pending folder of a format-1 file stays recorded by its path whether or not it is there. A pending startup line is resolved by reading its file: a file that holds the intended text has that text recorded, one that holds the prior text has the prior text recorded, and one that holds neither records no line. A pending registration is resolved when its file is read, without reading the agent, and the file is not rewritten until the plugin next writes it: it stays recorded as the command line it intended, or as the one it held before when it was being removed, so the next install replaces it and the next uninstall removes it. The module removes leftover staging files, of targets and of the plugin's file, and each leftover `.<name>.<random>.loom-staging` and `.<name>.<random>.loom-retired` folder beside a listed folder, for that folder's own `<name>` and a `<random>` of 16 lowercase hexadecimal digits, and nothing else, writes the result as `committed`, and then does what was asked. It keeps no backup, so an interrupted install finishes on the next run rather than restoring the files it replaced.
- **No lock.** Two runs that replace or remove a line in one startup file at once, of one application or two, or an editor that saves the file between the module's read and its rename, can lose the other's change; a record that then lists a line the file no longer holds is reported by the next uninstall and added again by the next install. Two runs of one plugin at once may each find the other's `pending` file and recover it, and the recovery of one can remove a staging file the other is still writing, so one run can fail with the runtime's error. Each target still holds whole content, the last commit wins, and the next run recovers. A file one wrote that the other's commit does not list is no longer recorded, so a later install refuses it until the operator removes it.
- **A path that cannot be reached.** Every read of a plugin's file also reads each file, folder, and directory it records, and an install reads each target before it writes, so a run meets a path below a file before it writes or removes any installed file or plugin's file. When a file sits where one of the folders of such a path is needed, the run fails naming the path, `Cannot reach /home/me/.local/share/notes/completion/notes.bash because a file sits where one of its folders is needed. Remove or rename that file, then run the command again.`, and leaves the installed files and the plugin's file as they were. Read as gone, the path would drop from the record while the folder that holds it may come back, and a later install would refuse the files the module wrote as unrecorded. A status that reads the plugin's file fails the same way. Two things can change first. A run that reads its plugin's file removes that file's leftover staging files, which a stopped run left, before it reads its targets. And a run that finds its plugin's file pending recovers it, committing the record and removing the stopped run's leftover staging files and folders, as the next run would. So a blocked target can fail a run that already did either. A removal the run's user may not make, in a folder that cannot be written, still fails with the runtime's error. A read the run's user may not make, because a folder on the way cannot be searched or the file cannot be read, fails naming the path: `Cannot read /home/me/.local/state/notes/installation/service.json because you do not have permission to reach or read it. Make it readable, then run the command again.` A folder that cannot be searched fails at the same point as a blocked path, and so does an installed file that cannot be read under an install, which reads every target first. An uninstall reads each recorded file as it removes it, so one it cannot read fails the run after it has removed the files before it, and the next uninstall, once the file can be read, removes the rest. The sentences name no command, because every plugin that installs files reaches them.
- **A failed write.** A write of a target, a created directory, a folder's staging folder, or the plugin's file that meets a file where a folder is needed fails with that sentence too. One whose location cannot be written, or whose file system is read-only, fails naming the path: `Cannot write /home/me/.config/systemd/user/notes.service because you do not have permission to write there. Make the location writable, then run the command again.` Such a write fails only when the module makes it, after the plugin's own steps before the install: the [service plugin](../plugins/service.md#the-children) stops and disables an earlier unit first, so an install whose new unit's location cannot be written fails with that unit stopped and disabled and its file still in place. Any other file system call that fails throws the runtime's error, which the plugin's Command reports as any failure. A failed write or rename of a staging file removes that staging file first. A `pending` file it leaves is recovered on the next run that can write the plugin's file.
