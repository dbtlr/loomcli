# Interaction

This page states the core rule for interaction: how a run decides once whether it may ask the operator questions, and how a local string option or a string argument becomes required only when input is not interactive. The [interaction plugin](../plugins/interaction.md) documents the option that lets the operator turn questions off.

Each run decides once whether it may ask the operator questions. Core computes the decision, an input's conditional presence rule reads it before the action, and the action reads it as `interactive`, so a [question](../libs/prompts.md) and the validation phase never disagree. [ADR-0082](../decisions/0082-an-action-asks-through-the-prompts-library-and-one-interaction-decision-governs-questions-and-conditional-requiredness.md) records the decision, and [ADR-0136](../decisions/0136-a-multiple-string-option-or-a-string-argument-may-be-required-only-when-input-is-not-interactive-and-a-question-may-link-an-argument.md) widens conditional requiredness to multiple string options and string arguments.

```ts
import { Application } from '@loomcli/core';

const app = new Application('mimir')
  .globalOption('input', {
    type: 'boolean',
    polarity: 'negative',
    interaction: true,
    description: 'Ask no questions, and take every answer from options.',
  })
  .argument('name', { required: 'non-interactive' })
  .option('port', { type: 'string', required: 'non-interactive' })
  .option('tag', { type: 'string', multiple: true, required: 'non-interactive' })
  .action(({ args, interactive, supplied, options }) => {
    const name: string | undefined = args.name; // undefined only when interactive
    const port: string | undefined = options.port; // undefined only when interactive
    const tags: string[] = options.tag; // [] only when interactive
    const typed = supplied.options.port; // the raw supplied value, never a default
    const given = supplied.args.name; // the raw supplied token, never a default
    // ...
  });
```

- **The decision.** After the [input-source stage](input-sources.md) and before the validation pass, core sets the run's decision to on when `host.terminal.stdin.isTTY` and `host.terminal.stderr.isTTY` are both true, the run is not under CI, and the marked option, when the application declares one, does not read `false`. A run is under CI when `CI` in `host.env` is set, nonempty, and not `false`, as ci-info, which npm uses, reads it: CI systems set `CI=true`, and `CI=false` is an operator saying the run is not CI. So a run in CI asks nothing even on a pseudo-terminal: a question takes its supplied linked input or fails, and a `required: 'non-interactive'` option is required. [ADR-0114](../decisions/0114-a-ci-run-is-not-interactive-draws-no-live-region-and-renders-as-the-standard-detectors-do.md) records the CI rule. Stdout plays no part, so `mimir setup > setup.log` still asks. A process handle decides as the terminal facts it supplies say, and an [invocation by name](invocation.md#invocation-by-name), with no terminal, is off, which makes every [MCP](../plugins/mcp.md) tool call off. A run that never reaches validation, such as one that ends at an unknown command, computes nothing.
- **The mark.** `interaction: true` on a Boolean global option, the application's or a plugin's, makes its final value the application's intent: the value argv, its environment binding, or the configuration source supplied, else its polarity's absent value. `false` turns interaction off, and `true` leaves the decision to the terminal facts, so the intent can turn interaction off and never on. An occurrence that faulted supplies nothing, so the absent value applies. `inspect()` publishes `interaction` on each Boolean option node, `true` on the marked one, and the manifest copies it. The [interaction plugin](../plugins/interaction.md) declares a marked `--no-input`.
- **Conditional requiredness.** A local string option, whether it takes one value or is multiple, and a string argument, scalar or variadic, may declare `required: 'non-interactive'`. With interaction off, the input is required, exactly as `required: true` is, and an omission is a `missing` problem of the run's `InputError`, in authoring order, exit 2 before the chain reaches the action. The sentence reads `Option "--port" is required when input is not interactive. Supply a value.` for an option that takes one value, `Option "--tag" is required when input is not interactive. Supply at least one value.` for a multiple option, `Argument "name" requires a value when input is not interactive. Supply a value for "name".` for a scalar argument, and `Argument "files" requires at least one value when input is not interactive. Supply a value for "files".` for a variadic one. By name, an option reads `Option "port" ...`, and an argument reads as it does from argv, because an argument has no spelling but its name. With interaction on, an omission is plain absence: `undefined` for an option that takes one value and a scalar argument, `[]` for a multiple option and a variadic argument, and no validator runs. A scalar's action value keeps `undefined` in its type, and a multiple option's or variadic argument's is never `undefined`. A default or `validateOmitted` beside it is the same declaration error as beside `required: true`. A content, Boolean, or counted option, a content argument, and a global option declare no such rule, and a global option declares no presence rule under [ADR-0044](../decisions/0044-a-global-option-declares-no-presence-rule.md).
- **An argument's place.** An argument that declares `required: 'non-interactive'` sits between the two kinds the argument order already has, under [`@loomcli/core/optional-argument-last`](diagnostics.md#loomclicoreoptional-argument-last): it never follows an optional argument, because with interaction off it is required, and a `required: true` argument never follows it, because with interaction on it is optional, and bare words fill the arguments left to right, so an operator at a terminal could never omit it and its question could never be asked. A variadic one is last, as every variadic argument is. The second fault reads `Argument "url" is required only when input is not interactive and precedes required argument "dir" on Command "clone".`, corrected by `Declare arguments required only when input is not interactive after required ones.` With interaction on, bare words still fill the arguments left to right, so an operator who omits it omits every argument after it too.
- **What the graph says.** `inspect()` publishes the rule as `required: false` and `requiredWhen: 'non-interactive'` on the string option node, whether or not it is multiple, and on the argument node, which gains `requiredWhen` for it, `null` otherwise, so a reader of `required` keeps its meaning. The manifest copies both. Help prints the fact `required when not interactive` on the input's row. It leaves such an option out of the usage line and prints such an argument there as a required one, `<name>` or `<files...>`, because its place among the arguments is fixed. An MCP tool schema lists the input as required, because a tool call is never interactive.
- **`interactive`.** The action context's `interactive` is the decision, a Boolean. An action's `invoke` and `app.invoke` compute their own, which is off.
- **`supplied`.** The action context's `supplied` is the record the [validation context](validation.md#validation-context) calls `supplied`: the raw value of every input any tier supplied, except a member of an [exclusive option group](options.md#declared-option-groups) that a lower tier filled beside a sibling a higher tier supplied, which core withdraws, and `undefined` for an omitted scalar input, an input left to its declared default, and an omitted Boolean or counted option, whose absent value is not supplied. It says whether a value was supplied and never which tier supplied it. Core builds the action's record once per run, after the input-source stage, frozen to every depth, from the same values each validator's per-call copy holds, so the action reads what the validators read and a validator's write to its copy changes nothing the action reads. Its `args` hold each argument of the routed Command by name, the token for a scalar and the tokens for a variadic, so an action and a [question](../libs/prompts.md#linking-an-input) tell a supplied argument from an omitted one. Under an invocation by name it holds the raw values the call's `values` lowered to and the tiers filled. The type is the exported `SuppliedInputs`.
- **`missingInputError(context, input)`.** Core exports the function that builds the `InputError` core reports for an omitted input of the routed Command, so a library that finds an input missing inside the action reports it in core's words. `input` is the name of a local option, or `{ argument: name }` for an argument, because an option and an argument may share a name. It builds one `missing` problem. An option is named by spelling from argv and by declared name from an invocation by name, with the sentence `Option "--database-url" is required when input is not interactive. Supply a value.` when interaction is off and `Option "--database-url" is required. Supply a value.` when it is on. A multiple string option's fix reads `Supply at least one value.`, as core's own missing sentence for it does: `Option "--tag" is required when input is not interactive. Supply at least one value.` For argv, a Boolean option's fix names the spellings its polarity accepts in place of a value: `Supply "--install" or "--no-install".`, `Supply "--install".` for a positive option, and `Supply "--no-install".` for a negative one. Under an invocation by name, a Boolean option's fix is `Supply a value.`, and a multiple string option's stays `Supply at least one value.` An argument is named by its name, with the sentence `Argument "url" requires a value when input is not interactive. Supply a value for "url".` when interaction is off and `Argument "url" requires a value. Supply a value for "url".` when it is on, and `at least one value` in place of `a value` in the first clause for a variadic argument. The problem's `input` is `{ kind: 'argument', name, global: false }` for an argument. The caller throws it, and the run exits 2. A name that is not a local option of the routed Command, and an `argument` that is not one of its arguments, throws a `DeclarationError` under [`@loomcli/core/missing-input-name`](diagnostics.md#loomclicoremissing-input-name), whose explanation reads `A missing input names a local option or an argument of the routed Command.`, and whose sentence for an argument reads `missingInputError() received argument "url", which Command "clone" does not declare.`, corrected by `Supply the name of an argument of the routed Command.`
- **One mark.** An Application declares one marked option. The fault throws from the call that brings the second mark into the Application, as a [spelling collision](options.md#declaration-and-invocation-errors) does, and names each option as [Input declaration errors](options.md#input-declaration-errors) names it: [`@loomcli/core/interaction-mark`](diagnostics.md#loomclicoreinteraction-mark).

The types reject `interaction` on `option()` and on every option type but `boolean`, and `required: 'non-interactive'` on a content, Boolean, or counted option, a content argument, and a global option.
