# Invocation

`run(options?)` returns `Promise<ExitCode>` and writes the same code to its [process handle](host.md#the-process-handle)'s `exitCode`. It resolves execution failures through the output path. `invoke(path, values, options?)` runs one Command by name instead, captures what the run writes, and resolves a structured outcome, under [Invocation by name](#invocation-by-name).

| Code          | Meaning                                                            |
| ------------- | ------------------------------------------------------------------ |
| 0             | Successful execution and core output                               |
| 1             | Expected action failure, internal failure, or invalid declarations |
| 2             | Invalid invocation inputs                                          |
| 3 through 125 | An application failure whose class declares that code              |
| 129           | Cancelled by `SIGHUP`                                              |
| 130           | Cancelled by `SIGINT`, a caller-supplied abort, or the action's `cancel()` |
| 131           | Cancelled by `SIGQUIT`                                             |
| 141           | Stopped because the reader of stdout closed the pipe               |
| 143           | Cancelled by `SIGTERM`                                             |
| Any, 0 through 255 | A middleware's takeover that [stated its code](middleware.md), such as the code of the program the [external-commands plugin](../plugins/external-commands.md) ran |

Codes 3 through 125 belong to the application: core raises none of them, and a failure exits with one only when its class declares it under [Declared exit codes](failures.md#declared-exit-codes). An application's class may also declare 1 or 2. Core resolves no other code of its own; a middleware's takeover may state any code from 0 through 255, as the last row says.

Each invocation follows this order:

1. Capture host facts from the run's [process handle](host.md#the-process-handle). A working directory that cannot be read fails the run here, under [An unreadable working directory](host.md#an-unreadable-working-directory), and so does a malformed value the build baked into the [release facts](release-facts.md). Then, in an Application that declares the [color mark](color.md), read the operator's color choice from `host.argv`, which sets the run's `color` policy field before anything else prints. Then settle the run's [background](background.md), reading the operator's background choice from `host.argv` in an Application that declares the background mark, and querying the terminal when no earlier source settles it, a theme entry is adaptive or an option carries the background mark, and no skip applies.
2. Build and validate the whole Command graph, or reuse the graph the Application already built for the run's build, under [Reusing the built graph](graph-inspection.md#reusing-the-built-graph). A graph build covers the global options, each Command's table, every installed plugin, every command name, alias, and spelling, then, in a [development build](release-facts.md#development-builds), every validated input's [schema converter](validation.md#input-schema), then every [`onGraphBuilt`](lifecycle-hooks.md#judging-the-built-graph) hook over the frozen graph. Then settle the run's [verbosity](verbosity.md) from `host.argv`, read with the parser's own word reader against the built graph, before anything that can write a lane runs. Run [environment preparation](plugin-contract.md#environment-preparation), then validate every declared default and implied value.
3. Copy invocation tokens for input processing.
4. Route from the root, reading option words against the global options and the own options of each Command with children that routing passes through, under [Global consumption and routing](commands.md#global-consumption-and-routing). An unknown command is held here, and routing stops at its word: steps 5 and 6 read nothing for it, and step 7 runs only the middleware declared `'always'`.
5. Parse the routed Command's remaining words against its table, up to the first bare `--`, and read the words after it under [Passthrough](options.md#passthrough): as plain words that fill the routed Command's arguments, or as its `passthrough` when it declares the passthrough mode. Hold the first structural fault in word order, raising nothing yet, and keep reading so every global option is found. A routed Command that is a group holds the missing-subcommand error behind any structural fault.
6. Run the [input-source stage](input-sources.md), which fills unfilled options from the environment and then the configuration source: the global options always, and the local options when nothing is held. Then compute the run's [interaction decision](interaction.md) from the terminal facts, `CI` in `host.env`, and the interaction-marked option's value. Then validate the global options in authoring order, and, when no structural fault is held and the Command is not a group, that Command's inputs in authoring order. When any fault is held, structural, input-source, or validation, validate as well each of a plugin's own options whose tokens parsed and that no pass reached, for that plugin's middleware's [`ownOptions`](middleware.md) alone; a validator runs at most once per run, so an option whose validator threw is not validated again. Hold the first fault by the precedence below, a validator's own developer error included, so a takeover swallows a broken validator as it swallows an input fault. A Command that [needs a terminal](commands.md#a-command-that-needs-a-terminal), run where stdin or stderr is not a terminal or under CI, holds `TerminalUnavailableError` in place of the input problems validation collected.
7. Run the [middleware](middleware.md) of each installed plugin whose activation matched, in installation order, loading each one as the chain reaches it. Each middleware reads the request. A middleware that takes over ends the invocation here, and a held fault is never raised. When the chain continues past its last middleware it reaches the dispatch boundary, where core raises the held fault, or reads the selected view, builds the [providers](providers.md) the routed Command opted in to, and dispatches the action.
8. Await its action. When it returns, close every [live region](output.md#live-region) the action opened that is still open, and before any failure renders, close every open region for the failure. Then close the run's ephemeral provided values, and, on the outermost run, its persistent ones, under [Closing](providers.md#closing).
9. Unwind the middleware chain. Once it has unwound, close every region still open, such as one a middleware or a configuration source opened, then remove the run's [`onShutdown`](signals.md#onshutdown) handlers while no shutdown is under way, then finish pending core output, call the [`onLiveRegions`](lifecycle-hooks.md#observing-live-regions) hooks with `'closed'` if a region still holds a frame because the write that would close it never reached stderr, end the run's reasons for core to listen, and set the exit status.

Error precedence follows these phases. An unknown command comes first among invocation-input faults. It skips invocation-input validation, but declared defaults and implied values validate before routing and can fail before an unknown-command takeover. Then the first structural fault in word order, then a group's missing subcommand, then a configuration source's fault or a validator's own thrown error, then a Command that needs a terminal run without one, then a validator issue. Unknown-command, misplaced-option, missing-value, repetition, and unexpected-argument diagnostics return code 2. Parsing, the input-source stage, and invocation validation run ahead of the chain so middleware can read the invocation. Core holds their faults until the dispatch boundary, and a takeover never observes them. A run cancelled before the chain starts, an abort landing inside a validator included, resolves its cancellation code under [Signals, cancellation, and shutdown](signals.md), and the held fault is never raised; core awaits the validator in flight and starts no further one. A run cancelled while the chain is running and before it reaches the dispatch boundary never reaches it: the `next()` that would have reached it resolves `'cancelled'`, the held fault and any bad `view` assignment stay unobserved, and the code is the signal's; a cancellation that lands after the action dispatched changes nothing here, and `next()` still resolves `'dispatched'`. The held fault is the input error carrying every issue collected in authoring order, or a validator's developer error, which stops validation where it happens and takes the place of anything collected before it, as [Issues and validator failures](validation.md#issues-and-validator-failures) states, or a configuration source's plugin fault or the failure it threw, which [Input sources](input-sources.md) ranks. The consequence is that a validator runs on an invocation a middleware then takes over, `app get --help` included: so a validator that reads the host or awaits a network still does so on such an invocation, and one with a side effect performs it there. A takeover skips neither invocation validation nor its effects. A declared default or implied value validates before tokens are parsed. A validator rejection, throw, or malformed result there fails before middleware can take over.

An action receives `{ args, options, supplied, interactive, passthrough, graph, command, out, host, signal, cancel, onShutdown, onSuspend, onResume, style, invoke, log, provided, stdin }`, where `log` records [log events](logging.md), `provided` holds the values of the [providers](providers.md) its Command opts in to, and `supplied`, `interactive`, and `cancel` are described under [Interaction](interaction.md). Core attaches no input-source or token-spelling metadata to the action's input values. `graph` is the frozen graph [`inspect()`](graph-inspection.md) returns, built for this run, and `command` is the routed node inside it: the same two values the run's [middleware](middleware.md) receive, under [ADR-0041](../decisions/0041-every-action-reads-the-frozen-graph-and-its-routed-command.md). An application's action and a plugin Command's action receive them alike, so a Command whose job is to project the graph, such as [completion](../plugins/completion.md), does it in its own action. The contextual `style` includes the installed theme's custom names. Its return value is ignored, including a resolved promise value. `run()` awaits action completion but does not render its return value. `signal` is the run's cancellation signal, which [Signals, cancellation, and shutdown](signals.md) describes; a caller signal, a process signal, the action's `cancel()`, or a closed pipe can abort it. `onShutdown` registers a synchronous handler that runs once, at the end of a shutdown or of the process, and is removed when the run ends while no shutdown is under way, under [onShutdown](signals.md#onshutdown). `onSuspend` and `onResume` register synchronous handlers for Ctrl-Z and `fg` that are removed when the run ends, under [Suspend and resume](signals.md#suspend-and-resume). `invoke` runs another Command of the same graph by name, under [Invocation by name](#invocation-by-name). `passthrough` is a member only on a Command that declares the [passthrough mode](options.md#passthrough), and the context of any other Command has no such member.

The application can run again. Each call captures host facts, and builds from its declarations unless the Application already built its graph for the call's build, under [Reusing the built graph](graph-inspection.md#reusing-the-built-graph). Core does not call `process.exit()` or track unrelated background work. Before the action runs, it consumes no stdin but for one bounded read: the [background query](background.md), made before graph build and environment preparation, which reads a terminal stdin until the terminal answers or one second passes, and pushes every byte that is neither a reply nor an interrupt key back onto stdin unless an interrupt key raised its signal, so the action reads what the operator typed. A declared content handle reads only when the action calls its read methods. It listens on its process handle's signal source while the run is live, and otherwise only while an `onShutdown`, `onSuspend`, or `onResume` handler asks it to, under [Listening](signals.md#listening), and it ends the process only by re-raising a signal it received after the [shutdown](signals.md#the-shutdown), so that the default disposition ends it with the shell's status. Beside that re-raise, it raises a signal on its handle's signal source only for an interrupt key a raw-mode reader read, where the key arrives as a byte, under [Raw-mode readers](signals.md#raw-mode-readers).

## Invocation by name

```ts sketch
import type { ExitCode, FailureExitCode, FailureForm, LoomError, ProcessHandle, ProgressEvent } from '@loomcli/core';

interface InvocationValues {
  readonly args?: Readonly<Record<string, string | number | boolean | readonly (string | number)[] | undefined>>;
  readonly options?: Readonly<
    Record<
      string,
      string | number | boolean | readonly (string | number)[] | readonly (readonly (string | number)[])[] | undefined
    >
  >;
  readonly passthrough?: readonly string[];
}
interface InvokeOptions<Mapped = LoomError> {
  readonly view?: string; // the starting view selection, as a middleware's `view` assignment
  readonly failure?: (
    failure: Readonly<LoomError>,
    context: {
      readonly application: string;
      readonly path: readonly string[];
      readonly exitCode: FailureExitCode;
      readonly form: FailureForm; // see The failure form
    },
  ) => Mapped;
  readonly signal?: AbortSignal; // composed with the parent run's signal
  readonly onProgress?: (event: ProgressEvent) => void; // see Progress events
  readonly exclude?: readonly string[]; // options the call leaves out of its run, by declared name
  readonly timeZone?: string; // the IANA time zone for this call and its nested calls
}
type InvocationOutcome<Mapped = LoomError> =
  | {
      readonly status: 'completed';
      readonly exitCode?: ExitCode; // present when a takeover stated a code other than 0
      readonly output: string;
      readonly messages: string;
    }
  | {
      readonly status: 'failed';
      readonly failure: Mapped;
      readonly form: FailureForm; // the failure form of the failure the handler received
      readonly exitCode: FailureExitCode;
      readonly output: string;
      readonly messages: string;
    }
  | { readonly status: 'cancelled'; readonly exitCode: 129 | 130 | 131 | 141 | 143 };

// One signature over an Application's Command paths, under Typed paths: a literal path the paths
// declare types `values` against that Command, and any other path takes `InvocationValues`.
type Invoke<Paths, Extra = {}> = <
  Mapped = LoomError,
  const Path extends readonly string[] = readonly string[],
>(
  path: PathParameter<Paths, Path>, // a literal path, checked against the declared canonical names
  values: PathValues<Paths, NoInfer<Path>>, // that Command's values, or InvocationValues
  options?: InvokeOptions<Mapped> & Extra,
) => Promise<InvocationOutcome<Mapped>>;
// The action's `invoke` names the registered paths in its base type alone, so they resolve only
// when a call reads them.
interface ActionInvoke extends Invoke<RegisteredPaths> {}

interface ActionContext<Args, Options = {}, Result = unknown, Provided = {}> {
  // ...the members under Invocation...
  readonly invoke: ActionInvoke; // bound to the graph this run built; typed by Register.paths
}
declare class Application<Paths, Plugins extends readonly Plugin[]> {
  // ...the members under Application declarations; published in every state, as run() is...
  readonly invoke: Invoke<
    ApplicationPaths<Paths, Plugins>, // the root's entry, every global option included
    {
      readonly process?: ProcessHandle; // the real process's handle when omitted
    }
  >; // builds the graph as run() does, reusing a kept one
}
```

```ts
import { Command, type Application } from '@loomcli/core';

export async function showKeys(jsonkit: Pick<Application, 'invoke'>) {
  // An embedding host runs `jsonkit keys user -f doc.json` with named values in place of argv.
  const outcome = await jsonkit.invoke(['keys'], { args: { path: 'user' }, options: { file: 'doc.json' } });
  if (outcome.status === 'completed') {
    process.stdout.write(outcome.output);
  }
}

// An action runs another Command of its own graph by name and reads its JSON view.
export const report = new Command('report').action(async ({ invoke, out, style }) => {
  const members = await invoke([], { options: { file: 'doc.json' } }, { view: 'json' });
  if (members.status === 'failed') {
    out.fatal(style.escape(members.messages));
  }
  if (members.status === 'completed') {
    await out.print(`${String(JSON.parse(members.output).length)} top-level keys`);
  }
});
```

`invoke(path, values, options?)` runs one Command of an already-built graph by its path, with named values in place of argv, captures what the run writes instead of writing it, and resolves a structured outcome. An action reaches it as `invoke` on its context, bound to the graph its own run built. An embedding host reaches it as `app.invoke`, which builds the graph as `run()` does, reusing the graph the Application already built for that build. [ADR-0059](../decisions/0059-a-command-runs-by-name-through-invoke.md) records the decision.

- **One run, spelled by name.** `invoke(path, values)` behaves as `run()` does on the argv that spells the same path and values: one table, routing and its held faults, the [input-source stage](input-sources.md), declared defaults and implied values, every validator, the middleware chain and its takeovers, [translators](failures.md#translators), failure views, [declared exit codes](failures.md#declared-exit-codes), and the precedence [Invocation](#invocation) states. A divergence between the two on the same inputs is a defect. The rules below state the only differences: values arrive by name, the call may exclude options or set its time zone, `passthrough` reaches only a Command that declares the passthrough mode, problems report by name, the output is captured, and the run makes no process effect.
- **The path.** `path` names Commands from the root, `[]` for the root. Each element reads as a plain word reads during routing: a canonical name or an [alias](commands.md#aliases) descends, and a hidden Command routes. An element that no child holds is the `UnknownCommandError` routing holds, with the partial path, as argv's is held, and a middleware's `unknownCommand` reads it with the path elements after it. So is an element after a Command that has no children, which lists no candidates, because a path names Commands alone and an argument goes under `args`. A path that ends at a group holds the missing-subcommand error, as argv does.
- **The values.** `values` mirrors the action context: `args` is keyed by argument name, `options` by the declared name of the routed Command's local options and of every global option, a plugin's included, and `passthrough` is the words a command line writes after the first bare `--`, delivered unchanged to a Command that declares the [passthrough mode](options.md#passthrough). On a Command without the mode, a non-empty `passthrough` is an `UnexpectedArgumentError`, under **Unknown names**, although argv would fill the Command's arguments with the same words, and an empty one is no fault. An argument after a variadic argument is named like any other, so a call by name never depends on the order the words of a command line fill. The two records are separate because an argument and an option may share a name. An option alias, a short spelling, and a negative spelling are spellings, never keys. A key whose value is `undefined` reads as an absent key.
- **Lowering.** Each value lowers to the tokens argv would give, once, at the point the parser produces its result, and never by building argv text. So `SuppliedInputs`, every validator, and the [input schema](validation.md#input-schema) meet exactly what they meet on a command line.

  | Value                                   | Input                                    | Lowers to                                                                                         |
  | --------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
  | A string                                | A string option or a scalar argument     | That token                                                                                        |
  | A finite number                         | A string option or a scalar argument     | The token `String(value)` gives, such as `5` or `0.5`                                             |
  | `true`                                  | A Boolean option                         | The spelling that reads `true`, or absence on a `negative` option, whose absent value is `true`   |
  | `false`                                 | A Boolean option                         | The negative spelling on a `both` or `negative` option, or absence on a `positive` option         |
  | `true`                                  | A string option with an implied value    | The bare spelling, which supplies the [implied value](options.md#implied-values)                            |
  | A whole number of 0 or more             | A counted option                         | That many occurrences, so 0 is absence                                                            |
  | A string, a number, or an array of them | A multiple option or a variadic argument | One occurrence per element in order; a single value is one occurrence, and an empty array is none |
  | A tuple of exactly the declared count of strings or finite numbers | An [arity option](options.md#option-value-arity) | One occurrence that holds the tuple's words in order |
  | A list of such tuples | A multiple arity option | One occurrence per tuple in order; a single tuple is one occurrence, and an empty list is none |

  A value no row covers is unlowerable: `null`, an object, a nested array, an array on a scalar input, a Boolean on an argument, on a counted option, or on a string option without an implied value, `false` on a string option with one, a number that is not finite, a number on a Boolean option, and a number on a counted option that is not a whole number of 0 or more. An unlowerable value supplies nothing, so an input source may still fill the option. It is an `invalid` problem of the run's `InputError`, in authoring order with the validation phase, with exit 2, and its one issue says what the input takes: `Use a string or a number.`, `Use a string, a number, or a list of them.` on a multiple option or a variadic argument, `Use true or false.` on a Boolean option, `Use a string, a number, or true.` on a string option with an implied value, `Use a string, a number, true, or a list of strings and numbers.` on a multiple option with an implied value, `Use a whole number of 0 or more.` on a counted option, `Use a list of 2 strings or numbers.` on an arity option, with its count, and `Use a list of 2 strings or numbers, or a list of such lists.` on a multiple arity option. Three cases follow from the equivalence. `false` on a `positive` option is absence, so an environment binding or the configuration file may still fill it, as it fills an option a command line omits. An empty array on a required multiple option is the missing-input problem. A number on a string option with no validator reaches the action as the string `String(value)`. A word of an arity option's tuple may be an option word or a bare `--`, which no command line can spell as one of its values: lowering writes occurrences, never argv text, so a call by name and an MCP client supply such a value, the one exception to the rule that a call by name behaves as the argv that spells it, under [ADR-0161](../decisions/0161-a-string-option-may-declare-an-arity-and-each-occurrence-takes-that-many-separate-words.md).
- **Unknown names.** A key of `options` that the routed Command's table does not hold is an `UnknownOptionError`, and a key of `args` the routed Command does not declare is an `UnexpectedArgumentError` whose `extra` holds the name and whose `accepted` holds the number of arguments the Command declares. A non-empty `passthrough` on a Command that does not declare the passthrough mode is an `UnexpectedArgumentError` whose `extra` holds those words and whose `accepted` holds the number of arguments the Command declares, with the sentence `Command "get" declares no passthrough. Remove passthrough from the values.` Each is a structural fault, held as argv's are, and the first held is the first in the order `options` keys, then `exclude` names, then `args` keys, each in its own order, then `passthrough`. It ranks after an unknown command and ahead of a group's missing subcommand and the validation phase, and a middleware takes it over as it takes over any held fault.
- **Excluded options.** `exclude` names options the call leaves out of its run, by declared name: any of the routed Command's local options and of every global option, a plugin's included. No tier supplies an excluded option. A key of `options` that names one is the `UnknownOptionError` an unknown key is, and the [input-source stage](input-sources.md) reads no variable for it and never asks the configuration source for it, so a variable or a configuration key bound to it is a value no input reads. A configuration source's own option that the call excludes reads no variable either, so it never selects what the source reads. It takes its declared default as any omitted option does, and a required one is the missing-input problem, by name. A name in `exclude` that the routed Command's table does not hold is an `UnknownOptionError`, held under **Unknown names**. The exclusion lasts for the one call: help, the manifest, completion, a command line, and the parent run still read the option, and a nested call excludes only what its own `exclude` names.
- **Reported by name.** An invocation by name types no spelling, so every problem core reports names an input by its declared name, the key the caller wrote, in place of the [reported spelling](failures.md#failure-classes) and of the spelling a parser fault names. `InputProblem.spelling` and `UnknownOptionError.spelling` hold that name. The sentences read `Option "file": Use a string or a number.`, `Option "depth" is required. Supply a value.`, `Option "min-bytes" (from TEXTSTAT_MIN_BYTES): Expected a whole number of at least 0.`, `Unknown option "verbos". Supply the name of a declared option.`, and `Command "get" declares no argument "pth". Supply the name of a declared argument.` An argument already reports under its name. A [configuration source](input-sources.md) reads `invokedBy` on its context and names a problem's option the same way.
- **Capture.** The run's stdout and stderr are capture sinks. `output` holds every byte the run wrote to stdout, decoded as UTF-8: the rendered result on a Command that declares one, and `out.print` and `out.render` text on one that does not. `messages` holds every byte the run wrote to stderr: the semantic lanes its [verbosity](verbosity.md) shows, the action's `print` and `render` on a result Command, a failure's diagnostic and its hints, and the [incomplete-result](results.md#a-sequence-that-stops-early) line. Stdin is an empty stream, `host.argv` is `[]`, and every terminal fact reads not a TTY, with no width or height, so a view's [`columns`](styles.md#width-padding-and-multiline-lanes) reads `undefined`. The captured text is plain: core resolves it as for a destination that supports no color, modifier, or hyperlink, whatever the rendering policy or `FORCE_COLOR` says, and `terminalControls` keeps the Application's setting.
- **The view.** `view` is the starting selection: the name a middleware's `view` reads before any assignment, in place of the declaration's default. A later assignment still wins, and the [formatter](../plugins/format.md) assigns only when `--format` was supplied. A name the routed Command's result does not hold and a `view` on a Command that declares no result are the view-selection defect at the dispatch boundary, exit 1, under `@loomcli/core/view-selection`, with `invoke()` named in the plugin's place: `invoke() selected view "yaml", which Command "count" does not name.` and `invoke() selected view "json" on Command "get", which declares no result.` A takeover or a cancellation leaves it unobserved, as it leaves a middleware's.
- **The outcome.** `completed` is a run that ended with no failure and was not cancelled, a takeover included, and `exitCode` is the code `run()` would resolve: 0, or the code a takeover stated through the middleware context's [`exitCode`](middleware.md). Core sets it only when it is not 0, so a reader takes an absent one as 0, an exact match of a completed outcome written before it still holds, and a test double that builds the outcome need not state it. `failed` is a run that would resolve a failure code: `exitCode` is that code, `output` and `messages` hold everything the run wrote, the failure's report included, and `failure` holds what the caller's handler returned, or the failure itself when the caller passed no handler, and `form` holds that failure's [failure form](failures.md#the-failure-form). `cancelled` is a cancelled run, and `exitCode` is the code of the cause that aborted it; its captured text is discarded. `invoke` never rejects for a call its types accept, except as [When author code fails](#when-author-code-fails) states. `Mapped` is inferred from the handler, and without one it is `LoomError`.
- **The failure path.** A failure takes `run()`'s path. A foreign throw is offered to the translators, each `onFailure` hook adds its [hints](lifecycle-hooks.md#failure-hints), and the failure's view renders, by build, into `messages`: a defect in a [distributed build](release-facts.md#development-builds) writes the generic defect message there. Then core calls the caller's `failure` handler once, for the primary failure, or, when the primary outcome succeeded and a fault reported after it set the code, such as a view's throw in an `out.render` call no code awaited, for the first such fault, with the failure as the run caught it, the translated failure and never the raw throw, and a context that holds `application`, `path`, the outcome's `exitCode`, and the failure's [failure form](failures.md#the-failure-form). The handler adds structure and never replaces the text: `messages` holds the same report `run()` writes to stderr when no [failure encoder](failure-views.md#failure-encoders) answers. It receives no style, because the form's hints are plain text, and no graph, which a failure raised at build lacks, under [ADR-0046](../decisions/0046-a-failure-view-reads-where-the-run-was-and-plugins-add-hint-lines.md). It receives the failure in both builds, its `cause` included, so what it exposes is the caller's decision. A cancellation never reaches it.
- **No encoded line.** The [failure-encoding stage](failure-views.md#failure-encoders) runs under `run()` alone. Under `invoke`, a failure's view renders into `messages` whatever media type the selected view declares, so `invoke(['paths'], …, { view: 'json' })` captures the failure's text, and the caller reads the form from the outcome and from its handler's context.
- **Spellings.** A value lowered by name is recorded in a middleware's [`spellings`](middleware.md) under the option's reported spelling, its long form, else its negative or short form, so [help](../plugins/help.md#help-variants) renders the extended page for `help: true`, as it does for `--help`.
- **Where the run was.** A run `invoke` started reads `invokedBy: 'name'` on the [failure view context](failure-views.md#failure-view-context) and the [failure hook context](lifecycle-hooks.md#failure-hints), and every other run reads `'argv'`. A hint that points at a command line skips an invocation by name: [help's hint](../plugins/suggestions.md#helps-failure-hint) and the example `--explain` hint return none for it, and the [suggestions](../plugins/suggestions.md) plugin offers declared names in place of spellings.
- **No process effects.** An invocation by name claims no process signal, and a handler registered inside `app.invoke` never starts core listening, though a shutdown under way on its process handle's signal source aborts the call's run and calls the handler, under [Listening](signals.md#listening). An action's call counts with its run, so its handlers keep core listening. It writes no `exitCode` to its process handle, writes to none of the handle's streams, and calls no `process.exit()`. Content preparation reads metadata but no content and rejects paths to the process stdin pipe or device, as [Content inputs](validation.md#content-inputs) states. Actions control later reads through accepted file handles. Apart from the per-call time zone below, an action's `invoke` takes the call's other host facts, such as `env`, `cwd`, `platform`, `readSource`, and [`release`](release-facts.md), from its run's host. `app.invoke` captures them from its [process handle](host.md#the-process-handle) at entry, as `run()` does. The call reads no `argv`, stream, or terminal fact from the handle, and its type accepts no `rendering`. A working directory that capture cannot read resolves `failed`, under [An unreadable working directory](host.md#an-unreadable-working-directory). A log event of the call reaches each `onLog` with the outermost run's destination, under [Observing log events](lifecycle-hooks.md#observing-log-events): the parent run's for an action's `invoke`, and a `null` stderr for `app.invoke`, so no log record enters the captured output.
- **The graph.** An action's `invoke` reuses the graph its run built and validated: no lifecycle hook runs again. For an explicit per-call zone, core reads the parent's `host.timeZone` for the reuse comparison even if the parent's code never read it. An omitted zone reuses the parent's values without forcing that read. It reuses declared-value checks only when the call's effective time zone matches the zone those values were validated under, with an array default copied for the call. When the zone differs, it validates every declared default and implied value anew from its declaration against the call's own host before input validation or middleware, and keeps those validated values and their zone for nested calls. `app.invoke` builds the graph as `run()` does: the first call or run of an Application in each build runs every `onCommandAttach` and [`onGraphBuilt`](lifecycle-hooks.md#judging-the-built-graph) hook, and a later one reuses that graph, under [Reusing the built graph](graph-inspection.md#reusing-the-built-graph). Every `app.invoke` call validates every declared default and implied value, and a build fault is a `failed` outcome with exit 1. Both render by the run's [release facts](release-facts.md).
- **Cancellation.** Each call has its own run signal. An action's `invoke` derives it from its run's signal and the call's `signal`, and the first to abort fixes the reason. A parent's abort carries the parent's reason, so the call reads `cancelled` with the parent's code, 129, 130, 131, 141, or 143, and an abort of the call's own `signal` reads 130 as a caller abort. `app.invoke` derives it from the call's `signal` alone. A signal already aborted at the call resolves `cancelled` having run no middleware and no action. Inside the call, the rules of [Signals, cancellation, and shutdown](signals.md) hold. The call has its own `onShutdown`, `onSuspend`, and `onResume`, scoped to the call. A shutdown aborts every live run, `app.invoke` included, with the signal's name as the source.
- **Concurrency.** Calls may overlap, from one action or from many. Each is its own run and shares nothing mutable with another but the [persistent provided values](providers.md#lifetimes) of their outermost run, and Loom adds no queue, limit, or timer. An application whose actions cannot overlap serializes the calls itself.
- **Nesting.** An invoked action may call `invoke` itself, under these rules, and its call's signal derives from its own run.
- **Not interactive.** An invocation by name has an empty stdin and no terminal, so its [interaction decision](interaction.md) is off: a local option or an argument that declares `required: 'non-interactive'` is required, and a question resolves without asking.
- **No terminal.** For the same reason, a Command that [needs a terminal](commands.md#a-command-that-needs-a-terminal) always fails by name, before its action, with `TerminalUnavailableError`, failure code `terminal-unavailable`, exit 1, from an action's `invoke` and from `app.invoke` alike, whatever terminal the calling run has.
- **Its own verbosity.** Each call settles its own [verbosity](verbosity.md) from the values it lowers, so `options: { verbose: 2 }` reads as `-vv` does and under `app.invoke` the log lines it reveals land in `messages`. A call inherits nothing from its parent run's verbosity, because it behaves as the argv that spells its values. Log lines are the exception: under an action's `invoke`, an MCP tool call included, they follow the outermost run's verbosity and reach its stderr, never the call's `messages`, as [At -v](logging.md#at--v) states.
- **Progress.** `onProgress` receives each [progress event](output.md#progress-events) of the call's run, in order, synchronously inside the `report` call or the region close that built it, so a caller reads a Command's progress while it runs. A call with no observer collects nothing. A call inherits no observer from its parent run, and the parent's observer receives none of the call's events. The call has no terminal, so none of its [live regions](output.md#live-region) draws, and a [progress line](../libs/prompts.md#progress) writes its start line and, unless it is cancelled or cleared, its end line into `messages`, and a line with a log that fails, warns, or is cancelled also writes its kept log lines above its end line (a cancelled line writes them alone), under [A line's log](../libs/prompts.md#a-lines-log).
- **Actions alone.** A middleware's context carries no `invoke`. A Command that serves other Commands by name does so in its own action, as the [MCP](../plugins/mcp.md) plugin's `mcp` Command does.
- **The call's time zone.** `timeZone` sets `host.timeZone` for this invocation before validation, without changing its process handle or its parent's zone. Without it, `app.invoke` reads the handle's zone, and an action's `invoke` inherits its immediate parent's effective zone. Nested calls inherit that zone unless they supply their own `timeZone`; siblings and concurrent calls are independent. No other host fact has a per-call override. A supplied zone-less token read by `dateTime()` uses this zone unless the validator declares its own; an offset or `Z` still names its own instant. If the effective zone differs from the zone the reused declared values were validated under, the call validates every declared default and implied value again against its own host. Both doors therefore resolve an omitted zone-less `dateTime()` default in the same zone as a supplied zone-less token. A call in the same resolved zone, or one that omits `timeZone`, reuses its parent's validated values.
- **A valid time-zone name.** Core's public `resolveTimeZone(timeZone: string): string | undefined` constructs `new Intl.DateTimeFormat('en-US', { timeZone })` and returns `resolvedOptions().timeZone`, unless that resolved name starts with `+` or `-`. It returns `undefined` for an offset or failed construction. This refuses numeric offsets, including a Unicode-minus input that the formatter resolves to an offset, and accepts `UTC` and runtime-known aliases. `host.timeZone` holds the resolved spelling. The check neither trims input nor reads a `process` global or default zone, and invoke and MCP share this one core implementation. A `dateTime({ timeZone })` pin remains the author's value under the validators' existing `isKnownZone` rule, which accepts offsets. An invalid per-call name resolves `failed` with `InputError`, exit 2, and an empty `problems` list, because the invocation option names no declared input. Its own sentence is `invoke() timeZone is not an IANA time zone name this runtime knows. Use a name such as "Asia/Tokyo".`, without repeating the received value. It follows the ordinary failure view, hints, form, and `failure` handler. It fails during host assembly, after existing working-directory and release-fact failures and before validation or middleware. [ADR-0193](../decisions/0193-invoke-takes-a-per-call-time-zone-and-mcp-reads-it-from-request-metadata.md) records the contract.
- **The call's shape.** The types reject a malformed call, such as a `path` that is not an array of strings, an `exclude` that is not an array of strings, a `signal` that is not an `AbortSignal`, or a `failure` or an `onProgress` that is not a function. A value that bypasses them gets no rule, under [ADR-0093](../decisions/0093-a-value-that-bypasses-the-types-gets-no-rule.md): the platform's own error reports it, as a rejection of the call or as a defect of its run. A `values` key other than `args`, `options`, and `passthrough` is not read. The call copies `path`, `passthrough`, and `exclude` where it enters, so a later change to any of those arrays changes nothing the run reads.
- **Names.** `resolveTimeZone`, `InvocationValues`, `InvokeOptions`, `InvocationOutcome`, `Invoke`, `CommandPaths`, and `PathsOf` are exported from `@loomcli/core`, and `ActionContext` carries `invoke`. `ProgressEvent` is exported under [Progress events](output.md#progress-events).

### Typed paths

`invoke` types a literal path and its values from the Command paths the Application declares, so `invoke(['gte'], …)` and `invoke(['get'], { options: { flie: 'x' } })` are compile errors rather than an `UnknownCommandError` and an `UnknownOptionError` at run time. Nothing changes at run time: the typing narrows what a call compiles with, and the rules above hold for every call that compiles.

- **Command paths.** Each Command carries its entry under its canonical name: the value each of its arguments and local options takes, by declared name, and its children's entries, by canonical name. `command()` joins a child's entry to its parent's, and the Application's root entry adds every global option, a plugin's included. `PathsOf<typeof app>` reads an Application's paths, and `CommandPaths` names one entry's shape.
- **A literal path.** A path written as a tuple of string literals, `[]` for the root, is checked one name at a time against the canonical names its level declares, so a mistyped name reads `Type '"gte"' is not assignable to type '"get" | "remote"'`, and a name after a Command with no children reads as a path one element too long. Its `values` take the routed Command's arguments and local options and every global option, each optional, so an undeclared name is an excess property and a wrongly typed value a type error. Each value takes what [Lowering](#invocation-by-name) accepts for its input: a string or a number on a string option or a scalar argument, a list of them on a multiple option or a variadic argument, `true` as well on an option with an implied value, a Boolean on a Boolean option, a count on a counted option, and a list of words on an arity option, whose length the run checks. `passthrough` is accepted on every path, and the run refuses a non-empty one on a Command without the passthrough mode.
- **A dynamic path.** A path typed as an array, such as `readonly string[]`, or a tuple with an element typed as the wide `string`, takes the dynamic `InvocationValues`, as every call did before. The MCP plugin and a caller that walks the graph pass their paths this way, and so does a caller whose values are typed as `InvocationValues`.
- **Canonical names only.** A literal path checked against canonical names takes canonical names alone. An [alias](commands.md#aliases) routes at run time, so a call that names one passes its path as `readonly string[]`; on an Application that installs a plugin, an undeclared root name, an alias at the root included, already reads dynamically, as the next bullets state.
- **One path, one Command.** A union of literal paths, such as `dry ? ['plan'] : ['apply']`, names no one Command whose values could type the call, so it takes the dynamic `InvocationValues`, and the run reports a misspelled branch. An explicit type argument, such as `invoke<string>(['get'], …)`, leaves the path at its default, so that call is dynamic too.
- **A union inside one name.** A path whose element is a union of literal names, such as `['remote', dry ? 'add' : 'rm']`, stays typed: its `values` take either Command's values, so an option either Command declares compiles, and a name neither declares is an excess property. The run checks the values against the Command the path routes to, so an option only the other Command declares fails there as an unknown option. A member that names no Command at its level, such as a misspelled `'rmm'`, makes the path read dynamically, so the run reports it.
- **Options a hook adds.** The values type the options a declaration states. An option a plugin's [`onCommandAttach`](lifecycle-hooks.md) hook adds exists only at run time, so a literal path rejects it: the [formatter](../plugins/format.md)'s `--format` and `--fields`, which it adds to every Command with a result, are such options. Select a view with the call's `view`, as `invoke(['list'], {}, { view: 'json' })` does in place of `--format json`, or pass the path as a `readonly string[]` to supply them by name.
- **Where no type states the names.** A path deeper than four Commands reads dynamically, and so does a path through a Command whose name is typed as the wide `string`, from its level on. A plugin may contribute Commands at the root, which no type names, so on an Application that installs any plugin a first name the Application does not declare reads dynamically; the Commands it declares stay typed. The neutral `Application` annotation states no paths, so each of its calls is dynamic.
- **An action's `invoke`.** A Command declared in its own module cannot name the Application it attaches to, so an action's `invoke` reads the paths the Application registers under `Register.paths`, beside its [environment](commands.md#modular-authoring), and is dynamic where none is registered. Register the completed Application's paths: unlike the environment, they are read only inside an action's body, so the registration creates no circular dependency. The context's `invoke` names them only in the base type of its own interface, so they resolve where a call reads `invoke`, and an action that never calls it does not resolve the Application's type.

```ts
// src/application.ts
import { Application } from '@loomcli/core';
import type { EnvironmentOf, PathsOf } from '@loomcli/core';
import { get } from './commands/get.js';
import { report } from './commands/report.js';

const configured = new Application('jsonkit').globalOption('file', { type: 'string' });

export const jsonkit = configured.command(get).command(report);

declare module '@loomcli/core' {
  interface Register {
    environment: EnvironmentOf<typeof configured>;
    paths: PathsOf<typeof jsonkit>;
  }
}

// src/commands/get.ts
import { Command } from '@loomcli/core';

export const get = new Command('get')
  .argument('path', { required: true })
  .action(({ args, out }) => out.print(args.path));

// src/commands/report.ts
import { Command } from '@loomcli/core';

export const report = new Command('report').action(async ({ invoke, out }) => {
  const result = await invoke(['get'], { args: { path: 'user' }, options: { file: 'doc.json' } });
  if (result.status === 'completed') await out.print(result.output);
});
```

- **Two Applications, two types.** An Application's type carries its Command paths, so two Applications that declare different Commands have different types. A variable or a parameter that holds either takes the `Application` annotation, whose calls are dynamic.

## When author code fails

An action, a middleware, a validator, a translator, a failure view, or a hook that throws or rejects during a run, or during a call `invoke` makes, takes the [ordinary failure path](failures.md#the-ordinary-failure-path), and an author's catch is final under [ADR-0097](../decisions/0097-one-ordinary-failure-path-where-an-authors-catch-is-final.md). Three outcomes differ:

- **A validator's developer error.** A validator that throws, rejects, or returns a malformed result is held as the validation phase's first fault, stops validation where it happens, and takes the place of anything collected before it. Core raises it at the dispatch boundary, so a takeover swallows it as it swallows an input fault. A declared default or implied value whose validator does so fails before middleware can take over.
- **A broken failure view or hook.** It reports through the plain fallback path and forces exit 1. Under `invoke`, the outcome is `failed` with exit 1 and the report lands in `messages`.
- **A caller's handler or observer.** A `failure` handler that throws makes `invoke` reject with that throw. An `onProgress` observer that throws is called no more, and `invoke` rejects with that throw once the run settles. In both cases the run's captured text is discarded.
