- Fix installs and uninstalls through `completion`, `skills`, `manpage`, and `service` that failed with core's generic line or changed files before they failed. Each run now reads every path it needs and checks that it may write every folder it writes or removes in, and empty every folder it replaces or removes, before it changes anything. A path it cannot reach, read, or write fails the run with `Cannot reach <path> because a file sits where one of its folders is needed.`, `Cannot reach <path> because one of its folders is a link to a folder that does not exist.`, `Cannot read <path> because you do not have permission to reach or read it.`, or `Cannot write <path> because you do not have permission to write or search there.`, each with its step, and with nothing changed. The sentence about a link is new; a phrasebook can say it through the `@loomcli/plugins` entry `installation.pathDangling`. The sentence about writing is reworded, because it now also prints for a folder that can be written but not searched: it read `because you do not have permission to write there. Make the location writable, then run the command again.` and reads `because you do not have permission to write or search there. Make the location writable and searchable, then run the command again.`; its entry `installation.writeUnwritable` keeps its name and parameters. See [Installation record](../docs/core/installation-record.md#installed-files).
  - `notes skills install --force` with a file at `~/.agents` or `~/.agents/skills` used to replace the Claude copy of the skill, removing any file the operator added to it, and record it before it failed. It now fails naming `~/.agents/skills/<skill>` and leaves both targets as they were. Every run that writes several recorded targets checks them all first: `skills install`, `update`, and `uninstall` for `claude` and `agents`, and `completion update` and `completion uninstall` for each shell.
  - An uninstall in a folder that cannot be written, such as a man page folder with mode `555`, used to fail with core's generic line, after the service plugin had stopped and disabled the service, or after the last completion shell had removed its script and left a record that listed it. It now fails before it stops anything or removes anything. Before, with `man1` at mode `555`:

    ```console
    $ notes manpage uninstall
    notes: Something went wrong.
    ```

    After:

    ```console
    $ notes manpage uninstall
    Cannot write /home/me/.local/share/man/man1/notes.1 because you do not have permission to write or search there. Make the location writable and searchable, then run the command again.
    ```

  - A recorded file the run cannot read, such as one man page of many with mode `000`, used to fail `manpage uninstall` after it removed the pages before it, and to fail an install that dropped the page after it wrote the new pages. Both now fail naming the page with every page in place.
  - A symbolic link to a folder that is gone, such as `~/.local/share/man`, `~/.local/share/notes`, or `~/.claude` left behind by a dotfile manager, used to make `manpage install`, `completion install`, and `skills install` fail with core's generic line, and made `manpage uninstall` read the pages below it as gone and report nothing installed. Each now fails naming the path below the link, with nothing changed.
  - A `ZDOTDIR` that names a file now fails `completion install`, `update`, and `uninstall` naming `.zshrc` below it, in place of core's generic line. `.bashrc` and the fish configuration read the same way.
  - `notes skills install --project` used to replace the Claude copy of a skill and then fail on an `.agents/skills` folder it could not write. It now checks every target's skill folder first, and names the folder it cannot write, empty, or create, such as `.claude/skills` under a `.claude` folder that cannot be written, with no copy replaced.
  - An installed skill folder an operator made read-only, such as with `chmod -R a-w ~/.claude/skills/notes`, used to make `skills update`, `install`, and `install --force` fail with core's generic line on every run, after they had moved the folder aside under a hidden retired name and left the record pending, and made `skills uninstall` fail with core's generic line too, with the folder still in place. Each now fails naming the folder, with both targets and the record as they were. The check covers every folder a run replaces or removes and each directory inside it, and names the first one the run may not write or search, such as `~/.claude/skills/notes/assets` after `chmod -R 644` on it. `skills update` used to fail there midway, with the Claude copy replaced, the Agents copy old, and the old folder left under a hidden retired name.
  - A leftover `.<skill>.<random>.loom-retired` or `.loom-staging` folder beside an installed skill folder, left by an earlier version or a failed run, can hold a folder the run may not write or search. `skills install`, `update`, and `install --force`, and `skills uninstall` while the record was pending, used to fail on it with core's generic line on every run and leave the record pending. Each run now checks every leftover it would remove before it changes anything, and fails naming the directory that refuses, with the leftover kept under its name. Once the run's user can list, write, and search that directory, the next run that writes the skill's folder or recovers a pending record listing it removes the leftover and completes.
  - A fresh install that fails on a blocked path now leaves a stopped run's leftover staging file of the record in place, and a pending record stays pending, until a run whose reads and checks pass removes or recovers them.
  - `notes service install` now checks that it may write the new unit and the record before it stops and disables an earlier unit or creates the `output` folder, so a unit or record folder that cannot be written fails with every unit running and no folder created. A retry after a record that stayed pending now reloads the manager and commits the record, where it reported the unit unchanged and left the record pending.
