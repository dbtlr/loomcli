# Deviations

Each row is a difference from the reference contract that the port introduces on purpose. The authoring API is Rust-native by [ADR-0002](decisions/0002-the-typescript-reference-is-the-behavioral-contract.md), so a renamed call or a builder in place of an options object is not a deviation; a changed rule, moment, or operator-visible byte is. The [core API design](design/core-api.md) gives each one's Rust form.

| Area | What differs | Why |
| --- | --- | --- |
| Validation | Validators are synchronous: `Validator::validate` returns its verdict. The reference accepts an asynchronous Standard Schema validator, and its `path` validator probes the file system asynchronously; the Rust `path` probes synchronously. | A validator judges one string, and the reference's asynchronous validators have no first-party user ([ADR-0003](decisions/0003-a-run-is-asynchronous-on-tokio.md)). |
| Validation | The validation context is a parameter of `validate`. The reference's `validationContext(options)` and `validationContextKey` have no counterpart; `validation_context(handle, facts)` replaces `validationOptions`. | Rust validators are a trait core defines, not Standard Schema values that receive context through an options bag. |
| Validation | `@loomcli/core/validator-failed` and `@loomcli/core/schema-converter-failed` are unreachable: a validator's result and its input schema are typed (`Result<Output, Vec<Issue>>`, `Option<Map>`), so neither can be malformed. | The types rule out the fault. |
| Validation | `missing_input_error()` names itself in the `@loomcli/core/missing-input-name` sentence, `missing_input_error() received option "port", which the root Command does not declare.`, where the reference names `missingInputError()`. | The sentence names the function the author called. |
| Validation | `validate_linked_value::<T>` answers `Result<Result<T, Vec<Issue>>, Error>`: the inner result is the validator's verdict, and a `T` the linked input's validator does not produce, or a `T` other than `String` for an input with no validator, is the outer `input-read` fault. The reference's types derive the output from the declaration. | The caller names `T` in Rust, so a mismatch is found when the call runs. |
| Validation | A multiple option or a variadic argument that declares a scalar default, `.default("x")`, validates and reads it as a list of one value, where the reference's types reject the default. | `DefaultValue` converts from a string and a list alike, and one value is a list of one. |
| Option sets | A reusable set can be built as an `OptionSet` value or declared as an `Inputs` struct with `#[inputs(option_set)]` and applied with a flattened field. Both use the same local option and group builders. Applying a set that repeats a receiver's local or global option name raises `option-declared-twice` at the call, where the reference's primary diagnostic is a compile error. A set from another incompatible copy of core is rejected by type. | The Rust builder keeps declarations and their names as values. The derive keeps the reusable options typed, with the same call-time checks for assembled declarations as other inputs. |
| Option groups | A dynamic group call, including `requires(option, needed)`, checks the number and membership of names at the call. The derive checks literal arity for requirements and both arity and membership for groups on a typed set. The reference checks membership and arity in its builder types. | The Rust builder accepts a slice of declared names, and the derive can check membership statically when the struct owns the whole set. |
| Plugins | No lazy loading. A middleware, a configuration-source resolver, and a provider opener are registered as functions, not `load: () => import(...)`. Activation still decides whether a middleware joins the chain. `@loomcli/core/plugin-loader-failed` is unreachable. | Rust links everything ahead of time ([ADR-0005](decisions/0005-a-plugin-is-a-value-any-crate-exports.md)). |
| Plugins | `@loomcli/core/foreign-value` is unreachable: values from two semver-incompatible copies of `loomcli-core` are distinct types, so mixing them does not compile. `@loomcli/core/two-package-copies` still reports two descriptors or declared views that share an identity with different value types, and its explanation says so: "Core keys each extension and each declared view by its identity and compares its value type. Two value types under one identity mean two copies of the crate that defines it are linked, and a value one copy made cannot be read through the other." The reference compares by reference and speaks of distinct objects and installed packages. | Cargo keeps one copy per semver-compatible version, and the compiler separates the rest. |
| Plugins | An extension's schema is its Rust value type (`Serialize + DeserializeOwned`), with optional value rules a `.check(fn)` states. `@loomcli/core/extension-output` fires only for a value serde cannot write as JSON (see Extensions). | serde gives plain data by type; Standard Schema has no Rust counterpart. |
| Plugins | An `on_command_attach` hook edits the Command in place through `&mut AttachedCommand`, so a call that succeeded keeps what it added; the reference's hook returns a value, and an `extend()` on a value the hook then discards registers nothing. A descriptor an `extend` admits joins the build's one registry at that call, so a second descriptor under one identity is reported at the `extend` that meets the first, which may be a hook on an earlier Command, where the reference reports it at the Command whose declaration carries the first. The fault's sentence and correction are the reference's. The `broken-attach-hook` and `broken-graph-hook` explanations and corrections describe a hook that returns `Result<(), Error>`: "on_command_attach receives each Command's declaration at graph build and edits it in place, synchronously, returning Ok(()). Core builds the Command the hook leaves, so an Err other than a DeclarationError leaves it nothing to build." with the correction "Return Ok(()) from on_command_attach, and return a DeclarationError as its Err only to reject the declaration.", and "on_graph_built receives the graph once per build and judges it: it returns Ok(()), and it rejects the graph only by returning a DeclarationError. Any other Err is a defect in the hook." with "Return Ok(()) from on_graph_built, and return a DeclarationError as its Err only to reject the graph." The reference's text tells a hook to return the value it received and to throw. Each sentence keeps the reference's hook name (`failed in onCommandAttach`). | Rust has no frozen value a hook can derive and drop; a builder edited in place is the Rust form, and a call that faults still changes nothing. A Rust hook has no value to return and nothing to throw, so the reference's advice names calls that do not exist. |
| Plugins | A failure view keyed by a class that others extend, such as `failure::<UsageError>()` or `failure::<LoomError>()`, reads the failure as that class: its message, cause, and the class's own fields, but not the class name or the fields of the class that extends it. The reference's view reads the thrown instance whole, its `name` included. An `on_failure` hook receives `&dyn Failure` and reads the class through `class().name()`. | A Rust failure is a struct that holds its parent class as a field; a typed view receives the part its key names. |
| Plugins | `@loomcli/core/broken-failure-encoder`'s "returned a number" and "returned a promise" reasons are unreachable: an encoder returns `impl IntoRendered`, a `String` or a `Result` of one. An `Err` reports with its reason as the reference's throw does. | The return type rules out the value. |
| Failure hooks | `FailureHookContext::received(&InputProblem)` returns `Option<SuppliedValue>`, and `FailureHookValues::received(reader)` supplies the optional reader for a unit context. | The existing input value type represents a token or collection, and `Option` represents the reference's absence. A builder supplies the test's callback. |
| Middleware | `Next::run` consumes its `Next`, so a second call does not compile and `@loomcli/core/next-misuse`'s "called next() twice" sentence is unreachable; only "called next() after its middleware returned" remains. Liveness is decided when the `Next` future is first polled: a `next.run()` the middleware never polls before its own future settles continues nothing and returns the defect, where the reference's call queued as a microtask before the middleware's promise settled still continues the chain. A misuse whose `Result` the caller drops is not reported; the reference reports a misuse no code observed after the chain settles and exits 1. A downstream result counts as observed once the `Next::run` future returned it: a failure returned into a spawned task whose handle the middleware dropped is lost and the run exits as the middleware decided, where the reference makes an unobserved `next()` rejection the entry's failure. A `Next` future dropped before it returned (a timeout, a `select!` branch) is unobserved, so the rest of the chain, which keeps running, decides the entry's outcome, its failure included; the reference's `Promise.race` against a timer observes the `next()` promise, so a later rejection is lost and the entry reports `dispatched`. | A Rust future runs only when polled, and a dropped `Result` has no observer core can see; `#[must_use]` on `Next` and on `Result` warns at compile time instead. Dropping a future is the only way a Rust caller declines its result, so core treats a dropped `Next` future as a `next()` no code observed. |
| Middleware | The records a middleware reads (`options`, `own_options`, `spellings`, `request`) are owned copies read by name, not frozen objects, so the reference's frozen-record checks and the `__proto__` own-key case have no counterpart. | A value a middleware receives is its own; no write reaches the action or another middleware. |
| Result transforms | A typed transform preserves the value or row type. A JSON transform serves hook-added views and results whose value or row type is `serde_json::Value`. An incompatible assignment is the `@loomcli/core/result-transform` plugin defect when the result is emitted. The reference passes any shape to any view. | Typed Rust views take the declared type. Hook-added views already use serialized JSON data. |
| Row cancellation | The process signal listener cancels the run on its own thread, and a row loop stops at its next cancellation check. The reference takes an event-loop turn after roughly 50 ms at a check point. Rust uses Tokio cooperative budget to let other runtime tasks make progress. | The separate signal thread delivers SIGINT independently of Tokio scheduling. |
| Providers | A provider is identified by its name, its value type, and its opener's type, not by object identity: two calls of one factory function are one provider, built once. The reference treats two values with one name and one type as two providers and rejects them under `@loomcli/core/provider-name-taken`. That rule's explanation ends with the Rust identity in place of the reference's "The types reject two such providers whose types differ; core rejects two that share one type, such as two values one generic factory returns, where the list is declared.": "A provider is its name, its value type, and its opener's type, so two calls of one factory function name one provider; core rejects two providers with one name and another value type or opener where the list is declared." | A Rust provider holds closures, so it cannot be a constant; a factory call is the way to share one, and its opener's closure type is the same on every call. An opener reads its settings from global options, so it captures nothing the identity would miss. |
| Providers | `RunOptions::substitute(&provider, opener)` builds a provider's value with a test's opener for every run inside the one it starts. The reference has no member that supplies a provided value to `run()` and substitutes an opener through the test runner's module mocking. | Rust has no module mocking; without a substitute, a Command that uses a provider cannot run in a test. |
| Providers | A provider value has no disposal protocol: `close` is the only close core calls, and a value whose provider declares none is dropped when the run lets go of it, which runs its `Drop`. The reference calls `close`, else `Symbol.asyncDispose`, else `Symbol.dispose`. | Rust's ownership is the disposal protocol; `Drop` cannot be awaited, so an asynchronous close is `close`. |
| Providers | The `error` field of the `A provider's close failed.` log event is `{"message": …, "name": …}`: the failure's message and class name, or a foreign error's text and type name (`Error` for one boxed through `Error::from_foreign`). The reference logs the thrown value through its log copy rules (`name`, `message`, `stack`, `cause`). | A Rust error is not serde data; its message and name are what every reader of the event can rely on. |
| Providers | An opener's error after the run was cancelled is silent only when it is the cancellation echo a refused write returned; every other error is reported under the signal's code. The reference also silences a rejection with the signal's own reason or an `AbortError`. | A `CancellationToken` carries no reason value an opener could return; the echo is the one error core recognizes as the cancellation. |
| Providers | The persistent values of one outermost run build one at a time, so two runs that first need one value build it once; when that build fails, a run that was waiting for it builds it again instead of failing with the same error. | `Error` is not `Clone`, so one failure cannot be handed to every waiter; a retry keeps every run's outcome its own. |
| Graph inspection | `locate` never fails: `@loomcli/core/foreign-graph` is unreachable. Core builds every `CommandGraph`. A clone shares the parser's tables, which a JavaScript copy loses. | The graph type is `#[non_exhaustive]`, so no other graph exists. |
| Declarations | A second `passthrough()` or `needs_terminal()` raises a declaration fault at the call, under `@loomcli/core/passthrough-declared-twice` or `@loomcli/core/terminal-need-declared-twice`. The reference closes the respective method in its builder type. | Both flags use the shared open builder state. The Rust call faults enforce one declaration without adding combinations of states. |
| Declarations | A group that needs a terminal is diagnosed with a `needs_terminal()` finding, and its correction and the MCP tool fault's correction name `needs_terminal()`. A group's passthrough finding prints `passthrough(Passthrough::new()…)`. | The diagnostics name the Rust calls. |
| Action context | `Context<I, R>::passthrough` is an empty vector when the Command leaves passthrough off. The reference omits the field on a production action's context. A Rust author can also use `#[passthrough]` to carry the tail in a derived inputs struct. | A handler and the testing context can share one concrete context type. The derive is the Rust mechanism for typed inputs. |
| Declarations | `@loomcli/core/command-attached-twice` is unreachable: `command()` moves its child and `Command` is not `Clone`, so one Command value cannot be reached through two paths. A Command that belongs in two places comes from a function that builds a fresh value for each, as the reference advises. | Rust's ownership states the rule as a type, ahead of the attach that would report it. |
| Declarations | A declaration cannot hold an explicit `undefined` default, so the graph never publishes the reference's `"default":{}` for `{ default: undefined }`; an option or argument without `.default(…)` publishes no `default` key. | Rust has no `undefined`; `.default(value)` takes a value. |
| Arity declarations | `StringOpt::arity` takes `usize`. The dynamic builder reports incompatible arity, last-wins, binding, and default shapes through `option-config` at the declaring call. A derived field's array size and attribute admit compile-time checks for those shapes. | The builder accepts facts in any order, and an author can compute the word count. The reference can reject incompatible literal declarations through its option types. |
| Visible aliases | A Command declares one name per `.visible_alias(name)` call. A finding marks that call for the offending name. A dynamic short-only option accepts computed empty alias lists and reports a non-empty list through `option-config` at declaration. The derive rejects either alias attribute beside `short_only`. | The setters follow the existing Rust builders. A Command finding reflects the one name a Rust call takes. The option builder receives iterable values, and an empty list adds no spelling. The TypeScript types reject the presence of either config key on a short-only option. |
| Declarations | The `option-config` faults name the Rust setters in their sentences (`Option "depth" declares a default beside required.`, `Option "paint" declares color on a local option; only a global option carries a run-wide mark.`), and a short spelling that is not one ASCII letter is one of them. The reference's types reject each combination at compile time with no sentence. | The rule exists only in Rust (see Rules); its sentence names what the author wrote. |
| Declarations | The `invalid-shutdown-timeout` correction reads `Set the shutdown timeout to a whole number of milliseconds from 0 through 2147483647, or leave it out for 500.`, where the reference names its `shutdown.timeout` key. `shutdown_timeout` takes a `u32`, so a negative or fractional budget is a type error and only a budget above 2147483647 reaches the fault. | The correction names the Rust call; the parameter type rules out the rest. |
| Declarations | A finding that holds extension values prints each as `…`, as in `extend([…, …])`, where the reference prints the value its descriptor was called with. A rule sentence that names the reference's option key keeps it (`declares an empty envDelimiter`). | A descriptor's value is typed author data with no printable source form; the sentence is the reference's bytes. |
| Extensions | A value that does not serialize to JSON (a map with non-string keys, for one) is `@loomcli/core/extension-output` at the call that carries it. A non-finite float serializes as `null` rather than faulting, as `serde_json` writes it. | serde decides what plain data a value is; the reference walks the schema's output. |
| Rules | Eight rules exist only in Rust. `@loomcli/core/passthrough-declared-twice` and `@loomcli/core/terminal-need-declared-twice` catch repeated declarations. `@loomcli/core/option-config` catches conflicting option builder settings. `@loomcli/core/plugin-option-name` catches a plugin's reference to an undeclared option in middleware activation or a `short` or `env` setting. `@loomcli/core/input-read` catches typed reads the declarations cannot answer, including reads of inputs, globals, linked question values through `validate_linked_value`, and provided values. `@loomcli/core/handler-registered-twice` catches repeated plugin middleware or lifecycle hook registration. `@loomcli/core/entry-point` catches `Application::main` called inside a Tokio runtime. `@loomcli/core/result-transform` reports an incompatible transform when the result is emitted. | Rust checks declarations and reads where the reference uses builder types, option config unions, typed option names, `Register` and `uses` typing, or one definition key per hook. `entry-point` exists because `Application::main` builds its own runtime. `result-transform` follows from the typed-transform deviation described above: core checks a type-erased assignment against the declared value or row type when it emits the result. |
| Rules | The failure-code grammar (`@loomcli/core/failure-code`), the exit-code range, and the rule-identity grammar (`@loomcli/core/rule-identity`) are compile errors: `FailureClass::new`, `FailureExitCode::new`, and `diagnostic_rule` assert them in `const`. Called outside a constant, each panics with one fixed sentence (`A rule identity is a package name, optional subpath segments, and a kebab-case rule name.`) in place of the rule's Developer Diagnostic, which never prints: no Rust value carries a code or identity outside the grammar to a run. | Types before diagnostics; Rust can check a constant at compile time. |
| Declaration faults | A fault at an author's authoring call or attach panics at the author's line, with the whole Developer Diagnostic as the message. The process prints Rust's panic header (`thread 'main' panicked at src/commands/list.rs:12:6:`) above the diagnostic and exits 101, where the reference's uncaught throw prints the runtime's own header and exits 1. Build faults are unchanged: `run()` renders them and exits 1. A lifecycle hook's own calls never panic: each returns its `DeclarationError`, which the hook propagates as a build fault or handles. | A panic is Rust's report of a mistake in the program as written, which a call-time fault is; a fluent builder that returned `Result` at every call would bury the declaration. |
| Diagnostics | A Developer Diagnostic's findings rebuild the declaration as Rust builder calls (`Command::new("get")` above `.option("raw", Opt::boolean().short('r'))`, the root as `Application::new("app")`), not as JavaScript. A string prints as a Rust string literal in double quotes and a character in single quotes, with a line break, a carriage return, and a tab as `\n`, `\r`, `\t` and every other escaped control as `\u{202e}`, where the reference writes `'a\u000ab'`. A mark names a builder setter by its name (`1.short`), and its carets cover `short('F')`. Caret columns count characters, where the reference counts UTF-16 code units. A number with a fraction prints as Rust's `Display` writes it, which differs from `String(number)` for an exponent such as `1e-7`, and a non-finite one as `f64::NAN` or `f64::INFINITY`. | The author reads the code they wrote; ADR-0002 names JavaScript-specific diagnostic content as an expected deviation. |
| Diagnostics | A defect's evidence is the Rust error chain: the heading names a foreign error's type as `std::any::type_name` gives it when `?` or `From` converted it (`Error` for one boxed through `Error::from_foreign`), a failure by its class name, and each `source()` link prints under `Caused by` with its `Display` alone. Frames are the `std::backtrace` captured where the error was converted, present only when `RUST_BACKTRACE` or `RUST_LIB_BACKTRACE` enables capture. The source excerpt reads the first frame under the working directory and outside any `.cargo` directory (the reference skips `node_modules`), resolves a relative frame path against the working directory, and counts lines at each line feed. A thrown value that is not an Error (`Thrown value:`) and an `AggregateError`'s `Holds` links have no Rust form. A fatal log event's defect names the Rust type the same way. | Rust errors carry no stack and no name; a type name, the `source()` chain, and a captured backtrace are what a Rust error offers. |
| Diagnostics | A correction of exactly one sentence prints as that sentence. The reference prints a one-element correction list under `- `, which `DiagnosticParts::correction` cannot express: one call is one sentence, two or more print as a list. | One builder for both forms; no core rule passes a one-element list. |
| Failures | A panic in author code (an action, a middleware, a hook, a view) is not converted into an `InternalError`: core does not catch it, and the process reports the panic. The reference's rules for a throwing view, encoder, or hook apply to the `Err` it returns: every render function, encoder, and `on_failure`, `on_log`, `on_command_attach`, and `on_graph_built` hook can return one. | A panic is Rust's report of a broken invariant; `Result` is the ordinary failure path, and catching unwinds across author futures would hide the platform's own report. |
| Failures | A translation matches a foreign error of exactly its type. The reference walks the thrown value's prototype chain, so a translation keyed on `Error` answers every error. A translator returns its failure or hands the error back (`Result<F, E>`), so "a translator that throws" has no Rust form and the `foreign-throw` defect for it is unreachable. | Rust errors have no inheritance; a type identity is the matching rule Rust can state, and a translator's `Result` holds both of its answers. |
| Input sources | A configuration answer is typed: a `SourceValue`, a `String` label, and an optional `PathBuf` directory, in a `BTreeMap` keyed by option name. Of the `@loomcli/core/source-answers` faults, a record that is not one, an answer that is not an object, and a list with a hole cannot occur; a label that is not one line of prose reads `... with an answer that is not { value, label }.` as the reference's does. The answers are read in name order, so when several break the rule the first by name is reported, where the reference reports the first in the record's own order. Each request is a copy of the graph's node, so a source tells a global option from a local one by name, where the reference compares the node with `graph.globals` by identity. | The resolver's answer is Rust data, and a node handed to a source is owned by its context. |
| Input sources | A count a variable or a configuration answer fills above 4294967295 reads as 4294967295, as a counted option's occurrences add up to at most that count. The reference reads any JavaScript number. | The run holds a count as a `u32`; no count that large is typed or meant. |
| Content | A process started with descriptor 0 closed has it on `/dev/null`: Rust's runtime reopens a closed standard descriptor on `/dev/null` before `main`, so `/dev/null` named as a content source is the process's own stdin and is rejected with `Expected a readable file that exists.` The reference's process keeps descriptor 0 closed after its own `closeSync(0)`, so `/dev/null` reads as an unrelated device there. Any other source stays usable, as in the reference. | Rust's standard library sanitizes descriptors 0 through 2 at start-up, and closing descriptor 0 from inside the process needs `unsafe`. |
| Results | A view record keeps the order of its `view()` calls. An integer-like view name such as `"2"` stays where the author put it, where the reference moves it ahead of the record's other names in ascending order, as JavaScript orders an object's keys. The graph's `views` and `mediaTypes` order, and the default view a record that names none falls back to, follow the calls. | The reordering is a property of JavaScript objects, not a rule of the contract, and the reference tells authors not to use an integer-like view name; a builder's calls have an order of their own. |
| Results | A result's value type, and a rows result's row type, is `Serialize`. | A plugin hook adds machine views (`json`, `jsonl`) to any result, which needs the data as JSON; `JSON.stringify` serializes any value in the reference. |
| Output | Whole messages, `render`, and `results` start when their futures are polled. Their unpolled calls add no work to the process-end queue and raise no error. The reference starts these calls at the call site, so its unawaited cases for `render.test.ts` and `results.test.ts` have no counterpart. Streamed messages start at the call and the run owns them through completion, as in the reference. | The ordinary output calls follow Rust's poll-based futures. A streamed message owns its source and can run independently of the caller's future. |
| Output | When a lane view fails at the final layout of a streamed `print` on a terminal, whether or not it failed at a chunk before (decision LM-q111), core writes only what the cursor has not received of the unfinished line, then `\n`. The reference writes that line from where the last layout began, so text already at the cursor shows twice. | A fallback that repeats bytes the operator already sees garbles the line; the fallback finishes it instead. |
| Output | Core sends no write for empty text, so a stream never sees a zero-length write, and an empty write to a terminal does not erase and redraw the live regions around it. The reference passes the empty string to the stream, as when an override of `incomplete_result()` returns `""`, and its passage erases and redraws the stack around it. | Every operator-visible byte is the same; a zero-length write is noise to a stream, and redrawing an unchanged stack around nothing changes nothing the operator sees. |
| Output | `ViewContext::wrap(text, Some(0))` leaves the text unwrapped, as `None` does. The reference's `wrap(text, 0)` throws a `RangeError` that fails the view. | The method returns `String`, and a context's own `columns` is never zero. |
| Output | A refused write's error, the cancellation echo, is a foreign error whose message reads `The run was cancelled.`; the reference rejects with the run signal's reason object. A run's signal records `Caller` with no cause when `RunOptions::signal` cancels it, and the closed pipe's cause is the write error's message. | A `CancellationToken` carries no value, and a reason's `cause` is text. |
| Regions | A region's close runs the handlers `Region::on_close` registered, synchronously, after `closed_by` is set and before the region's signal is cancelled, and a frame a handler draws is the region's last frame. The reference's abort listeners on the region's `AbortSignal` play that part; a task awaiting `Region::signal()` runs after the region has closed, so a frame it draws is not written. | A `CancellationToken` has no synchronous listener: a task awaiting it is woken, not called, so a frame drawn there would arrive after the region left the stack. |
| Regions | `Region::draw` renders its view at the call and returns a `'static` future that writes the frame; `Out::lend_terminal` counts the lend at the call, so a report waits for a lend whose future is spawned before it is first polled. Every other region and lend effect still happens when its future is polled, under the write-when-awaited row above: a concurrent `tokio::join!` of a row sequence and an info line writes the sequence's first row before the info line, where the reference's info line lands first. | A Rust future runs only when polled; these two calls must take effect at the call, as the reference's do, for a close handler's frame and for a lend that outlasts the action. |
| Progress | A `ProgressEvent` is an owned value, not a frozen object. An observer that panics is the Invocation row's. | `InvokeOptions::on_progress` takes `Fn(&ProgressEvent)`, which receives a borrow it cannot keep or change. |
| Logging | `LogFields::field` copies a value as the JSON data serde writes for it, when `field` is called, whether or not a hook listens; a value that does not serialize, and a number that is not finite, read `null`. The reference's copy rules for JavaScript values (`Date` through `toJSON`, a `bigint`'s decimal string, `"[Circular]"`, omitted functions and symbols) have no counterpart, and "a getter on its fields is never read" without a hook does not hold. | serde decides a Rust value's plain-data form, and the builder holds JSON, not the caller's values. For a Rust error, `LogFields::error_field` copies the error facts explicitly. |
| Logging | An invalid redaction path panics at the `Application::log_redact` call with the `@loomcli/core/invalid-redact-path` diagnostic. The sentence, correction, and rule match the reference. The finding reconstructs `.log_redact(&[...])` and marks `0.<index>`. The reference throws from `new Application` and marks `log.redact.<index>` in its options object. | The builder judges its list at the setter under the Declaration faults deviation. |
| Logging | A run's id is 128 bits from two hashes under randomly keyed `RandomState` hashers of a process-wide count and the time, written as 32 lowercase hexadecimal characters. The reference reads 16 bytes from `crypto.getRandomValues`. | The format, per-run uniqueness, and unpredictability are the reference's; the standard library offers no cryptographic generator, and a trace id needs none. |
| Views | A declared view is its identity and the type of the view it declares: two `view()` calls with one identity and one view type are one view, and an override keyed by either reaches both. ## MCP plugin (`mcp()`, `mcp::extension`)

| Area | What differs | Why |
| --- | --- | --- |
| Input facts | `McpInputFacts` is built with `McpInputFacts::described(text)` or `McpInputFacts::excluded()`. ## Toolchain (`cargo-loom`: `cargo loom changelog`, `init`, `build`, and the installer script)

The `cargo-loom` crate is not in this tree: it stays out of the workspace until its adapter is designed, and the rows below record the toolchain as the port built it. Two operator sentences still name `cargo loom build`, and they stay until the adapter is designed: core's build script corrects malformed release facts with `Rebuild with cargo loom build.` (`crates/loomcli-core/build.rs`, see Release facts), and the service plugin's refusal of a source or development build reads `Build it with cargo loom build, then run the built <name> service install.` (`crates/loomcli-plugins/src/service/messages.rs`, see the service plugin's Building row).

| Area | What differs | Why |
| --- | --- | --- |
| Command | The toolchain is the cargo subcommand `cargo loom`, the binary `cargo-loom`. Cargo runs it as `cargo-loom loom <words>`, and the binary drops that leading `loom`, so `cargo-loom <words>` reads alike. The Application is still named `loom`, so help pages, usage lines, and every sentence name `loom` as the reference does. | Cargo finds a subcommand as a `cargo-<name>` binary and passes the subcommand's name as its first argument. |
| Plugins | The Application installs help, interaction, version, verbose, the configuration plugin, and the suggestions plugin, which the reference's `loom` does not install. | The brief for the port asks for suggestions on a misspelled Command; it adds no Command or option. |
| Commands | The reference's hidden `pr` and `release` Commands, its repository's own release orchestration, are left out. | They are outside the toolchain's contract, as the reference's toolchain README states. |
| Manifest | Every command acts on the directory of the nearest `Cargo.toml` at or above the working directory, in place of `package.json`, and every sentence that names `package.json` names `Cargo.toml`. The version a cut reads and sets is `[package] version`, else `[workspace.package] version` in the same file; the cut replaces that string's bytes alone, a leading byte order mark and every other byte kept. A `Cargo.toml` that is not TOML fails with `<path> is not valid TOML: line L, column C <the parser's message>, so fix it there and run loom again.`, where the reference names what JSON needs at the place. `sharedVersion` lists `Cargo.toml` files. | A Rust package's version lives in its manifest, and TOML's parser reports its own expectation. |
| Manifest | A field a member inherits, `version.workspace = true` or `repository.workspace = true`, is read from `[workspace.package]` of its workspace root: the package's own manifest when it holds `[workspace]`, else the directory `package.workspace` names, else the nearest `Cargo.toml` above it that holds `[workspace]`, as Cargo finds it. `build --release` and `init`'s `install.sh` read the inherited version and repository. A cut of a member that inherits its version sets `[workspace.package] version` in the workspace root, so every member that inherits it moves with it, and `notes` reads the version there. A root without that version string fails with `Cargo.toml inherits version from <root>, which holds no [workspace.package] version string, so set one there and run loom again.` (`build` ends `…so set it to a semantic version there, such as 1.0.0.`), `<root>` relative to the package directory, such as `../../Cargo.toml`; a member with no workspace root fails with `Cargo.toml inherits <field> from its workspace, but no Cargo.toml at or above <directory> holds a [workspace] table, so set <field> in Cargo.toml or add the package to a workspace.` | `package.json` has no inheritance; a Cargo workspace member's version and repository live in the root manifest. |
| Changelog | A file operation of a cut that fails names the step and its paths, such as `Cannot move <package>/.changes/fix.md to <package>/.loom-changelog-<hex>/fragment.fix.md: Permission denied (os error 13).`, `Cannot write <file>: …`, `Cannot create <directory>: …`, and `Cannot create a staging folder in <package>: …`, where the reference prints Node's errno sentence, such as `EACCES: permission denied, rename '<from>' -> '<to>'`. A narrative that cannot be read fails with `Cannot read the narrative <path>: <the system's message>.`, where the reference prints Node's `ENOENT: no such file or directory, open '<path>'`. | Rust's I/O errors carry the system's message without the operation or the paths, and do not spell Node's errno sentences. |
| Configuration | `loom.config.json` is found from the working directory up to the directory that holds `Cargo.toml`. The plugin publishes no schema for it, so the graph's `configuration` fact is empty. `paths.application` and `paths.entry` default to `<source>/application.rs` and `<source>/main.rs`. | The root marker of a Rust package is `Cargo.toml`; the reference's schema is a valibot schema with no Rust counterpart, and no linked option reads it. |
| Changelog | The fragment guide is the reference's text with `package.json` replaced by `Cargo.toml`. The changelog skill, `.agents/skills/loom-changelog/SKILL.md`, is not a managed file of the Rust toolchain. Fragments, narratives, and changelogs are read as CommonMark blocks through pulldown-cmark, where the reference uses mdast-util-from-markdown; both follow CommonMark with no extension. | The skill is not in the brief for the port; the parser is the Rust ecosystem's CommonMark reader. |
| Init | The pieces are `package` (the `loomcli-core`, `loomcli-plugins`, and `loomcli-testing` dependencies of `Cargo.toml`, each added at the end of its table and printed as `Added <table>.<crate> to Cargo.toml.`), `application` (`src/application.rs`, an Application with help, version, and one Command), `entry` (`src/main.rs`, which declares the application module and the test module, by `#[path]` when the configuration moves them), `test` (`src/application_test.rs`, the assembly check through `loomcli-testing`), `config` (`loom.config.json`, `{}`), `lint` (`clippy.toml`), `changes`, and `install`. There is no `tsconfig` or `skill` piece and no `--linter` or `--test-runner` option or question. The reference writes no `loom.config.json`. | A Rust application has one compiler, one linter, and one test runner; the scaffold the port's brief names includes the configuration file. |
| Init | A new package's directory name must be lower-case ASCII letters, digits, `-`, and `_`, opening with a letter, and at most 64 bytes, as Cargo and an Application name accept; the refusal names `Cargo.toml`. A directory that is neither empty nor inside a package is refused with `…, so create one with cargo init, or your own tooling's equivalent, and run loom init again.`, and the question at a terminal reads `No Cargo.toml is here or above it. | Init | The reference loads an authored application module under Bun to learn how the entry imports it. The Rust toolchain loads nothing: an authored application module that declares no `pub fn application(` draws `warning: <entry> was not written because <application> declares no pub fn application() loom can call. Write the entry by hand.` (and the same for the test). A test written beside an entry the author already holds draws `warning: <test> runs only once <entry> declares it, so add #[cfg(test)] mod application_test; there, with #[path] when it sits elsewhere.` | A Rust module is not loaded at run time, and a test module runs only when the crate declares it. |
| Init | `clippy.toml` is a managed file that holds the host-bypass `disallowed-methods` and `disallowed-types` list of the core API design, section 13, each entry naming the run's member to use instead; the `tokio` entries carry `allow-invalid = true`, so an application without tokio lints clean. | Installer | The rendered `install.sh` is the reference's byte for byte, the release shape and the asset names included. `cargo loom build --release` names a Rust target triple's binary with the reference's asset scheme: `x86_64-unknown-linux-gnu` is `<name>-linux-x64`, `aarch64-unknown-linux-gnu` `<name>-linux-arm64`, `x86_64-unknown-linux-musl` `<name>-linux-x64-musl`, `aarch64-unknown-linux-musl` `<name>-linux-arm64-musl`, `x86_64-apple-darwin` `<name>-darwin-x64`, and `aarch64-apple-darwin` `<name>-darwin-arm64`; a release for any other triple fails before it builds. | The script reads the reference's release shape; only the build's names change. |

| Build | The binary's default path is `<paths.out>/<name>`, and for a release `<paths.out>/<asset>`, so builds for several targets share one directory; each build also sets the binary's line, `<sha256>  <file>`, in `SHA256SUMS` beside it, keeping every other line. The reference's build writes no `SHA256SUMS`, which each repository's release workflow writes.
